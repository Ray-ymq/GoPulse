瓶颈判断 搜索失败率 资源方案 复测与上线条件

一、瓶颈判断

资源上限测试提高了 API 的 HTTP 并发和读资源预算。256 并发持续 30 秒，记录约 1,700 个 HTTP 响应每秒，其中 HTTP 200 每秒约 1,538 个。标准容量测试在 128 并发时记录约 997 req/s、P95 66.0 ms，2,000 个请求全部成功。现阶段保留标准测试给出的单实例 128 并发、约 1,000 req/s 保守基线。两档测试的配置和时长不同。

Elasticsearch 持续触及 4 vCPU 配额，随后帖子搜索出现 search_unavailable。同轮 API CPU 约 102%（配额 2 vCPU），MySQL 约 317%（配额 4 vCPU），Redis 约 4%（配额 0.5 vCPU）。Elasticsearch 单节点 CPU 饱和是最符合现有数据的首要解释。原记录缺少 CPU 节流、搜索线程池排队和拒绝、GC 及磁盘读取的同步数据，排队、查询本身开销和各段超时的贡献仍待确认。

当前 Compose 运行单节点 Elasticsearch。帖子索引的默认定义为 1 个主分片、0 个副本。当前 API 的请求上下文时限为 1,500 ms。Compose 的 Elasticsearch 客户端默认时限为 3 s，但调用仍受上游 API 时限约束。P95 为 P50 的约 1,072 倍（1,500.4 ÷ 1.4），P99 为 1,501.3 ms。这表明混合流量的尾延迟集中在 API 时限附近。总体百分位无法确定慢请求所属接口、失败比例或 Elasticsearch 的排队时间。Compose 配置 · 索引定义 · API 时限 · Elasticsearch 客户端

帖子搜索先解析索引代次，首次查询打开 PIT（时间点快照），再执行 Elasticsearch 查询并从 MySQL 补全返回结果。用户搜索查询 MySQL。search_unavailable 也可出现在索引代次解析或打开 PIT 等阶段。复测应按接口和阶段定位开销。帖子搜索服务 · 用户搜索查询

二、搜索失败率

原记录列出 46,144 个 HTTP 200、4,864 个 HTTP 503 和 256 个请求错误。前两项正好合计 51,008，503 占 HTTP 响应的 9.54%。若 256 个请求错误都是另外发出且未获得 HTTP 响应的请求，则总尝试数为 51,264，整体失败率为 (4,864 + 256) ÷ 51,264 ≈ 9.99%。需要原始记录确认这 256 条的统计口径和接口归属。

以下按相同 HTTP 响应口径推算。若 4,864 个 503 全部来自帖子搜索，则帖子搜索的 503 占比等于 4,864 ÷ 帖子搜索的 HTTP 响应数。四种接口参与混合压测，实际请求构成需要由记录确认。

三、资源方案

Elasticsearch · 先测 CPU，再验证 6 GiB 内存

  • 先保持实测基线的堆和容器内存不变。在主机有 CPU 余量的隔离环境中，将 Elasticsearch 配额从 4 vCPU 调到 6 vCPU，观察同负载下的搜索成功吞吐、尾延迟和 CPU 节流是否改善。同时用阶段耗时确认查询、PIT 或 MySQL 回填的开销。
  • 当前根 Compose 配置为 2 GiB 容器上限、1 GiB 堆。历史测试使用 3 GiB 容器上限，实际堆大小需要在复测基线中核对。6 GiB 容器配 3 GiB 堆符合 Elastic 的 50% 堆上限建议。剩余 3 GiB 由页缓存、JVM 非堆内存、直接缓冲区等共同使用。记录中的 1.68 GiB 是采样值。若采样来自 Linux 的 docker stats，显示值还会扣除部分文件缓存，需同时检查容器内存与文件缓存指标。Compose 配置 · Elastic JVM 设置 · Docker stats 口径
  • 固定 CPU，将容器上限提高到 6 GiB 并保留基线堆，验证文件缓存增加是否降低磁盘读取并改善搜索。若堆使用率持续偏高，或出现较长的 GC 停顿、堆内存相关熔断，再在相同 6 GiB 上限下对照 3 GiB 堆。如果主要证据仍指向 CPU 节流，优先缩减单次查询成本或提高 CPU 配额。为帖子搜索设置独立的并发预算也值得验证，目的是在搜索超载时保护其他读接口。Elastic 搜索性能调优

Redis · 提高缓存收益，保留 256 MiB 测试配额

  • 约 3.5 MiB 是容器采样值，占 256 MiB 测试配额约 1.37%。优化目标是减少 MySQL 回源和详情延迟。当前 Redis 缓存帖子正文，默认 TTL 为 5 分钟。缓存命中后仍查询可见性和动态数据。帖子搜索不经正文缓存。原测试关闭了业务限流，需在复测中恢复生产限流，覆盖限流键和正文缓存同时使用的情况。Compose 配置 · 帖子详情实现
  • 用相同的热点分布对照冷缓存和热缓存。统计应用侧正文命中、未命中和错误，以及每次详情请求的 MySQL 正文查询次数和 P95。同步记录 Redis 的 used_memory、used_memory_rss、evicted_keys、expired_keys、命令延迟和 AOF 重写时的内存峰值。若正文键频繁过期且重复访问率高，再单独测试延长 TTL。保留版本化键和可见性查询。Redis INFO 指标
  • 当前 Compose 启用 AOF。若需要设置 maxmemory，根据实测为 AOF 缓冲和重写额外占用留空间。正文缓存和限流键共用 Redis 时，避免启用可能清除限流键的全局淘汰策略。若搜索词重复率高且 Elasticsearch 调用成本仍高，再评估短 TTL 的热门搜索缓存，先验证删除和可见性变更、索引代次和 PIT 分页的一致性。Redis 淘汰策略

MySQL · 从 128 MiB 对照到 2 GiB

MySQL 8.4 默认缓冲池为 128 MiB，实测起点应以 SELECT @@innodb_buffer_pool_size 为准。原记录显示业务表约 345 MiB、MySQL 内存约 500 MiB、慢查询数为 0。缓冲池增加可能减少反复读取数据页和索引页。现有记录缺少缓冲池未命中、磁盘读取延迟和 SQL 执行分布，无法估计收益。MySQL 缓冲池配置

建议在 3.5 GiB 测试容器配额内，先对照 512 MiB 或 1 GiB，再测试 2 GiB。2 GiB 约占容器配额的 57%，名义上剩余 1.5 GiB，供 InnoDB 其他开销、连接缓冲和临时表等使用。每档预热后，比较 ΔInnodb_buffer_pool_reads ÷ ΔInnodb_buffer_pool_read_requests、每秒未命中读、磁盘读取延迟，以及时间线、用户搜索和帖子搜索回填的延迟。若 512 MiB 或 1 GiB 已获得相近收益，采用较小档位。使用混合读写验证内存峰值和连接池等待。MySQL 状态变量 · MySQL 内存使用

四、复测与上线条件

  1. 建立可比基线。 固定 4 倍数据、镜像版本、索引、搜索词和分页分布、负载配比及 API 并发预算。先按已记录条件重建资源上限测试，再按目标生产配置测试。原记录未给出搜索词和流量配比，复测应记录实际发出的各接口请求数。可用固定到达率对照过载场景，并单独记录压测端未发出的迭代。仓库性能测试层级 · k6 负载模型 · k6 未发出的迭代
  2. 按接口记录结果。 分别统计时间线、帖子详情、帖子搜索和用户搜索的发起数、有效成功数、HTTP 状态、业务错误码及客户端超时或传输错误。校验响应正确性。分别输出成功请求和全部有耗时样本的 P50、P95、P99。失败率用失败数除以同一接口的实际发起数，并核对各结果分类的计数总和。
  3. 同步定位瓶颈。 记录 Elasticsearch 容器 CPU 节流、线程池 search 和 search_coordination 的队列与拒绝增量、GC、PIT 打开数、内存和磁盘读取情况。记录 API 中索引代次解析、打开 PIT、执行查询和 MySQL 回填各段耗时。用同一时间轴对齐这些指标和错误。Redis 和 MySQL 使用各自方案列出的指标。Elasticsearch 节点统计 · Linux cgroup v2 指标
  4. 逐项改变变量。 先做帖子搜索单接口阶梯加压，再做混合流量。按 CPU 配额、Elasticsearch 容器内存、JVM 堆、MySQL 缓冲池、Redis 缓存策略的顺序单项对照。覆盖基线附近和历史饱和区间。区分冷启动与预热后结果，重复测试，并增加稳态和含索引写入的场景。
  5. 按成功吞吐验收。 采用能在目标流量下满足各接口错误率与尾延迟目标、且有稳定 CPU 和内存余量的最小档位。若帖子搜索仍出现成片的 search_unavailable 或挤占其他读接口，保留原容量基线。原记录未定义生产错误率和延迟目标，应在复测前确定。单节点容量提升后，节点故障仍会影响帖子搜索。若要消除单点故障，需要另行验证跨故障域部署和副本。
本文各配置档位为复测方案。容量结论适用于原记录的测试范围。
