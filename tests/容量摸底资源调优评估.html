二、瓶颈判断

资源上限测试提高了 API 的 HTTP 并发和读资源预算。256 并发持续 30 秒，记录约 1,700 个 HTTP 响应每秒，其中 HTTP 200 每秒约 1,538 个。标准容量测试在 128 并发时记录约 997 req/s、P95 66.0 ms，2,000 个请求全部成功。现阶段保留标准测试给出的单实例 128 并发、约 1,000 req/s 保守基线。两档测试的配置和时长不同。

Elasticsearch 持续触及 4 vCPU 配额，随后帖子搜索出现 search_unavailable。同轮 API CPU 约 102%（配额 2 vCPU），MySQL 约 317%（配额 4 vCPU），Redis 约 4%（配额 0.5 vCPU）。Elasticsearch 单节点 CPU 饱和是最符合现有数据的首要解释。原记录缺少 CPU 节流、搜索线程池排队和拒绝、GC 及磁盘读取的同步数据，排队、查询本身开销和各段超时的贡献仍待确认。

当前根 Compose 的 Elasticsearch 配置是 2 GiB 容器上限和 1 GiB heap。历史压测记录使用 3 GiB 内存配额。两者属于不同配置档位。帖子索引的默认定义为 1 个主分片、0 个副本。当前 API 的请求上下文时限为 1,500 ms。Compose 的 Elasticsearch 客户端默认时限为 3 s，但调用仍受上游 API 时限约束。P95 为 P50 的约 1,072 倍（1,500.4 ÷ 1.4），P99 为 1,501.3 ms。这表明混合流量的尾延迟集中在 API 时限附近，但不能单独证明 Elasticsearch 返回了错误。总体百分位无法确定慢请求所属接口、失败比例或 Elasticsearch 的排队时间。Compose 配置 · 索引定义 · API 时限 · Elasticsearch 客户端

帖子搜索先解析索引代次，首次查询打开 PIT（时间点快照），再执行 Elasticsearch 查询并从 MySQL 补全返回结果。用户搜索查询 MySQL。search_unavailable 也可出现在索引代次解析或打开 PIT 等阶段。复测应按接口和阶段定位开销。帖子搜索服务 · 用户搜索查询

三、搜索失败率

原记录列出 46,144 个 HTTP 200、4,864 个 HTTP 503 和 256 个请求错误。前两项正好合计 51,008，503 占 HTTP 响应的 9.54%。若 256 个请求错误都是另外发出且未获得 HTTP 响应的请求，则总尝试数为 51,264，整体失败率为 (4,864 + 256) ÷ 51,264 ≈ 9.99%。原记录没有说明 256 条是否与 HTTP 结果重复计数，也没有说明接口归属。需要从原始压测结果确认统计口径。

以下按相同 HTTP 响应口径推算。若 4,864 个 503 全部来自帖子搜索，则帖子搜索的 503 占比等于 4,864 ÷ 帖子搜索的 HTTP 响应数。四种接口参与混合压测，实际请求构成需要由记录确认。

约 19% 可作为条件下限，前提是全部 503 均来自帖子搜索且帖子搜索响应占比不超过 50%。约 30%～50% 对应帖子搜索响应占比约 19.07%～31.79%。若其中一部分 503 来自其他接口，同一响应占比下的推算值会降低。按接口采集请求总数和各类失败数后，才能确认帖子搜索的实际失败率。

四、资源方案

Elasticsearch · 先测 CPU，再验证 6 GiB 内存

  • 先重建历史档位。使用 4 vCPU、3 GiB 容器内存，并保存实际生效的 heap。然后单独把 CPU 调到 6 vCPU，保持内存和 heap 不变，观察成功吞吐、尾延迟和 CPU 节流。
  • 再固定 CPU，分别对照 6 GiB 容器配 1 GiB heap 和 6 GiB 容器配 3 GiB heap。6 GiB 容器配 3 GiB heap 将 heap 控制在容器内存的 50%。剩余空间由文件系统缓存、JVM 非堆内存、直接缓冲区和其他开销共享。记录中的 1.68 GiB 是采样值。若采样来自 Linux 的 docker stats，显示值会扣除部分文件缓存，需同步检查容器内存、文件缓存和 cgroup 内存事件。
  • 每档先执行帖子搜索单接口阶梯测试，再执行四类接口混合测试。记录索引代次解析、PIT 打开、查询和 MySQL 回填耗时。记录 search、search_coordination 队列与拒绝、GC、PIT 数量、磁盘读取、CPU 节流和 OOM。CPU 增加只能验证节流影响，不能保证 P95 自动下降。Compose 配置 · Elastic JVM 设置 · Docker stats 口径 · Elastic 搜索性能调优

Redis · 提高缓存收益，保留 256 MiB 测试配额

  • 约 3.5 MiB 是历史压测采样值，占 256 MiB 压测配额约 1.37%。当前根 Compose 没有 Redis 的 mem_limit、maxmemory 或 maxmemory-policy。Redis 只启用 AOF 和密码。优化目标是确认缓存收益，不是仅按低内存使用量扩容。
  • Redis 同时存储帖子正文缓存和共享限流状态。正文缓存键包含数据代次、帖子 ID 和内容版本，默认 TTL 为 5 分钟，并带有 TTL 抖动。帖子详情命中正文缓存后仍需要读取查看者投影或动态数据。帖子搜索不使用正文缓存。当前缓存 hit、miss 和 error 的观测回调为空，不能直接确认缓存收益。缓存实现 · 帖子详情实现
  • 保持 256 MiB，先对照冷缓存和热缓存。记录应用侧正文 hit、miss、error、MySQL 回源次数和详情 P95。同步记录 used_memory、used_memory_rss、evicted_keys、expired_keys、keyspace_hits、keyspace_misses、命令延迟、客户端连接数和 AOF 重写峰值。只有在命中率、淘汰或内存压力数据支持时，才评估增加 maxmemory。Redis INFO 指标
  • 正文缓存和限流状态共用 Redis 时，不能直接采用可能淘汰限流键的全局策略。需要拆分 Redis 实例，或在复测中证明淘汰不会破坏限流正确性。Redis 优化不会直接降低 Elasticsearch 搜索 CPU。Redis 淘汰策略

MySQL · 从 128 MiB 对照到 2 GiB

MySQL 8.4 默认缓冲池为 128 MiB。当前根 Compose 没有 innodb_buffer_pool_size 配置，也没有挂载 MySQL 配置文件。实际起点应先执行 SELECT @@innodb_buffer_pool_size, @@innodb_buffer_pool_instances, @@max_connections。原记录显示业务表约 345 MiB、MySQL 内存约 500 MiB、慢查询数为 0。缓冲池增加可能减少反复读取数据页和索引页，但现有记录缺少缓冲池未命中、磁盘读取延迟和 SQL 执行分布。MySQL 缓冲池配置

在相同 3.5 GiB MySQL 压测配额内，依次对照 128 MiB、512 MiB、1 GiB 和 2 GiB。2 GiB 约占配额的 57.1%。InnoDB 还会为控制结构和其他缓冲区占用额外内存，不能只用 3.5 GiB 减去 2 GiB 估算剩余空间。每档记录进程 RSS、cgroup memory.current、连接数、临时表峰值、Innodb_buffer_pool_read_requests、Innodb_buffer_pool_reads、Innodb_buffer_pool_wait_free、pages data/free/dirty、磁盘读取、Threads_running、连接池等待和 SQL digest。若 512 MiB 或 1 GiB 已获得相近收益，采用较小档位。使用混合读写验证冷启动、内存峰值和连接等待。MySQL 状态变量 · MySQL 内存使用

2 GiB 方案尚未落地。需要通过 Compose 参数或 /etc/mysql/conf.d 配置文件注入，并在启动后核对实际生效值。

五、复测与上线条件

  1. 建立可比基线。 固定 4 倍数据、镜像版本、索引、搜索词和分页分布、负载配比及 API 并发预算。先按已记录条件重建资源上限测试，再按目标生产配置测试。原记录未给出搜索词和流量配比，复测应记录实际发出的各接口请求数。可用固定到达率对照过载场景，并单独记录压测端未发出的迭代。仓库性能测试层级 · k6 负载模型 · k6 未发出的迭代
  2. 按接口记录结果。 分别统计时间线、帖子详情、帖子搜索和用户搜索的发起数、有效成功数、HTTP 状态、业务错误码及客户端超时或传输错误。校验响应正确性。分别输出成功请求和全部有耗时样本的 P50、P95、P99。失败率用失败数除以同一接口的实际发起数，并核对各结果分类的计数总和。
  3. 同步定位瓶颈。 记录 Elasticsearch 容器 CPU 节流、线程池 search 和 search_coordination 的队列与拒绝增量、GC、PIT 打开数、内存和磁盘读取情况。记录 API 中索引代次解析、打开 PIT、执行查询和 MySQL 回填各段耗时。用同一时间轴对齐这些指标和错误。Redis 和 MySQL 使用各自方案列出的指标。Elasticsearch 节点统计 · Linux cgroup v2 指标
  4. 逐项改变变量。 按以下顺序执行，每轮只改变一个变量。历史基线 → Elasticsearch 增加 2 vCPU → Elasticsearch 6 GiB 容器 → Elasticsearch 3 GiB heap → MySQL 512 MiB → 1 GiB → 2 GiB → Redis 热缓存和 AOF 观察。覆盖基线附近和历史饱和区间。区分冷启动与预热后结果，重复测试，并增加稳态和含索引写入的场景。
  5. 按成功吞吐验收。 采用能在目标流量下满足各接口错误率与尾延迟目标、且有稳定 CPU 和内存余量的最小档位。若帖子搜索仍出现成片的 search_unavailable 或挤占其他读接口，保留原容量基线。原记录未定义生产错误率和延迟目标，应在复测前确定。单节点容量提升后，节点故障仍会影响帖子搜索。若要消除单点故障，需要另行验证跨故障域部署和副本。
