# GoPulse 工程稳定性改造方案

> 状态：开发规则和文档入口已重写；可执行改造已分配到 Phase-23-06，待实施。修订日期：2026-10-11。
> 调查基线：`0610f3f`，当时完成版本为 `2.5.5`；当前完成事实只读取 VERSION 和能力状态。

## 1. 要解决什么

这次改造来自成熟 Go 项目的工程组织对照，以及 GoPulse 源码、规则和文档的实际调查。
目标是让项目的日常开发有清晰入口、可靠准备、有效检查和可定位的失败原因。
AGENTS、正文、Make 和 CI 共同承担这个结果；新增工具必须对应实际缺口，旧实现有问题时可以删除重写。

| 调查发现 | 要得到的工程能力 |
| --- | --- |
| 开发规则偏执行制度，组件入口和命令分散；部分导航重复或过期 | 根 AGENTS 给源码地图、阅读顺序、最小验证和常见陷阱；当前正文各有明确职责 |
| 环境条件缺少统一检查；已有前端目录被当作依赖有效 | 完整运行前知道缺什么，锁文件或工具变化可靠触发安装 |
| 已有格式、vet 和类型检查，额外缺陷检查不足 | 少量高价值规则阻断新增问题，存量结果真实可见 |
| Make、选择器和 CI 重复维护模块与执行组合 | 同一模块清单、同一组 Make 命令、同一改动选择 |
| 临时目录和一次性容器退出时可能丢失诊断 | 先保存必要失败材料，再清理归属资源，主失败和清理失败都可定位 |
| 工程入口变化覆盖多个模块和真实环境 | 干净 checkout 能走通开发、测试与既有交付链 |

具体源码依据、允许文件、接口、固定门禁和成本统一写在
[Phase-23-06](../imple/Phase-23/Phase-23-06-工程稳定性改造.md)，本设计说明取舍，不再维护第二份执行清单。

## 2. 开发指南与文档

根 AGENTS 提供“改什么→先读哪里→怎么验证”，再保留必要的分支、版本、安全和证据约束。
工具验证说明放 ci/AGENTS，正文职责和代码约定放 dev/README。
下级文档只补特定内容，重复规则与无用转发页直接删除；有问题的正文允许重写。

设计登记目标，status 记录当前事实，contracts 定义接口与合同，operations/validation 提供步骤，
imple 定义执行要求，logs 记录实际结果。导航只给入口，不复制状态、门禁或维护删除历史。
仍有用途的历史证据按原候选阅读；三份冻结设计保留原路径与原文。

文档稳定性包括正文可理解、事实来源明确、代码入口准确和命令可用。
自动检查只负责本地链接/锚点、当前命令存在性和冻结 diff。
使用现有 Python 运行时，不因检查文档编译 Go、安装前端或启动产品。
范围从已有目录和导航确定，人工复核语义；不增加逐文件分类登记或待实现命令豁免协议。

## 3. 工具与依赖准备

doctor 输出实际工具、兼容条件和缺失原因；bootstrap 准备项目内 lint、前端依赖和 Chromium。
工具身份绑定实际版本与下载摘要，先验证兼容再锁定；交付镜像继续使用现有 build-bases lock。
环境、运行隔离和资源归属复用 devenv，不建立另一套环境管理器。

前端安装判断集中在 frontenddeps。package/lock、Node/npm、OS/架构和成功标记共同决定是否复用。
Make、源码开发和浏览器入口调用它，接入后移除旧目录存在性判断。
安装锁按工作区和应用隔离，失败不写标记，不在活动开发进程下替换依赖。

## 4. 少量缺陷检查

Go 首批为 staticcheck、errcheck、unused；前端首批为五项明确的 JavaScript/Vue 缺陷规则，
准确配置见实施方案。继续使用 gofmt、vet 和 TypeScript 类型检查。
共享配置定义一次，原生工具在对应模块运行；lint 包装只负责调用、增量判断和失败传播。

完整扫描保留工具原始结果，有 BASE_REF 时按真实共同祖先和本地工作区判断新增。
工具错误始终失败，不能把“新增为零”写成“全仓零告警”。
存量只登记实际问题，行为修复另按精确范围进入实施合同，不扩大成本做全仓格式或命名改造。

## 5. 本地与 CI

根 Makefile 是模块清单和模块命令组合的来源，选择器继续负责按路径选择。
本地 verify 消费已有选择器 JSON，CI 直接调用相同的 Make 目标。
JSON 保留 checks/reasons，只补实际需要的模块信息；不承载可执行 argv 或逐步骤协议。

权限、共享消费者、部署、工作流、版本和未知产品路径维持现有保守覆盖。
真实 integration/e2e/Compose 与 services 的独有准备仍有效，不能用普通测试代替。
Compose 静态断言从现有 workflow 提取成一个共用的小入口。

质量汇总只核对选中检查与 GitHub 实际 job 结果，缺失、失败、取消和意外跳过不能成功。
自动 PR 继续等待整个质量 workflow 和现有完成元数据判据，不解析日志正文。
文档-only 选择通过行为测试验证，新文档 job 在本批实际 CI 中运行，不另建嵌套回归 workflow。
缓存共用真实模块清单、核验输入身份；未运行的 main 专属预热如实说明。

## 6. 失败诊断

在现有 proc/testenv 和 acceptance Session 中补诊断，继续使用原有验收回执。
失败时保存命令、退出状态、必要日志、候选/环境与复现入口，再停止本次资源，记录清理结果。
浏览器容器删除前复制报告，结束后定向清理；归属、取消和失败传播沿用现有实现。

原始材料私有保存；成功运行复用已有输出、CI 与回执。
日常诊断按实施方案约定期限留存，接续或正式结论仍引用的材料遵循
[证据用途](../logs/README.md#证据按用途留存)。
CI 仅上传核验过的脱敏摘录；原始环境、凭据和浏览器完整产物不自动上传。
不为所有命令另建摘要、版本化报告协议、配额索引或证据登记系统。

## 7. 实施与完成

全部工作由一个 [Phase-23-06 实施文件](../imple/Phase-23/Phase-23-06-工程稳定性改造.md)交付。
H→A→B→C→D→E→F→G 共用分支与完成版本，先直接检查，再组合验收。
实际执行和版本分配从[总方案](../imple/Phase-23/Phase-23-总实施方案.md#2-正式分配与进入顺序)读取，
成本与停止点只从实施文件读取。

组合验收覆盖环境/依赖复用、17 模块、源码开发、两类 integration/e2e、Compose、
最小真实失败诊断及 Bundle 隔离安装。
同输入有效检查复用；版本、配置或制品改变后重验实际受影响集合，原回执不编辑、不换绑。
成功收口遵循根 AGENTS，最终 head 的权威 CI 必须成功；日志引用实际候选与结果。
本批完成的是工程能力，不据此新增容量、长期稳定性或完整备份恢复结论。

验收还要沿 AGENTS 实际找到代码、命令和事实来源，确认错误和重复正文已处理。
链接通过只是文档检查结果，工程完成由上述真实行为共同证明。
当前新增命令与代码检查仍待实施，规划修订不宣称工具已经可用。
