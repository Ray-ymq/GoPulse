## 1. 文档定位、目标与范围

目标依据为[高并发架构设计](<../../docs/GoPulse 高并发架构设计.md>)和[可观测架构设计](<../../docs/GoPulse 可观测架构设计.md>)。下文“业务 §n”“观测 §n”分别指两份设计的章节；共同身份和环境资源合同以观测设计第 5 节为定义来源。

本文回答三个问题：目标需要哪些设计产物、哪些行为必须满足前置条件、哪些跨模块结果证明目标成立。架构原文的约束全部适用，专题表和验收映射不替代原文。

| 最终能力 | 需要共同证明的结果 |
| --- | --- |
| 业务正确性 | 创建重试、相反操作、编辑/删除竞态和异步重投具有明确事实及完成语义 |
| 有界并发与恢复 | 固定资源和负载下，分类 goodput、尾延迟、热点隔离、积压及恢复边界可解释 |
| 多目标观测 | 同类目标和服务副本的配置、执行、身份、查询及聚合正确 |
| 查询与诊断 | 历史窗口、业务持久阶段和搜索可见性可查证，事实、遥测、推断与未知可区分 |
| 实验复现 | 他人可按相同候选、环境与配方重跑，并复核原始结果和归属清理 |

完整 CMDB、多租户、任意协议、通用 DAG、自动根因判定和自研存储引擎不进入默认范围。统计分桶、收件箱信息流、读副本、分片、领域微服务、长连接及多地域扩展须满足业务 §16.2 的触发条件。

当前差距与证据范围查询[能力状态](../status/capability-status.md)，完成产品版本读取 [VERSION](../../VERSION)，实际工作查询[实施日志](../logs/README.md)。本文不维护现状表、完成状态或未来 Phase 编号；上一版差距快照保留在 Git 历史中。

## 3. 完整案例与迁移路径

案例用于确定最小跨模块合同和失败边界，不能以单模块实现代替集成结果。

### V1. 创建命令到搜索可见与业务阶段查证

- 链路：B2/B3 校验身份及幂等请求，原子保存事实、命令结果与事件 → B6 可靠投递 → B7 按版本/代际投影并保存适用完成依据 → B10/M6/M7 查证持久阶段、遥测和受限可见性。
- 产物：跨模块时序、命令/事件/对象/消费者及数据/投影代际传播与证据表、权限/预算、兼容迁移和失败案例。
- 验证：响应或确认丢失、重复/乱序、重启、ES 延迟及遥测出口故障。持久应用完成与当前查询可见分别核实；缺 Span 不抵消持久完成依据，无证据的阶段保留未知。
- 独立性门槛：在业务依赖可用且预算有效时，观测接入、缓冲、存储或 OTLP 阻塞/不可用不作为普通事务提交或业务消息确认的前置条件。须分别核验业务响应、事实、副作用/确认及遥测缓冲/重试/丢弃；只展示缺遥测不能算通过。

### V2. 同一插件管理两个独立目标

- 链路：M2 保存目标和独立配置 → M4 来源策略就绪 → M3 验证并提交实际执行修订 → M4/M5 保持目标/实例身份 → M6/M7 查询和评估。
- 产物：最小对象关系、激活/恢复时序、端到端身份、权限/预算及管理流程。
- 验证：单目标故障、单配置更新、旧回报、控制端不可用和执行端重启；另一目标的状态及约定进展可查证。历史默认目标明确标注，不补造采集时不存在的身份。

### V3. 热点交互、删除、重建与恢复

- 链路：B1/B3～B9 的建立/取消、删除、事件投递、页面/通知读取及索引重建，由 M6/M7 查证、M8 组织实验。
- 产物：竞态交错表、锁/资源预算、最终事实与投影校验、删除及切换恢复证据。
- 验证：热点与无关对象、删除重叠、迟提交、旧消息、构建扫描/实时写入、切换崩溃和新数据代际；无遗漏、无复活或越权正文暴露。统计分桶等扩展仍按触发证据决定。

迁移路径统一为：**新增兼容结构 → 部署兼容读取/消费者 → 迁移或构建 → 验证 → 启用 → 受限退役**。详细设计须为每步给出失败停点、回退限制和证据；启用及清理门槛见第 4 章。

## 4. 硬依赖与必须解决的决策

### 4.1 行为启用、回退和清理门槛

| 受约束的变化 | 必须先成立的条件 | 未成立时的边界 |
| --- | --- | --- |
| 运行角色分离 | 路由/依赖/身份、就绪/排空、新旧兼容及共享预算核对通过 | 新旧角色继续遵守租约/owner；允许重投，不丢事件或产生重复业务副作用 |
| 命令/事件/完成记录启用 | 新结构和消费者模式兼容，历史与新记录范围明确 | 必要未知事件可持久停放；必要副作用完成前不因已发布而清理事件；不补造历史幂等结果或完成依据 |
| 统计来源切换 | 完整建立/取消事实流、初始基线、原子去重/计数及事实校准成立 | 保留原读取合同，不混用统计语义；分层缓存隔离个人字段与新旧键空间 |
| 删除生命周期启用 | 所有读取/交互/通知/索引兼容删除状态及持久屏障 | 不退回忽略新状态的版本；物理清理在预算内且不产生重复事件，满足旧写入失效条件后才清理屏障 |
| 移除 ES I/O 期间数据库持锁 | 内容版本、同版本确定的规范投影及持久删除屏障通过竞态验证 | 继续保留现有重建/删除协调保护，不能由这项撤锁推导撤除全部保护 |
| 撤除重建/删除协调保护 | 新捕获、追赶、切换恢复机制已实现且竞态验证通过 | 维持现有协调保护；捕获队列在扫描前绑定，不能把 `MAX(outbox.id)` 当作提交水位 |
| 索引代际切换及旧索引退役 | 捕获/扫描/追赶、删除校验、含未确认及正在写入的排空、切换意图和真实 alias 恢复查证成立 | 未核实实际 alias 和旧写入失效前，不回收旧索引或删除标记 |
| 多目标采集启用 | 目标/配置/执行身份 → 来源策略就绪 → 执行生效 → 存储身份保持 → 正确查询/聚合 | 保存与生效、实际版本与历史身份分别表达；控制故障只在有效授权快照内继续 |
| 告警与业务阶段诊断 | M6 查询语义/质量先成立；阶段诊断另需持久业务状态及适用的受限可见性 | 普通告警不附加全部业务诊断前置；平台不直接扫描业务表，结果注明来源及读取时间；查询失败不宣布告警恢复，缺遥测不能断言业务阶段未执行 |
| 恢复到过去数据点 | 新 `data_epoch` 持久化，事实/执行依据/删除状态及缓存/索引核对通过 | 旧事件拒绝；重放按恢复合同生成依据，不能只改标签或复用旧投影代际完成 |
| 正式容量/故障/恢复结论 | 各模块与工具预算已申报且实际生效，共享总量核对后冻结环境/负载/候选 | 运行时继续使用有效配置，不逐请求依赖 M8；声明与实际不符时不能归入该合同的结论 |

共享数据库按业务 §12.2 和观测 §5.4 校验 `Σ(N_r × P_r) + C_reserve ≤ C_safe`。覆盖业务、平台身份/元数据/诊断、投递/消费、发布重叠、维护及实验工具，预留只计一次；同实例的不同 schema 或连接池不证明后端故障隔离。

## 5. 系统成立条件与验收映射

来源为业务 §14～16 和观测 §7～8。A1～A12 固定跨模块验证方向；各批按范围引用并在正式方案中确定命令、阈值、次数和窗口，不能把某批通过外推为全部目标成立。

| 场景 | 协作模块 | 必须证明的结果 |
| --- | --- | --- |
| A1 同插件两个目标 | M2～M7 | 独立配置/修订/执行状态，身份和查询不混淆；单目标失败/恢复具有约定隔离 |
| A2 服务副本与统计 | M1、M3、M5～M7 | 已知 counter 增量、重置/重启、缺失、局部/共享值的解释和聚合正确 |
| A3 完成顺序与归属 | M4/M5/M8 | 较早阻塞、较晚成功不越位确认；重启和消费归属变化后仍正确 |
| A4 重复与阶段查证 | B3/B6/B7/B8、M6/M7 | 响应/确认丢失、重投、失败后成功可查证；持久完成与当前可见分开，缺遥测不等于未执行，缺证据保留未知 |
| A5 来源与观测后端故障 | M1/B6、M3～M6、M8 | 超限/阻塞范围、其他通道进展、资源和质量可查证；普通提交/业务确认不等待观测成功，遥测缓冲/重试/丢弃有界 |
| A6 控制端不可用 | M2～M5 | 有效快照内继续，失效按策略处置；新变更不误报生效 |
| A7 热点、缓存与信息流 | B1/B3/B4/B5/B9、M8 | 关系/统计/个人状态正确，旧回填不覆盖新正文，冷缓存有界回源，稀疏流有界扫描，无关类别有余量 |
| A8 编辑、删除与重建 | B3/B6/B7/B8/B9、M8 | 迟提交、乱序、扫描/实时竞态和切换崩溃后，最终版本与删除无遗漏、无复活或正文越权暴露 |
| A9 依赖故障与排空 | B1/B6/B7/B8/B9/B10、M8 | Broker/ES 降速或不可用时保留意图、水位准入；在线流量下净排空及恢复时间符合合同 |
| A10 发布、诊断与维护 | B1/B6/B7/B9/B10、M6/M8 | 新旧实例重叠、扩容、诊断和维护遵守共享预算，dispatcher 数量/排空独立且版本兼容 |
| A11 恢复后的旧事件 | B6/B7/B9、M5/M6/M8 | 旧代际拒绝，缓存/索引/事件代际一致；诊断和历史实验不混合 |
| A12 实验失败或停止 | M8 及被操作模块 | 实际已执行/失败/未开始记录、原始证据、有限恢复/归属清理及实际支持的接续能力 |

M8 的实验设计须把业务事实与遥测校验分开，记录计划/实际发出、工具丢弃、准入/拒绝/终态和各维度恢复时刻。goodput 仅计符合业务语义及时间合同的工作，成功/拒绝/失败延迟分别报告；观察到的失败、已证明原因和相关现象分别表达。

原始结果须能绑定候选、制品/Bundle/manifest、工具/配置/依赖、数据代际、实验身份、物理资源和公开负载配方；未知或缺失如实保留。已有容量结果只适用于原冻结条件，有限单链路或短窗结果不能外推为全站 Trace、长期保留或持续运行。

## 6. 详细设计与正式实施方案的衔接

详细设计按第 2 章专题与 V1～V3 的需要编写；先确定案例必需的共同合同、运行边界和环境预算，再细化所需接口，扩展其余能力，最终验证系统成立条件。该顺序用于设计展开，具体批次顺序由正式总方案分配。

每份详细设计至少能核对五项内容：

1. 架构来源、范围、领域所有者、现有实现差距及待决策事项。
2. 接口/权限/版本/错误、数据/唯一约束/索引与状态、事务/锁及外部 I/O、重复/乱序/失败/重启行为。
3. 实际资源预算、期限、超限结果、共享依赖和恢复余量。
4. 兼容迁移、启用/回退/清理门槛及失败停点。
5. 系统验收映射、所需证据及允许转入正式批次的条件。

一个专题可对应多份设计或批次，多个专题也可组成一个交付结果。后续正文链接、决策及实施对应关系登记在[设计索引](README.md)，正式合同入口见[阶段索引](../phases/README.md)。本文不预建空文件或分配未来 Phase、版本和分支。

批次范围、固定门禁、回归、预算、候选/证据、停止/接续及完成提交遵守[仓库规则](../../AGENTS.md)、[执行预算规则](../rules/implementation-execution-budget.md)和对应正式实施方案。本文不另设执行合同，也不修改已分配合同或历史证据；实现完成、验收完整和能力达标分别登记。

本大纲收口要求：目标及模块覆盖完整，专题产物和来源可追溯，硬依赖与迁移边界明确，A1～A12 有对应设计入口，动态信息有独立维护位置。
