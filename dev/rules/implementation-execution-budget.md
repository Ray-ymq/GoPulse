# 实施耗时预算与验收接续

本规则控制实施和重试成本。验收必须完成的能力、数据安全、候选身份与真实实验窗口继续
由 AGENTS.md、总方案和当前批次方案规定。时间到达上限表示暂停未完成工作，不表示验收通过。

## 1. 每份实施文件必须登记的成本

| 项目 | 必填内容 |
| --- | --- |
| 范围 | 一个主要交付结果、逐文件清单、固定门禁，明确哪些内容由其他批次承担 |
| 总预算 | 普通文件目标 120 分钟、累计上限 180 分钟；不是每条命令各 180 分钟 |
| 阶段预算 | 发现/实现、直接检查、构建/启动、真实验收、发布/清理的预计与上限；各项之和不超过总预算 |
| 实验成本 | 单元数 × 预热/测量/恢复时间，加上实际启动/配方/校验/清理成本；不能只估测量秒数 |
| 重试成本 | 同一未解决原因最多两次定向诊断，每次默认最多 10 分钟；全套入口不用于探查工具错误 |
| 停点 | 50%/80% 进度报告、开始下一命令前的剩余预算检查、超时收尾与接续依据 |

普通文件的参考分配为：实现 60 分钟、直接检查 10 分钟、构建/启动 20 分钟、真实验收
60 分钟、证据/清理 10 分钟、机动 20 分钟，共 180 分钟。这是任务规模上限示例；若已知
实验本身需要更多时间，必须在开工前拆分开发工作，并为专项验收登记实际总成本。
不能先接下一个超大范围，再通过反复重试或换目录消耗十余小时。

专项长时验收只执行冻结候选。它的上限依据不可缩短的实验与已观察到的启动/收敛成本
计算，登记到对应文件和总方案；不得使用“跑到通过为止”。每个验收单元有结束条件和
独立回执；单元完成后核对剩余预算，不能把最后一次失败后的重新执行自动计作新任务。

## 2. 时间与有效证据台账

执行前在私有工作目录登记 file_id、首次开始时刻、预算、候选 manifest、相关工具/config
digest、阶段和 case_id。每次命令追加实际开始/结束、耗时、结果、原因与原始证据路径；
执行器重启后从同一累计台账恢复，不能以进程的新单调时钟把过去的成本清零。
台账不包含密码、cookie 或命令中的凭据。

候选/工具发生变更时，登记受影响的案例和失效原因。未受影响的直接检查保持有效；
真实验收证据按原候选保留，是否可继续使用必须满足既有身份/配置/环境规则。
无法证明仍有效时标为待核对，不能重写旧回执或用旧候选结果冒充新候选通过。

重建遵循依赖关系：哪个源文件影响哪个镜像，就检查该构建目标；第三方镜像不因本地 Python
编排修改重新拉取。最终 manifest 仍绑定所有实际制品。复用 build cache 不等于复用无效证据。

## 3. 失败后的固定路径

1. 第一次工具/基础设施失败就退出全套入口，保存失败案例及其输入。
2. 用离线 fixture、接口契约或最小真实依赖重现失败；有结论前不启动整套项目。
3. 修正最小受影响层，运行对应直接检查；记录哪些案例必须重验、哪些事实仍有效。
4. 如确需新候选，按原规则建立身份；固定门禁通过后再运行必要验收。
5. 两次诊断仍无已证明原因，或累计预算耗尽，保存接续清单并停止；不能继续换一种报错
   后重启全套，也不能以延长超时掩盖采样器、测量口径或数据源问题。

缺方法、入口不可执行、schema/CLI 不匹配、子进程失败未传播等问题，应由直接检查发现。
真实依赖检查仍覆盖网络、权限、存储、并发和生命周期事实；不能把所有失败都归到产品容量。

## 4. 正在执行的验收如何接续

未收到停止指令时，让当前有界运行产生不可变结果；用户明确停止时立即停止新工作，
有界收尾并登记暂停检查点、该候选的通过/失败/待执行项和清理回执，等待明确恢复。
本规则的引入不要求重新构建当前候选，也不把已通过项因“过去耗时太长”判废。

| 本轮结果 | 后续动作 |
| --- | --- |
| 固定门禁完整通过 | 核验实际发布工件、完成日志与版本，按原方案收口；不追加一轮相同验收 |
| 同候选中断，已有有效通过项 | 核对身份、环境及工具实际支持的恢复粒度，只执行可恢复的未开始项 |
| 工具或产品案例失败 | 保存失败事实，围绕失败边界诊断并登记影响范围；只有实际变更影响到的证据才进入重验决策 |
| 用户明确暂停 | 保存原始证据和未提交工作，完成归属收尾；规划修改/推送不触发恢复，不把暂停记为通过 |
| 恢复功能或案例粒度尚未实现 | 如实登记限制，先给出可执行的剩余方案；不发一个不存在的 resume 参数，也不声称可以无条件拼接零散回执 |

接续预算从终态检查点后的首次操作开始；用户暂停时，从明确恢复后的首次操作开始，
历史累计成本和暂停时段分别保留。它只用于过渡这次已开始的工作，
未来任务不能反复借用“新检查点”重置总预算。

### 4.1 冻结执行来源与成功后的连续推进

昂贵验收使用一个已提交 revision 的干净固定源码工作树。可以通过
`git worktree add --detach <新源码目录> <完整revision>` 建立；从该目录调用构建、
runner 和 verifier，登记源码根、HEAD、manifest、制品/工具/config/依赖 digest 及环境。
矩阵执行中不改该工作树、不切换到其他源码根、不替换 manifest 或同名镜像标签。

过程中的工作记录和累计时间台账先追加在私有证据根；所有规定门禁成功后或实际失败/
预算停点才同步实施日志并提交。其他工作树中的纯日志提交不改变冻结根的 HEAD 或
其产品/工具输入，不能仅凭那个新 HEAD 重建本来未变化的冻结候选。验证仍针对原来源，
不跳过身份校验，不重写旧回执。这是固定执行来源的流程，不声明已新增证据复用接口。

以下三种情况必须分清：

- 同候选、相关输入/环境均未变化：保留有效检查，只执行工具实际支持恢复的未开始项；
  不因成功写入检查点或记录进度而追加相同验收。
- 应用、验收工具/config 或相关发布元数据改变：登记确切影响，按根规则建立新候选并
  重验受影响集合；构建缓存和未变的直接检查可保留，旧原始产品证据不得换绑。
- 当前工具不支持所需恢复粒度：如实登记它需要完整执行的单元集合及成本，提前检查
  是否装得进剩余预算，不承诺不存在的 --resume 或把多个局部回执手工拼成正式通过。

用户明确执行一个实施文件后，已登记的成功路径在剩余预算内连续推进。一个定向案例
通过只是检查点；下一阶段前置条件满足且预算足够时继续，不额外要求用户逐项确认。
实际失败、范围冲突、诊断停点、预算不足/耗尽或用户暂停仍按原规则停止，并给出失败
证据、已消耗成本、有效检查与可执行后续清单。规划修改本身不恢复已暂停的验收。

新增/修订计划必须分开写“观察到的失败”“已证明的原因”和“本次允许纠正的具体
代码边界”。不能因请求耗时接近配置超时就认定根因，也不能凭诊断偶然零错误改变
正式结果、扩展配额或启动一轮相同矩阵。已用诊断次数与历史时间缺口须继续保留。

## 5. 已取消 Phase 20 后续批次的历史事实

本节保留此前已观察到的失败与成本约束，不再提供当前执行或自动接续入口。
范围调整见[Phase 20 总实施方案](../imple/Phase-20/Phase-20-总实施方案.md)。
未来若沿用这些未完成工作，须由新方案明确分配，保留已有成本、诊断次数与失败证据。

2026-10-02 只读检查发现：05 的实现分支已有多次采样/编排/证据接口修复；私有历史根
`gopulse-phase20-05-20261001` 包含 13 份 incomplete 的 budget.json，另有多个候选的
preflight 失败回执。它们是失败尝试，不是必须重复的有效样本；不能仅凭提交时间推算
准确的 15 小时分项，准确分项需依据执行台账。

已观察到的错误包括采样器缺少 set_load_pid/failure、诊断模块缺少 read_jsonl、故障容器
无法定位和 marker observer 内存上限。预算 JSON 虽登记 execution_max_seconds /
candidate_build_max_seconds / b03_max_seconds，检查时预算与收口入口没有使用这些字段
建立统一累计 deadline；多个 subprocess timeout 不构成整份文件的时间上限。

这些事实属于取消前的历史记录，原验收结果仍以各候选回执为准。未来执行保护的落地应证明：
阶段和子进程共享剩余预算、跨启动保留累计耗时、超时停止新请求并有界收尾、回执保存
真实失败分类，以及仅恢复身份有效的未开始单元。实现此能力前不能称之为“已强制限时”。
