# GoPulse 高并发与可观测后续路线图

> 规划基线：2026-09-27，`upstream/main=ce08b1b`，根 `VERSION=2.0.2`。
>
> 本文说明发展顺序。Phase-18-03～18-05 已排期并分配版本；其余方向不预留 Phase、版本或分支。

## 1. 当前判断

GoPulse 已经完成业务、异步消息、搜索、Metrics、Logs、Events、内部告警、双 Frontend、
Linux `amd64` Bundle 和完整 Compose 生命周期。当前短板不是缺少组件，而是现有闭环仍主要建立在
单副本计算层与单节点状态层之上。

Phase-18-01/02 已得到以下边界：

- 固定负载可以完成请求，但不能据此宣称已经证明稳定承载 `150 RPS`；
- Outbox 的满批空等问题已在 `2.0.2` 修复；
- 多副本所有权、事件最终闭合、存储故障域、过载行为和独立诊断仍未形成完整证据；
- 当前单节点 Kafka、VictoriaMetrics、Elasticsearch、MySQL、Redis 和 RabbitMQ 不构成生产高可用。

因此，下一步不应先增加新中间件、业务功能或 Kubernetes YAML，而应先让已有系统具备
“可正确扩展、可受控降级、可独立诊断、可重复验证”的基础。

## 2. 目标架构原则

后续所有工作遵循六条原则：

1. **先证明正确扩容，再追求更高数字。** 多副本不能产生重复业务事实、错误提交、越权或状态漂移。
2. **过载必须显式。** 每一层都需要有限队列、超时、拒绝或降级语义，不能靠无界等待隐藏压力。
3. **业务与观测故障域分离。** 可观测链路、日志存储或管理查询故障不能阻断核心社交业务。
4. **状态层最后扩展。** 先扩大无状态计算层并取得瓶颈证据，再决定 MySQL、RabbitMQ、Kafka、
   Elasticsearch 或 VictoriaMetrics 的集群形态。
5. **健康与观测解耦。** 每个实例的启动、存活、就绪和关键容量信号必须能经独立通道直接检查，
   不能依赖待诊断的 Kafka、Marshaller 或存储链路。
6. **部署平台不替代产品语义。** Kubernetes 只能承载已经在 Compose 中证明的副本、所有权、
   背压、恢复和数据边界。

## 3. 已排期：Phase-18-03～18-05

Phase 18 继续使用 `2.0.x`，把容量定界后的多副本和隔离工作分三批完成：

| 顺序 | 版本 | 结果 |
| --- | --- | --- |
| Phase-18-03 | `2.0.3` | Backend、Business Worker、Search Indexer 多副本业务闭环 |
| Phase-18-04 | `2.0.4` | Router、Marshaller 多副本，可观测处理隔离，业务/观测双 Elasticsearch |
| Phase-18-05 | `2.0.5` | 机器合同单一来源、实例级独立诊断、完整扩缩容与故障矩阵 |

Phase-18-03～18-05 判断正确性、故障隔离和恢复边界，不发布吞吐 SLO，也不把单节点状态服务
描述成高可用。每个最终验收单元只运行两次，保留两次原值并取算术平均；无论成功或失败，
证据完整即完成批次并更新版本，禁止第三次筛选运行。
权威范围、顺序和完成条件见
[`Phase-18-总实施方案`](../imple/Phase-18/Phase-18-总实施方案.md)。

## 4. Phase 18 之后的发展顺序

以下方向只有前一项形成稳定候选和证据后才立项；它们目前不分配 Phase 或版本。

### 4.1 容量认证与证据驱动优化

在多副本正确性成立后，重新建立独立候选和容量证据：

- 固定硬件、数据配方、流量模型、候选 revision 和运行次数；
- 明确业务 SLI：成功率、P95/P99、恢复时间、Outbox/RabbitMQ/Kafka 收敛时间；
- 明确可观测 SLI：采集到查询的延迟、丢弃数、Kafka lag、存储写入失败和告警新鲜度；
- 先找第一瓶颈，再只优化直接相关的 SQL/索引、连接池、缓存、批处理或并发度；
- 每次优化都以同一配方做前后对照，不通过放宽阈值制造“通过”；
- 最终分别给出单实例、计算层多副本和状态层瓶颈，不把一个 RPS 数字外推到其他环境。

这一阶段完成后，项目才可以对指定 Linux `amd64` 资源规格给出有边界的容量声明。

### 4.2 状态层高可用与数据生命周期

只有容量证据表明状态层或恢复目标需要升级时，才按风险逐项引入：

- MySQL 高可用、只读副本、备份恢复与明确的 RPO/RTO；
- RabbitMQ quorum queue、节点故障与网络分区下的确认/重投语义；
- 多 broker Kafka、复制因子、最小 ISR、分区再分配和保留策略；
- 业务搜索与观测 Elasticsearch 的独立集群、快照、ILM/rollover 和磁盘水位；
- VictoriaMetrics 的保留、降采样、备份以及需要时的集群形态；
- Redis 始终保持可丢弃缓存角色，高可用不能把它提升为业务事实源。

每种状态服务独立立项，避免一次引入全部集群导致故障归因失效。

### 4.3 Kubernetes 迁移与弹性

完成多副本和至少一轮容量认证后，再将已验证语义迁移到 Kubernetes：

- 无状态组件使用 Deployment、Service、滚动更新和 PodDisruptionBudget；
- 有状态组件根据已完成的 HA/恢复合同选择托管服务或 StatefulSet，不用临时 YAML 替代数据设计；
- 统一 Ingress 保持同域登录、双 Frontend 和 Backend 授权边界；
- HPA 只使用已验证能代表饱和度的指标，例如并发、队列深度或消费 lag，不仅依赖 CPU；
- 通过真实扩缩容、驱逐、重调度和节点故障验证业务与可观测闭环；
- 保留 Compose 作为较小、确定性的开发与回归环境，Kubernetes 成为独立产品运行目标。

已有候选设计保存在 [`docs/future/kubernetes`](../../docs/future/kubernetes/README.md)。

### 4.4 SRE 与长期运营

最后补齐持续运行能力：

- 以用户请求、异步闭合和可观测新鲜度建立 SLI/SLO 与 error budget；
- 告警覆盖症状、容量、队列、数据新鲜度和恢复失败，并控制告警风暴；
- 建立变更、回滚、容量预测、灾难恢复演练和受控故障注入；
- 对 Metrics、Logs、Events 定义保留、归档、成本和删除策略；
- 形成运行手册和故障分级，使管理界面、日志、指标和直接探针能够共同完成定位。

## 5. 不建议的近期方向

- 不以继续堆组件或拆微服务代替容量与故障证据。
- 不在单副本所有权尚未证明时直接上 HPA。
- 不把单 broker、单节点数据库或单节点存储包装成生产 HA。
- 不先做大规模缓存、分库分表或 CQRS；当前没有证据表明它们是第一瓶颈。
- 不让日志、Events 或告警写入失败回压核心业务请求。
- 不同时改变负载模型、资源规格和产品算法后再比较性能结果。
