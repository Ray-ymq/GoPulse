# GoPulse 全局架构与发展总纲

> 决策日期：2026-10-03；已完成产品基线：根 VERSION=2.2.4。
>
> 本文件确定整个项目的定位、架构边界、发展顺序、取舍和完成终点，不是下一小批开发清单。
> 能力关卡不等于 Phase、版本或实施批次；未来分配仍只能由新 Phase 总实施方案完成。
> 已开工 Phase 20 的合同、分支、历史成本与有效证据保持不变，不因本规划自动恢复执行。
> 当前事实以 [能力清单](../../docs/capability-status.md)、
> [Phase 20 总实施方案](../imple/Phase-20/Phase-20-总实施方案.md)及实际实施日志为准。

## 1. 严厉判断：问题在主次失衡，不在组件不够

GoPulse 已有真实社交功能、完整 Compose 交付、可靠异步基础、自研观测链路和计算层多副本，
不是需要推倒重建的空壳。但它目前还不能被描述成普遍意义上的高并发系统、
完整 APM 平台或生产级高可用平台。

必须承认四个问题：

1. 旧路线把“证明成熟”变成主线，把真实业务降成实验负载，缺少整个产品何时完成的定义。
2. 固定 50/100/150/200 RPS 实验是有边界的事实，不证明热点、大数据量或更高吞吐；
   加入 RabbitMQ、Kafka 或更多副本本身也不证明高并发。
3. 数据采集、运输、存储已经较完整，但从用户问题出发的诊断体验还未闭合；
   单业务链路 Trace 已存在，不能把重新接 SDK 当成下一轮建设成果。
4. 把 Monitor HA、逐个状态服务 HA 和进一步容量认证放在 Kubernetes 前面，
   是超出当前规模的前置条件。基础部署适配需要清楚的恢复边界，不需要先做企业级 HA。

Phase 18～20 的背压、幂等、故障隔离、关联和生命周期工作保留；改变的是后续主线和准入条件，
不是否认历史成果。规划者的责任是控制复杂度、形成产品增量并定义终点，
不能用增加验收层数代替全局决策。

## 2. 唯一选定的项目定位

> GoPulse 是一个以真实社交业务为核心、以自研可观测系统为诊断核心的云原生项目：
> 用户可以实际使用；维护者可以解释热点、可靠异步与扩缩容的行为；学习者可以运行并理解这些取舍。

业务与观测都是一等能力，共享真实问题，但不共享故障命运。
项目面向当前维护规模下的自托管使用和架构学习，不竞争腾讯蓝鲸的企业平台广度。

最终成果必须同时包含：

- 可使用的用户端：现有内容、关系、互动、搜索和通知形成完整体验。
- 可诊断的管理端：能够从业务异常进入指标、日志、链路与相关运行事件。
- 可交付的运行系统：保留 Compose，增加一套明确支持环境的 Kubernetes 交付。
- 可解释的并发与弹性：知道哪条路径改善了、何时扩容有效、何时必须停止扩容。
- 可运行的跨语言边界：通过一个可替换的通知消费者学习协议与一致性，不重写整个项目。

“开源学习”是运行上述能力后的结果，不用教程或整理文档替代产品建设；
“高并发”是具体负载下的工程结论，不作为没有资源和数据规模前提的宣传标签。

## 3. 终态架构：模块化业务核心，按运行职责分离进程

    用户端 / 管理端 → Backend 模块化单体
                         ├─ MySQL：业务事实、事务、Outbox
                         ├─ Redis：可丢弃缓存
                         └─ Outbox → RabbitMQ
                                      ├─ Notification Worker → 通知事实
                                      └─ Search Indexer → 业务 Elasticsearch

    应用 / 基础设施 → Monitor → Router → Kafka → Marshaller
                                                      ├─ VictoriaMetrics：指标
                                                      └─ 观测 Elasticsearch：日志 / 事件

    现有 OTel 埋点 → OTLP → 成熟 Trace 后端 → Backend 授权查询 → 管理端

两条观测路径服务同一个诊断体验，不强行统一运输或存储模型。
Trace 的查询与存储优先复用 Jaeger 的公开稳定接口，不自研 Trace 数据库；
部署形态、存储和版本兼容性在对应实施方案中验证，不能直接假定可复用当前 Elasticsearch。
接口边界依据 [Jaeger API 合同](https://www.jaegertracing.io/docs/2.21/architecture/apis/)。

| 边界 | 唯一职责 / 事实归属 | 不允许承担 |
| --- | --- | --- |
| Backend | 身份、内容、关系、互动与授权；模块内维护事务边界 | 为每个业务名词增加 RPC 服务 |
| MySQL | 权威业务状态、Outbox、幂等通知事实；单一迁移所有者 | 把缓存、搜索或 Trace 当作提交成功的证明 |
| Redis | 可重建缓存，失效时按受限路径回源 | 成为未声明的业务事实库 |
| RabbitMQ / 业务消费者 | 已提交业务的可靠异步处理、重试与终态 | 用无限积压掩盖消费能力不足 |
| 业务 Elasticsearch | 可从 MySQL 重建的搜索投影 | 决定业务内容是否存在或用户是否有权限 |
| Monitor / Router / Marshaller | 采集控制、路由、类型转换各自独立；失败可诊断 | 回压核心业务提交，或接管业务任务 |
| 观测存储 / Trace 后端 | 保留窗口内的诊断数据 | 充当审计事实或承诺永不丢失 |

业务模块保持代码与数据边界，运行进程按 HTTP、通知、索引、观测运输的负载和失败域拆分。
没有独立扩展、故障隔离或团队所有权需求，就不增加业务微服务。
这种按运行职责扩展的选择参考 [Mastodon 的进程与连接预算](https://docs.joinmastodon.org/admin/scaling/)，
不照搬其 Redis 持久数据语义。

用户端和管理端继续共享 Backend 的权威身份系统。
诊断查询可以有独立准入与资源预算，但管理员实时授权仍以 MySQL 为准；
HTTP 隔离不等于数据库故障时管理端仍可用。

## 4. 高并发主线：围绕业务形状，不围绕一个总 RPS

整个项目只围绕三类代表性问题建立性能能力，不铺开全站调优：

| 业务形状 | 必须回答的问题 | 允许的演进方向 |
| --- | --- | --- |
| 信息流 / 帖子读多写少 | 数据量与关注关系增长时，查询和缓存回源是否仍有界 | 查询形状、索引、批量读取、受控缓存 |
| 热帖点赞 / 评论集中写入 | 一个热点是否拖慢无关请求；锁与事务时间在哪里消耗 | 缩小必要锁范围与事务窗口，保护删除和权限 |
| 通知 / 搜索异步突发 | 提交成功后多久可见；哪里排队；重投是否重复 | 可靠投递、幂等消费、受限并行与扩容 |

Following、缓存和异步消费者已经存在，后续是改善其实际行为，不重新包装成新增功能。
数据规模、热点偏斜、关系分布、读写比例与指定资源必须进入负载描述；
均匀随机请求不能替代热点场景，短窗口不能替代持续运行结论。
具体数值与固定门禁只由对应实施方案冻结，不在总纲另设一套阈值。

现有代码有值得验证的候选，不是已经证明的瓶颈：

- [点赞](../../backend/internal/like/repository.go)与
  [评论](../../backend/internal/comment/repository.go)在事务中取得父帖子排他锁；
  需要测量竞争，并证明任何调整仍保护并发删除、通知和幂等。
- [帖子读取](../../backend/internal/post/service.go)在缓存命中后仍有 revision 与个性化查询；
  不能为追求“零 SQL”删掉正确性保护。

先解释一种实际业务形状，再做对应改善；不同时引入分片、CQRS、读写分离和缓存重构。
没有可复现问题时保留现状，不制造优化收益。

资源预算必须按整个部署汇总：Backend、Worker、Indexer、滚动更新新增实例、
终止中的实例和维护任务共同消费数据库连接。只校验单个服务的副本倍数不够。
缓存故障后的回源、已提交任务的积压和消费重试都必须有边界；
观测数据可以按明确策略丢弃并暴露信号，已提交业务不能用同一种丢弃策略处理。

## 5. 可观测主线：从信号管道发展为诊断产品

继续保留自研采集、路由和转换，这是项目有价值的学习边界。
但后续主要产品增量必须落在“如何解决问题”，不继续为运输链路增加抽象层。
观测平台需要查询和分析体验，而非只有采集存储；
这一产品区分参考 [SigNoz 架构](https://signoz.io/docs/architecture/)，不据此替换现有存储栈。

诊断体验固定围绕三个入口：

1. 请求变慢：查看对应路由的尾延迟、拒绝、实例饱和度，再关联日志与可用 Trace。
2. 搜索或通知变迟：区分提交、Outbox、队列、处理、索引与可见阶段。
3. 扩容或发布后异常：区分实例身份、运行事件、消费变化与下游资源瓶颈。

必须补齐的架构边界：

- 每个进程实例的计数器和直方图有独立身份，先按实例计算再聚合；
  不经负载均衡器随机抓取后冒充完整副本观测，不平均多个 P99。
- request_id、trace_id、业务事件 ID 用于日志和链路关联，不进入无限增长的指标标签。
- 查询负载和普通业务请求有分别可解释的预算；不引入角色缓存绕过实时撤权。
- Trace 采样、过期、传输丢弃和“业务事件未产生”分别呈现；
  查不到 Trace 不等于业务未提交，采样链路不能直接充当总体新鲜度 SLO。
- 延续 Logs/Events 与指标的保留边界，并把副本身份 churn、Trace 保留和查询成本计入预算。
- Monitor 保持插件进程与期望状态的单一所有者；先沿用现有持久根和排他锁，
  不为了 Kubernetes 首次部署先建设分布式控制面。

当前 [component Envelope](../../monitor/internal/metrics/envelope/envelope.go)只接收组件 ID，
而[采集器](../../monitor/internal/metrics/collector/components.go)逐端点抓取后未传递实例身份；
这影响副本诊断，需要连同转换和查询合同修改。它不追溯否定独立验收采样器的历史结果。
[API 准入](../../backend/internal/http/router.go)目前覆盖同一 API 前缀，诊断查询预算需要明确隔离。

不建设 CMDB、统一 DataSet、通用查询 DSL、自定义大屏编辑器和企业工作流。
关联不同信号不等于给所有数据增加一套统一事实模型。

## 6. 云原生主线：明确支持一种环境，不承诺所有环境

Compose 继续作为受支持的开发、使用与确定性回归入口，不因 Kubernetes 贬值或废弃。
Kubernetes 首次交付选定一套可复现的 Linux 学习集群配置和一套 Helm 安装入口；
不同时维护多种部署生成器、多个云厂商适配或第二套业务运行逻辑。

云原生必须交付安装、升级、持久数据保留与恢复、滚动发布、受控服务发现和资源预算。
不是把 Compose 转成 YAML 后就宣告完成，也不声称 Kubernetes 本身提供状态层 HA。

运行边界：

- 复用现有镜像、startup/live/ready 和 drain 行为；不重新开发同名运行能力。
- 无状态应用按职责部署，内部服务保持私有，只通过统一入口访问双前端和 Backend。
- 应用版本、配置、迁移任务和备份恢复有明确顺序；回滚受数据迁移兼容性限制，
  不能保证任意旧版本一键回退。
- 初始状态服务可保持单实例与持久卷，明确节点、存储和恢复限制。
  数据恢复能力不可省略，自动故障切换与生产级 HA 不列为首次交付条件。
- Monitor 初始采用单实例 StatefulSet 和持久插件根，保留已有所有权保护；
  不另行部署脱离 Monitor 管理的六组 Exporter。
- 服务发现保留真实实例身份；集群观测只覆盖当前命名空间需要的 Pod、Workload 与相关事件，
  不借此扩展成跨集群运维平台。

单副本、Recreate 和持久卷不能单独证明任何时刻只有一个控制者。
Deployment 的 Recreate 主要约束升级，不排除手动删除期间的进程重叠；
强删、分区和存储语义的限制必须公开，不能假定已经解决。
依据 [Kubernetes Deployment 语义](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)。

基础 Kubernetes 交付不依赖所有状态服务 HA、Monitor HA 或更高容量认证。
真正公开到互联网或宣称生产支持时，必须另行确定外部安全和可用性合同；
本总纲不把受控学习部署冒充生产支持。

## 7. 全局能力关卡与建设顺序

下面是整个项目的递进成果，不是五份可以直接开工的小批计划。
每个关卡包含跨组件集成结果；具体实施拆分前估算发现、实现、构建、诊断、
验证与收尾成本，遵守仓库已有预算，不在这里预分配 Phase、版本或分支。

| 关卡 | 项目整体新增能力 | 依赖与结束条件 |
| --- | --- | --- |
| A：业务可诊断 | 实例指标身份、受限 Trace 查询与日志关联、独立查询准入形成管理端诊断入口 | 继承现有业务和观测链路；能解释代表性请求慢与发帖到搜索延迟，缺失信号能说明原因 |
| B：部署可迁移 | 同一产品在 Compose 和选定 Kubernetes 环境保持业务、观测、插件所有权与持久数据语义 | A 的最小实例/诊断边界可复用；完成安装、升级、重建恢复和一次应用滚动发布，不等待全栈 HA |
| C：并发可解释 | 三类业务形状具有可信边界；对实际热点做一次有依据的改善或明确无需优化 | 已有可查询诊断；同条件说明瓶颈、非退化与代价，不把增加机器计作代码优化 |
| D：扩展可控制 | 通知 Worker 的手动扩容与有限自动伸缩产生可解释收益或明确无收益边界 | B 提供运行环境；C 与独立消费测量确定下游余量；扩缩容不破坏幂等、终态和连接预算 |
| E：边界可复用，整体可发布 | Java 可替换通知消费者，公开交付上述完整产品与运行限制 | 复用稳定业务消息和数据库合同；Go/Java 首先择一运行，单一迁移所有者；外部使用者可运行与复现代表性案例 |

首次正式交付顺序为 A → B → C → D → E。
只传递下一关真正使用的合同：B 不等待 C 的全部性能实验；
D 必须等待通知消费者的扩展语义和数据库余量，而不要求整个站点达到任意“大并发”数字。
独立的设计和局部验证可并行，但不能将尚未完成的能力写成集成成果。

D 首次只覆盖通知 Worker，不给所有计算服务自动伸缩。
目前 [RabbitMQ Exporter](../../exporters/rabbitmq/internal/collector/collector.go)聚合整个固定 vhost，
包含不同职责的队列，不能直接用于通知扩容。采用 KEDA 时必须锁定通知主队列、
明确 ready/unacked 含义并核对对应 RabbitMQ 管理接口；重试与死信不能混入正常伸缩触发。
副本上限、冷却、连接余量和消费者退出语义进入对应实施合同；
信号语义依据 [KEDA RabbitMQ scaler](https://keda.sh/docs/2.21/scalers/rabbitmq-queue/)。

E 的跨语言成果必须真实处理通知业务：兼容事件版本、整数 ID、Trace 传播、重投、
确认、幂等入库和退出行为；不是 Hello World，不引入另一套用户系统或数据库迁移。
第二种语言属于明确的学习交付，不以此声称吞吐提升或微服务化成功。

关卡成本评估重点分别是：

- A：身份合同涉及采集、封装、转换、查询；Trace 后端集成涉及权限和存储，不是单个标签改动。
- B：主要成本在持久卷、迁移顺序、插件所有权及真实集群恢复，不在生成部署文件。
- C：主要成本在代表性数据与因果对照；性能实验与工具修改分别估算。
- D：先测消费者行为再冻结策略；扩容正确性验证与控制器接入分别估算。
- E：主要成本在跨语言一致性和集成交付；产品改动与必要长时认证分别切分。

这些关卡不覆盖或自动取消 Phase 20 的既有 05/06 合同。
05 仍处于实际失败停点，06 未开始；是否继续、修订剩余范围或改变执行顺序，
必须通过现有权威方案与用户的明确指令处理，不能由本总纲偷偷降低门禁。

## 8. 拒绝的复杂度，以及以后解锁的条件

当前整体规划明确不做：

- 蓝鲸式平台广度：多租户、CMDB、通用采集编排、DataSet、工作流与插件市场。
- 按用户/帖子/点赞机械拆微服务，服务网格、自研 Operator、跨地域和多活。
- 无证据的分库分表、整站 CQRS、全链路改写或引入新的分析数据库。
- 全部状态服务一次性 HA，或把 HA 建设变成所有新能力的共同前置条件。
- 所有服务多语言改写、全站 Trace 覆盖、通用 Trace 存储和大屏编辑器。
- 为扩充技术栈新增媒体、实时聊天、推荐等业务线。

它们不是永远不能做，而是不属于这份完整项目的终点。
未来只有出现明确用户、可复现瓶颈或新的学习目标，并说明收益、额外运行成本、
数据所有权和结束条件后，才讨论新一轮规划。

拆服务必须证明现有进程边界无法满足需求；分片必须证明索引、查询、锁与合理纵向资源
无法满足指定负载；HA 必须有可用性需求、故障模型与可承担恢复成本。
没有这些条件时，“技术先进”不能成为准入理由。

## 9. 防止再次偏航的决策规则

每项新工作立项前回答六个问题：

1. 哪个使用者遇到了什么问题，或哪个明确学习边界需要一份可运行交付？
2. 改变哪条业务、观测或运行路径？事实与配置由谁唯一负责？
3. 为什么现有能力不能满足，复用成熟组件是否更合适？
4. 代价是什么：进程、状态、连接、磁盘、权限和维护负担分别增加多少？
5. 什么结果足以结束？无改善或环境不具备条件时如何停止并保留真实结论？
6. 需要哪些直接验证与集成门禁，是否已经把工具开发和长实验成本单列？

说不清这些问题，不创建新的实施批次。
同一迭代集中解决一个主要产品问题，不能叠加多个彼此无关的架构迁移。
已完成能力在相关代码与环境未变时继续有效，不为每项变化重新运行全部历史矩阵。
正确性、安全、持久数据边界必须验证；普通开发不升级成无限期认证工程。
具体执行成本、停点和接续遵循
[实施耗时预算](../../docs/implementation-execution-budget.md)与权威批次方案。

## 10. 整个项目的完成终点

当 A～E 的实际能力完成，且既有实施合同得到真实完成或经明确授权处理后，停止新增架构主线。
整体交付必须让一位非作者使用者能够：

1. 在受支持的 Compose 或指定 Kubernetes 环境安装并使用真实社交功能。
2. 保留数据完成应用升级，并按已公开边界完成备份恢复或搜索重建。
3. 从管理端解释一次慢请求或异步延迟，不依赖作者手工拼日志。
4. 在公开资源与数据规模下复现正常、热点和异步突发的代表性行为，
   看懂拒绝、积压、恢复以及观测开销。
5. 看懂 Worker 扩容何时有效、何时受数据库限制，并运行符合相同业务合同的 Go 或 Java 消费者。

发布能力、候选、实测条件与未解决限制，不能只有一份“规划已完成”或漂亮架构图。
此后进入缺陷修复、兼容维护与真实反馈；不因为 Phase 数字还可以增加，就自动规划下一阶段。
没有实际设备和执行资源依据，不承诺固定总工期或虚构吞吐终点。

这份路线的终点是“真实业务可用，运行可交付，行为可解释，扩展有边界”，
不是“拥有更多中间件”，也不是“永远等待足够成熟”。

## 11. 参考项目的取舍

公开资料和本地参考用于判断边界，不把设计文档当成已经实现的运行事实：

- Kingeye v4/v5：本地阅读模块、采集控制、查询域与迁移文档；借鉴模块化融合、
  单一所有者与减少重复事实。v5 的 DataSet 退役和仍未落地的部分 APM 设计说明：
  企业项目也需要收缩抽象，GoPulse 不复制其域数量和控制平台。
- [Mastodon](https://docs.joinmastodon.org/admin/scaling/)：借鉴真实业务的运行职责与全局连接预算，
  不复制联邦业务和不同的缓存/持久队列语义。
- [SigNoz](https://signoz.io/docs/architecture/)、
  [Nightingale](https://github.com/ccfos/nightingale)：借鉴诊断与查询产品边界，
  不追加第二套通用观测平台或替换当前存储。
- [Jaeger](https://www.jaegertracing.io/docs/2.21/architecture/apis/)：
  借鉴公开稳定 Trace 接口，保留 GoPulse 授权边界，不依赖其内部 UI API。
- [OpenTelemetry Demo](https://opentelemetry.io/docs/demo/feature-flags/)、
  [DeathStarBench](https://github.com/delimitrou/DeathStarBench)：借鉴代表性故障与负载方法；
  示例部署和基准系统不能替代真实业务的权限、升级和数据恢复合同。

本次是全局架构规划，不构成产品改动、压测、Kubernetes 验证或跨语言实现证据。
