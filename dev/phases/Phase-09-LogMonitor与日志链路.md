# Phase 9：LogMonitor与日志链路

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.6.x`；阶段基线：`1.6.0`。
- 执行批次从 `1.6.1` 起编号，具体目标版本和开发分支由 Phase 9 总实施方案统一分配。

## 阶段目标

接入业务日志，完成从 Backend 到 Elasticsearch 的日志采集、传输、转换和查询链路。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 10。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 3，完整可观测 MVP。
- 本阶段在既有 Metrics 能力上增加第一条 Logs 端到端链路，并复用 Router、Kafka、Marshaller 与 Elasticsearch 形成真实日志查询能力。
- 业务日志的接收、传输、转换、隔离存储和 Backend 查询是当前里程碑的必需增量；复杂协议、分析和完整前端体验按`本阶段不做`延后。

## 开发范围

- LogMonitor 被动接收。
- 日志第一次清洗与标准消息封装。
- Router 与 Kafka 日志传输。
- Marshaller 日志转换。
- Elasticsearch 日志存储与 Backend 查询。

## 核心任务

- 由 Backend 主动向 LogMonitor 推送日志。
- 优先使用简单 HTTP 接收方式。
- 复用 Message Router 与 Kafka 传输统一日志消息。
- 由 Marshaller 转换后写入独立日志索引。
- 通过 Backend 提供日志查询能力。

## 前置依赖

- Phase 8 Metrics 链路闭环完成。
- Phase 4 已提供结构化业务日志。
- Elasticsearch 可用。

## 阶段产物

- 可运行的 LogMonitor。
- 完整 Logs 可观测链路。
- 独立的日志索引。
- Backend 日志查询入口。

## 最小端到端闭环

`Backend API 产生结构化日志 → LogMonitor → Message Router → Kafka → Marshaller → Elasticsearch 日志索引 → Backend 查询`

该闭环必须使用真实 API 日志证明传输、独立索引和查询可用，不能只交付 LogMonitor 接口或手工写入日志索引。

## 验收标准

- 调用 Backend API 产生的日志可最终进入 Elasticsearch。
- 日志可通过 Backend 查询。
- 帖子搜索索引与日志索引相互隔离。
- 日志源采用 Push，Metrics 继续采用 Pull。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，Logs 与既有 Metrics 链路可同时运行且数据职责不混淆。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且没有阻断验收的失败。
- 达到上述条件后停止扩展；复杂日志体验和分析能力转入后续事项，阶段产物作为 Phase 10 的输入并供 Phase 11 展示。

## 本阶段不做

- EventMonitor。
- 前端日志分析页面的完整体验。
- 复杂日志采集协议与日志分析能力。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次；需要跨批验证时，再安排 1 个集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按真实业务日志到 Backend 查询的闭环切分，不按 Monitor、Router、Kafka、Marshaller、Elasticsearch 和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；如安排收口批次，只执行跨批集成和固定验收，不加入新的功能范围。
- 接收接口、日志消息、索引结构、查询契约和运行参数由总实施方案根据实施前的真实代码基线确定，阶段提纲不提前冻结。
