# Phase 11：可观测前端

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.8.x`；阶段基线：`1.8.0`。
- 执行批次从 `1.8.1` 起编号，具体目标版本和开发分支由 Phase 11 总实施方案统一分配。

## 阶段目标

在保留普通用户社交平台体验的同时，将 Metrics、Logs、Events 和 Exporter 管理能力通过独立的 GoPulse 可观测管理域提供给管理员。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 12。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 3，完整可观测 MVP。
- 本阶段为该里程碑的收尾阶段，通过 Backend 统一代理把 Metrics、Logs、Events 和 Exporter 管理组合为管理员可操作的完整体验，并完成社交业务态与可观测管理态的前端分区。
- 三类数据的基础查看、查询、明确失败反馈和插件管理是本次 MVP 的必需能力；复杂大屏、告警中心和前端直连基础设施按`本阶段不做`排除。

## 开发范围

- 可观测总览。
- 指标查看。
- 日志查询。
- 事件查询。
- 采集插件管理。
- Backend 查询与管理代理。
- 普通用户社交域与管理员可观测域的信息架构、导航和路由边界。

## 核心任务

- 由 Backend 统一查询 VictoriaMetrics 与 Elasticsearch。
- 由 Backend 转发 Monitor 管理操作。
- 实现指标、日志、事件页面。
- 展示插件状态、最近采集与最近错误。
- 提供插件安装、启动、停止和更新操作及状态反馈。
- 根据当前用户 `role` 提供管理导航和路由守卫，同时由 Backend 对全部查询与管理 API 执行最终 admin 授权。

## 前置依赖

- Phase 10 Events 链路完成。
- 三类可观测数据均可由 Backend 查询。
- Monitor 已具备基础插件管理能力。

## 用户态与访问边界

- Frontend 必须明确区分普通用户社交业务域与管理员可观测管理域；管理域使用独立导航和路由空间，不把可观测组件混入普通用户默认信息架构。
- `admin` 是普通用户能力的权限超集：管理员继续使用同一注册、登录和 Cookie，也可以进入社交域；普通用户只能使用社交域，不获得可观测数据或管理能力。
- Frontend 根据 `/users/me` 的数据库当前 role 控制入口、导航和路由；普通用户直接输入管理 URL 时显示明确无权限状态或返回社交域，不加载敏感查询。
- 前端守卫不是安全边界。Metrics、Logs、Events 查询以及 Exporter 列表、安装、启动、停止、更新 API 全部由 Backend 再次执行 admin 授权，普通用户固定获得 `403 permission_denied`。
- Frontend 只能访问 Backend，不直接访问 Monitor、Router、Kafka、Marshaller、VictoriaMetrics 或 Elasticsearch；API 响应不得暴露内部地址、凭据、查询实现或原始底层错误。
- 管理域不可用或内部可观测组件故障时，普通用户社交页面和业务 API 仍应保持可用；管理页面只显示安全、有限的失败状态。

## 阶段产物

- 可观测总览与查询页面。
- Exporter 管理页面。
- Backend 统一查询与管理入口。
- 与现有社交平台并存的管理员导航、路由守卫和服务端权限回归。

## 最小端到端闭环

`管理员使用现有会话进入可观测管理域 → Backend admin 授权 → 查询或管理代理 → VictoriaMetrics、Elasticsearch 或 Monitor → Frontend 展示数据、状态或安全失败原因`

该闭环必须覆盖 Metrics、Logs、Events 的代表性查询、Exporter 的代表性管理操作，以及普通用户不可见导航、直接路由拒绝和 API `403`；不能只交付静态页面、只隐藏按钮或绕过 Backend 直连查询。

## 验收标准

- 管理员无需直接访问底层数据库即可查看指标、搜索日志和查询事件，并可通过页面管理 Exporter。
- 普通用户社交页面与既有业务行为无回归，不显示可观测管理导航；直接访问管理路由不会加载数据，直接调用全部可观测 API 固定获得 `403`。
- 管理员和普通用户共用现有身份与会话，不新增独立管理员登录；管理员仍可正常使用社交域。
- 前端不直接连接 VictoriaMetrics、Elasticsearch 或 Monitor。
- 失败操作能够展示明确状态或原因。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，Milestone 3 的三类数据与插件管理可由管理员在独立管理域共同使用，普通用户社交域保持隔离和可用。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且没有阻断验收的失败。
- 达到上述条件后完成完整可观测 MVP 验收并停止扩展；复杂大屏和告警能力转入后续事项，阶段产物作为 Phase 12 容器化的完整系统输入。

## 本阶段不做

- 前端承载核心采集或查询逻辑。
- 复杂大屏与告警中心。
- 绕过 Backend 直接访问基础设施。
- 独立管理员账号体系、第二套登录协议、普通用户自助提权或仅依赖前端隐藏的授权方案。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次；需要跨批验证时，再安排 1 个集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按管理员可完成的查询或管理闭环及普通用户隔离证据切分，不按页面、Backend 代理、数据源和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；如安排收口批次，只执行跨批集成和固定验收，不加入新的功能范围。
- 页面信息架构、查询 API、管理契约和状态反馈细节由总实施方案根据实施前的真实代码基线确定，阶段提纲不提前冻结。
- 总实施方案必须交付双使用态信息架构、导航/路由守卫、Backend 权限矩阵和普通用户 `403` 验收，不得将这些边界降级为后续优化。
