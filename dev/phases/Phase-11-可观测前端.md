# Phase 11：可观测前端

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.8.x`；阶段基线：`1.8.0`。
- 执行批次从 `1.8.1` 起编号，具体目标版本和开发分支由 Phase 11 总实施方案统一分配。

## 阶段目标

将 Metrics、Logs、Events 和 Exporter 管理能力通过统一的 GoPulse 页面提供给用户。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 12。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 3，完整可观测 MVP。
- 本阶段为该里程碑的收尾阶段，通过 Backend 统一代理把 Metrics、Logs、Events 和 Exporter 管理组合为用户可操作的完整体验。
- 三类数据的基础查看、查询、明确失败反馈和插件管理是本次 MVP 的必需能力；复杂大屏、告警中心和前端直连基础设施按`本阶段不做`排除。

## 开发范围

- 可观测总览。
- 指标查看。
- 日志查询。
- 事件查询。
- 采集插件管理。
- Backend 查询与管理代理。

## 核心任务

- 由 Backend 统一查询 VictoriaMetrics 与 Elasticsearch。
- 由 Backend 转发 Monitor 管理操作。
- 实现指标、日志、事件页面。
- 展示插件状态、最近采集与最近错误。
- 提供插件安装、启动、停止和更新操作及状态反馈。

## 前置依赖

- Phase 10 Events 链路完成。
- 三类可观测数据均可由 Backend 查询。
- Monitor 已具备基础插件管理能力。

## 阶段产物

- 可观测总览与查询页面。
- Exporter 管理页面。
- Backend 统一查询与管理入口。

## 最小端到端闭环

`用户操作 Frontend → Backend 查询或管理代理 → VictoriaMetrics、Elasticsearch 或 Monitor → Frontend 展示数据、状态或失败原因`

该闭环必须覆盖 Metrics、Logs、Events 的代表性查询和 Exporter 的代表性管理操作，不能只交付静态页面或绕过 Backend 的直连查询。

## 验收标准

- 用户无需直接访问底层数据库即可查看指标、搜索日志和查询事件。
- 用户可通过页面管理 Exporter。
- 前端不直接连接 VictoriaMetrics、Elasticsearch 或 Monitor。
- 失败操作能够展示明确状态或原因。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，Milestone 3 的三类数据与插件管理可通过统一页面共同使用。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且无 P0/P1 阻塞。
- 达到上述条件后完成完整可观测 MVP 验收并停止扩展；复杂大屏和告警能力转入后续事项，阶段产物作为 Phase 12 容器化的完整系统输入。

## 本阶段不做

- 前端承载核心采集或查询逻辑。
- 复杂大屏与告警中心。
- 绕过 Backend 直接访问基础设施。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次，再固定保留 1 个 Review、集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按用户可完成的查询或管理闭环切分，不按页面、Backend 代理、数据源和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；收口批次只执行跨批集成、固定验收和实际 Review 整改，不加入新的功能范围。
- 页面信息架构、查询 API、管理契约和状态反馈细节由总实施方案根据实施前的真实代码基线确定，阶段提纲不提前冻结。
