# Phase 12：Docker化

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.9.x`；阶段基线：`1.9.0`。
- 执行批次从 `1.9.1` 起编号，具体目标版本和开发分支由 Phase 12 总实施方案统一分配。

## 阶段目标

为所有自研组件建立标准容器运行方式，并通过 Docker Compose 启动完整 GoPulse。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 13。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 4，云原生自观测 MVP。
- 本阶段先把完整业务与可观测系统固化为可重复构建和启动的容器基线，为迁移到 Kubernetes 提供一致运行单元。
- 全部自研组件镜像、必要基础设施和完整 Compose 验证是当前里程碑的必需增量；生产级供应链、多环境发布和高可用按`本阶段不做`延后。

## 开发范围

- Frontend、Backend、Business Worker 容器。
- Monitor、Message Router、Marshaller、Exporter 容器。
- 官方基础设施镜像。
- 完整 Docker Compose 开发与验证环境。

## 核心任务

- 为每个自研组件建立独立镜像构建方式。
- 配置容器间服务发现和必要持久化。
- 使用官方镜像编排所有基础设施。
- 提供完整系统的启动、停止与验证流程。

## 前置依赖

- Phase 11 可观测前端完成。
- 所有组件已具备可独立启动方式。
- Docker 与 Docker Compose 可用。

## 阶段产物

- 全部自研组件镜像。
- 完整 Docker Compose 编排。
- 不依赖本机基础设施安装的运行环境。

## 最小端到端闭环

`构建自研组件镜像 → Docker Compose 启动全部组件与基础设施 → 验证业务闭环和三类可观测链路 → 停止并可再次启动`

该闭环必须证明完整系统仅依赖 Docker 与 Docker Compose 可运行，不能只交付若干独立 Dockerfile 或基础设施编排。

## 验收标准

- 仅依赖 Docker 与 Docker Compose 即可启动完整 GoPulse。
- 业务与三条可观测链路均可验证。
- 组件重启后必要持久化数据仍可用。
- 容器间不依赖本机固定地址通信。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，完整系统可从明确的容器构建与编排入口重复启动。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且无 P0/P1 阻塞。
- 达到上述条件后停止扩展；生产级镜像和发布治理转入后续事项，镜像与 Compose 拓扑作为 Phase 13 的迁移输入。

## 本阶段不做

- Kubernetes 资源。
- 生产级镜像供应链。
- 复杂多环境发布与高可用部署。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次，再固定保留 1 个 Review、集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按可启动的完整系统闭环切分，不按单个组件 Dockerfile、基础设施和测试等技术层或组件清单机械拆分。
- 测试、文档和实施记录随对应能力完成；收口批次只执行跨批集成、固定验收和实际 Review 整改，不加入新的功能范围。
- 镜像基线、Compose 拓扑、服务发现和持久化参数由总实施方案根据实施前的真实组件基线确定，阶段提纲不提前冻结。
