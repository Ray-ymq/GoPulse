# Phase 19：容量认证与性能可观测

## 阶段目的

在 Phase 18 已证明计算层多副本、故障隔离和独立诊断的基础上，建立指定 Linux `amd64`
资源规格、数据配方和混合业务负载下的容量曲线。Phase 19 不追求一个脱离环境的“高并发数字”，
而是交付可复核的吞吐、尾延迟、拒绝、积压、恢复和资源成本边界。

## 前置事实

- 当前完成版本为 `2.1.2`；Phase-19-01 与 Phase-19-02 已完成。
- Phase-18-01/02 没有证明稳定 `150 RPS`，历史 Outbox 与重复性边界保持不变。
- Phase-18-03～18-05 已证明固定矩阵内的计算层多副本、故障隔离、恢复与独立诊断。
- 原 Phase-19-03 正式预检确认 runner 的配方物化、轮次 endpoint、真实恢复证据和宿主版本合同不闭合；
  正式入口没有调用，容量认证已顺延。
- 当前状态层仍可为单节点，Phase 19 不把容量认证描述为生产高可用。

## 阶段验收

- `/startup`、`/live`、`/ready` 和私有诊断在业务并发槽耗尽时仍遵循各自合同；业务请求按明确语义拒绝。
- HTTP 运行时指标能够按固定 route template、method、status class 计算 P50/P95/P99，且标签集合有界。
- 容量 runner 将负载生成器与 SUT 资源分别记录，绑定候选、Compose、数据配方、宿主和统计规则。
- 每轮在空数据卷中物化同一确定性配方，使用该轮实际 endpoint；逐阶梯恢复和观测进展来自原始事实。
- 最终报告展示每个负载阶梯的原始重复值、聚合值、错误/拒绝、资源峰值、队列与恢复时间。
- 报告明确区分执行完整性和能力结论；验收基础设施错误不能伪装成产品边界。
- 若容量目标未达到但执行与证据完整，阶段可以以 `boundary_found` 收口；不得宣称通过。

## 非目标

- 不引入 Trace 存储、Monitor HA、状态层集群、Kubernetes 或新的业务功能。
- 不在容量认证之前进行无证据 SQL、缓存、GC、连接池或批处理调参。
- 不删除或改写 Phase 18 历史 evidence。
