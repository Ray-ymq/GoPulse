# Phase 14：插件体系与组件可观测闭环

> 本文档是阶段开发提纲。插件 Manifest、配置 Schema、指标目录和批次由总实施方案根据真实基线确定。

## 版本规划

- 版本线：`1.11.x`；阶段基线：`1.11.0`。
- 执行批次从 `1.11.1` 起编号，由 Phase 14 总实施方案统一分配版本与分支。

## 阶段目标

把 Redis Exporter 原型扩展为六类官方、单实例、单目标插件，并补齐 GoPulse 自研组件的基础运行指标，使组件可观测能力在 Compose 中完整运行。

## 开发范围

- 官方插件固定为 Redis、MySQL、RabbitMQ、Kafka、Elasticsearch 和 VictoriaMetrics。
- 每种插件最多一个运行实例，一个实例只配置一个采集目标；不开放同类第二实例。
- 建立受限 Manifest、版本兼容、制品完整性、目标配置 Schema、Secret 隔离、安装/启停/更新/回滚和重启恢复契约。
- Redis 现有状态安全迁移到通用契约。
- Backend、Business Worker、Search Indexer、Monitor、Router 和 Marshaller 提供有限、稳定、低基数的基础运行指标。
- 六类指标继续通过既有 Monitor、Router、Kafka、Marshaller、VictoriaMetrics 和 Backend 查询链路处理。

## 最小端到端闭环

`管理员配置一种官方插件 → 连接测试 → 安装并启动 → 真实目标指标进入既有链路 → Backend 查询 → 插件失败局部降级并可恢复`

## 验收标准

- 六类官方插件各自对一个真实目标产生可区分指标。
- 同类第二实例和第二目标在 Backend、Monitor 与状态存储层均被拒绝。
- 插件配置、日志、事件和公共 DTO 不泄漏 Secret 或完整连接串。
- 一种插件不可达、崩溃或更新失败不影响其他插件、历史数据和社交业务。
- 自研组件指标覆盖请求/处理结果、延迟、队列或消费进度、最近成功与依赖降级，且不使用业务 ID 级高基数标签。
- 指标可经完整既有链路查询，不能只以插件自身 `/metrics` 作为完成证据。

## 本阶段不做

- 同类插件多实例、单实例多目标或目标自动发现。
- 未受信第三方插件、插件市场或通用代码沙箱。
- 告警、管理端重构、跨平台产品交付或 Kubernetes。

## 总实施方案约束

- 每个插件批次必须交付真实目标到 Backend 查询的最低有效证据。
- 超过三个批次时必须说明插件契约迁移、组件差异或故障隔离的独立风险。
- 多实例未来设计保留为独立方案，不得静默进入本阶段。
