# Phase 10：EventMonitor与事件链路

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.7.x`；阶段基线：`1.7.0`。
- 执行批次从 `1.7.1` 起编号，具体目标版本和开发分支由 Phase 10 总实施方案统一分配。

## 阶段目标

补齐 Events 数据类型，记录插件生命周期、采集失败和系统运行中的离散事件。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 11。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 3，完整可观测 MVP。
- 本阶段在 Metrics 与 Logs 基础上补齐 Events 数据类型，以真实插件生命周期或采集失败事件验证第三条可观测链路。
- 真实事件产生、接收、传输、转换、存储和查询是当前里程碑的必需增量；告警、复杂关联和 Kubernetes 事件全面采集按`本阶段不做`延后。

## 开发范围

- EventMonitor 被动接收。
- 统一事件模型。
- Router 与 Kafka 事件传输。
- Marshaller 事件转换。
- Elasticsearch 事件存储。

## 核心任务

- 选择插件启停、采集失败等真实事件源。
- 接收并基础校验事件。
- 封装统一 events 消息并经 Router 写入 Kafka。
- 由 Marshaller 转换并写入 Elasticsearch。
- 提供事件查询基础能力。

## 前置依赖

- Phase 9 日志链路完成。
- Message Router、Kafka、Marshaller 与 Elasticsearch 可复用。

## 阶段产物

- 可运行的 EventMonitor。
- 统一事件数据。
- 完整 Events 可观测链路。
- 事件查询能力。

## 最小端到端闭环

`插件启停或采集失败 → EventMonitor → Message Router → Kafka → Marshaller → Elasticsearch 事件索引 → 事件查询`

该闭环必须由真实系统行为产生事件并通过完整链路查询，不能以手工构造的 Elasticsearch 文档代替事件源和传输链路。

## 验收标准

- 插件启动、停止或采集失败可产生事件。
- 事件可通过完整链路进入 Elasticsearch。
- 事件可被查询并表达来源、严重程度、时间和描述。
- EventMonitor 保持被动接收模式。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，Metrics、Logs、Events 三条后端链路可同时运行且职责清晰。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且无 P0/P1 阻塞。
- 达到上述条件后停止扩展；告警和复杂事件分析转入后续事项，阶段产物作为 Phase 11 统一前端的输入。

## 本阶段不做

- 指标告警系统。
- 复杂事件关联分析。
- Kubernetes 原生事件的全面采集。
- 可观测前端。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次，再固定保留 1 个 Review、集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按真实事件源到事件查询的闭环切分，不按 Monitor、Router、Kafka、Marshaller、Elasticsearch 和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；收口批次只执行跨批集成、固定验收和实际 Review 整改，不加入新的功能范围。
- 事件来源、消息模型、索引结构、查询契约和运行参数由总实施方案根据实施前的真实代码基线确定，阶段提纲不提前冻结。
