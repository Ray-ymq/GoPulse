# Phase 6：Monitor

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.3.x`；阶段基线：`1.3.0`。
- 执行批次从 `1.3.1` 起编号，具体目标版本和开发分支由 Phase 6 总实施方案统一分配。

## 阶段目标

实现双用户态授权边界、Monitor 的 MetricsMonitor 与基础 Plugin Manager，建立管理员可控的指标采集和插件管理能力。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 7。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 2，指标采集 MVP。
- 本阶段把单个 Exporter 原型接入可调度的周期采集和基础插件管理，形成指标进入统一消息链路前的完整上游能力。
- 周期采集、标准消息封装和最小管理流程是当前里程碑的必需增量；其他 Monitor 类型和完整插件平台按`本阶段不做`延后。

## 开发范围

- MetricsMonitor 周期拉取。
- 采集目标管理。
- 第一次基础校验与结构化。
- GoPulse 标准消息封装。
- Exporter 基础生命周期管理。
- `user|admin` 持久化角色与可观测管理授权边界。

## 核心任务

- 周期请求 Exporter 并解析指标结果。
- 将采集结果封装为统一可观测消息。
- 通过 Plugin Manager 支持安装、启动、停止、更新与状态查询的基础流程。
- 由 Backend 发出管理指令并由 Monitor 执行。
- 普通用户与管理员共用现有登录和会话；由 Backend 根据数据库当前角色保护全部插件管理接口。

## 前置依赖

- Phase 5 Exporter Plugin 原型完成。
- Backend 与 Exporter 可独立运行。

## 阶段产物

- 可运行的 MetricsMonitor。
- 基础 Plugin Manager。
- Backend 到 Monitor 的管理链路。
- 统一封装的 metrics 消息。
- 管理员身份、提升方式和社交/可观测双用户态权限矩阵。

## 最小端到端闭环

`普通用户注册/登录 → 运维显式提升管理员 → Backend 服务端授权`、`管理员管理操作 → Monitor → Exporter 状态变化`，以及 `MetricsMonitor 周期拉取 Exporter → 基础校验与结构化 → GoPulse 标准 metrics 消息`

三个链路必须共同可验证，不能只新增角色字段、只做前端隐藏、只交付采集循环或只交付插件状态接口。

## 验收标准

- 管理员可通过 Backend 查看、安装、启动、停止和更新 Exporter，普通用户对全部插件管理接口固定获得 `403`。
- 管理员与普通用户使用同一套身份和会话，既有社交业务对两者无回归，公开作者摘要不暴露角色。
- MetricsMonitor 可周期采集 Exporter。
- 采集结果已转换为 GoPulse 内部统一消息。
- Monitor 只进行基础处理，不承担最终存储格式转换。

## 阶段完成与停止条件

- 三条最小端到端链路及全部阶段验收标准通过，双用户态边界稳定，Exporter 可被管理员管理并持续产生标准 metrics 消息。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且没有阻断验收的失败。
- 达到上述条件后停止扩展；最终格式转换、Kafka 路由和其他 Monitor 类型留给后续 Phase，阶段产物作为 Phase 7 的输入。

## 本阶段不做

- LogMonitor 与 EventMonitor 的完整实现。
- 独立插件平台。
- Kafka 路由。
- 最终指标存储。

## 总实施方案生成与批次切分约束

- 本阶段固定为 4 个可执行批次：管理员身份与双用户态授权边界、插件安装包与生命周期、MetricsMonitor 周期采集与标准消息、集成验收与阶段收口；具体版本和分支以总实施方案为唯一权威。
- 超过默认 2～3 批是因为持久化身份/授权属于独立安全边界，需要在文件、进程和内部服务能力进入公共 API 前单独完成迁移及社交回归。
- 实现批次按身份授权、插件管理或周期采集的可运行闭环组织，不按 Backend、Monitor、消息模型和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；如安排收口批次，只执行跨批集成和固定验收，不加入新的功能范围。
- 管理接口、标准消息、生命周期和运行参数由总实施方案根据实施前的真实代码基线确定，阶段提纲不提前冻结。
