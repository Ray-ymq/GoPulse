# Phase 4：业务日志基础

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.1.x`；阶段基线：`1.1.0`。
- 执行批次从 `1.1.1` 起编号，具体目标版本和开发分支由 Phase 4 总实施方案统一分配。

## 阶段目标

统一 Backend 业务日志，为后续 LogMonitor 与日志处理链路提供稳定数据源。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 5。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 2，指标采集 MVP。
- 本阶段统一真实业务运行信号和请求上下文，为后续采集组件提供稳定观测对象，也为 Phase 9 日志链路保留可靠输入；本阶段本身不提前建设日志传输和查询链路。
- `开发范围`和`验收标准`中的统一日志能力是当前里程碑的必要基础；复杂日志采集、传输和分析按`本阶段不做`延后。

## 开发范围

- Backend 结构化日志。
- 统一基础日志字段。
- 请求链路标识。
- 主要 API 的业务与错误日志。

## 核心任务

- 确定项目统一的结构化日志输出方式。
- 为主要 API 补齐关键过程日志。
- 在一次请求内传递 request_id。
- 确保日志可被后续采集组件稳定读取。

## 前置依赖

- Phase 3 业务搜索完成。
- Backend 主要业务接口已稳定。

## 阶段产物

- 统一格式的 Backend 业务日志。
- 可关联单次请求的日志链路。
- 供 LogMonitor 使用的真实日志源。

## 最小端到端闭环

`Backend 请求 → 主要处理过程输出结构化日志 → 同一请求内传递 request_id → 稳定日志输出`

该闭环必须通过真实主要 API 证明字段一致和请求可关联，不能只交付日志库封装或格式说明。

## 验收标准

- 主要 API 均输出统一格式日志。
- 日志至少可表达时间、级别、服务、模块、消息和 request_id。
- 可通过 request_id 关联一次请求中的关键日志。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，且主要 API 的正常与错误路径具备必要日志。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且无 P0/P1 阻塞。
- 达到上述条件后停止扩展；日志传输、存储和分析能力留给后续 Phase，阶段产物作为 Phase 5 的输入并保留给 Phase 9 复用。

## 本阶段不做

- LogMonitor。
- Kafka 日志传输。
- 日志写入 Elasticsearch。
- 完整日志查询平台。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次，再固定保留 1 个 Review、集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按真实请求到统一日志输出的闭环切分，不按日志库、Middleware、业务 Handler 和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；收口批次只执行跨批集成、固定验收和实际 Review 整改，不加入新的功能范围。
- 日志 API、字段 Schema、输出方式和运行参数由总实施方案根据实施前的真实代码基线确定，阶段提纲不提前冻结。
