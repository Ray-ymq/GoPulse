# Phase 15：Kubernetes可观测闭环

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.12.x`；阶段基线：`1.12.0`。
- 执行批次从 `1.12.1` 起编号，具体目标版本和开发分支由 Phase 15 总实施方案统一分配。

## 阶段目标

让运行在 Kubernetes 中的 GoPulse 通过自身可观测系统观测业务、基础组件和集群对象。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 16。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 4，云原生自观测 MVP。
- 本阶段为该里程碑的收尾阶段，使 Kubernetes 中的 GoPulse 使用既有 Metrics、Logs、Events 链路观察业务、基础组件和代表性集群对象。
- 真实集群采集、既有链路接入和统一页面展示是本次 MVP 的必需能力；全面集群监控、复杂告警、自动修复和跨集群采集按`本阶段不做`延后。

## 开发范围

- Kubernetes 环境中的组件采集目标。
- Backend 与基础设施指标。
- Node 与 Pod 等集群对象。
- 业务日志与系统事件统一展示。
- Worker-3 集中插件部署。

## 核心任务

- 扩展 Exporter 或采集目标以覆盖关键组件。
- 通过 Kubernetes Service 或目标地址跨节点采集。
- 将集群中的指标、日志和事件接入既有链路。
- 在 GoPulse 页面汇总业务状态和系统状态。

## 前置依赖

- Phase 14 统一入口完成。
- GoPulse 与完整可观测链路均运行在 Kubernetes。
- 插件管理与查询页面可用。

## 阶段产物

- GoPulse 自观测能力。
- Kubernetes 环境采集配置。
- 业务、指标、日志和事件的统一视图。
- 完整项目闭环。

## 最小端到端闭环

`Kubernetes 中的业务、关键组件和代表性集群对象 → GoPulse 既有采集与处理链路 → 指标、日志和事件存储 → Backend → 统一页面展示`

该闭环必须使用集群中的真实数据证明 GoPulse 能观察自身运行环境，不能以静态演示数据或集群外独立链路代替。

## 验收标准

- 页面可同时查看业务运行状态、组件指标、业务日志和系统事件。
- 关键组件和 Kubernetes 对象具备实际采集数据。
- 采集链路使用集群 Service 或明确目标地址。
- GoPulse 能够观测其自身运行环境。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，Milestone 4 的容器、集群、统一入口和自观测能力可共同运行。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且没有阻断验收的失败。
- 达到上述条件后完成云原生自观测 MVP 验收并停止扩展；全面监控、告警和自动修复转入后续事项，既有系统进入 Phase 16 最终工程质量收口。

## 本阶段不做

- 生产级集群监控全面覆盖。
- 复杂告警与自动修复。
- 跨集群采集。
- 大规模高可用与容量保障。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次；需要跨批验证时，再安排 1 个集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按真实集群数据到统一页面的自观测闭环切分，不按 Exporter、Kubernetes 对象、数据类型、页面和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；如安排收口批次，只执行跨批集成和固定验收，不加入新的功能范围。
- 采集对象、目标发现方式、数据映射和页面汇总细节由总实施方案根据实施前的真实集群与系统基线确定，阶段提纲不提前冻结。
