# Phase 16：跨平台产品化与双前端交付

> 本文档是阶段开发提纲。支持版本、生命周期入口和制品发布细节由总实施方案根据真实环境确定。

## 版本规划

- 版本线：`1.13.x`；阶段基线：`1.13.0`。
- 执行批次从 `1.13.1` 起编号，由 Phase 16 总实施方案统一分配版本与分支。

## 阶段目标

把 Phase 13～15 的完整业务与可观测能力提升为可在 Linux、macOS 和 Windows 宿主上安装、运行、升级、诊断和恢复的双前端 Compose 产品。

## 开发范围

- 最小真实支持矩阵固定包含 Linux `amd64`、macOS `arm64` 与 Windows `amd64`。
- 全部自研容器、两个 Frontend 和六类受管插件提供 `linux/amd64`、`linux/arm64` 制品契约。
- 同一域名提供统一登录入口；Backend 根据 `user` 或 `super_admin` 将用户送入独立用户端或管理端，两端共用同源安全会话。
- 统一两个应用的设计令牌、公共交互质量、桌面/窄屏、加载/空/错误/过期状态、键盘焦点和时区表现，同时保持信息架构独立。
- 建立共享的初始化、启动、停止、状态、日志、验证和脱敏诊断入口；平台脚本只能是薄启动器。
- 建立从 `1.9.4` 到本阶段的可重复升级，以及业务、可观测、插件、角色、告警和配置的最小一致备份/恢复能力。

## 最小端到端闭环

`干净 Linux/macOS/Windows 宿主 → 统一入口启动 Compose → 登录并按角色进入独立应用 → 完成代表性业务/插件/告警流程 → 升级或恢复 → 受控停止`

## 验收标准

- 三类真实宿主均可启动完整 GoPulse，不要求宿主安装 Go、Node.js 或基础设施。
- 同一域名和登录入口可稳定分流两个独立 Frontend；越权路径由 Backend 拒绝。
- 用户端可完成代表性社交闭环，管理端可完成大屏、插件和告警闭环。
- 升级与隔离恢复后，业务事实、搜索投影、可观测历史、插件期望状态、角色和告警记录保持一致或可重建。
- 诊断、日志、API、Frontend bundle 和制品元数据不泄漏凭据、Cookie、连接串或宿主私有路径。
- 正常、失败和中断路径只清理当前运行强归属资源。

## 本阶段不做

- 原生 Windows Service、macOS LaunchDaemon 或两套重复编排实现。
- Kubernetes 资源、Ingress、集群对象采集或生产级高可用。
- Phase 13～15 范围之外的新业务、插件或告警功能。

## 总实施方案约束

- 真实宿主验收不能由交叉编译、Compose 静态解析或 WSL 内运行替代。
- 总方案必须先确认可用验收环境，再分配批次、版本和 `develop/x.x.x` 分支。
- 平台、双前端入口、升级恢复属于独立风险域，超过三个批次时应据此说明原因。
