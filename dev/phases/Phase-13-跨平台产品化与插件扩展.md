# Phase 13：跨平台产品化与插件扩展

> 本文档是阶段开发提纲，具体支持版本、公共接口、数据模型、插件 Manifest、制品发布和验收命令将在本阶段进入总实施方案时根据真实基线补充。

## 版本规划

- 版本线：`1.10.x`；阶段基线：`1.10.0`。
- 执行批次从 `1.10.1` 起编号，具体目标版本和开发分支由 Phase 13 总实施方案统一分配。

## 阶段目标

将 Phase 12 已验证的完整 Docker Compose 系统从“工程环境中可运行”提升为“可在 macOS、Windows 与 Linux 上交付和操作的可观测产品”，同时完成普通用户与管理员前端产品化，并把 Redis Exporter 原型扩展为可支持多种组件、每种组件单实例采集的插件体系。

本阶段完成后，应形成可独立安装、启动、验证、诊断、升级和恢复的结果，并能够直接支撑 Phase 14 Kubernetes 基础部署。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 4，跨平台可交付可观测产品 MVP。
- Phase 12 提供完整容器运行基线；本阶段完成跨平台交付、单实例多类组件采集、双用户态前端产品化与最小升级/恢复能力。
- Milestone 4 只证明产品可在支持的桌面宿主环境中通过 Linux 容器交付；Kubernetes、Ingress 和集群自观测属于 Milestone 5。

## 支持模型与术语边界

### 跨平台的含义

- 用户可从 macOS Terminal 或 Windows PowerShell/Terminal 执行受支持的统一产品生命周期入口。
- Frontend、Backend、Worker、Indexer、Monitor、Router、Marshaller 和 Exporter 继续运行在 Linux 容器中，不把基础设施改造为原生 Windows 或 macOS 服务。
- 产品入口不依赖 WSL 专用路径、Linux 文件权限巧合或宿主 Go/Node/npm/Python，并明确处理路径、换行、端口、文件共享和退出行为差异。
- 主要编排逻辑必须共享；如需 shell/PowerShell 文件，它们只作为薄入口，不复制两套产品逻辑。

最小宿主与架构验收矩阵必须包含 Linux `amd64`、macOS `arm64` 与 Windows `amd64`。macOS Intel、Windows ARM 及具体 OS/Docker Desktop 版本范围由总实施方案根据可获得的真实环境确定，不以交叉编译冒充支持。

### 插件实例的含义

- 本阶段可同时安装和运行多种 Exporter 插件。
- 每个 `plugin_id` 最多只有一个运行实例，每个实例只配置一个采集目标。
- 不支持同时采集两个 Redis、两个 MySQL 或其他同类多目标。
- 多实例的未来模型、迁移与验收单独记录在 [Exporter 插件多实例采集设计](../../docs/Exporter插件多实例采集设计.md)，该设计不是 Phase 13 完成条件。

## 开发范围

### 1. 跨平台交付与多架构制品

- 定义支持的宿主系统、CPU 架构、容器运行时和浏览器矩阵。
- 为全部自研容器与受管插件建立 `linux/amd64` 与 `linux/arm64` 制品契约，保留可核对的 version、revision、source、user、entrypoint 和摘要。
- 建立统一的初始化、启动、停止、状态、日志、验证和环境诊断入口。
- 保持默认只向宿主回环地址发布 Frontend/Backend，不因 Docker Desktop 网络差异公开内部服务。

### 2. 多种组件的单实例插件体系

- 将当前写死 Redis ID、source、入口和单 Registry 假设的插件契约扩展为可受控支持多种官方插件，同时保持每种插件单实例。
- 建立受限 Manifest、GoPulse/插件版本兼容、制品完整性、目标配置 Schema、Secret 隔离和安全状态契约。
- Redis 插件迁移到通用契约时，保留已安装版本、期望状态、更新回滚和 Monitor 重启恢复语义。
- 完成 Redis、MySQL、RabbitMQ、Kafka、Elasticsearch 与 VictoriaMetrics 六种官方采集插件或等价受管适配器，每种只针对一个真实目标验收。
- 插件仍常驻、被动拉取、不保存历史数据；Monitor 负责调度、基础校验与封装，Marshaller 继续负责存储格式转换。
- 一种插件的目标不可达、进程崩溃或配置失败只造成该插件局部降级，不停止其他插件和社交业务。

### 3. GoPulse 自研组件的基础运行指标

- 为 Backend、Business Worker、Search Indexer、Monitor、Router 与 Marshaller 建立有限、稳定、可聚合的指标目录或等价健康数据源。
- 优先表达请求成功/错误、处理延迟、队列或消费进度、最近成功和依赖降级，不引入业务 ID 级高基数标签。
- 自研组件指标继续通过 Backend 查询和管理员页面展示，不向浏览器公开内部指标端点。

### 4. 普通用户与管理员前端产品化

- 建立统一设计令牌和公共页面组件，统一导航、表单、按钮、列表、表格、弹窗、状态、错误和反馈样式。
- 收口注册/登录、帖子、评论、点赞、搜索与通知等普通用户主路径的信息层级、窄屏布局、加载/空/错误状态和操作反馈。
- 管理员总览以真实多组件指标、Logs、Events 和插件状态展示系统健康，支持受限时间范围、基础图表、安全自动刷新、手动暂停和过期数据标识。
- 插件页面按组件类型显示单实例配置、连接测试、安装、启动、停止、更新、回滚结果与最近错误，不提供“新建第二实例”入口。
- 普通用户与管理员继续使用同一身份系统；界面呈现两种使用态，但不创建第二套用户，也不把前端隐藏当作授权。
- 固定验证桌面和窄屏 viewport、键盘焦点、可读对比度、长文本、时区和局部依赖故障下的可用性。

### 5. 初次交付、升级、备份与诊断

- 为干净环境提供可理解的前置检查、配置初始化和首次启动结果，失败时明确指出缺失条件。
- 提供脱敏环境诊断和支持摘要，不收集密码、Token、Cookie、完整连接串、插件私有路径或用户内容。
- 建立从 Phase 12 完成版本 `1.9.4` 到 Phase 13 目标版本的可重复升级路径，保留业务事实、搜索和可观测数据、消费进度与插件期望状态。
- 建立受管持久数据与配置的最小备份/恢复契约，不把复制未一致的运行中卷当作备份成功。
- 升级、恢复或插件更新失败不得让用户数据或最后一个已验证插件版本停留在半切换状态。

## 前置依赖

- Phase 12 及其 Review 整改已完成，根、Frontend 与镜像版本基线为 `1.9.4`。
- Phase 12 的范围、验收结论、实施方案和实施记录保持完成时原貌；插入本阶段不会重新打开 Phase 12，也不把任何 Phase 13 工作追记为 Phase 12 成果。
- 完整 Compose 冷启动、双用户态、三类可观测、Redis Exporter 管理、局部故障、持久恢复和强归属清理基线可用。
- 总实施方案必须先核对可用的 macOS、Windows、Linux 本机或远程验收环境，不以未实际运行的脚本冒充平台支持。

## 用户态与访问边界

- Frontend 和 Backend 继续是唯一用户访问面；Monitor、Router、Marshaller、Exporter、Kafka、VictoriaMetrics、Elasticsearch 和数据库不因跨平台调试或多插件而公开。
- 全部 Metrics、Logs、Events、插件配置和生命周期操作由 Backend 根据数据库当前角色执行 admin 授权；未登录为 `401`，普通用户为 `403 permission_denied`。
- 不同插件只获得其采集目标需要的最小配置与 Secret；公共 DTO、Frontend bundle、日志、Events 和诊断输出不回显凭据或内部拓扑。
- 任一插件、指标存储或可观测页面故障不得改变普通用户代表性社交读写的可用性。

## 阶段产物

- macOS、Windows 与 Linux 支持矩阵及经过真实验收的统一产品生命周期入口。
- `linux/amd64` 与 `linux/arm64` 自研镜像、受管插件包和可核对的版本/来源信息。
- Redis、MySQL、RabbitMQ、Kafka、Elasticsearch 与 VictoriaMetrics 单实例采集能力。
- GoPulse 自研组件基础运行指标和组件目录。
- 产品化的普通用户与管理员界面。
- 首次启动、诊断、升级、备份和恢复说明及验收证据。

## 最小端到端闭环

```text
干净 macOS / Windows / Linux 宿主
  → 统一入口检查环境并启动多架构 Compose 系统
  → 普通用户完成社交主路径
  → 管理员管理多种单实例插件
  → 真实组件指标经 Monitor / Router / Kafka / Marshaller 入库
  → 管理员在产品化页面查看 Metrics / Logs / Events 与插件状态
  → 执行诊断、备份、升级/恢复和受控停止
```

该闭环必须使用真实宿主差异、真实容器、真实组件目标和真实浏览器证明，不能只通过交叉编译、Compose config、单元测试或静态页面宣称跨平台支持。

## 验收标准

- Linux `amd64`、macOS `arm64` 与 Windows `amd64` 的固定真实验收入口均可从干净本批资源启动完整 GoPulse，不要求宿主安装 Go、Node.js 或六个基础设施。
- 两种自研 Linux 容器架构的镜像、插件、version/revision/source 与非 root 运行契约可验证。
- 六类目标均由各自单实例插件产生真实、可区分、有限标签的指标，不存在同类第二实例入口。
- 一种插件目标不可用或进程替换时，其他插件、历史可观测数据和代表性社交业务仍可用，恢复后采集自动继续。
- 普通用户可在桌面和窄屏完成登录、帖子、评论、点赞、搜索和通知主路径，不可获得管理数据或内部地址。
- 管理员可在总览和详情页面查看多组件 Metrics、Logs、Events，并完成一种代表插件的配置、连接测试、安装、停止、启动和更新/回滚。
- 页面清楚表达加载、空数据、数据过期、局部失败和权限撤销，桌面/窄屏、键盘与长内容代表验收通过。
- 从 `1.9.4` 升级后，用户/角色、帖子/通知、搜索、必要可观测历史与 Redis 插件期望状态保留；备份恢复在隔离资源中可验证。
- Frontend bundle、公共 API、日志、Events、诊断和制品元数据不泄漏凭据、Cookie、完整连接串、宿主路径、内部端口或进程事实。
- 正常、失败、中断和停止路径只清理当前验收强归属的容器、网络、卷、制品和临时文件，不破坏用户日常环境。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，Phase 12 容器基线与本阶段跨平台产品、多类单实例采集、前端、升级和恢复能力可共同运行。
- 对应实施记录如实记录改动、真实平台、验证命令与结果、偏差和后续事项，固定本地/远程门禁通过且没有阻断失败。
- 达到上述条件后完成 Milestone 4 验收并停止扩展；多实例、告警、公开插件市场、Kubernetes 自动发现和生产级高可用进入后续阶段或独立规划。

## 本阶段不做

- 同种插件多实例、单实例多 target 或同类目标自动发现。
- 未受信第三方插件的通用沙箱或公开插件市场。
- 原生 Windows Service、macOS LaunchDaemon，或将 MySQL/Kafka/Elasticsearch 改为宿主原生安装。
- Kubernetes Deployment/Service/StatefulSet/PVC、Ingress、集群对象采集或节点调度。
- 任意 PromQL/MetricsQL/Elasticsearch DSL、完整告警引擎、外部通知渠道或自动修复。
- 生产级 HA、容量承诺、长时压测、跨地域容灾或完整 SRE 体系。

## 总实施方案生成与批次切分约束

- 本阶段允许超过默认 2～3 个批次，因为宿主/架构支持、插件通用安全边界、多组件采集、前端产品体验与持久数据升级分别属于独立风险域。
- 总实施方案建议按“跨平台生命周期与多架构制品 → 通用单实例插件契约 → 真实多组件采集 → 双用户态前端产品化 → 跨平台升级/恢复集成收口”的可运行闭环切分，不按 Backend/Frontend/测试等技术层机械分批。
- 每个插件批次必须交付“真实目标 → Exporter → Monitor → Router → Kafka → Marshaller → VictoriaMetrics → Backend → Frontend”的最低有效证据，不只实现采集器单元测试。
- 平台验收在真实支持环境各执行一次固定完成门槛；不能用交叉编译取代宿主生命周期与浏览器闭环。
- 测试、文档、升级路径和实施记录随对应能力完成；最终收口批次只执行跨批集成、平台矩阵和 Milestone 4 固定验收，不增加新功能。
- 每个执行批次的精确版本、`develop/x.x.x` 分支和顺序只由 Phase 13 总实施方案权威表分配。

## Phase 14 交接

向 Phase 14 Kubernetes 基础部署交付：

- 通过真实跨平台 Compose 验收的 `linux/amd64` 与 `linux/arm64` 自研镜像及身份契约。
- 多种官方插件、每种单实例/单目标的运行、配置、Secret、健康、重启与持久状态契约。
- 已产品化的 Frontend/Backend 用户面和仍不对浏览器开放的内部服务面。
- 从 `1.9.4` 演进后的数据迁移、备份/恢复、诊断和强归属验收基线。

Phase 14 必须迁移上述产品行为，不回退到 Redis-only 页面、单架构制品、浏览器直连内部服务或在集群中临时编译源码。

## 后续待细化事项

- 支持的 macOS、Windows、Linux、Docker Desktop/Engine 和浏览器版本矩阵。
- 跨平台生命周期入口的技术形态、配置目录和制品发布方式。
- 通用插件 Manifest、配置 Schema、Secret 存储、端口分配和状态数据迁移。
- 各组件指标目录、安全标签、默认采集间隔与故障错误码。
- 前端视觉语言、组件库、页面信息架构、图表库与浏览器验收细节。
- 备份一致性、升级/回滚边界、数据保留与诊断脱敏格式。
- 本阶段批次拆分、固定验收命令、远程环境和实施顺序。
