# Phase 5：Exporter Plugin原型

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.2.x`；阶段基线：`1.2.0`。
- 执行批次从 `1.2.1` 起编号，具体目标版本和开发分支由 Phase 5 总实施方案统一分配。

## 阶段目标

实现首个独立指标采集插件，验证常驻、被动拉取的 Exporter 工作模式。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 6。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 2，指标采集 MVP。
- 本阶段交付首个真实指标来源，验证 Exporter 常驻、被动拉取和目标故障隔离模式，为后续 Monitor 采集提供可运行对象。
- 单一组件的真实采集与失败表达是当前里程碑的必需增量；多组件支持和完整插件平台按`本阶段不做`延后。

## 开发范围

- 单一组件 Exporter 原型。
- 指标采集与统一输出。
- 健康检查。
- 目标组件异常处理。

## 核心任务

- 从 MySQL 或 Redis 中选择一个组件作为首个采集目标。
- 运行常驻 HTTP 服务并等待采集请求。
- 连接目标组件并输出指标。
- 在目标不可用时返回明确失败状态且保持进程存活。

## 前置依赖

- Phase 4 业务日志基础完成。
- 至少一个可持续运行的基础组件可作为采集目标。

## 阶段产物

- 首个可独立运行的 Exporter Plugin。
- 指标访问入口。
- Exporter 健康状态入口。
- 插件原型运行说明。

## 最小端到端闭环

`真实 MySQL 或 Redis 组件 → Exporter 采集 → HTTP 指标入口 → 实际指标或明确失败状态`

该闭环必须使用一个真实运行组件验证成功采集，并在目标不可用时保持 Exporter 存活，不能以静态样例指标代替。

## 验收标准

- 访问 Exporter 可获得目标组件的实际指标。
- Exporter 不主动向 Monitor 推送数据。
- Exporter 不保存历史数据。
- 目标组件关闭时 Exporter 不崩溃并能表达采集失败。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，且成功与目标故障两种代表性场景均可重复验证。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且没有阻断验收的失败。
- 达到上述条件后停止扩展；其他采集目标和插件平台能力转入后续事项，阶段产物作为 Phase 6 的真实采集输入。

## 本阶段不做

- 同时支持多个组件插件。
- Monitor 采集调度。
- Kafka 与 VictoriaMetrics。
- 完整插件平台。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次；需要跨批验证时，再安排 1 个集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按真实组件到 Exporter 结果的闭环切分，不按采集器、HTTP 服务、健康检查和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；如安排收口批次，只执行跨批集成和固定验收，不加入新的功能范围。
- 首个目标、指标契约、接口和运行参数由总实施方案根据实施前的真实代码与可用组件确定，阶段提纲不提前冻结。
