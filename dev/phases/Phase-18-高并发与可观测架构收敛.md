# Phase 18：高并发与可观测架构收敛

> 本文档是阶段开发提纲。具体性能目标、接口、配置、批次、版本和分支在总实施方案中确定。

## 版本方向

- 本阶段以 `2.x.x` 作为下一主版本方向。
- 具体基线、执行版本和 `develop/x.x.x` 分支由后续总实施方案分配。
- 当前根版本为 `2.0.1`；本提纲与后续规划调整不修改 `VERSION`。

## 阶段目标

GoPulse 的定位保持为“高并发业务系统 + 内建可观测系统”。

本阶段不增加新业务，而是证明系统的并发能力、扩容边界、背压行为和故障隔离。

## 优先级

### P0：必须先完成

- 建立输入固定、结果可复核的高并发容量基线。
- 验证主要无状态和消费组件的多副本能力。
- 分离业务搜索与观测数据的 Elasticsearch 故障域。
- 建立 HTTP、RabbitMQ、Kafka 和存储写入的端到端背压。

P0 全部通过前，不得以扩展 P1 或引入 Kubernetes 代替并发与故障合同的验证。

### P1：P0 成立后收敛

- 建立不依赖可观测数据面自证的基础健康通道。
- 将 Envelope、日志、指标和 API 错误合同收敛为机器可读单一来源。

P1 是本阶段完成条件，不是可选优化；其实施顺序低于 P0。

## 里程碑定位

- 所属里程碑：Milestone 5，可量化的高并发与可观测故障隔离。
- 将“按高并发设计”推进为“在固定 Linux `amd64` Compose 环境中具有有界、可复核证据”。
- 阶段结果只对记录的硬件、负载和候选版本成立，不扩大为通用生产容量承诺。

## 开发范围

- **P0**：建立固定的数据配方、混合业务负载和容量基线。
- **P0**：记录 RPS、P95/P99、错误率、资源使用、消息积压和恢复时间。
- **P0**：验证 Backend、Worker、Indexer、Router 和 Marshaller 的多副本能力。
- **P0**：明确 Outbox lease、RabbitMQ consumer、Kafka partition、告警 lease 和 Monitor 插件所有权。
- **P0**：分离业务搜索 Elasticsearch 与 Logs/Events Elasticsearch 的运行和故障域。
- **P0**：为 HTTP、连接池、Outbox、RabbitMQ、Kafka、Marshaller 和存储写入建立有界背压。
- **P1**：建立不依赖 Kafka、VictoriaMetrics 或观测 Elasticsearch 自证的基础健康通道。
- **P1**：收敛 Envelope、日志字段、指标目录和 API 错误码的机器可读来源。

## 核心任务

- 先测量现有系统，再修复已有证据的瓶颈，不做泛化性能优化。
- 为可水平扩容组件建立多副本 Compose 验证。
- 为不可盲目扩容的任务固定单例、租约或分区所有权。
- 对两个 Elasticsearch 使用独立服务、卷、凭据和资源边界。
- 验证超载时有界拒绝或积压，负载回落后可恢复。
- 扩展 lifecycle 诊断能力，区分进程健康、依赖健康和数据链路收敛。
- 用确定性生成和 CI 检查防止 Go、TypeScript、Schema、Marshaller 与 Elasticsearch mapping 漂移。

## 前置依赖

- Phase 17 已完成，当前 Linux `amd64` Compose 产品和 Runtime Contract 可用。
- 业务、搜索、Metrics、Logs、Events、告警、插件和双 Frontend 闭环保持为回归基线。

## 阶段产物

- 高并发负载配方与容量报告。
- 多副本扩容与任务所有权合同。
- 业务搜索与观测存储故障隔离。
- 端到端背压配置、指标和故障恢复证据。
- 独立健康诊断与合同漂移门禁。
- 与候选版本绑定的 Linux `amd64` Compose 验收证据。

## 最小端到端闭环

`固定数据与混合负载 → 多副本业务与观测处理 → 超载/存储故障 → 有界积压 → 恢复追赶 → 业务事实和观测数据最终收敛`。

## 验收标准

- 在固定参考宿主、负载配方和单个冻结候选上，并发、延迟、错误率和收敛达到量化门槛。
- 多副本与实例替换不产生消息越权提交、重复副作用或持久数据丢失。
- 观测 Elasticsearch 故障不拖垮业务搜索，业务搜索故障不阻断 Logs/Events 收敛。
- 超容量时无 OOM、无无界队列/重试/日志增长，且不静默丢弃已接受数据。
- 可观测数据面故障时，独立健康通道仍可用。
- 公共数据合同可确定性再生成，全仓漂移检查通过。
- Phase 18 直接影响的业务、搜索、可观测与生命周期回归通过；未受影响的 Phase 17 场景不做全量重跑。

## 阶段完成与停止条件

- 容量、多副本、背压、存储隔离、独立健康和合同收敛全部通过固定验收。
- 容量报告明确记录可扩容组件、状态单点、第一瓶颈、超容量行为和适用边界。
- 总实施方案中分配的批次及对应实施记录已完成，固定门禁无阻断失败。
- 达到条件后结束 Milestone 5，不继续进行无证据的优化。

## 本阶段不做

- Kubernetes、Helm、Ingress 或 Operator。
- MySQL、RabbitMQ、Kafka、Elasticsearch 或 VictoriaMetrics 的生产级 HA。
- 新业务、新插件、新管理页面或多租户。
- 无压测证据的分库分表、读副本、新消息中间件或新存储。
- 将单机 Compose 验收结果宣称为通用生产容量或高可用承诺。

## 总实施方案约束

- 根据真实代码基线确定参考硬件、数据配方、性能目标、批次、版本和分支。
- 批次按“容量基线”、“扩容/故障收敛”和“候选验收”等可运行闭环切分，不按技术文件清单机械拆分。
- 负载工具、数据生成和最小证据校验在正式运行前完成确定性预检，不建设可扩展验收矩阵。
- 总实施方案必须定义阶段验收线和每批完成条件，不允许在实施中临时降低标准。

## 后续待细化事项

- 参考宿主规格、数据量、负载比例、目标 RPS 与 SLO。
- 各组件的扩容类型、副本数和替换顺序。
- 两个 Elasticsearch 的迁移、备份恢复和资源配额。
- 背压参数、拒绝码、积压指标和恢复时限。
- 合同源路径、生成物范围与兼容策略。
