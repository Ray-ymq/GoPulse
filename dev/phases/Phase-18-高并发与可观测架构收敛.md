# Phase 18：高并发与可观测容量定界

## 阶段目的

在固定 Linux `amd64` Compose 环境中，记录 GoPulse 当前容量、失效行为和第一瓶颈。
本阶段用于暴露问题，不承担将所有问题修到 150/300 RPS 达标的责任。

## 优先级

- **P0**：保留固定负载的真实结果，采纳已定位的 Outbox 最小修复，明确哪些能力已证明、
  未证明或不达目标。
- **P1**：将多副本、双 Elasticsearch 隔离与背压、独立健康和合同单一来源
  整理为下一阶段输入，不在 Phase 18 中继续扩大实施范围。

## 结果判定

- `target_met`：达到固定探测目标，阶段完成。
- `boundary_found`：未达到目标，但已得到可解释的边界、瓶颈或风险，阶段同样完成。
- `incomplete`：证据无效或待交付修改自身回归，阶段关闭但不升级版本。

三种都是终态。未达到性能目标不触发重跑，`incomplete` 也不触发无限修订实施文件。

## 完成与版本

- Phase-18-01 已交付 `2.0.1` 负载工具和失败基线。
- Phase-18-02 仅收口 Outbox 修复和容量结论。修复自身通过回归后发布 `2.0.2`；
  容量仍可记录为 `boundary_found`。
- 若修复自身不可交付，保持 `VERSION=2.0.1` 并关闭 Phase 18，不在本阶段重开批次。

## 下一阶段输入

- Outbox 稳态积压和事件闭合未证明项。
- Backend、Worker、Indexer、Router 和 Marshaller 的多副本所有权正确性。
- 业务搜索与观测 Elasticsearch 故障域隔离和代表性背压。
- 不依赖观测数据面的健康通道和机器合同单一来源。

下一阶段必须重新建立总实施方案、目标版本和分支分配，不复用 Phase 18 的运行次数或证据。
