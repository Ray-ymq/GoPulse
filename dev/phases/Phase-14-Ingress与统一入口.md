# Phase 14：Ingress与统一入口

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.11.x`；阶段基线：`1.11.0`。
- 执行批次从 `1.11.1` 起编号，具体目标版本和开发分支由 Phase 14 总实施方案统一分配。

## 阶段目标

为 Kubernetes 中的 GoPulse 提供统一 HTTP 访问入口，并收敛外部暴露面。

本阶段完成后，应形成可独立运行和验证的结果，并能够直接支撑 Phase 15。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 4，云原生自观测 MVP。
- 本阶段在集群内完整运行的基础上建立面向用户的单一 HTTP 入口，并收敛基础设施的外部暴露面。
- Frontend 与 Backend 的统一访问、内部服务边界和完整用户访问流程是当前里程碑的必需增量；公网证书、复杂网关治理和多集群流量按`本阶段不做`延后。

## 开发范围

- Ingress Controller 对接。
- Frontend 与 Backend 路由。
- 统一域名或访问地址。
- 内部基础设施访问边界。

## 核心任务

- 配置统一入口并将页面与 API 请求路由到对应 Service。
- 确保内部组件继续通过 ClusterIP 通信。
- 关闭不必要的直接外部暴露。
- 验证用户端完整访问流程。

## 前置依赖

- Phase 13 Kubernetes 基础部署完成。
- Frontend 与 Backend Service 可用。
- 集群已安装或可使用 Ingress Controller。

## 用户态与访问边界

- 单一 HTTP 地址同时承载普通用户社交域和管理员可观测域，但两者必须具有明确的前端路由与 Backend API 权限边界；统一入口不等于统一授权。
- 普通用户只能进入社交域；可观测导航、管理路由和 Metrics/Logs/Events/Exporter API 仅对 admin 开放，直接构造 URL 或 API 请求仍由 Backend 返回 `403 permission_denied`。
- Ingress 只公开 Frontend 与 Backend 所需路由，不公开 Monitor、Router、Marshaller、Kafka、VictoriaMetrics、Elasticsearch、数据库或任意内部管理端口。
- Ingress 不通过可伪造 header 赋予 admin 身份，不把路径隐藏当作授权；用户身份和角色继续由 Backend 的现有会话与数据库当前角色裁决。
- 可观测管理路由或内部组件故障不得阻断普通用户社交路由；错误页和代理响应不得泄漏 Service 名称、集群地址或上游原始错误。

## 阶段产物

- GoPulse 统一访问入口。
- Frontend 与 API 的 Ingress 路由。
- 受控的集群外部暴露策略。

## 最小端到端闭环

`普通用户访问单一地址完成社交操作；管理员使用同一地址和会话进入可观测管理域 → Ingress 仅路由 Frontend/Backend → Backend 授权后访问内部 Service`

该闭环必须同时证明用户入口可用和基础设施保持内部访问，不能只交付 Ingress 资源或继续依赖 NodePort 完成验收。

## 验收标准

- 用户只需一个地址即可访问页面和业务 API。
- 用户不需要直接访问 NodePort。
- MySQL、Redis、Kafka、Elasticsearch、VictoriaMetrics 等基础设施不直接暴露公网。
- 内部组件通信保持正常。
- 普通用户直接访问可观测页面或 API 不获得数据且 API 为 `403`；管理员可经同一入口完成代表性查询和管理操作。
- 可观测上游故障时普通用户社交流程仍可用，Ingress 与错误响应不泄漏内部拓扑。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，普通用户和管理员可通过一个入口进入各自授权的产品域，内部组件仍正常通信且不直接暴露。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且没有阻断验收的失败。
- 达到上述条件后停止扩展；公网域名、证书和复杂网关能力转入后续事项，统一入口作为 Phase 15 自观测验收的用户入口。

## 本阶段不做

- 公网生产域名和证书体系。
- 基础设施外部管理入口。
- 复杂网关治理和多集群流量策略。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次；需要跨批验证时，再安排 1 个集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的风险隔离、依赖关系或独立交付理由。
- 实现批次按用户经统一入口完成操作的闭环切分，不按 Controller、路由、Service、安全边界和测试等技术层机械拆分。
- 测试、文档和实施记录随对应能力完成；如安排收口批次，只执行跨批集成和固定验收，不加入新的功能范围。
- Controller 选择、域名、路由规则和暴露策略由总实施方案根据实施前的真实集群与网络基线确定，阶段提纲不提前冻结。
- 总实施方案必须提供普通用户/管理员路由与 API 矩阵、Ingress 暴露清单、禁止透传的身份 header、内部服务负向探测和故障隔离验收。
