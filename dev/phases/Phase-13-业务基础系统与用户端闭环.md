# Phase 13：业务基础系统与用户端闭环

> 本文档是阶段开发提纲。具体 API、Schema、事件契约和批次由总实施方案根据 `1.9.4` 真实基线确定。

## 版本规划

- 版本线：`1.10.x`；阶段基线：`1.10.0`。
- 执行批次从 `1.10.1` 起编号，由 Phase 13 总实施方案统一分配版本与分支。

## 阶段目标

在现有用户、帖子、评论、点赞、通知和搜索之上补齐关注、Following 信息流、收藏、帖子编辑/删除、用户资料与用户搜索，使基础业务系统和独立用户端形成完整闭环。

交互参考 X 的简洁信息结构，但只实现 GoPulse 已确认的必要能力，不复制 X 的完整产品范围。

## 开发范围

- 用户资料：登录用户名保持稳定身份；用户可维护显示名称和个人介绍；资料页展示基本资料和该用户发布的帖子。
- 用户发现：按登录用户名或显示名称搜索用户；可从搜索结果、帖子作者和资料页关注或取消关注。
- 关注关系：提供仅包含已关注用户帖子的 Following 信息流；新增关注进入既有通知中心，取消关注不产生通知；本人可查看自己的关注与粉丝关系，其他用户不可查看关系列表。
- 收藏：收藏/取消收藏帖子并提供仅本人可见的收藏列表。
- 帖子编辑：仅作者可编辑，保存最新标题和正文并记录最后编辑时间；同步更新缓存和搜索投影。
- 帖子删除：仅作者可在明确二次确认后永久删除；评论、点赞、收藏和搜索投影随之删除，历史通知保留并显示原内容已删除。
- 用户端：形成独立的用户 Frontend 应用，收口首页、Following、搜索、收藏、资料和帖子详情/编辑等主路径。

## 最小端到端闭环

`搜索用户 → 关注 → Following 查看对方帖子 → 收藏 → 作者编辑帖子 → 搜索与缓存同步 → 作者确认永久删除 → 关联数据清理且历史通知可解释`

## 验收标准

- 用户可维护显示名称和个人介绍，并可通过用户名或显示名称被搜索到。
- 关注、取消关注和 Following 信息流结果一致；他人不能读取关注/粉丝列表。
- 收藏列表仅本人可见，帖子删除后不残留收藏关系。
- 非作者不能编辑或删除帖子；编辑后详情、列表、缓存和搜索均为最新内容并展示最后编辑时间。
- 永久删除必须二次确认，且评论、点赞、收藏和搜索投影被清理；历史通知不会形成失效链接或泄漏已删正文。
- 既有注册、登录、评论、点赞、通知、搜索和管理员可观测能力不回归。

## 本阶段不做

- 图片、视频或其他媒体发布。
- 私信、转发、引用、话题、趋势、推荐算法、广告、付费或创作者体系。
- 公开关注/粉丝列表、私密账号、关注审批、拉黑和举报治理。
- 管理端重构、告警、插件扩展或 Kubernetes。

## 总实施方案约束

- 批次按可运行的业务闭环切分，不按数据库、Backend 和 Frontend 技术层机械拆分。
- 必须固定验证权限、并发关系幂等、缓存/搜索一致性、永久删除边界和既有业务回归。
- 阶段通过后直接进入 Phase 14，不以 Kubernetes 运行作为验收条件。
