# Phase 16：Linux 产品化与双前端交付

> 本文档是阶段开发提纲。支持版本、生命周期入口和制品发布细节以总实施方案为准。

## 版本规划

- 版本线：`1.13.x`；阶段基线：`1.13.0`。
- 六个执行批次固定为 `1.13.1` 至 `1.13.6`，由 Phase 16 总实施方案统一分配版本与分支。
- `1.13.1` 已完成；后续规划调整不重建或重编号已推送分支。

## 阶段目标

把 Phase 13～15 的完整业务与可观测能力提升为可在真实 Linux `amd64` 环境安装、运行、升级、诊断和恢复的双前端 Compose 产品。

## 开发范围

- 支持与验收环境固定为 Linux `amd64` host/server。
- 全部产品容器、两个 Frontend 和六类受管插件以 Linux `amd64` 制品作为阶段合同。
- 同一 edge origin 提供统一登录入口；Backend 根据 `user` 或 `super_admin` 将用户送入独立用户端或管理端，两端共用同源安全会话。
- 统一两个应用的设计令牌、公共交互质量、桌面/窄屏、加载/空/错误/过期状态、键盘焦点和时区表现，同时保持信息架构独立。
- 建立共享容器化的初始化、启动、停止、状态、日志、验证和脱敏诊断入口。
- 建立从 `1.9.4/linux/amd64` 到本阶段的可重复升级，以及业务、可观测、插件、角色、告警和配置的一致备份/恢复能力。
- Phase-16-01 已生成的额外架构制品作为历史结果保留，不构成后续支持或完成门禁。

## 最小端到端闭环

`干净 Linux amd64 交付目录 → Bundle 启动 Compose → 登录并按角色进入独立应用 → 完成代表性业务/插件/告警流程 → 同架构恢复或 1.9.4 升级 → 受控停止`

## 验收标准

- 真实 Linux `amd64` Docker server 可从独立 Bundle 启动完整 GoPulse，不要求宿主安装 Go、Node.js 或基础设施客户端。
- 同一域名和登录入口可稳定分流两个独立 Frontend；越权路径由 Backend 拒绝。
- 用户端完成代表性社交闭环，管理端完成大屏、插件和告警闭环。
- 加密备份可恢复到同架构空 project；升级与恢复后业务事实、搜索投影、可观测历史、插件期望状态、角色和告警记录保持一致或可重建。
- 诊断、日志、API、Frontend bundle 和制品元数据不泄漏凭据、Cookie、连接串或宿主私有路径。
- 正常、失败和中断路径只清理当前运行强归属资源。

## 本阶段不做

- macOS、Windows、`linux/arm64` 产品支持与运行验收。
- 原生宿主服务、重复宿主编排实现或 GUI 安装器。
- Kubernetes 资源、Ingress、集群对象采集或生产级高可用。
- Phase 13～15 范围之外的新业务、插件或告警功能。

## 总实施方案约束

- 最终验收必须来自真实 Linux `amd64` runtime，不能由交叉编译、Compose 静态解析或模拟运行替代。
- 各批按直接依赖开工，不再等待其他宿主 owner、运行窗口或访问方式。
- 制品、生命周期、双 Frontend、备份恢复、升级和最终产品矩阵属于独立风险域，因此拆分为六个批次。
