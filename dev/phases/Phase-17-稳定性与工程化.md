# Phase 17：稳定性与工程化

> 本文档是阶段开发提纲，具体接口、数据模型、消息格式和部署参数将在本阶段进入详细设计时补充。

## 版本规划

- 版本线：`1.14.x`；阶段基线：`1.14.0`。
- 执行批次从 `1.14.1` 起编号，具体目标版本和开发分支由 Phase 17 总实施方案统一分配。

## 阶段目标

在业务、可观测、告警、双前端和跨平台交付闭环后，统一强化配置、退出、健康检查、错误处理和消息消费可靠性。

本阶段完成后，完整 GoPulse 必须在不依赖 Kubernetes 的条件下通过产品级集成验收，再将同一产品交给 Phase 18 部署。

## 里程碑定位与 MVP 贡献

- 所属里程碑：Milestone 4，完整可交付产品 MVP 的收口阶段。
- 本阶段不增加新的产品域，而是 Kubernetes 前的工程质量门槛。
- 前序 Phase 必须各自实现正常运行所需的基础正确性和必要可靠性；本阶段只统一既有契约、补齐跨组件差异并验证整体稳定性，不得把前序阶段的必需修复延后到这里。
- `开发范围`和`验收标准`限定最终收口内容；生产级高可用、完整 SRE、跨地域容灾和未专项设计的性能承诺继续按`本阶段不做`排除。

## 开发范围

- 统一配置管理。
- Go 服务优雅退出。
- 可供 Kubernetes Probe 使用的启动、存活与就绪契约。
- 结构化日志与 Request ID。
- 统一 API 错误响应。
- 数据库 Migration。
- Kafka 与 RabbitMQ Consumer 可靠性。

## 核心任务

- 统一各组件环境变量和配置结构。
- 支持 SIGTERM、SIGINT 下的优雅退出。
- 统一启动、健康与就绪检查语义，为 Phase 18 配置三类 Probe 提供稳定端点。
- 规范日志、请求标识和 API 错误响应。
- 建立明确 Schema Migration 流程。
- 处理 Kafka offset、重试和异常消息。
- 处理 RabbitMQ ack、重试和幂等。

## 前置依赖

- Phase 16 跨平台产品化与双前端交付完成。
- 所有主要组件与数据链路已具备稳定形态。

## 用户态与访问边界

- 最终工程收口必须把“普通用户端”和“超级管理员端”作为跨组件稳定契约，不得在统一错误、配置或健康检查改造中合并或弱化权限边界。
- 两端共用身份系统与同源会话；Backend 必须以数据库当前角色保护全部 Metrics、Logs、Events、Alerts 与 Exporter API，Frontend 分流和路由守卫不能替代服务端授权。
- 最终回归矩阵必须固定覆盖：未登录 `401`、普通用户全部管理 API `403`、超级管理员查询/管理成功、角色变更后的重新分流以及公开作者摘要不暴露 role。
- 部署负向验收必须证明浏览器与外部入口不能直达 Monitor、Router、Marshaller、Kafka、VictoriaMetrics、Elasticsearch 或数据库。
- 可观测链路关闭、超时或部分故障时，普通用户代表性社交闭环仍可运行；统一日志、状态和错误响应不泄漏凭据、内部地址、服务器路径或原始异常。

## 阶段产物

- 统一工程规范。
- 服务生命周期与健康检查能力。
- 数据库迁移机制。
- 增强后的消息消费者。
- 可定位错误的日志和状态接口。

## 最小端到端闭环

`完整 Compose 产品 → 统一配置、信号处理、健康与就绪契约 → 受控停止、重启并恢复服务`，同时验证 `Schema 变更 → Migration`、`消息消费异常 → 明确处理路径` 和 `告警评估异常 → 可恢复且不阻断业务`。

该闭环必须在已经完成的业务、可观测、告警和双前端 Compose 系统上验证，不能依赖 Kubernetes 掩盖产品自身缺口。

## 验收标准

- 组件正常重启不会造成明显数据混乱。
- 错误可通过日志和状态接口定位。
- 全部服务提供可供后续 Kubernetes Probe 直接使用的启动、存活和就绪契约。
- Kafka 与 RabbitMQ 消费异常具备明确处理路径。
- 数据库结构变更可通过 Migration 管理。
- `user`/`super_admin` 权限矩阵在两个 Frontend、Backend 和 Compose 中保持一致，普通用户不能读取或管理可观测数据。
- 引导超级管理员保护、按用户 ID 调整角色和内部告警状态机在重启与依赖故障后保持正确。
- 超级管理员与普通用户代表性闭环、内部服务负向探测和可观测故障下的社交业务回归全部通过。

## 阶段完成与停止条件

- 最小端到端闭环及全部阶段验收标准通过，完整业务与可观测产品在统一工程约束下共同运行。
- 对应实施记录已如实记录改动、验证、偏差和后续事项，固定完成门槛通过且没有阻断验收的失败。
- 达到上述条件后完成 Milestone 4 验收并停止扩展；同一产品作为 Phase 18 Kubernetes 部署输入，不在部署阶段补做产品功能。

## 本阶段不做

- 大规模生产级高可用。
- 完整 SRE 体系。
- 跨地域容灾。
- 未经过专项设计的性能承诺。
- Kubernetes 资源、Ingress 或集群对象采集。

## 总实施方案生成与批次切分约束

- 默认规划 1～2 个实现批次；需要跨批验证时，再安排 1 个集成验收与阶段收口批次，总计尽量控制在 2～3 个批次。
- 超过 3 个批次时，总实施方案必须记录具体的跨组件风险隔离、依赖关系或独立交付理由。
- 实现批次按可验证的跨组件质量闭环切分，不按配置、信号、Probe、日志、Migration 和 Consumer 等技术清单机械拆分。
- 测试、文档和实施记录随对应强化能力完成；如安排收口批次，只执行跨批集成和固定验收，不加入新的功能范围。
- 统一契约、兼容策略、Migration 和消费者可靠性细节由总实施方案根据 Phase 16 完成后的真实系统基线确定，阶段提纲不提前冻结。
- 总实施方案必须把身份/权限矩阵、内部服务暴露清单、敏感错误过滤和故障隔离纳入固定完成门槛，而不是作为一般安全审查或可选改进。
