## 4. 跨批共同合同

### 4.1 身份、数据与消息

| 身份 | 生成/所有者 | 稳定与适用范围 |
| --- | --- | --- |
| `data_epoch` | 业务持久环境记录，规范 UUID | 普通重启不变；空库初始化、数据重置或恢复建立新值。旧事件不能写入新代际 |
| `command_id` | 业务创建事务，规范 UUID | 一次已提交发帖的稳定身份；同键成功重试不改变。无键调用每次都是新命令 |
| `event_id` | 业务事件生成者 | 同一事件领取、发布、重试和消费者重投不改变；Trace/attempt 可变化 |
| `content_revision` | posts 事实 | 沿用现有单调内容版本，不引入第二个竞争版本源 |
| `projection_generation` | 搜索物理索引实际身份 | 重建产生新值，数据 epoch 不因此改变；完成记录采用真实 ES 写入结果的索引 |
| `routing_contract_revision` | 业务领域合同 | V1 固定 `post-created-search/1`，必要消费者集合为 `search` |

新增业务 Envelope v2 保留现有事件类型及 routing key 的业务语义，新增 epoch；
发帖事件另含 command_id。其他业务事件只补代际身份，不承诺新的命令幂等或应用账本。
v1/v2 都严格校验；新消费者先就绪，旧二进制因严格解码不能消费 v2。
历史 v1、既有帖子和日志不补造 command、epoch 或完成依据。

命令唯一范围为 `(data_epoch, user_id, post.create, idempotency_key_hash)`，摘要取
现有 title/content 规范化后的确定编码。命令结果只保存稳定业务 ID、事件 ID、成功状态和提交时间，
不存重复正文快照。事实、命令、事件和必要消费义务同一个 MySQL 事务提交。
公开重放结果仍按当前权限读取正文；帖子已删除时只能返回已提交的最小结果。

新发帖的必要应用记录唯一范围为
`(data_epoch, event_id, search, routing_contract_revision, projection_generation)`。
记录实际应用版本和 `applied` / `no_effect_resource_absent` 结果；后一种需要事实检查和投影删除成功。
ES 副作用与 MySQL 完成记录不能原子提交；失败时按相同事件重投，完成落库后才 ack。
保留原有“retry/dead 持久发布确认后才 ack 原消息”的规则。

### 4.2 阶段语义

| 阶段 | 可作为依据的事实 | 不能据此推导 |
| --- | --- | --- |
| 命令已提交 | MySQL 同事务结果与业务 ID | 已返回给客户端、搜索已经可见 |
| Broker 确认已记录 | owner 校验成功的 Outbox published 状态/时间 | 必要消费者完成；pending 也不证明 Broker 从未收过消息 |
| 搜索应用完成 | 正确 epoch/事件/消费者/路由修订/实际代际的持久结果 | 新索引代际也已完成、当前查询一定可见 |
| 当前搜索可见 | 此次受限查询的实际 alias/物理代际、版本、结果与读取时间 | 永久可见、与其他来源组成原子快照 |
| 遥测已观察 | 查询到的 Logs；可用 Trace ID/受控原始 Span | 日志或 Span 缺失意味着业务没执行 |

接口逐来源返回 `source`、`read_at`、适用身份/修订、值和质量。
质量至少区分 `known`、`no_evidence`、`legacy_unknown`、`expired`、
`stale_epoch`、`backend_error`、`not_configured`；质量与业务结果是独立字段。
尚无完成记录时表达“完成未知/义务未闭合”，不生成“消费未发生”的确定结论。
Trace 后端未配置时保留关联 ID 和 `not_configured`，不伪造可查询的 Trace。

### 4.3 资源、留存与超限

以下值为 V1 的保守运行默认与有限验收合同，参数变化由所属批次核验实际资源后记录，
不能无记录扩容或把它们写成生产容量认证。

| 参数/所有者 | 固定值与适用条件 | 超限或失败行为 |
| --- | --- | --- |
| 共享 MySQL / B10 | 2 API + 2 Worker + 2 Indexer，各池 8；平台池 4；常驻上限 52；维护 4 + 工具/探针/Exporter 4，总额 60 | 诊断复用已有池；维护串行。现有 8 连接余量不容纳另一个完整 API 发布副本，受控停止发布 |
| 单对象查证 / B10、M6 | 业务每实例 2 个槽；平台业务查询总并发 4；不等待槽位；领域读取 500 ms，业务 RPC 2 s，平台总期限 3 s | 固定 `503 business_stage_busy` 或来源 backend_error；取消传递，不借查询占据全部业务槽 |
| 查询形状 / M6 | epoch 必填，command/event/post 三选一；最多 1 对象、20 条完成/失败摘要；Logs 单次最多 100 条、窗口最多 24 h、最多 1 次请求；无自动高频轮询 | 非法 400，结果截断明确返回；不能做全业务表扫描或跨对象任意 ES 查询 |
| 重试结果 / B3 | 成功命令至少保留提交后 7 日；未闭合义务及其引用不得按 TTL 清理；前端自动重试窗口最多 7 日 | 过期结果未知；不承诺永久一次执行，前端过期不自动生成新命令 |
| 事件/完成 / B6 | 必要消费者完成后再保留 7 日；原 cleanup 每批最多 500、每小时执行；未完成事件保持原 payload | published 不解锁清理；清理失败事务回滚，计数不提前释放 |
| 持久水位 / B6、B3 | 新发帖全局未闭合义务最多 10,000；保留事件/命令最多 100,000 组；编码 payload 加每组 1 KiB 元数据计费最多 1 GiB，80% 在只读查证中提示水位 | 创建事务原子预留；达硬限返回 `503 business_async_backlog`，已提交重放和普通读继续。清理/首次完成原子释放相应预算 |
| 遥测 / M9 | 沿用日志非阻塞有限队列、Tracing 有限 Batch 队列、现有重试/丢弃/关停预算 | 不进入普通提交和业务 ack 的前置；command/event/epoch/Trace ID 不作普通指标 label |

未闭合义务按 epoch 统计，保留组/字节按整个 V1 领域累计，历史 epoch 也占用保留预算；
数据库按固定锁顺序原子更新，禁止每请求无界 COUNT，恢复换 epoch 不将保留预算清零。
计费是逻辑增长上限，
不冒充 InnoDB 实际占用；正式主机另核验磁盘余量和依赖实际配置。
历史事件/其他业务写入仍受已有运行合同约束，本水位不表示全领域积压治理完成。

### 4.4 迁移、回退与恢复

01 增加一组连续 up/down 迁移，命令表也先建结构；后续无需要不追加占位 DDL。
当前二进制要求数据库恰好等于 embedded target，旧二进制不接受 ahead；
迁移采用停止相关应用 → 新 migration up → 新兼容读者/消费者 → 构建当前 epoch 索引 → 验证。
不承诺旧二进制在新 schema 上继续运行或零停机滚动升级。

02 启用前停止写入，核对 v1 Outbox、ready/unacked/retry/dead 队列。
可处理意图先排空；不能识别或处理的历史意图按原 payload 和来源持久停放并阻止静默丢弃。
确认新消费者、当前 epoch 索引及完成屏障后启用所有业务事件 v2。
历史记录仍是 legacy_unknown；不能将迁移成功写成历史应用完成。
启用后的行为回退只能使用兼容 v2/新 schema 的构建；migration down 不作为产品回退。

01 只部署并直接测试新恢复准备分支，02 的 v2 activation 才使其成为正式恢复流程；
01 兼容阶段沿用原 v1 排空备份/恢复合同，不声明可识别历史 v1 的数据代际。
启用后的数据恢复沿用 lifecycle 的 drained backup 约束，并增加必要应用未闭合检查。
恢复首先按原合同验证导入字节、事实数量和 hash；随后在应用启动前执行有 journal 的代际准备：
持久新 epoch → 隔离业务缓存键/游标 → 从已恢复事实构建新 epoch/新代际搜索索引 →
核验 alias 和旧事件拒绝 → 才启动应用。失败保留 restore-pending、禁止 ready。
旧完成记录保留历史作用域，不能换标签当作新完成；重建事实也不补造事件完成。
只验收同 Bundle、已排空备份的恢复准备，不扩展为任意过去时点恢复或跨版本恢复保证。
