## 1. 阶段结果与依据

把当前混合 Backend 装配拆成可独立启动的业务服务与管理服务；复用同一 Backend 制品、账号、MySQL 数据库和 Cookie/JWT 会话。浏览器继续通过同一入口使用现有路径、请求响应和权限合同。

业务服务负责注册、登录、账号资料、关注、帖子、评论、点赞、收藏、通知和搜索。管理服务负责指标、日志、事件、告警、插件管理、管理概览与角色管理。Outbox 投递及其采样仍归业务服务，独立 dispatcher 不在本阶段。

架构依据为[高并发设计](<../../../docs/GoPulse 高并发架构设计.md>)、[可观测设计](<../../../docs/GoPulse 可观测架构设计.md>)及[落地大纲](../../design/GoPulse-目标架构落地大纲.md)的 R1～R4 运行责任边界。本阶段只实现该边界的最小迁移，不实现整份目标架构。[能力状态](../../status/capability-status.md)记录现状；设计目标不等于完成能力。

Phase 20 已按调整范围结束于 `2.2.4`。取消的 Phase-20-05/06、其未完成代码和失败候选不是前置条件，不恢复原资源矩阵，不把重新编号当作历史故障修复。若在本阶段实际复现历史现象，保留原始证据并按当前固定门禁判定，不能忽略失败。

## 3. 冻结的迁移合同

### 3.1 角色与所有权

新增 `BACKEND_SERVICE_ROLE=combined|business|platform`；默认 `combined` 保持旧启动兼容。它与 `GOPULSE_RUNTIME_MODE=host|container` 分别校验，未知角色在监听、建连接或启动 goroutine 前失败。

| 装配 | business | platform | combined |
| --- | --- | --- | --- |
| 公共配置、HTTP、私有探针/指标、结构化日志、MySQL 用户/会话验证 | 是 | 是 | 是 |
| 注册/登录/退出、当前用户与社交业务 API | 是 | 否 | 是 |
| 管理 API、当前数据库角色授权、审计 | 否 | 是 | 是 |
| Redis 缓存、业务 Elasticsearch、RabbitMQ publisher、Outbox dispatcher/采样 | 是 | 否 | 是 |
| VictoriaMetrics/观测 Elasticsearch 查询客户端、Monitor 控制客户端、告警评估 | 否 | 是 | 是 |

角色不通过创建全套依赖再隐藏路由实现；加载、校验、建连接、就绪依赖及后台任务均按责任装配。管理服务直接复用现有账号库验证会话及实时角色，不向业务服务远程鉴权，不新建账号表、会话库或角色写入机制。迁移不改变 logout/会话失效的现有语义。

保留既有 Outbox lease/owner 和多业务副本安全；平台不启动 dispatcher、Outbox 采样或业务事件消费者。告警评估只在 platform/combined 启用，最终 Compose 为一个管理实例。Worker、Indexer 和 Monitor 的职责不迁移。

### 3.2 公共入口与权限

| 同源路径 | 最终目的地 |
| --- | --- |
| `/api/v1/observability`、`/api/v1/alerts`、`/api/v1/admin`、`/api/v1/exporter-plugins` 的精确基路径及其子路径 | platform-api |
| 其余既有 `/api/v1` 业务路径，包括 `/auth/*`、`/users/me` | backend / backend-2 |
| `/` 与 `/admin` 静态应用 | 既有用户 Frontend / 管理 Frontend |

Nginx 必须同时覆盖基路径和以 `/` 分隔的子路径，不让相似前缀误匹配；保留上传限制、超时、安全错误和请求标识。两个前端的 API URL、Cookie 属性和响应结构保持兼容。直接访问错误角色的 API 为未注册的 `404`；正确管理角色上未登录为 `401`、普通用户为既有 `403 permission_denied`。管理员降级后同一会话下一次管理请求即被拒绝，引导管理员保护继续有效。

### 3.3 部署、采集与资源

最终 Compose 保留 `backend`、`backend-2` 两个业务实例，新增一个 `platform-api`，三者共用相同 Backend 镜像 digest。HTTP `8080` 与指标 `19101` 可在各自容器命名空间重复使用，均不向宿主发布。生命周期、Bundle 生成与验收必须明确 `platform-api → backend` 的制品映射，不能虚构第二种制品。

沿用封闭的 Backend 指标目录、token 和 `component/source=backend`；`BACKEND_ENDPOINTS` 显式包含 `backend,backend-2,platform-api`。实例身份分别为 `backend-1`、`backend-2`、`platform-api-1`，运行合同关联其职责。增加一个封闭的 platform-api 运行单元，不扩展插件类型或多目标采集。平台不适用的 Outbox 指标不能被解释成业务积压清空。

| 项目 | 本阶段默认分配 | 验证含义 |
| --- | --- | --- |
| 2 business + 2 Worker + 2 Indexer 的 MySQL 池 | 每进程最多 8，共 48 | 从现有每进程 10 的默认配置重新分配 |
| platform-api 的 MySQL 池 | 最多 4 | 使用 `PLATFORM_API_MYSQL_MAX_OPEN_CONNS=4` 映射现有池参数 |
| 连接余量 | 8；总额仍为 60 | 最多一个池上限 4 的维护任务，其余 4 留给探针/Exporter/验收；禁止超额并行或未登记副本 |
| HTTP 准入 | 每 business 128；platform 32 | 使用 `PLATFORM_API_HTTP_MAX_CONCURRENCY=32` 映射既有参数；各进程独立 semaphore，满额返回原 503 |
| 退出 | Backend 关停 5 秒，Compose grace 15 秒 | 不放宽既有时限，不留进程/任务/连接 |

这些数值限定新增进程的默认配置与本次验收，不是容量认证或生产规格。02 必须校验常驻池总额 52 + 余量 8 ≤ 60，并从实际容器配置/池上限取证；不能只把表写进合同。临时维护和验收数据库连接也须计数。若改变副本数，先重算分配并校验，不能直接扩大总额。

03 完整固定案例通过并核验实际发布证据后，才能声明 Phase 21 完成。01/02 完成只解锁下一批，不能代替最终同一候选验收。检查范围、期限、命令、失败分类与证据细节以分方案为准；不默认重跑 Phase 18～20 的容量/长时全矩阵。

验证按改变的边界分层：装配、授权和准入优先复用所属模块 Go 测试；同源 Cookie 与两个前端复用现有 Playwright；部署、单侧停止、真实采集和清理由现有 `scripts/ci/runtime_acceptance.py` 承载有限的 `service-split` 用例选择。`scripts/ci/verify_runtime_contracts.py` 补该用例组必需的回执/脱敏核验。新增接口均在 02 实现并预检，03 不开发工具；旧默认套件及历史证据合同保留。具体已有覆盖、缺口、文件和命令见分方案。

## 5. 成本、停止与证据

| 批次 | 预计总活跃时间 | 累计上限 | 主要成本 |
| --- | --- | --- | --- |
| 01 | 120 分钟 | 180 分钟 | 装配改造、直接回归、最小真实依赖、清理 |
| 02 | 120 分钟 | 180 分钟 | 部署/合同、生命周期映射、复用入口的有限适配与非正式 preflight |
| 03 | 90 分钟 | 180 分钟 | 候选/Bundle、一次定向矩阵、证据核验与清理 |

分阶段预算见各分方案；不存在长时实验豁免。每个文件跨命令、候选、工作目录和 agent turn 累计，诊断/失败/清理不重置计时。到累计上限的 50%（90 分钟）和 80%（144 分钟）报告进度；预算不足以完成预计命令及安全清理时不得启动。

第一次验收基础设施失败即停止整组，最多两次每次 10 分钟的最小诊断。仅在复现原因、实际修正和受影响检查通过后重跑；新报错不视为进展。到上限/诊断停点保留 passed/failed/not_started、候选、原始证据与归属清理，登记具体剩余事项，不创建完成提交。接续须先修订剩余预算并由用户明确要求继续。用户停止后不自动恢复。

原始证据不改写，候选、Bundle/manifest、运行合同、工具和配置身份绑定；相关变更使受影响证据失效。完成时核验被选中的脱敏文件及来源，不复用另一个候选回执。规则细节见[执行预算](../../rules/implementation-execution-budget.md)。

## 6. 完成、限制与后续

各批实际执行完成后才创建 `dev/logs/Phase-21/` 下与分方案同名的日志，仅记录实际改动、命令/结果、偏差与限制。成功完成、必要检查通过后提交本批文件及完成版本，不纳入其他工作目录改动。

Phase 21 完成结果为“两种运行角色在最终双服务部署中工作，现有业务与管理合同兼容，固定 S01～S07 通过”。共享 MySQL 的故障仍同时影响业务数据、认证和管理授权；同宿主、共享镜像及其他共享状态也不构成完整故障隔离或高可用。

本阶段不包含新业务、独立 dispatcher、多目标插件/采集、领域重构、容量认证、观测开销认证或长时稳定性实验。后续需求重新形成实施合同，不在此预留 Phase、版本或分支。
