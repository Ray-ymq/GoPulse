# Phase 18：高并发与可观测架构收敛总实施方案

> 规划基线（2026-09-19）：主远程 `upstream/main` 为
> `fe596514487649a59678200af1cfb3ca40b4b16f`，当前完成版本为 `1.14.5`。
> Phase 18 首次分配 `2.0.x`，`2.0.0` 为阶段基线，可执行批次从 `2.0.1` 开始。

## 1. 阶段目标

GoPulse 的定位保持为“高并发业务系统 + 内建可观测系统”。

Phase 18 不增加新业务，重点完成：

- 建立可重复的高并发压测基线。
- 验证 Backend、Worker、Indexer、Router、Marshaller 的多副本能力。
- 分离业务搜索与观测数据的 Elasticsearch 故障域。
- 建立 HTTP、RabbitMQ、Kafka 和存储写入的端到端背压。
- 保留一条不依赖可观测链路本身的健康诊断通道。
- 统一 Envelope、日志、指标和 API 错误合同的机器可读来源。

## 2. 范围

### 2.1 本阶段交付

- 固定负载模型、数据量、并发数、成功率、P95/P99 和恢复时间。
- 多 Backend、Worker、Indexer、Router 和 Marshaller 的 Compose 验证配置。
- 单例、租约、消费组与分区所有权的明确边界。
- 业务搜索 ES 与观测 ES 的独立服务、卷、凭据与配置。
- 主要队列、并发、超时、重试和拒绝的上限与指标。
- lifecycle 独立健康诊断和端到端 canary。
- 合同单一来源、确定性生成和 CI 漂移检查。
- 最终 Linux `amd64` Compose 高并发与故障收敛证据。

### 2.2 本阶段不做

- Kubernetes、Helm、Ingress 或 Operator。
- MySQL、RabbitMQ、Kafka、Elasticsearch 或 VictoriaMetrics 的生产级 HA。
- 新业务、新插件或新管理页面。
- 无压测证据支持的分库分表、读副本或新中间件。
- 将单机 Compose 验收结果宣称为通用生产容量。

## 3. 批次、版本与分支

| 批次 | 版本 | 分支 | 主题 |
| --- | --- | --- | --- |
| Phase-18-01 | `2.0.1` | `develop/2.0.1` | 高并发数据配方、压测工具与容量基线 |
| Phase-18-02 | `2.0.2` | `develop/2.0.2` | 多副本扩容、负载均衡与任务所有权 |
| Phase-18-03 | `2.0.3` | `develop/2.0.3` | 双 Elasticsearch 隔离与端到端背压 |

分为 5 个批次，是为了将容量测量、多副本正确性、存储/背压改造、合同收敛和最终昂贵验收分开，避免故障无法归因。

## 4. 批次验收约定

### Phase-18-01：容量基线

- 固定参考 Linux `amd64` 宿主与数据配方。
- 覆盖登录、列表、详情、发布、评论、点赞、关注、通知与搜索的混合负载。
- 记录 RPS、P95/P99、错误率、资源使用、RabbitMQ 积压、Kafka lag 和收敛时间。
- 交付未优化基线和首个有证据的瓶颈，不在本批做泛化性能优化。

完成条件：同一候选和参考宿主上可重复获得结果，且负载生成器不是主要瓶颈。

### Phase-18-02：多副本与所有权

- Backend 至少 3 副本，Worker、Indexer、Router、Marshaller 至少 2 副本。
- 验证 Outbox lease、RabbitMQ consumer、Kafka partition、告警 lease 和 Monitor 插件所有权。
- 逐一替换实例时，已接受业务不丢失，幂等副作用不重复，搜索和观测数据最终收敛。

完成条件：每个长运行组件都有明确的“可水平扩容”或“单例/分区所有”结论并有实测证据。

### Phase-18-03：存储隔离与背压

- 业务搜索 ES 和 Logs/Events ES 使用独立服务、卷、凭据和资源边界。
- 观测 ES 故障不影响业务搜索；业务 ES 故障不影响 Logs/Events 收敛。
- HTTP、连接池、Outbox、RabbitMQ、Kafka producer、Marshaller 和 sink retry 都具有上限与指标。
- 超载时系统有界拒绝或积压，不 OOM、不无界增长、不静默丢弃已接受数据。

完成条件：两个 ES 故障域成立，主要队列和重试路径均可限制、可观测、可恢复。

### Phase-18-04：独立健康与合同收敛

- 扩展 lifecycle `status/verify/doctor`，直接检查 Edge、组件 Probe、队列积压、Kafka lag 和各存储。
- 通过唯一 canary 识别“进程健康但数据链路不收敛”，结果不依赖 Kafka、VM 或观测 ES 自证。
- 将 Envelope、日志字段、指标目录和 API 错误码收敛为机器可读单一来源。
- 生成 Go、TypeScript、Schema、Marshaller vocabulary 和 ES mapping 所需产物，CI 验证零漂移。

完成条件：可观测链路故障不会同时消除基础诊断证据，且公共数据合同只有一个机器可维护源。

### Phase-18-05：最终验收

- 冻结单一 `2.0.5` Linux `amd64` manifest、Bundle、runtime contract 和合同 catalog。
- 在同一候选上运行稳态、突发、多副本替换、超载、存储故障、恢复追赶和备份恢复。
- 发布脱敏容量报告，记录参考环境、负载、RPS、P95/P99、错误率、第一瓶颈、单点和适用边界。

完成条件：阶段固定矩阵全部通过，证据绑定同一候选，`VERSION=2.0.5`。

## 5. 阶段验收标准

- [ ] 已建立可重复的并发、延迟、错误率和异步收敛基线。
- [ ] 五类主要无状态/消费组件通过多副本与替换验证。
- [ ] 单写者、租约和分区所有权没有重复副作用或越权提交。
- [ ] 业务搜索 ES 与观测 ES 交叉故障隔离通过。
- [ ] 端到端背压在超容量时有界，负载回落后可恢复。
- [ ] 可观测数据面失效时，独立健康通道仍可用。
- [ ] 合同生成与全仓漂移门禁通过。
- [ ] 完整业务、搜索、可观测、告警、插件、双 Frontend、备份恢复和产品生命周期回归通过。
- [ ] 最终证据脱敏且绑定同一 `2.0.5` 候选。

## 6. 里程碑完成条件

Phase 18 通过后形成 Milestone 5：“可量化的高并发业务与可观测故障隔离”。

- 所有批次都有同名实施记录，且只记录实际结果。
- 容量报告明确记录可扩容组件、状态单点、第一瓶颈和超容量行为。
- 支持边界仍为 Linux `amd64` Docker Compose，不宣称生产 HA。
- 只有在本阶段证明多副本、背压和故障隔离成立后，才重新评估 Kubernetes。
