# Phase 18：高并发与可观测架构收敛总实施方案

> 规划基线：2026-09-26，`upstream/main=76c8169`，根 `VERSION=2.0.1`。
>
> Phase-18-01 已交付负载工具和失败诊断，但没有证明容量基线通过。
>
> 本版废止旧 Phase-18-02～18-09；旧分支、receipt 和原始数据只作历史输入。

## 1. 阶段目标

GoPulse 保持“高并发业务系统 + 内建可观测系统”定位，不增加业务域。

- **P0**：修复已确认的 Outbox 第一瓶颈，证明短时容量、多副本正确性、双 Elasticsearch
  故障隔离和代表性背压。
- **P1**：建立不依赖可观测数据面自证的健康通道，并收敛公共机器合同。
- 最终只用一次有界验收确认容量和观测 ES 跨边界故障恢复；替换与其他依赖结果由前序批次负责。

本阶段只证明记录环境中的 Compose 能力，不宣称通用生产容量或高可用。

## 2. 执行原则

1. **先处理已有结论**：Phase-18-01 已明确 Outbox 是第一瓶颈；不得再次运行三轮基线来重复发现它。
2. **证据服务于决策**：出现第一个可行动瓶颈即停止场景，修产品或修订计划，不继续收集同类数据。
3. **验收基础设施不是产品批次**：不得新增通用 runner、heartbeat、receipt 平台或 observer 框架。
   批次脚本只能薄编排现有命令并输出摘要。
4. **正式运行从入口启动即计数**：不带 `--preflight-only` 的批次入口一旦启动，环境、验收工具或
   产品失败都消耗一次；不得删除 work directory 后重算。
5. **Phase-18-02～18-05 每批最多两次正式运行**：第一次失败后只允许一次最长 15 分钟的定向动态诊断；
   产品失败必须有新产品候选才能运行第二次；验收基础设施失败可在修复工具后用同一产品候选运行第二次。
   第二次失败时，无论原因是否相同，批次立即以 incomplete 结束。
6. **Phase-18 只允许新增一个补救批次**：Phase-18-02 归档为 incomplete 后，最多新增一个
   `Phase-18-02R` 补救批次；补救批次只能进行一次不带 `--preflight-only` 的正式运行。补救批次再次失败时，
   Phase 18 直接结束为 incomplete，不再新增批次。
7. **Phase-18-06 只允许一次正式运行**：失败后不得在本批修复再跑，必须回到 `update` 新增修复批次。
8. **候选不能靠证据变更刷新**：新产品候选必须包含产品代码、运行配置或依赖的实质修改，并产生新的
   commit、manifest 和相关 image digest。只修改文档、timeout、验收脚本、摘要或 receipt 不产生新产品候选。
9. **预检和条件先冻结**：正式运行前固定场景、输入、样本数、阈值和 deadline。批次入口必须提供
   `--preflight-only`；预检最多执行两次、不得启动产品场景，但耗时计入累计预算。第二次仍失败则批次结束。
10. **总时限是累计硬约束**：表中累计预算包含预检、正式运行、定向动态诊断、证据整理和清理。
   启动下一项前，剩余预算必须覆盖该项完整上限；不足则直接 incomplete，不允许启动后靠 timeout 截断。
   达到预算立即结束批次，不加时、不后台等待、不通过修改方案清零。
11. **不以共享宿主扩容比作为正确性门禁**：吞吐增益只记录；多副本门禁是流量分发、所有权、替换和无丢失。

任何批次若需要扩大为新框架、增加未计划矩阵或超过时间预算，必须以 incomplete 停止；如需继续，
只能在本方案中新增后续批次和版本，不得扩写当前批次后继续计时。

## 3. 参考输入与容量边界

- 固定 seed：`18002005`；沿用 Phase-18-01 已生成的数据配方与负载分类。
- 参考宿主：Linux `amd64`、8 vCPU、12 GiB RAM、8 GiB swap、Compose v2。
- 正式容量窗口：150 RPS 稳态，300 RPS 突发；负载器不得成为第一瓶颈。
- 核心观测：请求错误与 P95/P99、Outbox pending/oldest age、Rabbit depth、Kafka lag、
  sink 收敛、CPU/RSS/OOM 和 swap 增量。
- Phase-18-01 的 404 修复、少量未定位 500、Outbox 持续增长和未收敛恢复是本阶段输入，
  不是通过证据。

## 5. 批次闭环

### Phase-18-01：历史失败诊断

保留数据配方、负载工具、失败报告和排查记录。该批只说明“发现了什么”，不满足 P0 容量门禁，
不再补跑三轮或修补历史 evidence。

### Phase-18-02（P0）：先修 Outbox

- 用最长 5 分钟重现或核对 Outbox 发布能力，确认根因后立即停止。
- 只修改 Outbox claim/publish/lease、必要配置与对应指标，不顺带做全链路调优。
- Phase-18-02 已归档为 incomplete；本次只执行 `Phase-18-02R`，工具修正只做局部验证，未执行过正式验证。

### Phase-18-02R（P0）：唯一补救批次

- 只采用已记录的最小工具修复和必要产品修复，绑定补救批次自己的候选、manifest、digest 和 evidence。
- 预检最多执行两次；不带 `--preflight-only` 的正式入口只能启动一次，明确称为新补救批次的唯一一次运行。
- 该唯一一次运行已失败（`steady_pending_bound`、`event_state_check` 未通过）；Phase 18 直接结束为
  incomplete，不再新增批次。

### Phase-18-03（P0）：多副本正确性

- 交付 Backend×3、Worker/Indexer/Router/Marshaller×2、Monitor×1 和 Kafka 至少 4 partitions。
- 每个可扩容组件只做一个逐实例替换场景，证明存活实例继续推进、替换实例重新加入。
- 拒绝越权提交、重复持久副作用或已接受数据静默丢失；不设置 `1.3x` 吞吐门槛。

### Phase-18-04（P0）：隔离与代表性背压

- 业务搜索 ES 与 Logs/Events ES 使用独立服务、卷、凭据和资源边界。
- 只验证 clean 启动、直接前序迁移和两个 ES 的交叉停机，不做多版本迁移矩阵。
- 背压只选三个代表场景：HTTP 过载、Rabbit 积压、Kafka/Marshaller sink 积压。

### Phase-18-05（P1）：独立健康与合同

- lifecycle 直接检查运行时和依赖，提供一个正常 canary 和一个观测数据面不可用 canary。
- Envelope、日志、指标和 API error 以机器可读 catalog 为唯一手编辑来源，并做确定性生成/漂移检查。
- 不新增常驻 watchdog、监控平台或故障矩阵。

### Phase-18-06：最终收口

- 同一候选只执行一次 30 分钟 150 RPS 稳态和一次 300 RPS 突发。
- 唯一故障场景为：稳态业务流量持续时停止观测 ES，确认业务搜索继续服务、独立健康准确报错，
  恢复后 Logs/Events 在固定期限内收敛。
- 不重复实例替换、六依赖故障、历史迁移或 Phase-18-02～18-05 的完整场景。

## 6. 阶段验收线

1. 150 RPS 稳态非预期错误、超时和连接失败总和不超过 1%；读 P95/P99 不高于
   500 ms/1.5 s，写 P95/P99 不高于 800 ms/2 s。
2. 300 RPS 突发的明确 `server_overloaded`/`Retry-After` 拒绝不超过 5%；不得 OOM、挂死或伪成功。
3. Outbox 和消息链路积压有硬上限；压力解除后在批次规定窗口内恢复，已接受数据无静默丢失。
4. 多副本替换无越权提交、重复持久副作用或持续中断；Monitor 保持单所有者。
5. 任一 Elasticsearch 停止时，另一数据面仍可工作；恢复后新旧数据可查。
6. 可观测数据面不可用时，独立健康输出和本地 canary 结果仍可获得。
7. 公共合同可确定性生成，手工漂移会被门禁拒绝。
8. Phase-18-02～18-06 均有同名实施记录，最终根 `VERSION=2.0.6`，无阻断项。

## 7. 证据与停止规则

Git 只保留：

- 同名实施记录；
- 一份脱敏摘要 JSON，包含 product candidate、正式运行序号、累计耗时、环境、场景、结果和原始附件 SHA-256；
- 必要的小型失败摘要。

完整日志、采样流、压测原始结果和打包附件存放于 GitHub Actions Artifact，不提交到 Git。
单个摘要不能证明的内容，应链接原始附件及其 checksum，而不是复制数万行数据。

以下任一情况立即停止当前正式验收：

- 得到首个可行动产品瓶颈；
- 场景超时、环境不满足或观测工具本身失败；
- 正式运行次数或批次累计时间达到上限；
- 需要降低门槛、扩大矩阵或新增通用验收框架才能继续。

停止后记录事实和下一次最小动作，不用新的长跑掩盖失败。已经消耗的运行次数和累计时间写入实施记录；
修改方案、分支、work directory 或失败分类均不得清零。Phase-18-02 之后只允许 `Phase-18-02R` 这一个补救批次；
补救批次已失败，Phase 18 直接结束为 incomplete，不再新增批次。

## 8. 通用完成检查

每个拆分方案必须列出最小受影响测试、一个批次专用动态入口、版本/分支检查和 `git diff --check`。
动态入口须有外部 timeout，且只清理当前 Compose project；禁止 Docker 全局 prune。

批次完成前在 `dev/logs/Phase-18/` 创建同名记录，只写实际改动、实际命令、结果、偏差和后续项。
只有该批全部条件通过，才更新 `VERSION` 到目标版本。
