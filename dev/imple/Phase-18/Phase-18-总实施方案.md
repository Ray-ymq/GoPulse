> 初始规划基线：2026-09-26，`upstream/main=97b8226`。
>
> 扩展规划基线：2026-09-27，`upstream/main=ce08b1b`，根 `VERSION=2.0.2`。
>
> Phase-18-01/02 已完成并保持历史原貌；根据 2026-09-27 的明确规划决定，原先取消且从未创建的
> Phase-18-03～18-05 重新分配，用于完成多副本、故障隔离、背压和独立诊断。

## 1. 阶段目的

Phase 18 在同一 `2.0.x` 版本线完成两类交付：

1. Phase-18-01/02 记录单副本容量边界并交付已定位的 Outbox 调度修复；
2. Phase-18-03～18-05 把边界转化为计算层多副本、业务/观测存储隔离、显式背压、
   独立诊断和机器合同闭环。

本阶段的验收目标是取得完整、不可筛选的事实，不要求所有性能或正确性目标达到预设阈值。
有效的成功、失败、退化或基础设施错误结果都必须被保留，并在完成固定次数后结束批次。

## 2. 统一结果语义

| 结果 | 含义 | 批次动作 |
| --- | --- | --- |
| `target_met` | 两次证据表明目标达到 | 记录事实，完成批次并更新版本 |
| `boundary_found` | 两次证据表明目标未达到或产品存在问题 | 记录边界，完成批次并更新版本 |
| `execution_failed` | 命令、候选或验收基础设施失败，但失败阶段、退出码和原始输出完整 | 记录失败，完成批次并更新版本 |

版本更新只表示“该批固定实施与验收动作已完成”，不表示目标一定达到。报告必须同时展示结果类型，
禁止将 `boundary_found` 或 `execution_failed` 描述为能力通过。

只有以下情况不允许声称批次完成：没有执行两次、证据被覆盖/丢失、候选绑定无法识别，或者实际
修改文件不在拆分方案的文件验收清单中。这些属于流程未完成，而不是测试失败。

## 3. 有且只有一次重复规则

### 3.1 固定次数

- 每个拆分方案列出的**最终验收单元**总共执行两次：首次执行一次，再以完全相同条件重复一次。
- 两次必须绑定同一 candidate version、revision、manifest/image digest、数据配方、实例数、资源配额、
  配置、故障顺序和验收程序 commit。
- 不允许第三次运行，不允许因一次失败而替换 candidate、放宽阈值、换 seed、挑选较好结果或补跑。
- `run-1` 的失败不得让 runner 提前跳过 `run-2`；runner 先保存失败与清理结果，再在相同条件下执行
  唯一一次重复。只有归属或清理失败使继续执行不安全时才停止，并明确记录流程未完成。
- 开发期的低层诊断不计入最终验收次数；它不得被纳入最终均值，也不得替代两次固定验收。

### 3.2 结果合并

- 数值指标保留两次原值，并按同名指标计算算术平均值 `(run_1 + run_2) / 2`。
- P50/P95/P99、错误率、吞吐、资源峰值、队列峰值和恢复时间分别按名称取两次结果的平均；
  不把两次原始样本混成一次新的分位数。
- 确定性检查不伪造平均值，记录为 `2/2`、`1/2` 或 `0/2`，并保留两次退出码与输出摘要。
- 两次结果分歧本身就是边界；不得启动第三次运行消除分歧。

### 3.3 Evidence

每个最终验收单元必须生成：

- `run-1/` 与 `run-2/` 两个只写一次的原始证据目录；
- 同一候选与条件的 binding/receipt；
- `summary.json`，包含两次原值、算术平均、确定性检查计数和最终结果类型；
- 失败阶段、退出码、日志路径和清理结果；
- 实施记录中的实际命令、两次结果和未达到项。

## 5. 历史批次结论

### 5.1 Phase-18-01

- 交付确定性配方、负载器、资源取样和失败证据。
- 历史三轮不能证明稳定承载 `150 RPS`，不得重放或补造通过证据。
- 该批运行次数不计入 Phase-18-03～18-05 的两次固定验收。

### 5.2 Phase-18-02

- 交付满批后立即继续 claim 的 Outbox 修复及最小测试。
- 容量结果保持 `boundary_found`，根版本已更新为 `2.0.2`。
- 多副本、事件闭合、双 Elasticsearch、背压、独立健康和合同单一来源转入后续批次。

## 6. Phase-18-03～18-05

### 6.1 Phase-18-03：业务计算层多副本与异步闭合

- Backend、Business Worker、Search Indexer 支持至少两个副本。
- 同一会话跨 Backend 副本工作，不依赖粘性会话。
- Outbox 多 owner、RabbitMQ 多 consumer、告警租约、ack/requeue 和搜索投影保持正确边界。
- 连接池、prefetch、in-flight、队列和关闭预算有显式总量/每副本上界。
- 补齐 accepted event → Outbox → RabbitMQ → 最终业务投影的闭合证据。
- 全栈 Compose 权威闭合门禁与单一 Frontend 宿主入口一致：Backend 不发布宿主端口。

文件级验收、两次验证单元和完成条件见
[`Phase-18-03`](Phase-18-03-业务计算层多副本与异步闭合.md)。

### 6.2 Phase-18-04：可观测计算层多副本、双 ES 与背压隔离

- Router、Marshaller 支持至少两个副本；多 partition Kafka 允许两个 group member 同时活跃。
- generation ownership、手动 offset、永久坏记录继续和存储成功后提交语义保持。
- 业务搜索 Elasticsearch 与 Logs/Events Elasticsearch 使用独立服务、卷、地址和网络边界。
- Metrics、Logs、Events 目标级故障互不形成全局阻塞；队列满和远程失败有明确、有界行为。
- 每个 Router/Marshaller 副本都具有可区分的日志、指标和处理证据。

文件级验收、两次验证单元和完成条件见
[`Phase-18-04`](Phase-18-04-可观测计算层多副本双ES与背压隔离.md)。

### 6.3 Phase-18-05：合同单一来源、独立诊断与完整矩阵收口

- 一个权威机器合同覆盖进程角色、副本能力、监听器、探针、依赖、预算与关停语义。
- 每个实例可脱离 Monitor → Router → Kafka → Marshaller → 存储链路接受直接诊断。
- 冻结候选执行两次完整扩缩容与故障矩阵，生成逐次证据与两次平均摘要。
- 无论两次结果为达到目标、发现边界或执行失败，只要证据与文件清单完整，就更新 `2.0.5`
  并以相应结果类型关闭 Phase 18。

文件级验收、两次验证单元和完成条件见
[`Phase-18-05`](Phase-18-05-合同单一来源独立诊断与完整矩阵收口.md)。

## 7. 文件级验收规则

- 每个拆分方案必须列出本批允许新增或修改的每个文件，以及该文件独立可检查的验收条件。
- 同一行可以覆盖成对的源文件/测试文件，但不能使用 `backend/**`、`scripts/**` 等无限通配范围。
- 发现必须修改清单外文件时，先在 `update` 修订总方案与拆分方案；不得在开发分支事后补登记。
- 实施记录按实际文件逐行标记 `changed`、`not_needed` 或 `deviation`，并引用对应验证证据。
- 版本元数据文件作为一个封闭集合验收；实施记录仍须列出其中每个实际变更文件。

## 8. 阶段完成条件

1. Phase-18-03、18-04、18-05 分别只执行各自定义的两次最终验收，没有第三次筛选运行。
2. 每批的文件验收清单、两次原值、平均值、确定性结果计数和失败输出完整。
3. 每批不论结果类型均按固定顺序创建实施记录、同步版本元数据并提交。
4. Phase-18-05 记录已证明、未证明和未达到能力，不能用版本号代替能力声明。
5. 完成后停止 Phase 18；容量认证、状态层 HA、Kubernetes 与 SRE 使用未来新规划，不追加 18-06。

## 9. 非目标

- MySQL 主从、Redis Sentinel/Cluster、RabbitMQ quorum 集群、多 broker Kafka、
  Elasticsearch 集群或 VictoriaMetrics cluster。
- Kubernetes、HPA、Service Mesh、跨地域、多活、生产 TLS/SASL 或外部告警。
- 新业务功能、Backend 微服务拆分、一般代码审计、依赖升级或无证据性能调参。
