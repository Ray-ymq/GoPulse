# Phase 22 总实施方案：本机开发与测试流程简化

> 状态：待实施。日期：2026-10-07。当前完成版本：`2.3.3`。
> 用户已授权实施本方案；规划先在 `update` 提交并以 merge commit 合入 main，再依次执行四批。

## 1. 阶段结果

日常改代码时在本机运行 Go/Vite，Docker 只提供所需持久依赖；普通测试直接使用 Go、Vitest、Playwright。容器部署、容量、恢复和发布检查保留独立入口，只有相关改动或实施合同要求时运行。

复用已支持的 host/combined 模式作为本机单实例便利环境；不改变正式 business/platform 分离部署、业务 API、权限、消息或正式证据合同。架构依据为冻结的两篇设计及落地大纲；不修改这三个文件，不重写 Phase 21 或历史证据。

## 3. 接口与共同约束

| 接口 | 行为与完成批次 |
| --- | --- |
| `make dev` | 01：复用开发依赖；本机单实例 Backend、Worker、Indexer、用户 Vite；关闭 Trace/告警评估 |
| `make dev-observe` | 01：增加 Kafka、VM、观测 ES、Router/Marshaller、管理 Vite；Monitor 使用固定 Linux 容器 |
| `make test MODULE=backend` | 01：指定 Go 模块运行 go test；指定两个前端之一运行 npm test；未知模块失败 |
| `make integration` | 02：独立测试项目/数据卷，运行真实依赖集成测试；串行 Go 包，避免共享队列互扰 |
| `make e2e` | 03：测试项目上的源码应用与现有业务 Playwright；不连接开发数据库 |
| `make stop` | 01：停止本工作树启动的本机进程与依赖容器，保留命名卷 |
| `make monitor-image` | 01：显式首次准备或修改 Monitor/插件后，仅构建 Monitor 开发镜像；日常入口不隐式构建 |

新增入口只是环境准备与命令转发，不建立通用 runner/证据框架。新增本机助手的必要性：现有 dev/down 仅管理完整容器栈，不能管理本机进程、源码二进制与独立测试配置；保持旧入口和历史 CLI 兼容。Python 标准库承担可移植的环境解析、归属核对、进程启动/有界退出；测试断言留在原生测试模块。

源文件及配置相同则复用本机二进制和 Go/npm 缓存；重启不要求当前 HEAD 对应全部镜像。所有日常入口禁止 build/push/Bundle；Monitor 镜像准备是独立显式命令。依赖采用已有固定版本，开发/测试项目名、数据卷和端口不同；仅 loopback 发布。端口冲突、子进程退出、错误配置明确失败，禁止全局 prune、杀其他进程或删除其他项目卷。

官方插件保持 Linux 信任与制品合同；macOS 不扩展插件平台支持。容器内 Monitor 用受控 host 访问本机 Router/组件；本机进程保持 loopback。Linux 采用 host 网络的独立 Monitor 服务配置。插件特殊验收及正式分离角色验收继续使用既有容器工具。

## 5. 成本、证据与停止

每批预计 120 分钟、累计上限 180 分钟，无长时实验；各阶段预算、固定命令、实验单元及精确文件见分方案。诊断和清理均计入原预算；同一原因最多两次、每次 10 分钟。90/144 分钟报告进度，剩余预算不足以执行和安全清理时不启动新命令。

首次基础设施失败停止整组，保存失败边界，用最小复现修正后只重验受影响项。达到诊断/时间停点保留实际改动、passed/failed/not_started、源码/config/tool/环境身份和归属清理，批次保持未完成；接续须修订有限剩余预算并由用户明确继续。已通过且相关输入未变的检查不重复；原始历史回执不换绑。
