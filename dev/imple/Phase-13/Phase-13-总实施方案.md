# Phase 13：业务基础系统与 X 风格用户端闭环总实施方案

> 当前状态：原 5 个批次已通过 PR #114–#118 合入 `main`（最终版本 `1.10.5`）；追加 Phase-13-06 Review 整改已验收，完成版本 `1.10.6`，待合入（2026-09-08）。本文档于 2026-09-07 基于主远程 `origin/main` 提交 `036de42`、规划远程 `origin/update` 提交 `1223ab5` 与已完成产品版本 `1.9.4` 编写。Phase 13 使用 `1.10.x` 版本线，原拆分为 5 个执行批次，追加 1 个 Review 整改批次。本文档是 Phase 13 批次顺序、目标版本和开发分支的唯一权威来源；实际开工时每个批次仍须 fetch 主远程并从最新 `origin/main` 创建对应 `develop/x.x.x` 分支。

## 1. 阶段目标

在 Phase 12 已容器化的用户、帖子、评论、点赞、通知和帖子搜索基础上，补齐一个参考 X 信息架构、但主动收缩产品范围的基础社交业务闭环：

```text
用户资料与用户发现
  → 关注 / 取消关注
  → Following 信息流与关注通知
  → 仅本人可见的关注、粉丝和收藏列表
  → 作者编辑帖子
  → 缓存与搜索收敛到最新内容
  → 作者二次确认后永久删除
  → 依赖数据清理、搜索删除、缓存不可复活、历史通知墓碑化
```

阶段完成必须同时证明：

- 登录用户名继续作为稳定身份；用户可以维护显示名称和个人介绍，并可按用户名或显示名称被发现。
- 关注关系具备权限、并发幂等和隐私边界；Following 只返回当前用户已关注作者的帖子，新增关注进入通知中心，取消关注不产生通知。
- 收藏状态和收藏列表仅属于当前登录用户，不进入公共计数或共享缓存投影。
- 只有作者可以编辑或永久删除帖子；编辑后的详情、列表、缓存和搜索结果最终一致，删除后的陈旧缓存或乱序事件不能让帖子重新可见。
- 历史通知在关联帖子删除后继续可解释，但不再提供失效链接、帖子标题或正文。
- 独立用户端形成首页、Following、搜索、通知、收藏、资料、帖子详情与作者管理主路径；现有管理员可观测界面不被 Phase 13 的视觉重构波及。
- 全部能力在 Phase 12 的 Compose 产品环境中验收，不以 Kubernetes 为前置条件。

只完成数据库表、只提供 API、只制作静态页面、只在 happy path 下编辑/删除，或依赖人工清 Redis/Elasticsearch 才能收敛，均不构成 Phase 13 完成。

## 2. 产品范围与非目标

### 2.1 本阶段交付

- 用户资料：`display_name`、`bio`、公开资料页、用户发布的帖子。
- 用户发现：按登录用户名或显示名称搜索用户；从搜索结果、帖子作者和资料页进入用户资料。
- 关注：关注、取消关注、Following 信息流、关注通知、本人关注/粉丝列表。
- 收藏：收藏、取消收藏、本人收藏列表、所有帖子 DTO 的 `bookmarked_by_me`。
- 帖子编辑：作者更新标题和正文、记录明确的最后编辑时间、缓存与搜索投影收敛。
- 帖子永久删除：作者二次确认、依赖关系清理、缓存/搜索删除、历史通知墓碑化。
- 用户端 UI：X 风格的信息架构、时间线密度、导航和反馈，同时保留 GoPulse 品牌色与标题/正文内容模型。

### 2.2 明确不做

- 图片、视频、音频、头像上传或其他媒体能力。
- 私信、转发、引用、分享计数、话题、趋势、推荐算法、“为你推荐”、广告、付费或创作者体系。
- 私密账号、关注审批、拉黑、举报治理、公开任意用户的关注/粉丝列表。
- 帖子历史版本、软删除、回收站、恢复、管理员代编辑/代删除。
- 管理端视觉重构、告警体系、插件扩展或 Kubernetes 部署。
- 大型 UI 组件库、复制 X 商标、Logo、专有图标、文案或像素级品牌资产。

范围外需求记录为 Phase 14 或后续候选项，不扩展当前批次的验收合同。

## 3. 当前基线与关键约束

- MySQL 当前包含 `users`、`posts`、`comments`、`post_likes`、`business_outbox` 和 `notifications`；用户尚无显示名称/个人介绍，帖子尚无明确 `edited_at`。
- 现有业务事件包括 `comment.created`、`post.liked` 和 `post.created`；通知当前以帖子资源为中心，`post_id` 约束不足以表达关注通知和删除墓碑。
- Redis 帖子详情缓存包含标题、正文、作者和计数，现有缓存命中路径可能绕过 MySQL 帖子存在性判断；Phase 13 不得让陈旧缓存成为已编辑/已删除内容的权威事实。
- Elasticsearch 当前只索引帖子 id、标题、正文和创建/更新时间，查询结果再由 MySQL 水合；编辑和删除必须扩展现有 outbox/indexer 收敛机制，而不是从 HTTP 请求直接双写多个系统。
- Frontend 为 Vue 3、Vue Router、TypeScript、Vite、Vitest 与 Playwright 应用；当前普通用户和管理员入口共用一套偏渐变、圆角卡片的视觉外壳。
- Phase 13 必须建立独立 `UserAppShell` 和用户端样式作用域，继续复用同一 Frontend 构建产物和认证会话，但不得顺带重构 `AdminLayout`、管理路由或管理员可观测页面。
- 数据事实以 MySQL 为权威；Redis 和 Elasticsearch 均为可重建投影。viewer-specific 状态、可变显示名称和权限结果不得被错误固化在跨用户共享缓存中。

## 5. 跨批次实施顺序与依赖

```text
13-01 用户资料 + 用户发现 + UserAppShell
   ↓
13-02 user_follows + Following + user.followed + 通知泛化
   ↓
13-03 post_bookmarks + 私有收藏列表 + 共享/私有投影边界
   ↓
13-04 posts.edited_at/content_revision + post.updated + 缓存/搜索更新
   ↓
13-05 DELETE post + post.deleted + 依赖清理 + 通知墓碑 + 阶段 E2E
```

- 后续批次必须建立在前序批次已合入 `main` 的能力上，并从当时最新 `origin/main` 创建自己的开发分支。
- 每批只修改实现本批闭环所需的数据库、Backend、Worker/Indexer、Frontend 和验证脚本；不得预做后续全部功能。
- 数据库 migration 必须可向前应用并提供对应 down migration；涉及不可恢复的业务删除时，down migration 只恢复 schema，不伪造已删除数据。
- 若实施中发现已有公共接口、持久数据或共享基础设施存在阻断风险，可按记录的具体风险扩展必要回归；不得把一般代码审查、依赖审计或覆盖率提升变成默认门禁。

## 6. 持久数据模型合同

### 6.1 用户资料

- 在 `users` 增加非空 `display_name` 和可空或非空默认空字符串的 `bio`；迁移时以 `username` 回填已有用户的显示名称。
- `username` 继续是不可修改、区分身份和路由定位的稳定字段；显示名称允许重复，不承担授权或唯一身份语义。
- API 层统一对显示名称和个人介绍做 Unicode 字符数而非字节数校验：显示名称 trim 后 1–64 个字符，个人介绍 trim 后 0–160 个字符。
- 资料响应只返回产品公开字段，不返回密码摘要、内部角色细节、邮箱类未来字段或其他敏感数据。

### 6.2 关注关系

- 新增 `user_follows(follower_id, followed_id, created_at)`，以 `(follower_id, followed_id)` 为主键或等价唯一键。
- 为“我关注的人”和“关注我的人”两种游标分页建立与排序匹配的索引；排序以 `created_at DESC` 加稳定 id 组合消除同秒歧义。
- 数据库外键保证用户删除时不残留关系；应用层和数据库约束共同拒绝自己关注自己。
- 同一关注关系的重复或并发创建只产生一条事实和一个 `user.followed` 事件；取消关注幂等且不产生通知事件。

### 6.3 收藏关系

- 新增 `post_bookmarks(post_id, user_id, created_at)`，以 `(post_id, user_id)` 为主键或等价唯一键。
- 本人收藏列表使用 `(user_id, created_at DESC, post_id DESC)` 对应索引和签名/有界游标。
- 帖子删除时数据库外键级联删除收藏；收藏数不作为公共产品字段，不建立公共计数缓存。

### 6.4 帖子编辑版本

- 在 `posts` 增加可空 `edited_at`，首次发布为 `NULL`，每次成功编辑写入最新编辑时间；`updated_at` 可继续服务通用持久化语义，但 UI 只根据明确的 `edited_at` 展示“已编辑”。
- 推荐增加单调递增的 `content_revision`，创建时为 1，每次标题/正文成功变更后递增，用于缓存接受条件、事件去重和乱序防护。
- 不保存历史版本；提交与现有值完全相同的请求应采用明确且可测试的行为，优先视为幂等成功且不产生新 revision/event。

### 6.5 通知资源与删除墓碑

- 通知模型必须同时表达帖子相关通知和纯用户关系通知：`post_id`、`comment_id` 等资源引用按事件类型可空，不能再假设所有通知必有帖子。
- 与可删除帖子/评论的外键采用允许保留通知行的策略，Phase-13-06 最终使用 nullable 列、RESTRICT 外键与活动/完整墓碑形状 CHECK，删除事务先同时清空 post/comment 引用（替代 Phase-13-05 的 `ON DELETE SET NULL`）；删除后通知保留 actor、type、created/read 状态及可解释的墓碑状态。
- 通知响应包含显式资源可用性/墓碑字段。已删内容统一显示“原内容已删除”，不返回失效链接、已删标题或正文。

## 7. API、授权与错误合同

### 7.1 用户资料与发现

- `PATCH /api/v1/users/me/profile`：仅当前登录用户更新自己的显示名称和个人介绍。
- `GET /api/v1/users/:username`：读取公开资料摘要、是否为本人和 viewer 对该用户的关注状态；未知用户返回稳定 not-found。
- `GET /api/v1/users/:username/posts`：读取该用户仍存在的帖子，沿用有界、稳定游标。
- `GET /api/v1/search/users?q=...`：按 username/display name 搜索，限制 query 长度、limit 范围和游标签名；Phase 13 使用 MySQL 有界检索即可，不新增用户 Elasticsearch 索引。

### 7.2 关注与 Following

- `PUT /api/v1/users/:userId/follow`：创建关注；成功新建返回明确状态，重复请求保持关系存在且不重复发通知。
- `DELETE /api/v1/users/:userId/follow`：取消关注；关系不存在时仍满足最终“不关注”状态。
- `GET /api/v1/users/me/following` 与 `GET /api/v1/users/me/followers`：只允许读取当前登录用户自己的关系。
- `GET /api/v1/posts/following`：只返回当前 viewer 已关注作者的现存帖子；不隐式包含本人帖子，除非产品实现明确记录了本人关注自己，而本方案禁止自关注，因此本人帖子不进入 Following。
- 不提供 `/users/:id/followers`、`/users/:username/following` 等任意用户公开关系列表端点。

### 7.3 收藏

- `PUT /api/v1/posts/:postId/bookmark`、`DELETE /api/v1/posts/:postId/bookmark`：分别收敛到已收藏/未收藏状态，目标帖子不存在时返回 not-found。
- `GET /api/v1/bookmarks`：只返回当前登录用户收藏且仍存在的帖子。
- 所有面向登录用户的帖子 DTO 增加 `bookmarked_by_me`；该字段在列表、详情、搜索、用户帖子和 Following 中语义一致。

### 7.4 编辑与删除

- `PATCH /api/v1/posts/:postId`：仅作者更新完整标题与正文，沿用帖子创建的长度、空白和内容校验；非作者返回 permission denied，帖子不存在返回 not-found。
- `DELETE /api/v1/posts/:postId`：仅作者永久删除；API 本身不依赖前端确认参数提供安全性，Frontend 必须另外提供不可逆二次确认。
- 认证失败统一 `401 authentication_required`，已认证但无权限统一 `403 permission_denied`，资源不存在统一 `404`，字段错误统一既有验证错误结构；不得通过响应差异泄漏私有关系列表。
- 修改关系、收藏、编辑和删除均使用当前会话身份，不接受 body 中的 actor/owner id。

## 8. 事件、事务与异步收敛合同

| 事件 | 产生事务 | 消费者 | 幂等/收敛要求 |
| --- | --- | --- | --- |
| `user.followed` | 新关注关系与 outbox 同一 MySQL 事务 | Business Worker / Notification | `source_event_id` 去重；重复/并发关注不重复通知 |
| `post.updated` | 帖子内容/revision 与 outbox 同一事务 | Search Indexer；必要缓存失效路径 | 消费时重读 MySQL 当前事实；旧 revision 不覆盖新 revision |
| `post.deleted` | 删除帖子与 outbox 同一事务 | Search Indexer；必要缓存失效路径 | 删除幂等；缺失 MySQL 事实时收敛为删除，绝不重建文档 |

- HTTP 请求不得以“先写 MySQL，再直接写 Redis/Elasticsearch”的无事务双写作为成功条件。
- outbox 事件 payload 只携带定位、版本和必要审计信息；Indexer 以 MySQL 当前事实决定 upsert 或 delete，避免陈旧事件正文覆盖新事实。
- `post.created` 或 `post.updated` 在删除事件之后乱序到达时，消费者发现 MySQL 已无该帖子，必须执行幂等删除而不是重新索引旧 payload。
- 关注通知写入继续依赖通知表 `source_event_id` 唯一性作为最终去重屏障。

## 9. Redis 缓存与 viewer-specific 投影合同

- 共享帖子缓存只保存可跨 viewer 复用的稳定内容和用于验证的新鲜度元数据；`liked_by_me`、`bookmarked_by_me`、关注状态和权限按钮不得写入共享缓存。
- 用户显示名称可修改，不能在长期共享帖子缓存中无限陈旧。实现可选择读取帖子后批量水合作者公开资料，或建立有明确版本/失效合同的用户投影；不得依靠无界 TTL 最终“自然变新”。
- 帖子详情读取在接受 Redis 内容前，必须以低成本权威检查确认帖子仍存在且 revision 与当前事实相符；MySQL 已不存在时直接 not-found，并主动清理陈旧 key。
- 编辑成功后的缓存删除/刷新失败不得使后续详情继续返回旧正文。若失效不是事务性的，读取路径必须用权威 revision 拒绝旧缓存并回源。
- 删除成功后，不论 Redis 删除是否暂时失败，任何列表、详情、收藏、搜索水合都不能返回该帖子。
- 缓存 key/version 变化要可灰度兼容或显式全量失效，不把人工清 Redis 写成发布步骤。

## 10. Elasticsearch 搜索合同

- 帖子创建、编辑和删除统一通过 outbox 驱动 Search Indexer；索引文档至少包含 id、当前标题、当前正文、创建/编辑时间和内容 revision。
- 编辑事件消费时重读 MySQL：存在则以当前 revision upsert，不存在则 delete。删除事件始终幂等 delete。
- 搜索命中必须继续由 MySQL 水合当前帖子事实和 viewer-specific 状态；MySQL 缺失的 hit 被过滤并触发或记录投影清理，不向浏览器泄漏陈旧标题/正文。
- 索引收敛后，新关键词可以命中，只有旧内容才包含的关键词不再命中；删除后索引最终无文档。
- 迁移或 mapping/alias 变化必须使用现有 initialize/reindex 生命周期，保持失败可观察和重复执行安全，不要求人工直接修改 Elasticsearch。

## 11. X 风格 GoPulse 用户端设计合同

### 11.1 设计原则

本阶段定义的风格是 **X-inspired GoPulse**：借鉴 X 的信息架构、时间线密度、导航位置和即时反馈，不复制 X 的品牌、商标、专有图标、营销文案或本阶段不支持的功能。

- 用户端以内容优先、低装饰、连续时间线为主，不再使用大面积渐变背景、浮空阴影和每条帖子独立大卡片。
- 保留 GoPulse 的蓝色强调色和标题/正文模型；帖子标题作为克制的粗体首行，正文随后展示。
- 明亮主题是 Phase 13 唯一验收主题；可预留暗色 token，但暗色模式和主题切换不进入完成条件。
- 只使用 Vue 3、CSS design tokens 和一套可审计的 SVG 图标；不引入大型 UI 组件库。

### 11.2 响应式壳层

- Desktop：三栏布局，左侧导航约 240px，中间主时间线 600–640px，右侧上下文栏约 320px；主时间线有清晰左右边界。
- Tablet：左侧收缩为图标导航，中间主栏保持可读宽度，隐藏右侧上下文栏。
- Mobile：单栏主内容、底部导航和发布 FAB；弹层、编辑和确认在触屏尺寸可完整操作。
- 建立独立 `UserAppShell`、用户端路由容器和样式作用域；`AdminLayout` 及管理页保持现有结构与样式合同。

### 11.3 导航与页面

- 左侧主导航固定为：首页、搜索、通知、收藏、个人资料、发布；管理员可观测入口放入账户菜单，不占普通用户主导航。
- 首页顶部 sticky tabs 为 `全部 / Following`，禁止出现“为你推荐”等未实现算法语义。
- 搜索页提供 `帖子 / 用户` tabs；查询、空状态、加载、错误和继续分页反馈一致。
- 资料页：本人显示“编辑资料”和私有关系列表入口；他人显示“关注/取消关注”。任何他人资料页都不显示可点击的关注/粉丝列表。
- 通知页同时表达评论、点赞、关注和内容已删除墓碑；不可用资源没有详情链接。
- 收藏、关注和粉丝列表均位于登录用户私有路由，直接访问和刷新仍由认证守卫保护。

### 11.4 时间线与交互

- 帖子使用连续行与 1px 分隔线；默认背景 `#FFFFFF`，次级背景 `#F7F9F9`，边框 `#EFF3F4`。
- 文字 `#0F1419`，弱化文字 `#536471`，GoPulse 强调色 `#2563EB`，危险操作 `#F4212E`。
- 帖子动作仅包含评论、点赞、收藏；不显示转发、分享、媒体或其他伪功能。
- 无头像上传时使用稳定的字母头像；头像颜色和文字对比度可访问，不假装提供头像编辑。
- 作者自己的帖子通过明确菜单进入编辑/删除；删除必须使用带帖子识别信息、危险色和“永久删除”文案的第二确认 modal。
- 关注、收藏、点赞等乐观反馈只在失败时可靠回滚并展示错误；禁止仅改变图标但服务器状态失败。

### 11.5 可访问性与可测试性

- 所有图标按钮具有可读 label、键盘焦点和至少 44px 触控目标；tabs、menu、modal 使用正确语义和焦点管理。
- 颜色不是状态的唯一表达；加载、空、错误、禁用和提交中状态均有文本或可访问描述。
- Responsive、sticky header、modal 和关键时间线状态由代表性组件测试/Playwright 路径证明；不追求所有像素快照。

## 13. 阶段级验收标准

### 13.1 业务端到端

在真实 Compose 环境中，以至少两个普通用户和一个已有管理员身份完成：

1. 用户 A 修改显示名称和个人介绍；用户 B 可按用户名和新显示名称搜索到 A，并打开 A 的公开资料和帖子。
2. B 关注 A；重复/并发关注后数据库只有一条关系、一条关注事件对应通知，A 在通知中心看到关注通知。
3. B 的 Following 出现 A 的帖子；B 取消关注后新刷新结果不再包含 A，且取消关注不新增通知。
4. B 收藏 A 的帖子并在本人收藏列表看到；A 或其他用户不能读取 B 的关注、粉丝或收藏列表。
5. A 编辑标题和正文；详情、全部时间线、用户帖子、Following、收藏和搜索水合均显示最新内容及最后编辑时间，旧-only 关键词在索引收敛后不再命中。
6. 非作者 B 编辑/删除均被拒绝。A 通过明确二次确认永久删除帖子。
7. 删除后详情 not-found，评论/点赞/收藏关系已清理，Redis 陈旧 key 不能返回帖子，Elasticsearch 最终无文档；乱序 create/update 事件不能复活该文档。
8. 历史评论/点赞相关通知仍存在但显示“原内容已删除”，无帖子链接且不泄漏已删标题/正文。

### 13.2 UI 与响应式

- Desktop 三栏、Tablet 双栏/图标栏、Mobile 单栏/底部导航主路径可用。
- 首页只有 `全部 / Following`；搜索具有帖子/用户 tabs；操作行只有评论、点赞、收藏。
- 本人/他人资料操作和关系列表隐私表现正确；作者菜单和删除确认具备键盘/焦点/错误状态。
- 用户端达到 X-inspired 的连续时间线和低装饰目标，同时管理员代表性页面未发生结构或视觉回归。

### 13.3 既有能力回归

- 注册、登录、退出、帖子创建/详情、评论、点赞、现有通知读取、帖子搜索继续工作。
- 管理员至少完成 Metrics、Logs、Events、Exporter/Plugin 管理中的方案规定代表性访问，不因用户端壳层、路由或 CSS 作用域而失败。
- Phase 12 Compose build/up/verify/down 生命周期继续成立；纯可观测局部故障不破坏普通用户社交事实。

## 15. 安全、隐私与失败语义

- 关系和收藏列表只能通过 `/me` 语义读取；UI 隐藏不是授权，Backend 必须拒绝或根本不暴露任意用户端点。
- username、target user、post owner、bookmark owner 均从数据库与会话解析，不信任客户端传入身份。
- 并发关注/收藏用唯一约束和事务保证最终状态；不能仅靠“先查再插”。
- 搜索 query、display name、bio、cursor、limit 和 id 参数使用统一边界校验；响应/日志不包含密码摘要、Cookie、token、数据库 DSN 或内部异常细节。
- 删除确认属于 UX 防误触，不替代 Backend 作者授权；网络重试后的结果必须可解释，不产生半删除或重新可见状态。
- Worker/Indexer 暂时不可用时，MySQL 业务事实仍正确，积压可观察并在恢复后幂等收敛；不得静默丢弃事件。
