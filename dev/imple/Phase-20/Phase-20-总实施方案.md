## 1. 阶段目标

围绕现有社交业务与 Metrics/Logs/Events 链路，走完“可信测量 → 单链路解释 → 证据驱动优化
→ 数据生命周期 → 资源预算 → 冻结验收”。交付可以解释正确性、吞吐、尾延迟、异步新鲜度、
恢复和观测成本的工程闭环，不增加业务功能或以部署平台变化替代能力验证。

Phase 19 的 complete / boundary_found 保持历史事实。当前代码可确认恢复检查共享业务与观测
结束条件、Events 必须增长、负载休息窗口与恢复检查窗口不同；这些是本阶段需要核实的测量
风险，不预先认定为产品瓶颈，也不追溯宣布历史验收通过。

## 2. Phase 级能力与集成结果

1. 业务恢复、观测可查询和验收程序运行分别计时、分别归因；每阶梯不受后一阶梯负载污染。
2. “发帖 → Outbox → RabbitMQ → Search Indexer → 搜索可见”具有关联上下文和分段时刻，
   能识别排队、投递、处理、索引与可查询等待；新鲜度测量不等同于 HTTP 响应延迟。
3. 对一个被证据支持的瓶颈形成同条件基线与变更后对照；明确改善、无改善或无需产品优化，
   不为了完成阶段强行修改 SQL、缓存、GC 或消息参数。
4. Logs/Events 的保留、过期删除、迟到数据和删除失败有产品行为；VictoriaMetrics 的原生保留
   配置与实际边界明确；查询和业务索引不受观测清理破坏。
5. CPU、内存、连接、队列、磁盘增长、采样/Trace 开销有机器可读预算和超限行为。
6. 最终同一候选同时验证业务闭合、链路关联、容量、数据生命周期和持续运行的资源变化。

## 5. 测量、对照与证据合同

### 5.1 验收语义

- 沿用 Phase 19 数据规模、业务比例和 50/100/150/200 RPS 作为参考输入，建立独立 Phase 20
  profile；不得覆盖 Phase 19 profile、原始证据或发布摘要。
- 每个重复包含四个阶梯；每阶梯在新归属空项目中物化同一配方，分别预热、测量、恢复和清理。
  总计三个重复、十二个阶梯单元，不增加第四次重复。该隔离用于防止超时积压影响后续阶梯。
- 停止当前阶梯的新请求，最多等待 30 秒收集所有已调度请求的终态，再开始各维度独立的
  120 秒恢复计时。请求终态缺失属于 incomplete；已确认事实/标记在截止时未闭合属于能力边界。
  超时仍保存未闭合项与原始事实，清理该项目后才启动下一阶梯，禁止携带其积压或卷。
- 业务终态按 01 的接受台账、事件集合和最终事实快照逐项核对；编辑以最新 content_revision
  为准，删除以投影不存在为准，幂等无操作不能要求新事件。无法建立关联不算通过。
- 持续采集时按本阶梯水位、标记或已确认消息核对存储和可查询，不要求整个 Kafka group
  在任意瞬间 lag 必为零。Events 门禁必须有确定产生且可关联的真实事件。
- 每个维度记录首次达到时刻及超时原因，不能共享一个超时终点冒充多个独立恢复时间。
- 跨进程时间差记录时钟前提和误差；单进程耗时使用单调时钟。高基数 ID 不进入指标标签。

### 5.2 基线与优化

03 在开工前冻结 mode=optimize 或 mode=verify_only。optimize 的 B0 为包含 02 完成提交的
主线候选，B1 为只增加已登记优化及版本元数据的候选，两者各固定三次重复。
verify_only 只对 B0 执行三次独立复验，不生成 B1 或改善率，符合条件时报告 not_needed。
两种模式都绑定宿主资源预算、配方、负载、采样、Trace 配置与恢复语义。
optimize 执行前冻结主指标、最小有意义改善阈值；两种模式均冻结正确性/错误率/尾延迟/
资源非退化门禁。verify_only 的改善字段为 not_applicable，不要求不存在的 B1。
全部原值、median/min/max/CV 和失败保留，不混合样本伪造分位数、不筛选最好结果。

04/05 的生命周期与预算变更会形成新候选；03 的改善结论只适用于其 B0/B1，
不能直接外推为最终 2.2.5 候选的改善。06 单独证明最终集成能力。

### 5.3 执行状态与能力结论

- execution_status=complete：候选、环境、合同、全部规定运行、原始证据和归属清理完整。
- execution_status=incomplete：工具故障、漂移、证据缺失、归属丢失或不安全清理；批次不能完成。
- 执行完整后容量能力为 target_met 或 boundary_found；边界必须解释，不等于工具错误。
- 03 单独报告 optimization_status=improved|no_improvement|not_needed；
  no_improvement 仅在正确性和非退化门禁通过时可作为实验结论完成，不声明优化成功，
  且按 03 规则撤回实验产品改动。not_needed 不伪造另一个对照候选。
- 关联、生命周期、权限和数据安全等确定性验收必须通过；不能用 boundary_found 豁免缺失实现。
- 发布前严格校验选定脱敏工件与来源 digest，不编辑回执、替换 tag 或复用另一候选证据。

## 6. 验证和回归原则

拆分方案列出已知最小检查与最终固定门禁；文中标注“待实现”的命令属于计划接口，不表示已有工具。
每批只补充证明变更行为的最低有效测试，不重跑相关内容未变化的昂贵矩阵。
03 的产品回归在解锁时据实际瓶颈冻结；05 的最终验收合同冻结后，06 只运行该固定合同。

05 的三种成本比较固定为正常观测 O3-O0、Trace O2-O1、采样器 O1-O3；四组合使用相同
业务负载和独立基准计数器，采样器与压测器分别核算。05 支持受限局部诊断和同候选未开始
单元的检查点恢复，诊断不代替正式三重复；修复后新候选的受影响证据重新执行，旧回执不
改写或换绑。具体执行时限、失败停点、重验登记及必需真实预检以 05 的 2.4 节为准。

每项门禁必须有 case_id、前置条件、操作、预期结果、时限/阈值、原始证据路径和失败分类。
verifier 逐项重算并输出 pass/fail/incomplete，拒绝缺字段、未执行项、错候选引用和只给结论的摘要。
必需真实依赖案例被跳过或没有原始执行结果时不能记为通过；工具自测与真实产品证据分别记录。
03/04/05 的数值依赖前序事实，开工前必须在 update 填完各自冻结表并合入 main；任一必填项
仍为待定、缺省或未绑定证据时不得创建该批开发分支。02 的固定目录、传播及采样配置同样
必须在其开工前登记；这属于合同细化，不允许事后放宽本方案的安全与能力判据。
已开工的 05 记录合同修订及失效范围，保留失败证据和已创建分支，不追溯改写为开工前通过。

阶段验证入口计划为：

- scripts/verify-phase20-diagnostic.sh：恢复语义、事件产生、采样开销及真实有界预检。
- scripts/verify-phase20-chain.sh：单业务链路、重复投递、延迟依赖及观测失败隔离。
- scripts/verify-phase20-optimization.sh：按模式执行 B0/B1 固定对照或 B0 单候选复验。
- scripts/verify-phase20-retention.sh：过期、未过期、迟到、删除失败及归属安全。
- scripts/verify-phase20-budget.sh：预算、超限行为与观测开销。
- scripts/verify-phase20-closure.sh 和 scripts/verify-phase20-evidence.py：最终执行与严格证据校验。

日志采用 dev/logs/Phase-20/ 下与拆分方案相同的 Markdown 文件名。只在实际执行时创建对应
实施记录，记录实际文件、命令、结果、偏差和限制；不预填完成日志。

所有拆分方案共同允许以下封闭完成文件集合：本批同名实施日志、README.md、
docs/capability-status.md、dev/phases/Plan.md、dev/phases/README.md、

## 7. 最终验收与里程碑完成条件

01～05 按拆分条件完成并合入 main。05 冻结构建配方、依赖/第三方镜像 digest、
所有 profile、预算、runtime contract、Trace 配置、生命周期策略、runner/verifier 和脱敏发布清单；
05 不冻结尚未从其完成提交构建的最终自研镜像/Bundle digest。
05 必须先通过其 4.1 节的完整工具交付门禁：正式 U1～U4 路径可执行、正式任务图可 dry-run、
持续运行与真实短预检使用同一 runner、真实 C01/生命周期案例有原始回执、完整 closure 和
publication/source 接口有严格校验。仅有 preflight、单元测试通过或人工填入 pass 不足以解锁 06。
06 从包含 05 完成提交的主线 revision 构建并冻结实际候选 manifest、自研镜像/Bundle digest，
再对该候选执行预检和正式矩阵。05 的预检证据只证明其自身候选，不替代 06 的候选预检。

06 被测版本为 2.2.5，收口版本为 2.2.6；两者分别展示，最终容量正式入口调用一次，
完成三个独立重复。另执行两次独立 60 分钟持续运行，每次使用空项目、同一配方、
同一冻结负载，检查前/中/后资源、磁盘增长、业务终态、观测新鲜度及故障后恢复。
60 分钟证明有限窗口行为，不证明多日稳定或真实经过完整保留期；历史时间 fixture 与真实
时钟证据分别展示，不全局修改宿主时钟。

阶段只有在以下条件满足后完成：

1. 所有确定性能力、数据/权限边界和必需回归通过，六批日志与证据完整。
2. 诊断区分已证明原因、相关现象和未解决项；Trace 能解释一条真实业务链路。
3. 03 完成符合证据的对照或 not_needed 结论，未发生需保留的阻断退化。
4. 生命周期与预算有实际行为和超限结果，最终持续运行证据完整且通过冻结门禁。
5. 最终 execution_status=complete，容量为 target_met 或已解释的 boundary_found。
6. 发布严格核对的脱敏摘要、候选绑定、原值及限制，更新能力清单和 VERSION=2.2.6 并提交。

最终容量边界仍可保留；工具故障或尚未实现的必要能力不能被阶段版本掩盖。
