# Phase-16-05：1.9.4 升级与恢复闭环实施方案

> 执行序号：5 / 6。目标版本`1.13.5`、开发分支`develop/1.13.5`及唯一支持来源以[Phase-16-总实施方案.md](Phase-16-总实施方案.md)为准。

## 1. 批次目标

使用锁定主线`1.9.4`真实Compose产物和数据，建立可重复、可诊断且失败可恢复的直接升级：

```text
1.9.4 / commit 102aa4f...
  → exact source + ownership + schema preflight
  → Phase-16-04 encrypted pre-upgrade backup
  → quiesce/drain
  → current immutable image digests
  → migrations + init + Redis v1 trusted migration
  → one user Frontend → same-origin dual Frontend
  → verify preserved facts/history/session + new operations
  → commit lifecycle version state

failure after persistent mutation
  → restore verified pre-upgrade backup to a new owned project
```

本批不承诺任意历史版本、未知镜像/卷或直接二进制降级。无法精确识别`1.9.4`来源时必须拒绝，而不是尝试“尽力升级”。

## 2. 前置条件

- Phase-16-04已合入最新`upstream/main`，版本`1.13.4`的backup format v1、加密backup、空project restore及跨架构逻辑插件恢复均已通过。
- fetch后从最新主线创建本批分支；升级实现必须复用正式`gopulse backup/restore`，不得创建仅验收使用的另一套数据复制逻辑。
- 锁定来源为提交`102aa4fa9bb5256dfd0733f42454b0ec5deaf043`、根`VERSION=1.9.4`；有界核对其Compose services/volumes、migration最高版本、Frontend route、`user|admin`、JWT/Cookie、Redis v1 package和数据索引契约。
- 从该提交通过当时Dockerfile构建或取得可验证的amd64 image digest，记录revision/label/package archive；不复用来源不明的本地`gopulse/*:1.9.4`tag。
- 确认当前全部migration可从`1.9.4`顺序重跑，Phase 14 Redis v1迁移扩展可识别精确`1.9.4/linux/amd64`包，Phase 15角色migration可处理一个或多个旧admin。

## 3. 实施范围

### 3.1 权威1.9.4 fixture

- 在独立amd64环境从锁定提交启动完整`1.9.4`Compose，不从当前代码创建旧schema，不直接INSERT当前字段，不用mock API伪造历史。
- 通过旧产品公开/operations路径建立至少：两个旧admin、一个普通用户、活动HttpOnly session、用户资料、帖子、评论/点赞、通知、搜索、Outbox历史。
- 启动旧Redis Exporter/Monitor并形成受信v1 plugin version/config/Secret/desired state；产生可区分且时间早于升级边界的Metrics、Logs和Events历史。
- 记录MySQL table/row/hash、RabbitMQ queue、Kafka topic/group/offset、ES alias/index/count、VM series/point和Monitor registry/desired摘要，不记录密码、Cookie值、业务正文或宿主path。
- fixture使用随机强归属project和独立volume，失败/清理不操作日常系统。

### 3.2 来源识别与升级preflight

- `gopulse upgrade`读取旧root version、Compose labels/config digest、image version/revision/source、migration表、volume集合和plugin identity，全部精确匹配支持清单后才继续。
- 未知版本、已部分升级schema、dirty/edited Compose asset、同名非归属resource、缺volume、多container、未知image、损坏plugin或daemon arch错误在任何持久修改前拒绝。
- source支持固定`linux/amd64`；可在Linux amd64或Windows amd64 Docker Desktop Linux containers运行。不存在`1.9.4/linux/arm64`直接来源，不在macOS编造fixture。
- preflight运行旧系统只读verify并生成脱敏before摘要；任何业务事实、必要队列、ES/VM历史或plugin状态无法读取时阻断升级。

### 3.3 强制升级前备份与停写

- 每次升级必须调用Phase-16-04正式backup流程并验证可解密/manifest/digest；用户不能用`--skip-backup`绕过。
- backup路径默认新建且不覆盖，由用户提供passphrase；CLI state只记录backup的非敏感checksum/format，不保存passphrase或明文路径详情。
- backup完成后沿用同一operation identity和排空边界进入升级，避免恢复edge产生新写入；中断前若尚未修改持久事实，可恢复原`1.9.4`运行状态。
- migration开始后不自动启动旧镜像猜测兼容。失败进入`upgrade_failed_after_mutation`，明确要求验证backup restore或由受控自动流程恢复到新project。

### 3.4 数据库、角色与会话迁移

- 运行从`1.9.4`之后到当前的全部幂等migration，记录每步版本/耗时/结果；中断后只能由明确migration状态重试，不手工跳号。
- Phase 13业务表/字段、Phase 14插件相关合同和Phase 15 bootstrap/alerts/audit schema全部建立；重跑migration不重复数据或改变完成事实。
- 全部旧`admin`原位迁移为`super_admin`，稳定选择最小用户ID为不可降级/删除bootstrap，其他管理员保持可管理；普通用户不变。
- password hash、用户ID/创建时间和JWT secret保留。旧session只在原合同允许时继续使用；Backend仍从数据库当前role授权，Cookie不携带新授权事实。
- 升级后公开作者摘要、帖子/评论/search/cache不泄漏role；管理API固定401/403/super_admin成功矩阵通过。

### 3.5 业务、搜索、异步与可观测迁移

- MySQL继续是业务事实；已有资料、关系、帖子、评论、点赞、通知和Outbox行保持。新增Phase 13能力可在升级后正常使用。
- 业务Elasticsearch投影可从MySQL重建并核对旧帖子/作者/删除状态；不得把旧index反向覆盖MySQL。
- RabbitMQ/Kafka沿backup排空后用当前幂等topology初始化；旧已确认事实不重复，升级后新通知/search和新遥测正常收敛。
- 升级前Logs/Events alias历史和VM point在同一旧时间边界前仍可查询；不得用升级后新数据冒充保留。
- Phase 15告警表在旧版本不存在时为空建立；升级后用真实metric/log/event分别完成代表触发/持续/恢复，不直接写incident。

### 3.6 Redis v1插件升级

- 只接受Phase-16-01登记的`1.9.4/linux/amd64`archive/entrypoint digest和已知旧layout；unknown content保留并安全失败，不执行或自动收编。
- 保留旧plugin ID、config/Secret、installed/updated可继承时间和desired state；按现有迁移提交点导入通用active revision，再显式迁移到当前amd64 v2 package。
- desired=running时当前package需health且真实采集后提交；desired=stopped保持stopped。失败恢复旧逻辑事实或进入可解释repair状态，不删volume。
- 其余五类plugin在`1.9.4`不存在，升级后显示可安装但未配置/未运行；不得伪造六插件历史状态。

### 3.7 双Frontend与生命周期state切换

- 旧单Frontend升级为当前user/admin两个独立image和唯一edge；旧合法用户deep link保持或安全重定向，super_admin登录/恢复默认进入`/admin/`。
- upgrade期间edge关闭，完成verify前不对外宣称新版本ready；失败页面只显示固定维护状态，不泄漏内部步骤。
- 完整verify通过后原子写入lifecycle state的version/revision/manifest digest和upgrade report；文件VERSION、container digest和state必须一致。
- 再次执行同目标upgrade返回幂等already-current，不重跑migration、重建plugin或生成第二份成功审计。

### 3.8 失败恢复

- 在image pull后/持久修改前、某个DB migration后、plugin migration提交前后和最终verify失败中选择最小代表中断点；不枚举每条SQL/文件写入。
- 持久修改前失败恢复原`1.9.4`运行状态且before摘要不变。
- 持久修改后失败不运行旧镜像；使用预升级backup恢复到新owned project，验证旧业务/历史/plugin/session基础后再报告恢复完成。
- source project、backup和failed project分别具有独立identity；清理只能删除明确选中的failed/new project，不能自动删除唯一旧数据来源。

## 4. 不在本批范围

- `1.9.3`及更早、`1.10.x`、任意自制tag/镜像、部分手工migration库或未知plugin包的直接升级承诺。
- `1.9.4/linux/arm64`来源、从macOS创建旧fixture或用amd64模拟作为arm64历史支持。
- 在线滚动/零停机升级、双写、自动二进制降级或保留所有历史镜像。
- 新业务、插件、告警、Frontend设计或Phase 17可靠性范围。
- 手工SQL、直接改volume、删除旧project、跳过backup或用验收fixture专用trust bypass。

## 5. 建议实施顺序

1. 冻结`102aa4f...`fixture构建digest、旧schema/compose/plugin契约和before摘要schema。
2. 实现strict source detector和所有Docker/persistent-write前负向self-test。
3. 接入正式backup并实现跨阶段operation state、停写和失败分类。
4. 先完成migration/role/session和业务/search/历史验证，再接Redis v1到当前v2迁移。
5. 启动双Frontend和完整当前stack，验证旧事实/历史与升级后新业务/plugin/三源告警。
6. 验证幂等重跑及代表性pre/post-mutation失败；post-mutation必须通过正式restore返回可用project。
7. 在第二个真实amd64宿主补路径/daemon差异最小升级，更新runbook、版本和实施记录，运行固定门禁后提交。

## 7. 批次验收标准

### 7.1 来源与preflight

- fixture确由`102aa4f...`构建/运行，before数据通过旧公开/operations路径产生，旧image/plugin digest和schema可验证。
- 精确`1.9.4/linux/amd64`来源在持久修改前被识别；未知version/image/compose/schema/resource/plugin各有代表性安全拒绝。
- 每次升级存在可认证解密且digest正确的正式pre-upgrade backup；没有绕过路径，Secret/passphrase不入输出。

### 7.2 升级后事实

- 两旧admin均变为super_admin，最小ID是bootstrap；普通用户、password hash、ID/time和活动session按合同保留，401/403/授权矩阵正确。
- 旧用户/业务/通知/Outbox事实、搜索投影、升级前Logs/Events/VM历史保留或按明确投影规则重建；时间边界证明不是新数据冒充。
- Redis v1 config/Secret/desired state迁移到当前受信v2并真实采集；其他五插件保持未安装，不伪造。
- 双Frontend统一登录、大屏和管理查询可用；升级后新业务、新notification/search、新metric/log/event和三源告警闭环通过。

### 7.3 重跑与失败恢复

- migration和init重跑幂等；再次upgrade到同版本不改变数据、plugin revision或审计数量。
- persistent mutation前中断恢复旧项目；mutation后代表失败通过正式backup恢复到新project，旧source和backup保留。
- failed/new project清理只操作强归属资源，无关Docker/文件/端口快照不变；报告不含Secret或私有path。
- Linux amd64完成完整升级，Windows amd64或第二Linux amd64完成最小重复升级并覆盖不同host path；不把一次运行写成跨宿主完成。

### 7.4 完成条件

上述验收及固定门禁全部通过，无升级/恢复阻断；根与受管metadata为`1.13.5`，分支为`develop/1.13.5`，同名实施记录包含所有真实旧/新摘要和失败轮次。提交后停止，不提前标记Phase 16或三宿主矩阵完成。

## 8. 固定验证命令与回归范围

```bash
(cd lifecycle && test -z "$(gofmt -l .)" && go test -count=1 ./... && go vet ./...)
(cd lifecycle && go test -race -count=1 ./internal/upgrade/... ./internal/backup/... ./internal/ownership/...)
(cd monitor && test -z "$(gofmt -l .)" && go test -count=1 ./internal/plugin/... && go vet ./internal/plugin/...)
scripts/verify-upgrade.sh --self-test
scripts/verify-upgrade.sh --from 1.9.4 --full
scripts/verify-upgrade.sh --from 1.9.4 --repeat-host
scripts/verify-backup-restore.sh --upgrade-recovery
python3 -m unittest discover -s scripts/ci -p 'test_*.py'
python3 scripts/ci/validate_versions.py
python3 scripts/ci/validate_branch.py --branch develop/1.13.5 --base-ref upstream/main
git diff --check
git diff --cached --check
```

- `--full`只在一个amd64host运行完整旧数据、浏览器、plugin、历史、失败恢复矩阵；`--repeat-host`在另一amd64host只重复source/path/migration/plugin和核心事实，避免复制长矩阵。
- upgrade改变migration/plugin/Frontend/全部持久事实，因此固定门禁包含完整产品verify；已在Phase-16-04通过且输入未变的加密tamper全排列不重复。
- 如果旧fixture暴露具体migration缺陷，只增加一条重现和一条成功回归；不扩展为任意历史版本兼容。
- 提交后补充`git diff --check upstream/main...HEAD`。
