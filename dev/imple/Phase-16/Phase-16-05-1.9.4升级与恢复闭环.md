# Phase-16-05：1.9.4 升级与恢复闭环实施方案

> 目标版本：`1.13.5`  
> 开发分支：`develop/1.13.5`  
> 运行与验收平台：真实 Linux `amd64`

## 1. 批次目标

使用唯一可复核的 `1.9.4/linux/amd64` 来源，在真实 Linux `amd64` 产品环境完成：

```text
source validation
  → upgrade preflight
  → mandatory encrypted backup
  → write quiesce
  → ordered migrations
  → atomic target-state switch
  → product verification
  → idempotent rerun / failure recovery
```

升级必须保留身份、业务、搜索、可观测、告警、插件和审计事实，并复用 Phase-16-04 的 backup/restore 合同。

## 2. 前置条件

- 从 Phase-16-04 合入后的最新 `upstream/main` 创建 `develop/1.13.5`。
- 提交 `102aa4f...` 对应的来源、`1.9.4` 受管版本 metadata、fixture checksum 和 Redis v1 legacy 包 digest 可核对。
- Phase-16-04 的 format v1 backup、空 project restore、operation lock、强归属和诊断已通过。
- 目标 `1.13.5` release manifest 与所有 Linux `amd64` digest 可拉取。
- 已确定 `1.9.4` 到当前 schema、角色、会话、业务、搜索、异步、指标和插件的迁移映射。

## 3. 实施范围

### 3.1 权威 1.9.4 fixture

- 使用固定源码、工具链、seed 和 manifest 生成或恢复 fixture。
- 记录源版本、Git revision、Linux `amd64` 架构、镜像/plugin digest、数据规模和 fixture checksum。
- Fixture 至少包含代表用户/管理员、目标、Redis v1 插件状态、历史、告警和审计事实。
- 禁止手工伪造数据库最终状态冒充旧版本运行结果。

### 3.2 来源识别与 preflight

- 读取并交叉校验 state、数据库 schema/version、release metadata 和 fixture digest。
- 只接受明确支持的单节点 Compose 拓扑与 `linux/amd64` 来源。
- 检查目标 digest、磁盘、健康、operation lock、端口和 backup 路径。
- 未识别、已损坏、版本跳跃或不支持拓扑在停写和创建目标资源前拒绝。

### 3.3 强制升级前备份与停写

- 复用 Phase-16-04 生成 format v1 加密 backup，并完成独立 inspect/checksum 验证。
- 备份失败或未完成时禁止进入迁移。
- 进入维护窗口，阻止新写入并排空 Worker、Indexer、告警和插件采集队列。
- 固定源事实摘要作为升级后与恢复后的对照。

### 3.4 有序迁移

1. 数据库 schema 和持久配置。
2. 用户、角色、凭据/session 失效策略和审计链。
3. 业务对象、操作历史和告警状态。
4. Elasticsearch、VictoriaMetrics、RabbitMQ/Kafka 的可重建事实。
5. Redis v1 到 current v2 插件迁移。
6. 双 Frontend、edge 和 lifecycle state。

每步记录 operation id、输入/输出版本、事实摘要和完成标记；重复执行不得重复创建或破坏事实。

### 3.5 Redis v1 插件升级

- 旧包只能来自 Phase-16-01 锁定的 `1.9.4/linux/amd64` legacy catalog。
- 迁移通过正式插件接口完成，转换身份、配置、授权、采集历史和版本意图。
- 目标包从 current Linux `amd64` 受信 catalog 重新物化并真实采集。
- 不在 Monitor 中加入只为 fixture 服务的一次性绕过逻辑。

### 3.6 原子切换、幂等与恢复

- 所有迁移与验证通过后，才原子切换安装 state 和 release manifest digest。
- 同一已升级 installation 重跑返回稳定“无需升级”，不得再次修改数据。
- 在迁移前、数据库后、插件后和 state 切换前设置代表 failure injection。
- 失败时保留源事实、已验证 backup、阶段、恢复命令和脱敏诊断；按明确策略继续或恢复，不能停留在伪 ready。
- 使用升级前 backup 恢复后，源事实必须与对照一致；目标升级 project 也必须能生成新的可恢复 backup。

## 4. 不在本批范围

- 其他历史版本、跨多个大版本、集群/高可用或在线零停机升级。
- macOS、Windows、`linux/arm64` 来源和运行验收。
- 修改 Phase-16-04 的 backup format 或另建升级专用回退格式。
- Kubernetes 数据迁移。

## 5. 建议实施顺序

1. 固定 fixture、source manifest 和事实摘要。
2. 实现来源识别、支持矩阵和 preflight。
3. 接入强制 backup、维护窗口和排空。
4. 实现分阶段迁移、journal 和幂等。
5. 完成 Redis v1 到 current v2 正式迁移。
6. 实现原子 state 切换、失败注入、继续/恢复。
7. 运行完整升级、幂等、失败恢复和升级后 backup 门禁。
8. 更新实施记录和 `VERSION`，提交后停止。

## 7. 批次验收标准

1. Fixture 的来源提交、版本、Linux `amd64` 架构、镜像/plugin digest、数据摘要和 checksum 可复核。
2. 不支持来源在任何停写或资源修改前拒绝，诊断不泄露 Secret。
3. 每次升级前均有完成且通过 inspect/checksum 的 format v1 加密 backup。
4. 升级后用户/角色、业务、搜索、指标、告警、审计和双 Frontend 关键事实保持。
5. Redis v1 通过正式接口迁移到 current v2，并从受信 Linux `amd64` catalog 真实采集。
6. 安装 state 只在全量验证后原子切换为 `1.13.5`。
7. 幂等重跑不改变数据；各 failure injection 可继续或从 backup 恢复，无半升级 ready 状态。
8. 升级后可以继续写入并生成、恢复一份新 backup。
9. 根与受管版本更新为 `1.13.5`，同名实施记录完整且无阻断问题。

## 8. 固定验证命令与回归范围

```bash
scripts/build-legacy-fixture.sh --version 1.9.4 --platform linux/amd64
scripts/verify-upgrade.sh --from 1.9.4 --to 1.13.5 --platform linux/amd64
scripts/verify-upgrade.sh --from 1.9.4 --to 1.13.5 --platform linux/amd64 --idempotent
scripts/verify-upgrade.sh --from 1.9.4 --to 1.13.5 --platform linux/amd64 --failure-matrix
scripts/verify-backup-restore.sh --platform linux/amd64 --post-upgrade
scripts/verify-compose.sh
```

若真实脚本名不同，按同等语义调整并记录。固定门禁使用一个权威 fixture；只有为证明失败恢复所需时才复制最小 project，不增加第二平台或无关历史版本。
