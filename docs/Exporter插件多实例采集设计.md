# Exporter 插件多实例采集设计

> 文档状态：未来设计，当前不实施。
>
> 当前边界：[Phase 13](../dev/phases/Phase-13-跨平台产品化与插件扩展.md) 允许多种 Exporter 插件并行，但每种插件只运行一个实例，一个实例只采集一个目标。本文档不改变当前实现或 Phase 13 的范围与验收标准。

## 1. 先用一个例子说明

假设未来一套 GoPulse 需要同时观察两个 Redis：

- `redis-business`：业务缓存。
- `redis-session`：会话缓存。

两者都使用同一种 Redis Exporter 程序，但连接地址、密码、采集状态和生命周期不同。多实例能力的目标是：

```text
一个 Redis Exporter 插件包
    ├── redis-business 实例 → 业务 Redis
    └── redis-session  实例 → 会话 Redis
```

其中一个 Redis 不可用时，另一个 Redis 的采集不应被停止，管理员也应能在页面上分清两者。

## 2. 三个需要分清的概念

| 概念 | 含义 | 例子 |
|---|---|---|
| 插件包 | 可安装、验证和升级的程序制品 | `redis-exporter` 2.0.0 |
| 插件实例 | 使用某个插件包创建的独立运行单元 | `redis-business` |
| 采集目标 | 插件实例真正连接和观测的组件 | `redis:6379` |

三者的关系是：

```text
插件包 1 ──创建──> N 个插件实例
插件实例 1 ──采集──> 1 个采集目标
```

本设计中的“多实例”是指同一个插件包可创建多个独立实例，不是让一个庞大进程同时管理无限目标。

## 3. 为什么当前先做单实例

单实例可以先验证每一种组件的核心采集能力，不需要同时引入以下复杂度：

- 多份目标配置和密钥存储。
- 多进程、多端口和资源上限管理。
- 实例级启动、停止、重启和故障隔离。
- 指标、日志和事件中的实例身份区分。
- 页面上的实例列表、配置、筛选和状态展示。
- 插件包升级时多个实例的顺序、失败与回滚。

因此，当前阶段可以增加多种插件，但每种插件仍只创建一个实例。等插件包、配置、Secret 和生命周期契约稳定后，再实施多实例。

## 4. 设计目标

未来实施多实例时，应达到以下结果：

1. 同一种 Exporter 可同时采集多个同类目标。
2. 每个实例拥有独立的配置、Secret、运行状态和错误状态。
3. 一个实例失败不影响其他实例、Monitor 或社交业务。
4. Metrics、Logs 和 Events 可明确追溯到具体实例，又不泄漏内部地址或凭据。
5. Monitor 重启后能按持久化的期望状态恢复每个实例。
6. 插件包更新失败时不留下半升级状态，并有可解释的回滚结果。
7. 管理员可以在页面上看懂“安装了什么插件”和“正在采集哪些目标”。

## 5. 非目标

本设计不默认扩展到：

- 一个插件实例同时采集多个目标。
- 运行未受信的第三方代码或建设公开插件市场。
- 自动扫描网络并发现所有可采集服务。
- 跨 GoPulse 集群统一调度插件实例。
- 无限制地创建实例。
- 因多实例而改变 Exporter 被动拉取、不保存历史的职责边界。

## 6. 总体结构

```text
管理员页面
    ↓
Backend（认证、admin 授权、安全 DTO）
    ↓
Monitor Plugin Manager
    ├── 插件包管理
    │     └── redis-exporter 2.0.0
    └── 插件实例管理
          ├── redis-business → 独立进程 → 业务 Redis
          └── redis-session  → 独立进程 → 会话 Redis
```

推荐每个实例使用独立进程。这会增加一定内存占用，但可以获得清晰的故障、资源、启停和 PID 归属边界，也与“一个插件故障不影响其他采集”的初衷一致。

## 7. 数据与身份

### 7.1 插件包记录

插件包记录只描述制品本身，例如：

- `plugin_id`：插件类型的稳定身份。
- `name` 与 `version`：名称和已安装制品版本。
- `kind` 与 `source`：插件类型与采集源。
- 平台、架构、入口文件和完整性校验信息。
- 实例配置 Schema 的版本。

插件包记录不保存具体目标地址和目标密码。

### 7.2 插件实例记录

每个实例至少需要：

- `instance_id`：机器可读的稳定唯一标识，创建后不变。
- `display_name`：供管理员辨认的名称。
- `plugin_id`：该实例使用的插件包。
- `config_revision`：非敏感配置的修订号。
- `secret_ref`：指向该实例专用 Secret，不是密码明文。
- `desired_state`：管理员期望的 `running` 或 `stopped`。
- `observed_state`：实际的启动中、运行中、已停止或失败等状态。
- 最近启动、采集、成功和安全错误时间。

### 7.3 运行事实

运行时为每个实例保存独立的进程归属记录，例如 PID、启动标识和经验证的执行文件路径。这些是 Monitor 内部事实，不通过公开 API 返回。

## 8. 配置与 Secret

实例配置应由插件包提供受限 Schema，Backend 与 Frontend 只允许该 Schema 中声明的字段。字段分为：

- 可公开配置：目标别名、采集间隔、超时等。
- 内部配置：组件服务名和端口，只在受控边界内使用。
- 敏感配置：密码、Token、TLS 私钥等，只写入 Secret 存储。

管理员可以替换 Secret，但页面和 API 不得重新显示原始明文。状态、事件、日志和支持诊断包也不得包含这些内容。

## 9. 进程、端口与采集调度

### 9.1 进程边界

- 每个运行中实例拥有独立子进程和独立运行目录。
- Monitor 启动前必须验证实例使用的插件包、配置和 Secret 引用。
- Monitor 只停止已证明由自己管理的进程，不根据一个未验证的 PID 直接发信号。
- 实例退出时只修改自己的观察状态，不将整个 Monitor 置为不就绪。

### 9.2 端口分配

Exporter 仍只绑定 Monitor 所在运行边界的回环地址。Monitor 从明确的内部端口段为实例分配端口，并在持久化状态中记录分配结果。

端口冲突不应改用随机对外端口或暴露 Exporter；Monitor 应选择另一个未占用内部端口，或让该实例以安全错误进入失败状态。

### 9.3 采集调度

- 每个实例拥有独立采集周期和超时。
- 同一实例的前一次采集未结束时，不重叠启动第二次采集。
- 不同实例之间加入小幅时间错开，避免在同一时刻集中访问组件和 Router。
- 连续失败的实例可进入有上限的退避，成功后恢复正常周期。
- Monitor 必须有全局实例数和同时采集数上限，避免耗尽本机资源。

## 10. 生命周期

### 10.1 创建实例

1. 管理员选择已安装的插件包。
2. 填写实例名称、目标配置和凭据。
3. Backend 完成 admin 授权和请求结构校验。
4. Monitor 验证配置 Schema、Secret 引用、实例上限和目标地址策略。
5. 连接测试通过后持久化配置，再按期望状态启动。
6. 任一步失败都不留下半创建实例或凭据文件。

### 10.2 启动、停止和修改配置

- start/stop 以 `instance_id` 为作用对象，不影响同一插件的其他实例。
- 修改配置时先验证新配置，再停止旧进程并用新修订重启。
- 新配置启动失败时，默认恢复上一份已验证配置；若恢复也失败，该实例进入 `failed`，其他实例继续运行。

### 10.3 删除实例与卸载插件包

- 删除实例前先有界停止并核对进程归属，再删除实例的配置、Secret 和运行事实。
- 只要某个插件包仍被实例引用，就不允许直接卸载该插件包。
- 不提供“卸载插件包并静默删除所有实例”的破坏性捷径。

### 10.4 更新插件包

插件包更新会影响使用它的所有实例，因此必须：

1. 先校验新插件包和配置 Schema 兼容性。
2. 保存原版本、实例配置修订及期望状态。
3. 按稳定顺序逐个更新实例，不同时停止全部实例。
4. 任一个实例无法使用新版本时，停止继续更新并回滚已切换实例。
5. 回滚后核对每个实例的实际版本、进程归属和状态。

本设计默认同一插件的所有实例使用同一个已安装版本。若未来需要实例长期使用不同版本，必须另行设计。

## 11. Metrics、Logs 和 Events 如何区分实例

每条由插件实例产生的可观测数据都应带有有限、稳定的实例身份：

- `plugin_id`：来自哪种插件。
- `instance_id`：来自哪个实例。
- `target_alias`：管理员可读的受限别名。

目标密码、完整连接串、内网 IP、Secret 名称和本地路径不得成为指标标签或公开字段。`display_name` 可以修改，因此历史关联以不变的 `instance_id` 为准。

为避免时序基数无限增长，`instance_id` 必须由 GoPulse 生成并限制总数，不允许插件从业务数据中动态生成实例标签。

## 12. Backend API 与管理页面

### 12.1 API 概念

对外 API 应明确分开两类操作：

- 插件包操作：列表、安装、更新和卸载。
- 插件实例操作：列表、创建、查看、修改配置、启动、停止和删除。

所有操作继续通过 Backend 执行登录与 admin 授权，浏览器不直连 Monitor。公开 DTO 只返回安全状态和脱敏配置摘要，不返回 Secret、进程信息和内部路径。

精确 URL、请求字段和错误码应在实施前根据当时公共 API 基线确定，本文档不提前冻结。

### 12.2 页面概念

管理页面首先展示“插件类型”，进入某个插件后再展示“实例列表”：

```text
Redis Exporter 2.0.0
实例 2 / 上限 5

├── 业务 Redis    运行中     最近成功 10 秒前
└── 会话 Redis    采集失败   最近成功 4 分钟前
```

页面至少需要：

- 创建实例向导和保存前连接测试。
- 实例级启动、停止、编辑和删除。
- 每个实例的期望状态、实际状态、最近成功和安全错误。
- 按插件和实例查看 Metrics、Logs 和 Events。
- 明确告知插件包更新会影响哪些实例。

批量启停不是首批多实例实现的必需功能，先保证单实例操作清晰、安全和可恢复。

## 13. 故障隔离和资源限制

- 某个实例的目标不可达，只影响该实例的采集和状态。
- 某个实例进程崩溃，Monitor 只对该实例执行有上限的重启与退避。
- Router、Kafka 或存储暂时不可用时，各实例按已有传输和故障语义处理，不变成无界本地队列。
- Monitor 应限制每种插件和全局实例数、同时启动数、同时采集数及重启速率。
- 达到上限时拒绝创建新实例，而不是挤掉已有实例。

## 14. 从当前单实例如何迁移

实施多实例时，不要求用户删除已有 Redis Exporter 后重新安装。建议迁移步骤为：

1. 读取当前 Redis 插件包、版本、期望状态和采集配置。
2. 保留原插件包记录，将目标配置迁移为一个默认实例。
3. 为默认实例生成稳定 `instance_id`，显示名称可以是“Redis 默认实例”。
4. 把原 `desired_state`、安装时间和最近状态尽可能映射到默认实例。
5. 原实例处于 running 时，迁移后启动默认实例并验证健康与真实采集。
6. 只在新 Registry、进程和采集都验证成功后提交迁移；失败时保留原状态。

历史数据在迁移前没有 `instance_id`，查询层可把它展示为“历史默认实例”，但不应伪造一个当时并不存在的实例身份标签。

## 15. 实施前置条件

只有满足以下条件时，才应把本设计拆成实施计划：

- 已存在至少一个需要同时采集两个同类目标的真实使用场景。
- 多种单实例插件已证明通用插件契约可用。
- 插件配置 Schema 与 Secret 存储边界已稳定。
- 已确定实例数、内存、端口和采集并发上限。
- 已定义从单实例 Registry 到多实例 Registry 的可回滚迁移方案。
- 已准备管理员实例管理页面和普通用户权限负向验收。

## 16. 建议的最小实施切分

将来真正实施时，建议分为三个可独立验证的批次：

1. **实例模型与可回滚迁移**：拆分插件包/实例 Registry，将当前 Redis 迁移为默认实例，但暂时仍限制最多一个实例。
2. **第二实例与故障隔离**：放开有上限的多实例创建，完成独立进程、端口、采集、状态、重启恢复，并验证一个实例成功、一个实例失败时互不影响。
3. **管理界面、升级回滚与集成收口**：完成实例管理页面、指标筛选、事件追溯、逐实例升级/回滚和完整验收。

第一批引入数据边界但不立即开放多实例，可以先证明迁移和回滚安全，再放开资源数量。

## 17. 验收方向

未来实施的固定验收至少应包括：

- 从现有单 Redis 实例完成迁移，原有期望状态和新采集能正常恢复。
- 同一 Redis Exporter 包创建两个实例，两者均产生可区分的真实指标。
- 关闭其中一个目标，该实例表达失败，另一实例持续采集。
- 停止或修改某个实例不影响另一实例。
- Monitor 替换或重启后按各自期望状态恢复，不出现双进程或孤儿进程。
- 插件包更新成功时所有实例运行新版本；代表性失败时所有实例回到原版本和原期望状态。
- 管理员可管理实例并查看状态，普通用户的列表、读取和操作请求全部为 `403 permission_denied`。
- 浏览器、API、Metrics、Logs、Events 和诊断输出均不泄漏凭据、完整连接串、内部路径或进程信息。
- 达到实例上限后明确拒绝新建，已有实例和社交业务保持可用。

## 18. 实施时仍需确定的参数

以下内容应根据实施时的真实代码、运行环境和资源预算确定，不在本设计中凭空固定：

- 每种插件和全局最大实例数。
- 内部端口段与分配持久化格式。
- 默认采集周期、超时、退避和同时采集上限。
- Secret 存储的具体实现与密钥轮换方式。
- 插件包更新时实例检查的超时和回滚策略。
- API URL、数据库 Schema、错误码和前端组件细节。

## 19. 一句话总结

当前先把“多种插件，每种一个实例”做稳定；将来真正需要时，再通过“插件包与实例分离、每实例独立运行、独立配置与状态”实现可控的多实例采集。
