# 01. 数据类型与表设计

## 一、八股文基础

### 1. `CHAR` 与 `VARCHAR` 怎么选？

- `CHAR(n)` 定长，适合长度固定的标识；`VARCHAR(n)` 变长，适合用户名、标题等长度不固定的文本。`n` 对字符类型通常指字符数，而不是字节数，实际空间与字符集有关。
- `TEXT` 用于较长的正文；`TEXT` 的默认值、索引、排序与行存储成本需要单独考虑。
- `JSON` 用于结构可能变化的事件载荷，但不应替代需要约束、关联和高频过滤的关系型字段。

GoPulse 中，`users.username` 是 `VARCHAR(32)`，`posts.title` 是 `VARCHAR(120)`，`posts.content` 是 `TEXT`；`business_outbox.event_id` 采用 `CHAR(36)`，`payload` 使用 `JSON`。

### 2. 为什么主键经常使用 `BIGINT UNSIGNED`？

`BIGINT UNSIGNED` 取值范围大，适合自增业务 ID。InnoDB 主键索引是聚簇索引，主键值会出现在二级索引的叶子记录中，因此主键越大，二级索引的存储成本通常也越高。这里是容量与简单性的取舍，不是所有系统都必须选择 `BIGINT`。

### 3. 主键、唯一索引、外键各解决什么问题？

| 机制 | 主要作用 | GoPulse 实例 |
|---|---|---|
| 主键 PK | 标识一条记录，不能为 NULL | `posts.id` |
| 联合主键 | 多列共同标识一条关系 | `post_likes(post_id,user_id)` |
| 唯一键 UNIQUE | 约束候选业务键不得重复 | `users.username`、`business_outbox.event_id` |
| 外键 FK | 在数据库层限制非法引用 | `posts.author_id → users.id` |
| CHECK | 约束单行数据的合法取值/组合 | `user_follows` 禁止自己关注自己 |

普通 `UNIQUE` 索引在 MySQL 中通常允许多个 `NULL`；因此 `business_commands` 的可空 `idempotency_key_hash` **不能**解释为“对所有空键命令只能存在一条”。

### 4. 为什么不能只靠应用层校验？

应用层的“先查询、再插入”在并发下仍可能发生竞态：两个请求同时发现不存在，然后都执行插入。数据库 `UNIQUE` 约束才是最终冲突裁决点；应用层负责将约束异常转成可理解的业务结果。

## 二、GoPulse 中的实际应用

**场景 A：防止重复点赞。**

迁移 `000001_phase1_schema.up.sql` 中：

```sql
CREATE TABLE post_likes (
    post_id BIGINT UNSIGNED NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (post_id, user_id),
    KEY idx_post_likes_user_id_post_id (user_id, post_id),
    -- 省略外键声明
    ...
);
```

此处是**联合主键**，不是增加一个无业务意义的自增 `id`。用户对同一帖子只能存在一条点赞记录。反向索引 `(user_id,post_id)` 支持从用户维度查询；联合主键 `(post_id,user_id)` 优先支持从帖子维度查找。上述 DDL 是讲解摘录，`...` 不是可执行 SQL。

**场景 B：幂等创建帖子。**

`business_commands` 定义：

```sql
UNIQUE KEY uq_business_command_idempotency
  (data_epoch, user_id, command_type, idempotency_key_hash)
```

相同数据代际、用户、命令类型、**非空**幂等键哈希发生并发插入时，数据库保证最多一条成功。项目的业务代码会在约束冲突后回滚竞争失败的事务，再查询已提交的赢家结果。

**场景 C：软删除后的名称复用。**

`alert_rules` 使用存储型生成列 `live_name`：

```sql
live_name VARCHAR(80) COLLATE utf8mb4_bin
    GENERATED ALWAYS AS (IF(deleted_at IS NULL, name, NULL)) STORED,
UNIQUE KEY uq_alert_name(live_name)
```

未删除规则的 `live_name=name`，受到唯一约束；已删除规则的 `live_name=NULL`，允许多个历史记录共存。这是“有条件唯一性”在 MySQL 中的一种实现方式。

`posts.author_id` 有外键，`business_commands.user_id` 在迁移中却**没有声明外键**。需要严格区分“字段指向某个业务实体”和“数据库存在 FK 约束”，不能按字段名推断出外键。

另一个有意需要留意的事实是：`post_likes` 删除引用使用 `RESTRICT`，`post_bookmarks` 使用 `CASCADE`。项目的删除逻辑会显式处理某些关联数据，这直接影响事务范围和删除顺序。

## 四、设计思考

1. **什么时候用联合主键？** 关系表天然由两列唯一确定时，联合主键能同时表达唯一性及一种主要访问顺序；但要评估二级索引中的主键附加成本。
2. **什么时候用 `JSON`？** Outbox 事件载荷是整包读取/投递，JSON 合适；用户名、作者 ID、状态不能一律放入 JSON，否则约束和索引更复杂。
3. **字符集与排序规则决定什么？** `utf8mb4_0900_ai_ci` 适用大小写/重音不敏感的比较；事件 ID 的 `ascii_bin`、告警名称的 `utf8mb4_bin` 则采用更严格的比较语义。不能只看字段长度。
4. **`DATETIME(6)` 是否带时区？** 不带。GoPulse 的 MySQL 驱动配置 `ParseTime=true`、`Loc=time.UTC`，但数据库的 `DATETIME` 本身仍不保存时区信息。跨服务必须统一时间语义。
5. **`CHECK` 是否总能生效？** MySQL 8.0.16 起才开始真正强制检查相关约束；项目要依据受支持的 MySQL 版本验证迁移。

## 五、关联面试题

1. **主键和唯一索引有什么区别？** 主键不能为 NULL，InnoDB 以主键组织聚簇索引；表可以有多个唯一键，但只有一个主键。
2. **为什么 `post_likes` 使用联合主键？** 关系天然由帖子和用户共同唯一确定，直接在数据库层拒绝重复关系。
3. **MySQL 唯一索引允许 `NULL` 吗？** 允许多个 `NULL`，所以不能把可空字段当成严格的业务唯一标识。
4. **外键和应用层校验有什么区别？** FK 是数据库约束；应用层校验可以改善体验，但并发场景不能单独代替约束。
5. **`CHAR`、`VARCHAR`、`TEXT`、`JSON` 应该怎么选？** 根据数据长度、查询方式、结构稳定性、索引及约束需求选，不以“灵活”作为唯一标准。
