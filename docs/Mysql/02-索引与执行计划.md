# 02. 索引与执行计划

理解 B+Tree、聚簇索引、联合索引、覆盖索引、最左前缀和 `EXPLAIN`，能分析 GoPulse 的帖子流及消息任务索引

## 一、八股文基础

### 1. 为什么 InnoDB 主要使用 B+Tree 索引？

B+Tree 是平衡的多路搜索树：非叶子页维护导航信息，叶子页存储有序索引记录。相对于普通二叉搜索树，它的扇出更高，读取一条记录需要访问的树层数通常更少；叶子节点有序，适合范围扫描与排序。

- **聚簇索引**：InnoDB 主键 B+Tree 的叶子记录包含行数据。
- **二级索引**：叶子记录包含索引键值和定位行所需的主键值。二级索引不能覆盖所需字段时，通常需要回到聚簇索引取完整数据，即“回表”。
- **覆盖索引**：查询所需字段可由索引读取，不必再获取完整行。并不是所有联合索引查询都天然覆盖。

### 2. 什么是最左前缀原则？

联合索引 `(a,b,c)` 可以有效用于从 `a` 开始的一组连续列，如 `a`、`a,b`、`a,b,c`。能否继续利用后续列进行范围定位、过滤或排序还与范围条件、方向和优化器有关，不能机械理解成“遇到范围条件后所有后续列都完全没用”。

## 二、GoPulse 中的实际应用

### 场景 A：帖子列表

迁移 `000001_phase1_schema.up.sql`：

```sql
KEY idx_posts_created_at_id (created_at DESC, id DESC),
KEY idx_posts_author_id (author_id)
```

[帖子列表源码](https://github.com/Ray-ymq/GoPulse/blob/reset/docs-zero-base/backend/internal/post/repository.go) 中，普通帖子流用 `created_at DESC, id DESC` 排序，并在构造 SQL 时使用：

```go
join := "FORCE INDEX (idx_posts_created_at_id)"
```

说明当前实现明确倾向使用这个排序索引。但 `FORCE INDEX` 只是给优化器的强制性索引提示，**不代表实测该索引在所有过滤条件下都是最优**；例如指定 `author_id` 的查询，其候选方案可能不同。

`id` 作为第二排序列有两个作用：当多篇帖子拥有相同时间戳时给出稳定顺序；同时构成唯一分页边界。

### 场景 B：评论列表

```sql
-- 表中的真实索引
KEY idx_comments_post_id_id (post_id, id DESC)

-- 仓库实际使用的查询条件与排序
WHERE c.post_id = ? AND c.id < ?
ORDER BY c.id DESC
LIMIT ?
```

用 `post_id` 等值定位，再按 `id DESC` 向后读取，是联合索引常见的访问模式；没有游标时不拼接 `c.id < ?`。

### 场景 C：Outbox 待处理事件

`business_outbox` 同时有三个工作索引：

| 索引 | 字段 | 服务的查询 |
|---|---|---|
| `idx_business_outbox_pending` | `(status,available_at,id)` | 待领取任务 |
| `idx_business_outbox_lease_recovery` | `(status,lease_expires_at,id)` | 超时租约恢复 |
| `idx_business_outbox_published_cleanup` | `(status,published_at,id)` | 已发布记录清理 |

这不是冗余地堆索引，而是不同状态和时间字段对应不同访问条件。不过并行维护多个索引也增加了写入成本。

## 三、项目源码分析：用 `EXPLAIN` 解释索引

以下 SQL 是**可复现的分析模板**，不是已运行的性能测试结果：

```sql
EXPLAIN
SELECT id, author_id, title, created_at
FROM posts
WHERE created_at < '2026-01-01 00:00:00.000000'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

阅读 `EXPLAIN` 的重点：

| 字段 | 看什么 |
|---|---|
| `type` | 访问方式：`const`、`ref`、`range`、`index`、`ALL` 等 |
| `possible_keys` | 优化器可考虑的索引 |
| `key` | 实际选择的索引，可能为空 |
| `key_len` | 被使用的索引键长度；并非查询性能分数 |
| `rows` | 预计扫描行数，不是实际值 |
| `Extra` | `Using index`、`Using where`、`Using filesort` 等 |

MySQL 8.0.18+ 可以对合适的查询使用 `EXPLAIN ANALYZE` 查看实际执行行为；它会执行查询，不能把它当成不执行的纯语法检查。

## 四、设计思考

1. **排序索引不等于覆盖索引**：读取 `posts.content` 时，`idx_posts_created_at_id` 没有覆盖正文，仍可能回表。
2. **联合索引需要与真实查询顺序匹配**：`(post_id,user_id)` 适合先限定帖子；查“某用户点赞的帖子”则考虑 `(user_id,post_id)`。
3. **多索引存在写放大**：插入、更新、删除都需要维护相关索引，应结合读写比例决定保留哪些索引。
4. **必须实测**：不同数据规模、参数分布、统计信息下，优化器可能给出不同计划。只看 SQL 无法宣布“已经命中索引”或“没有回表”。

## 五、关联面试题

1. **B+Tree 为什么适合范围查询？** 叶子节点按键有序，索引可以从边界位置连续扫描。
2. **聚簇索引与二级索引有什么区别？** 主键叶子保存整行，二级索引叶子保存索引键和主键值。
3. **什么是回表和覆盖索引？** 二级索引没有全部所需列时再查主键索引；全部可由索引获得则是覆盖。
4. **联合索引 `(a,b,c)` 为什么不能简单替代 `(b,a)`？** 两者对应不同的左侧定位和排序路径。
5. **`EXPLAIN` 的 `rows` 是实际扫描量吗？** 通常是估算；以 `EXPLAIN ANALYZE` 等运行证据补充。
6. **`FORCE INDEX` 是不是索引优化的证据？** 不是，只说明代码有显式索引提示，仍须对照执行计划与负载。
