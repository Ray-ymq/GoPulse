# 05. 锁机制与并发控制

> 学习目标：理解行锁、共享锁、排他锁、间隙锁、死锁和 `SKIP LOCKED`，能解释 GoPulse 如何让多个 Worker 并发领取 Outbox 事件。

## 一、八股文基础

### 1. InnoDB 常见锁有哪些？

| 类型 | 典型用途 | 关键理解 |
|---|---|---|
| 共享锁 S | `SELECT ... FOR SHARE` | 多个共享锁可兼容，但与同一记录上的排他锁冲突 |
| 排他锁 X | `SELECT ... FOR UPDATE`、UPDATE、DELETE | 用于保护需要修改的记录 |
| 记录锁 Record Lock | 锁定索引记录 | 通常口头称为“行锁”；实际锁依赖索引定位 |
| 间隙锁 Gap Lock | 锁定索引记录之间的间隙 | 约束其他事务向该间隙插入的行为 |
| 临键锁 Next-Key Lock | 记录锁 + 间隙锁 | RR 场景下用于范围保护 |
| 意向锁 | 表级锁状态 | 表示事务将持有哪些行级锁，并非用来锁住全表业务数据 |

`SELECT ... FOR UPDATE` 不等价于“只锁一行”：范围条件、索引是否可用、隔离级别可能使锁范围更大。索引设计与锁冲突概率直接相关。

### 2. 什么是死锁？

两个或多个事务互相等待对方持有的锁，形成循环依赖。InnoDB 通常会检测死锁并回滚其中一个事务。应用侧需要识别死锁错误、使重试有边界并保证业务幂等；不能简单把所有 SQL 错误无限重试。

## 二、GoPulse 中的实际应用：Outbox 并发领取

出处：[`backend/internal/outbox/repository.go`](https://github.com/Ray-ymq/GoPulse/blob/reset/docs-zero-base/backend/internal/outbox/repository.go) `Claim`。

核心 SQL（来自仓库）：

```sql
SELECT id, event_id, event_type, schema_version, payload, status,
       available_at, attempt_count, lease_owner, lease_expires_at,
       published_at, last_error, created_at, updated_at
FROM business_outbox
WHERE (status = 'pending' AND available_at <= ?)
   OR (status = 'leased' AND lease_expires_at <= ?)
ORDER BY id
LIMIT ?
FOR UPDATE SKIP LOCKED;
```

核心操作顺序：

```text
Worker A                            Worker B
   |                                   |
   +-- BEGIN (RC)                      +-- BEGIN (RC)
   +-- 选择并锁定可领取事件              +-- 跳过 A 已锁住的事件
   +-- UPDATE status='leased'          +-- UPDATE 自己领到的事件
   +-- 写入 lease_owner、expires_at     +-- 写入自己的租约
   +-- COMMIT                          +-- COMMIT
```

这里有三层设计：

1. **`FOR UPDATE`**：领取时持有排他锁，防止多个事务同时认领同一行。
2. **`SKIP LOCKED`**：遇到被其他事务锁住的记录直接跳过，降低多个 Worker 的排队等待；不会保证严格的 FIFO 顺序。
3. **租约字段**：`status='leased'`、`lease_owner`、`lease_expires_at` 使任务领取结果持久化；Worker 崩溃后，过期租约可以被重新领取。

取到行之后，源码在**同一个事务**中执行：

```sql
UPDATE business_outbox
SET status='leased', lease_owner=?, lease_expires_at=?, updated_at=?
WHERE id=?;
```

最终 `Commit()`，完成领取。它不是单条 SQL 的瞬时“弹出队列”，而是带行锁与租约状态的数据库任务分配。

## 三、另外两个项目案例

### 1. 删除帖子：当前读保护业务对象

[`backend/internal/post/delete.go`](https://github.com/Ray-ymq/GoPulse/blob/reset/docs-zero-base/backend/internal/post/delete.go) 使用：

```sql
SELECT author_id FROM posts WHERE id=? FOR UPDATE;
```

先锁住对应帖子，再校验操作人、清理通知/点赞/评论等引用、删除帖子，并把 `post.deleted` 写入 Outbox；最后提交事务。

该路径还通过 `GET_LOCK('gopulse:post-search-reindex:v1', 10)` 获取 MySQL **命名锁**，用于协调搜索索引重建与删除。命名锁按连接持有，不属于普通 InnoDB 行锁，不能把 `RELEASE_LOCK` 误认为 `ROLLBACK` 的等效动作。

### 2. 业务容量：锁定预算记录

[`backend/internal/businessstate/commands.go`](https://github.com/Ray-ymq/GoPulse/blob/reset/docs-zero-base/backend/internal/businessstate/commands.go) 包含：

```sql
SELECT data_epoch, open_requirements, retained_groups, retained_bytes
FROM business_async_budget
ORDER BY data_epoch FOR UPDATE;
```

通过锁定预算记录协调并发准入，避免多个请求都基于同一旧容量判断放行，最终超过数据库定义的业务预算约束。

## 四、设计思考

1. **为什么 `SKIP LOCKED` 不适合普通列表分页？** 结果允许跳过正被锁住的数据，属于有意不完整的视图。适合任务领取，不适合要求完整一致视图的用户查询。
2. **为什么有租约仍需要锁？** 租约是已提交的领取状态，行锁保护多个 Worker “读取候选行 → 修改租约”的并发事务边界；两者解决不同时间尺度的问题。
3. **如何减少锁竞争？** 使用能定位目标记录的索引、缩短事务时间、避免在事务中执行慢网络操作、统一多资源加锁顺序。
4. **`ORDER BY id LIMIT ?` 是否一定走 `idx_business_outbox_pending`？** 不一定。该查询有两个状态分支和排序要求，具体访问路径必须以执行计划确认。
5. **为什么必须处理死锁和超时？** 它们在正确使用行锁的系统里仍可能出现；重试应有限次、有退避，并以幂等语义保证安全。

## 五、关联面试题

1. **行锁一定锁单行吗？** 不一定，锁作用于索引记录及可能的范围，取决于索引和查询条件。
2. **`FOR UPDATE` 和 `FOR SHARE` 区别是什么？** 分别获取排他锁和共享锁，兼容性不同。
3. **什么是 Gap Lock 与 Next-Key Lock？** 前者锁间隙，后者组合记录与间隙以保护某些范围。
4. **`SKIP LOCKED` 解决什么问题？** 多个消费者并发选择待领取任务时减少对已锁行的等待，但允许跳过行。
5. **发生死锁该怎么办？** 识别数据库错误、回滚并有限重试，优化索引和锁顺序。
6. **`GET_LOCK` 是行锁吗？** 不是，它是 MySQL 连接级命名锁，生命周期与事务锁不同。
