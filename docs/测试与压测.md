# 测试与压测

## 集成测试

集成测试由 Testcontainers for Go 管理依赖，入口保持为：

```sh
make integration SCOPE=business
make integration SCOPE=observe
```

每次运行都会创建独立的 Testcontainers 网络、容器和动态映射端口，并把实际地址写入本次运行的私有环境文件。业务测试使用 MySQL、Redis、RabbitMQ 和 Elasticsearch；`observe` 还会启动 Kafka、VictoriaMetrics 和观测用 Elasticsearch，然后编译并启动本地 Go 服务进程。

依赖镜像版本固定为：

```text
mysql:8.4.0
redis:7.2.5-alpine
rabbitmq:3.13.3-management-alpine
docker.elastic.co/elasticsearch/elasticsearch:9.5.2
confluentinc/confluent-local:7.5.0
victoriametrics/victoria-metrics:v1.151.0
```

Kafka 在容器网络内使用 `kafka:9092` 做协议和主题初始化，宿主机进程使用动态映射的外部端口。测试环境会将 Testcontainers 的主机覆盖为 `127.0.0.1`，避免 Unix socket Docker daemon 把 Kafka 对外地址解析成不可通告的 `0.0.0.0`。Testcontainers 的 Ryuk 回收器必须启用；设置 `TESTCONTAINERS_RYUK_DISABLED=true` 会直接拒绝启动。

就绪检查使用数据库查询、Kafka 协议命令、RabbitMQ 诊断命令或 HTTP 健康接口。测试失败时先保存容器和应用日志，再清理应用进程、容器和网络；正常结束、失败和可捕获中断都会执行清理。observe 的 Monitor 插件注册表和 spool 目录使用每次运行唯一的私有目录，避免复用上一次测试的插件状态。

## k6 输入和配置

正式压测需要先准备私有的确定性数据集。`recipe` 命令要求 DSN 和密码分别放在权限为 `0600` 的私有文件中，并把 corpus、credentials 和脱敏 receipt 写入被忽略目录：

```sh
umask 077
mkdir -p .run/load
(cd perflab && go run ./cmd/recipe \
  --dsn-file ../.run/private/load-dsn \
  --password-file ../.run/private/load-password \
  --receipt ../.run/load/recipe.json \
  --corpus ../.run/load/corpus.json \
  --credentials ../.run/load/credentials.json)
```

目标数据库必须是空的 recipe 目标。不要把 DSN、密码、credentials 或 corpus 提交到 Git。复制 `perflab/k6/config.json` 后，至少修改 `target.base_url`、`target.health_url`、输入文件路径和 `report_dir`；若要检查后台积压，还要填写 `target.backlog_url` 和 `target.backlog_json_path`。`recovery.require_observation` 为 `true` 时，没有 backlog 观测会把阶段标记为 `capacity_insufficient`，不会伪造恢复结论。

k6 固定为 0.56.0，默认按 `perflab/k6/toolchain.json` 的 SHA-256 校验和自动安装到 `.run/tools/k6`。也可以通过 `K6_BIN` 指定已安装的同版本二进制；`K6_AUTO_INSTALL=0` 会禁止自动下载。

## 三阶段入口

先检查 boundary 阶段计划：

```sh
make load MODE=boundary CONFIG=.run/load/config.json DRY_RUN=1
```

执行正式 boundary：

```sh
make load MODE=boundary CONFIG=.run/load/config.json
```

默认从 10 RPS 开始按 2 倍递增，单档预热 30 秒、测量 120 秒，最高到 1,000 RPS；每档结束后最多观察恢复 120 秒。首次失稳后停止后续档位。如果到达最高档仍稳定，报告会写明尚未找到边界。

使用 boundary 报告执行二分细化：

```sh
make load MODE=refine \
  CONFIG=.run/load/config.json \
  PREVIOUS_REPORT=".run/load/reports/boundary-<timestamp>.json"
```

细化阶段每档测量 5 分钟，直到稳定和失稳区间的相对宽度不超过 10%，或达到配置的最大迭代次数。使用已确认的稳定容量执行 80% 持续运行：

```sh
make load MODE=soak \
  CONFIG=.run/load/config.json \
  PREVIOUS_REPORT=".run/load/reports/refine-<timestamp>.json"
```

soak 默认运行 30 分钟。每次业务迭代只发出一个被测 HTTP 请求；登录初始化单独统计。路由按模板聚合，避免把具体资源 ID 作为高基数指标。报告格式为 `gopulse.k6.load.v1`，结构定义在 `perflab/k6/report.schema.json`，默认输出到 `.run/load/reports`。

稳定标准默认是 P95 不超过 1 秒、P99 不超过 2 秒、失败率不超过 1%，并要求达到目标请求率。429、503、超时和传输错误分开统计；未发出的迭代会标记为容量判断不充分。连续 30 秒错误率超过 20%或健康检查连续失败 30 秒时停止加压。缺少资源指标时，报告只记录 `resources.source=not_observed`，不推断具体瓶颈。

## 本次验收结果

2026-10-19 在真实 Docker 环境完成以下验证：

- `make integration SCOPE=business`：通过。
- `make integration SCOPE=observe`：通过；观测集成测试覆盖 exporter 启停、Kafka metrics、VictoriaMetrics 查询、后台日志和 Monitor 事件。
- `make load MODE=boundary CONFIG=perflab/k6/config.json DRY_RUN=1`：通过，生成 10、20、40、80、160、320、640、1000 RPS 阶段计划。
- 使用受控本地 HTTP 服务运行真实 k6 0.56.0：通过认证、业务请求、错误分类、阶段报告和恢复观察验证。

本次没有在独立正式容量环境运行完整的 boundary、refine、soak 时长，因为仓库没有可直接使用的正式目标地址、私有 corpus/credentials 和后台积压接口。上述命令和报告链路已经可用；完成正式容量结论前，必须提供独立的固定资源环境和经审核的私有配置，不能用本地受控服务的结果代替容量结论。
