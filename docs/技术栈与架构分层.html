01从用户界面到基础服务

以下分层是对现有实现的职责抽象。各层可能位于同一 Go 模块或同一进程中，层级编号不代表每个请求都会依次经过全部层。

L1

用户交互层

页面、路由、界面状态

Vue 页面与组件展示社交业务；composables 管理认证、关注、收藏和发帖状态；Fetch 封装请求与错误处理。

Vue 3TypeScriptVue RouterCSS
L2

HTTP 接入层

代理、契约、请求保护

Nginx 提供静态资源与 API 代理；Gin 注册路由和中间件，处理认证、授权、同源检查、限流及请求日志。

NginxGinOpenAPI 3.1JWT / Cookie
L3

业务应用层

用例与业务规则

按认证、用户、关注、帖子、评论、点赞、收藏、搜索和通知组织业务包。Service 执行输入校验、权限相关规则与业务流程。

GoService业务模型businessstate
L4

数据访问层

仓储、事务、外部适配

Repository 使用 SQL 读写业务事实；platform 封装依赖连接与客户端。帖子正文缓存和搜索适配器分别连接 Redis 与 Elasticsearch。

database/sqlRepositorygo-redisES Client
L5

异步协作层

事件分发与后台消费

事务 Outbox 保存待分发事件；API 内的 Dispatcher 发布消息。Worker 处理异步业务和通知，Indexer 更新搜索索引。

OutboxAMQP 0-9-1Worker重试 / 死信
L6

基础服务层

存储、缓存、队列、检索

MySQL 保存业务事实与异步状态；Redis 提供缓存与限流相关能力；RabbitMQ 传递消息；Elasticsearch 提供全文搜索。

MySQLRedisRabbitMQElasticsearch

配置与运行管理

internal/platform/config/ 校验配置；internal/logging/ 输出 JSON 日志；internal/platform/ 提供健康探针。各命令通过标准库处理信号与退出。

工程与交付

Makefile 提供模块验证与镜像构建入口，Docker 打包，根 Compose 配置单机部署。宿主机源码运行前需自行准备依赖。

质量与容量

Go testing、竞态检测、Vitest 与静态检查验证实现；Playwright 使用隔离接口 fixture 验证浏览器流程。仓库不提供压测工具，真实依赖联调需另行准备。

依赖方向

业务 Service 通过仓储接口访问数据。异步链路从事务提交后分叉，不要求用户请求等待通知或索引处理完成。

架构判断：根据目录、构建入口与进程职责，可将当前后端理解为“按业务模块组织的应用 + 独立异步进程”。这些逻辑层不等同于独立部署的微服务。

03三条核心链路

读请求、事务写入和后台处理承担不同职责。MySQL 保存业务事实，缓存和搜索索引服务各自的读取场景。

同步读取

Vue / Fetch→Nginx→Gin / Service
  1. 前端请求 /api/v1，代理将请求交给 API。
  2. 中间件处理认证和请求保护，Handler 调用业务 Service。
  3. 仓储从 MySQL 读取事实；帖子正文读取可使用 Redis 缓存。缓存重建由有界协调器管理。

事务写入与消息分发

业务写入→MySQL + Outbox→RabbitMQ
  1. 以帖子写入为例，仓储在同一数据库事务内保存业务事实与 Outbox 事件。
  2. API 内 Dispatcher 领取待处理记录并发布消息；分发具有租约、超时和重试控制。
  3. Worker 处理异步业务和通知；Indexer 更新 Elasticsearch。重试与死信队列保留失败处理路径。

事务提交与消息消费分属不同阶段，不能将其视为跨 MySQL、RabbitMQ 和 Elasticsearch 的单一原子事务。

搜索查询与索引维护

Search API→Elasticsearch
MySQL 事实→Indexer / Reindex→搜索索引
  1. 查询通过搜索 Service 访问 Elasticsearch，并执行可见性相关处理。
  2. 在线变更由 RabbitMQ 消息驱动 Indexer 更新索引。
  3. search-reindex 根据数据库事实重建索引。搜索投影可能晚于业务事务提交。

04代码模块与运行进程

根 Makefile 是模块注册来源。一个模块可以构建多个进程。根 Compose 包含 10 个服务容器：8 个常驻服务和 2 个一次性初始化任务；API、Worker 和 Indexer 各运行一个容器。

目录边界与职责主要入口 / 产物
frontend/web/用户端 npm 模块，包含页面、组件、composables、HTTP 客户端与类型定义Vite 开发服务；由 Nginx 托管的静态构建产物
backend/business/业务 Go 模块；module 名称保持为 github.com/Ray-ymq/GoPulse/backend常驻：server、business-worker、search-indexer
按需：migrate、search-reindex、admin-role
tools/ci/ · tools/make/共享 CI 脚本和构建规则，未注册为独立 Go 模块模块选择、提交校验、自动 PR 回归与 Makefile 片段
deploy/部署说明与 Nginx 模板根 compose.yml 编排服务；Dockerfile 和专用忽略文件位于 backend/business 与 frontend/web

05理解架构时需要保留的边界

目录分层与调用分层各有用途

目录按前端、后端、工具和部署划分。HTTP Handler 位于 transport/http，业务包内部组织 Service、Repository 与模型。六层视图用于解释职责和链路，不表示仓库已经采用严格的六级目录或完整的 DDD 分层约束。

业务事实与派生数据分别维护

MySQL 保存业务事实；Redis 缓存和 Elasticsearch 索引由相应机制维护。Outbox、消费重试、businessstate 中的数据 epoch、命令幂等与异步预算共同支撑恢复和异步处理，具体约束以各业务实现为准。

依赖声明需要与实际使用区分

go.mod 中仍有 OpenTelemetry、MongoDB 驱动等间接依赖。当前业务说明明确删除了指标采集与链路追踪，部署配置使用 MySQL。仅凭间接依赖不能将这些组件列为已启用的业务基础服务。

版本和部署状态有独立证据

本报告记录当前源码声明与默认部署配置。Docker 和 Compose 的宿主工具版本未在此处确定。本次未启动业务服务或容器，也未验证线上拓扑；配置校验不能代替真实部署验证。
