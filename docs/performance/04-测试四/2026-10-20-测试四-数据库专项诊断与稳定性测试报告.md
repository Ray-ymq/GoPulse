# 测试四：数据库专项诊断与稳定性测试报告

状态：已完成 100 RPS 基线和 120 RPS 复现实验。

## 执行范围

本次测试固定使用测试方案中的数据、业务比例和部署配置：Redis 关闭，MySQL 限制为 2 vCPU 和 2 GiB，API MySQL 连接池上限为 8。每组执行 30 秒预热、300 秒正式测量和 600 秒恢复观测。正式测量使用同一混合业务脚本，超时和未完成请求计为失败。

两次正式运行的配置摘要均为 `config_sha256=d8626199c7b734dd95bdb141f865ac711f74a0e37bd918040547f317402fc634`。本次未执行 110 RPS，因为 100 RPS 正常、120 RPS 退化的分界已经复现。

原始证据目录如下：

- `baseline-100`：`.run/pt4/observations/baseline-100-20261020T142630616762Z/`
- `reproduce-120`：`.run/pt4/observations/reproduce-120-20261020T144626136619Z/`

100 RPS 的 300 秒窗口完整结束，所有响应均成功。120 RPS 的错误分类为：500 `internal_error` 4,784 次，503 `backend_busy` 4,050 次，503 其他错误 67 次。每分钟错误率从 20.15% 上升到 24.33%、26.06%、26.17% 和 26.92%。120 RPS 的成功请求速率为 90.33 RPS。

## 数据库和资源证据

两组 SQL 摘要增量均通过有效性检查，`SUM_ERRORS=0`，没有新增 digest。SQL 统计窗口内，`business_async_budget` 的加锁读取如下：

| 组别 | `COUNT_STAR` | `SUM_TIMER_WAIT` | `SUM_LOCK_TIME` |
| --- | ---: | ---: | ---: |
| baseline-100 | 3,401 | 0.350556 s | 3.063 ms |
| reproduce-120 | 3,699 | 1.083205 s | 4.755 ms |

120 RPS 下，`business_environment` 读取摘要的 `COUNT_STAR` 为 11,209，`SUM_TIMER_WAIT` 为 4.276922 s，`SUM_LOCK_TIME` 为 161.145 ms。SQL 累计时间表示数据库摘要窗口中的累计等待时间，不能直接解释为 CPU 时间。

锁等待证据集中在 `gopulse_load.business_async_budget` 的 `PRIMARY` 记录上。等待锁均为 `X,REC_NOT_GAP`，可见的阻塞锁主要为同一模式。100 RPS 的锁等待采样为 4 个采样、46 条等待记录；120 RPS 为 39 个采样、819 条等待记录，单个采样最多 55 条。代表性阻塞事务同时持有 2 条记录并修改 2 条记录，等待事务和阻塞事务在同一秒启动。该证据显示 120 RPS 下预算表的事务竞争明显增加。

API 连接池上限保持为 8。120 RPS 的 MySQL CPU 采样峰值为 210.47%，cgroup CPU 节流计数增量为 3,040；100 RPS 对应值为 157.93% 和 33。120 RPS 测量窗口内 MySQL 原始内存峰值约为 1.834 GiB，其中内存压力值约为 1.011 GiB，可回收文件缓存约为 0.830 GiB。MySQL 未发生 OOM，主机 OOM kill 为 0；主机可用内存和磁盘空间均未触发测试保护阈值。

## 异步结果和恢复

100 RPS 的观测 backlog 峰值为 13，120 RPS 为 20。两组的 600 秒恢复观测均完成，最后一次业务检查均通过。恢复结束时，`business_async_budget.open_requirements` 均为 0；100 RPS 的 `retained_groups=65450`、`retained_bytes=84973988`，120 RPS 的 `retained_groups=65781`、`retained_bytes=85400844`。恢复后登录、读、写、更新、点赞、收藏、评论和删除冒烟检查均返回预期状态码。

## 结论

在 Redis 关闭、MySQL 2 vCPU / 2 GiB、API 连接池 8 的配置下，100 RPS 通过 300 秒正式测量和 600 秒恢复观测。120 RPS 完整复现退化：错误率为 24.725%，P95 和 P99 约为 1.5 秒，且错误随分钟窗口上升。

120 RPS 同时出现 API MySQL 连接池等待、读写资源容量拒绝、MySQL CPU 节流增加和 `business_async_budget` 锁等待增加。SQL 摘要没有错误或新增 digest，内存和磁盘也没有触发保护条件。现有证据支持优先检查连接池压力和预算表持锁事务，但这些指标同时变化，不能据此宣称唯一根因。

下一项验证应保持 120 RPS、数据和部署不变，先检查 `business_async_budget` 持锁事务的调用路径和事务持续时间。若锁内工作不足以解释错误，再采集相同负载下的短时 CPU 栈。每次验证只改变一个因素。
