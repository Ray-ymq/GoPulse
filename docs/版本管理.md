# 版本管理

本文统一维护 GoPulse 的产品版本、版本分支和发布规则。提交格式与允许的提交类型见 [CI 与提交规范](../tools/ci/CI.md#提交规范)。

## 1. 适用范围

产品版本采用 [语义化版本](https://semver.org/lang/zh-CN/)，正式版本格式为 `主版本号.次版本号.修订号`。

版本号描述相邻产品发布之间的兼容关系。开发阶段、任务数量、提交数量和分支数量不决定产品版本。一次发布可以包含多个任务、多个提交和多种提交类型。

## 2. 历史编号与当前基线

历史 `2.6.5` 及相关开发分支编号用于阶段管理，不作为规范发布序列的计算依据。保留已有 Git 分支、提交、标签、旧交付物和带日期的历史资料，不追溯重新编号。

本次编号转换以 `1.0.0-rc.1` 为首个规范候选版本，首个正式发布目标为 `1.0.0`。该调整属于从阶段编号切换到发布版本管理，不表示产品功能回退，也不表示正式版验收已经完成。首次规范发布的说明必须记录这一编号转换。后续产品版本以根 `VERSION` 为准。

本次基线转换沿用已有工作分支。后续新建开发分支使用第 6 节的规则。历史分支与新目标分支同名时，不得覆盖、重置或自动删除已有分支；先核对其用途，再经维护者明确同意将旧分支归档到其他名称，并保留原提交引用。不得仅为绕过分支名称冲突而递增产品版本。

## 3. 版本递增规则

以最近一次正式发布为比较基线，评估本次发布的整体变化：

| 变化 | 递增规则 | 示例 |
| --- | --- | --- |
| 向后兼容的问题修复 | 修订号加一 | `1.0.0 → 1.0.1` |
| 向后兼容的功能新增 | 次版本号加一，修订号归零 | `1.0.1 → 1.1.0` |
| 不兼容的公开契约变更 | 主版本号加一，次版本号和修订号归零 | `1.1.0 → 2.0.0` |

同一次发布包含多项变化时，取最高升级级别，只递增一次。提交中的 `feat`、`fix`、`!` 和 `BREAKING CHANGE` 用于辅助评估，最终以实际产品影响为准。

兼容性评估范围包括 HTTP API、公开配置、消息与数据格式，以及文档承诺的部署和升级方式。数据库迁移是否要求不兼容升级，需要结合旧程序兼容性和承诺的升级流程判断，不能仅凭新增迁移认定为主版本变化。

内部代码重组、文档、测试和格式调整不自动触发版本升级。依赖维护、性能优化、构建和部署变更按实际影响评估。纯文档或测试任务可以继续在当前版本分支完成，不为此单独递增产品版本。

## 4. 候选版规则

候选版格式为 `x.y.z-rc.N`，序号从 `1` 开始，例如：

```text
1.0.0-rc.1 → 1.0.0-rc.2 → 1.0.0
```

进入候选阶段前，固定本次发布的功能范围和交付内容。候选阶段主要处理缺陷、契约校正和交付问题。修复后需要重新交付候选版时，递增 `rc` 序号，保留相同的正式版本目标。

候选版验收通过后，准备对应的正式版。若功能范围或兼容性发生变化，应重新评估目标版本和验收范围。

每个实际发布的候选版和正式版必须对应确定的提交与交付物。不得覆盖已发布内容，也不得移动已有版本标签。

## 5. 版本来源与同步范围

根 [VERSION](../VERSION) 是产品版本的唯一来源，只保存一行版本值，不带 `v` 前缀。普通开发期间保留既有值，由 Git 提交号或独立镜像标签区分开发构建。

只有明确的发布准备任务可以调整产品版本，并必须在同一项改动中同步：

- 根 `VERSION`。
- [OpenAPI](../backend/business/api/openapi.yaml) 的 `info.version`。
- [前端 package.json](../frontend/web/package.json) 的项目 `version`。
- [前端 package-lock.json](../frontend/web/package-lock.json) 顶层及 `packages[""]` 的项目 `version`。
- 本次发布说明及当前说明中实际引用的产品版本。

前端作为产品的一部分交付，不独立维护产品发布序列。锁文件中的依赖包版本不得随项目版本统一替换。

根 Makefile 在构建时读取 `VERSION`，用于默认镜像标签和镜像内的产品版本元数据。自定义 `GOPULSE_IMAGE_TAG` 只改变镜像标签，不能代替产品版本字段同步，也不会改变已经构建的旧镜像。

依赖库版本、运行环境版本、数据库迁移编号和历史资料中的版本保持各自含义。`/api/v1` 属于接口版本，由接口兼容策略单独管理，不随产品版本直接改号。

## 6. 开发分支与提交

开发分支统一使用 `develop/x.x.x`，其中 `x.x.x` 表示本轮计划发布的正式版本。候选版继续在同一分支准备，例如 `develop/1.0.0` 对应 `1.0.0-rc.1`、`1.0.0-rc.2` 和最终的 `1.0.0`。

同一版本分支持续承载该版本的全部开发工作，包括功能、修复、性能优化、架构重构、依赖、构建、测试、CI、部署、文档和维护。提交类型遵循仓库规范，不限于 `feat`、`fix`。

单个任务或提交完成时，不自动递增产品版本，也不要求新建版本分支。每项完整改动仍需按仓库协作规则完成验证并创建提交。

本轮完成并合入主线后，根据下一轮整体改动确定目标版本，再从最新主线创建对应的 `develop/x.x.x` 分支。新建分支、任务完成或合并 PR 本身均不触发产品版本字段修改。

开发期间若范围变化导致目标版本不再合适，应重新评估并调整分支名称。分支已推送或关联 PR 时，调整前需明确对现有协作的影响，并与维护者协调，不得覆盖其他分支。

## 7. 发布准备与验证

发布前按以下顺序执行：

1. 固定发布范围及纳入本次交付的改动。
2. 评估相对上一正式版本的兼容性，确定目标版本。
3. 同步产品版本字段和发布说明。
4. 按改动范围执行必要的静态检查、测试和构建。
5. 对目标版本验证部署和核心业务流程；涉及已有数据时，验证相应升级和恢复流程。
6. 如实记录验证结果，提交发布准备改动，确定用于实际发布的提交。
7. 实际发布时，为该提交创建版本标签并记录交付物标识。

构建命令和验证入口见 [后端说明](../backend/README.md)、[前端说明](../frontend/web/README.md) 和 [部署说明](../deploy/README.md)。单元测试、构建或集成测试编译通过不能代替真实依赖联调。

发布记录必须包含版本、提交、交付物标识、主要变化、兼容性影响、迁移要求和实际验证结果。未执行的验证必须说明原因，不能记录为通过。

Git 版本标签使用 `v` 前缀，例如 `v1.0.0-rc.1`、`v1.0.0`。更新版本文件和创建发布准备提交不自动授权创建标签、推送或发布。
