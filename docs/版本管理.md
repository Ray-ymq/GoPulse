# 产品版本管理

根 `VERSION` 是产品版本的唯一来源。当前产品版本只使用 `x.y.z`，不使用 `rc`、其他预发布后缀或构建元数据。版本各位使用不带前导零的非负整数。

## 提交与版本变化

每项完整改动对应一个 commit。提交前，以父提交的 `VERSION` 为基准计算目标版本，并将代码与版本变化放在同一个 commit 中。规则统一维护在根 `.conventional-commits.json` 的 `versioning` 字段。

| 提交信息 | 升级级别 | 基准为 `1.2.3` 时的结果 |
| --- | --- | --- |
| 任意类型的标题带 `!`，或正文声明 `BREAKING CHANGE: 描述` / `BREAKING-CHANGE: 描述` | 主版本 | `2.0.0` |
| `feat`，无破坏性标记 | 次版本 | `1.3.0` |
| `fix`、`perf`、`revert`，无破坏性标记 | 补丁版本 | `1.2.4` |
| `build`、`chore`、`ci`、`refactor`、`style`、`test`，无破坏性标记 | 不升级 | `1.2.3` |

升级主版本时，次版本和补丁版本归零。升级次版本时，补丁版本归零。一个 commit 只递增一次，破坏性标记优先于类型。正文声明必须独占一行并带非空描述；代码块和 HTML 注释中的声明示例不触发主版本升级。

连续提交分别计算。例如，`1.2.3` 后依次提交 `feat`、`fix`，版本依次变为 `1.3.0`、`1.3.1`。`revert` 按补丁升级，不自动抵消被撤销提交的版本影响。真正的 merge commit 只检查版本一致性，不重复递增；合并冲突需要同步解决所有产品版本字段。

## 同步字段

以下字段必须一致：

- 根 `VERSION`。
- `backend/business/api/openapi.yaml` 的 `info.version`。
- `frontend/web/package.json` 的根 `version`。
- `frontend/web/package-lock.json` 的根 `version` 和 `packages[""].version`。

同步工具只修改这些产品版本字段，不替换历史记录、依赖版本或 API 路径中的版本号。JSON 文件统一按两空格缩进写回。

## 本地操作

1. 运行 `make hooks-install`，安装提交钩子和提交说明模板。
2. 完成改动，准备包含“背景”“改动”“验证”的完整提交说明文件。
3. 如需在构建前更新版本，按顺序执行下列命令。将路径替换为实际提交说明文件路径：

   ```sh
   make version-plan MESSAGE_FILE=/path/to/message.txt
   make version-update MESSAGE_FILE=/path/to/message.txt
   make check-version-files
   ```

4. 根据改动范围完成检查。涉及系统运行时，使用更新后的版本执行 `make container-build`，并按实际标签核对镜像。
5. 暂存本次改动，使用同一份提交说明同步暂存区版本并创建 commit：

   ```sh
   make commit MESSAGE_FILE=/path/to/message.txt
   ```

`version-plan` 只输出基准版本、目标版本和升级级别。`version-update` 更新工作区，不自动暂存。两个命令默认以 HEAD 为基准，重复执行不会累加版本。可通过 `BASE_REF=<父提交>` 显式指定计算基准。

`make commit` 先检查提交说明，再以暂存区内容同步产品版本，然后执行 `git commit -F`。该入口只暂存需要更新的产品版本文件，保留这些文件中已暂存的其他修改。需要更新的文件有未暂存修改时，命令会停止；先暂存或保存这些修改，再重试。版本字段既不是基准版本，也不是目标版本时，工具会停止并要求核对。

提交钩子只校验，不修改文件或暂存区。直接使用 `git commit` 时，必须提前同步并暂存全部产品版本字段，否则钩子拒绝提交。使用 `git commit --only` 时，也必须显式包含全部产品版本文件。

修改尚未发布的最后一个 commit 时，应以其父提交为基准，避免再次递增：

```sh
make version-update BASE_REF=HEAD^ MESSAGE_FILE=/path/to/message.txt
git add -- VERSION backend/business/api/openapi.yaml frontend/web/package.json frontend/web/package-lock.json
GOPULSE_VERSION_BASE=HEAD^ git commit --amend -F /path/to/message.txt
```

如果修改提交类型导致目标版本变化，先将产品版本字段恢复为父提交的版本，再执行上述命令。不要覆盖版本文件中本次改动之外的内容。

## CI 检查

`make check-version-files` 检查工作区版本格式和各字段的一致性。

`make check-versions` 检查新增非 merge 提交。PR 使用来源分支的实际提交，push 检查本次新增提交，手动运行检查受版本规则约束的历史。可在本地使用 `make check-versions BASE_REF=origin/main` 指定比较基准。每个提交都必须按其父提交版本和提交说明递增，CI 不修改文件或创建版本提交。

`versioning.required_after` 固定规则启用前的历史基准，已有历史不追溯修改。仅从该基准迁移时，允许读取旧的 `x.y.z-rc.N`，去掉后缀后按当前提交规则升级；新的版本字段必须全部使用 `x.y.z`。当前迁移提交属于 `feat`，因此从 `1.0.0-rc.1` 变为 `1.1.0`。

## 分支和发布

`develop/x.x.x` 表示创建分支时计划的本轮版本。逐次提交的版本递增不触发分支重命名或切换。本轮完成并合入主线后，再从最新主线创建下一轮 `develop/x.x.x`；名称冲突时不得覆盖已有分支。

更新 `VERSION` 不自动创建 Git 标签、推送或发布。实际发布时，才按根 `VERSION` 创建对应版本标签。已有分支、提交、标签及历史版本记录保留。
