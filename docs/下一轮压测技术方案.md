## 2. 目标与容量口径

本方案验收单后端实例、固定业务依赖与完整消费者的混合负载。维持 22 条路由、45/10/10/15/15/5 比例、1024 个容量测试身份、5 秒客户端超时，以及当前保护预算；不为提高数字扩大 executor、关闭限流或放宽 SLO。

| 输出 | 定义 | 不能推导的结论 |
| --- | --- | --- |
| `C_interval=[L,U]` | 同一快照、时长、配置下，重复确认稳定的最高下端点与失稳上端点，相对宽度 `(U-L)/L ≤ 10%` | 未找到 U 时只写容量下界，不写已找到最大容量 |
| `C_operating=0.8L` | 在该到达率完成 1800 秒测量和恢复验证的运行点 | 80% soak 通过不证明 L 能持续 30 分钟 |
| `C_30m` | 在某个明确到达率完整通过 1800 秒的最高已测点 | 没有在 L 测过 30 分钟，不能把 L 标为 `C_30m` |
| 异步能力 | 同窗口的实际提交事件率、broker 确认率、确认后成功落库率及下游消费进度 | HTTP RPS、写请求比例、publisher 数量均不能替代 events/s |
| 保护行为 | 超载时错误原因、成功吞吐、依赖与进程存活、恢复时间 | 超载成功吞吐不等于满足 SLO 的容量 |

同步 SLO 为全业务错误率 ≤1%、P95 ≤1000ms、P99 ≤2000ms、实际发起率 ≥目标的 95%。保留全请求延迟，并补成功请求延迟和各路由延迟，防止大量快速 503 拉低总体分位数。setup 和 health 从业务分母剔除；429、503、超时、传输错误、非预期状态均计业务失败。

异步验收要求测量期间无持续积压增长、oldest age 不持续恶化，结束后 120 秒内恢复。每次写入可能提交零个或多个事件，使用事务提交成功事件数和最终发布落库事件数的计数差值；禁止用 published 行数净增量代替累计发布量，因为 cleanup 同时删除历史。

正式稳定候选还须通过最后三个完整 60 秒窗口的检查：pending 不连续三个窗口末值递增，oldest age 不连续三个窗口末值递增；无未解释的发布失败、重试或下游 lag 增长。记录每窗实际提交、发布、积压差额，结合结束后完全排空判读。此项是本轮预先固定的保守门槛，不代表已证明无限时长稳定；120 秒 boundary 只用于筛选，不足以做此项长期判定。

## 3. 开测前冻结的环境和数据

### 3.1 环境

- 优先使用独立压测机，固定 k6 0.56.0 及 SHA-256；目标侧固定 CPU、内存、磁盘、网络路径和依赖镜像。记录宿主机与 cgroup 配额、CPU 核数口径、swap、磁盘余量及跨机时钟偏差。
- 目标拓扑保持单 backend、固定 worker/indexer 数量，MySQL/Redis/RabbitMQ/Elasticsearch 完整运行；需要声称观测链路容量时，再固定 Monitor/Marshaller/Kafka/VictoriaMetrics 一并验收。不同拓扑独立出报告，不与旧单机数字直接相减。
- 若只能同机，k6 与目标使用互不重叠的 CPU 集、固定配额，并记录分配；结果标为受控同机容量，生产绝对容量仍待独立机器验证。
- 压测机运行 k6 和 runner；资源、MySQL、Redis 采样在目标侧或固定观测节点执行。现有 backlog 命令只监听 loopback，跨机访问使用受控隧道或已有受保护的观测入口，不直接把无认证探针暴露出去。
- 所有生效值同时从 backend 启动日志与运行进程核对：API 池 8、outbox 池 4、probe 池 1、publisher 8、claim batch 50、executor 8、waiter 256、TTL 5m，以及准入、限流和超时。具体值若变更，建立新配置指纹，禁止混入同一个边界区间。
- 记录 backend/tool revision、构建产物 SHA-256、migration 版本、非敏感生效配置哈希。前序报告必须与当前候选、拓扑、数据档案和 SLO 指纹一致，才允许 refine/soak 继承。

### 3.2 数据档案

| 档案 | 初始状态 | 用途 |
| --- | --- | --- |
| `small-history` | 固定业务数据，pending=0，固定且已记录的小规模 published 历史 | 与旧干净档对照、定位历史影响；不代替正式长历史容量 |
| `history-550k` | 相同业务分布，550,000 条 published 历史，pending=0 | 正式 boundary/refine/soak 的主档案 |
| `overload-chain` | 从已确认档案开始，各超载阶段之间仅等待恢复、不恢复快照 | 单独观察历史积累与过载恢复，不参与主档案二分 |

每档先停止上一档业务流量并保存恢复证据，然后恢复数据库、Redis、RabbitMQ 和搜索索引的一致基线，重新准备会话，等待必要依赖与消费者就绪。只恢复 MySQL 而保留旧缓存、旧消息和旧搜索索引，不能视作同一基线。快照 hash、数据 epoch、行数、pending/leased/published、最老积压年龄、缓存状态和队列基线写入 stage receipt。

正式“清洁状态”指基线一致，允许有 550k 已发布历史。`clean` 与 `recovered` 分开记录：前者是前置状态证据，后者是本次运行结束后的排空证据。恢复失败时，必须先保留失败产物，不能通过清空表把该档改成 recovered。

重置仅作用于明确标识的专用压测环境；优先恢复完整快照。若提供 pre-stage reset，须检查目标环境标识和数据库归属，失败即停止；不能删除 pending、未到期 command、开放 requirement 来制造“干净”。生产保留期和消费者语义不随压测放宽。

550k 历史还须冻结 published_at 年龄及保留资格分布。若全部历史都可立即清理，cleanup 启动后会把长历史测成小历史。每档记录历史行数曲线；规定的 550k 规模因后台清理消失时，该次只能用于 cleanup 实验。主档案在正常保留策略内准备不会在测量期间到期的历史；另设可清理/受保护混合历史回归，验证 cleanup 竞争与游标推进。

## 4. 工具改造设计

### 4.1 分类与提前中止分离

SLO threshold 使用测量 phase 的指标，边界采用 `rate >= 0.99`，`abortOnFail=false`。runner 用成功/失败整数计数核对恰好 1% 的边界，避免 `1-rate` 浮点误差把恰好达标判成失败。k6 最终因 SLO 未通过而非零退出，仍属于一次完整的失稳测量，不得记为提前中止。`early_success_rate` 可保留作观测，但不作为累计 Rate 的 abort 开关。

`delayAbortEval` 只是推迟开始评估；不能证明连续 30 秒超限。实现以 [k6 thresholds 文档](https://grafana.com/docs/k6/latest/using-k6/thresholds/) 为语义依据，最终行为必须用仓库固定的 0.56.0 二进制验证。

本轮把“连续 30 秒错误率 >20%”固定为以下可测试规则，避免“一个 30 秒均值”与“持续超限”混用：runner 将**所有 VU** 的业务完成样本聚合为 1 秒桶，只有连续 30 个完整秒桶均有样本且每桶失败率 >20%，才中止；同时保存最近 30 秒按请求数加权的错误率。一个尖峰、某个 VU 失败或一个空桶不满足该规则。错误等于 20% 不触发。预热与测量分别计时，跨 phase 清空连续计时；预热可触发保护，但不能生成容量上端点。

`/ready` 以 1Hz 发起，runner 按连续失败时间判断：从首次失败起，至少 30 秒未出现成功且探针持续有结果时中止；一次成功清零。`/live` 独立记录存活，不替代 `/ready`。探针自身停止采样属于观测故障，不能伪装成目标故障。保留当前稳定分类中任何 `/ready` 失败即记录健康异常的严格口径；连续 30 秒只决定何时结束加压。

采用 runner 聚合是因为 VU JS 状态彼此隔离，SharedArray 只读，不能让一个 VU 的滚动数组代表全局。该约束见 [k6 生命周期说明](https://grafana.com/docs/k6/latest/using-k6/test-lifecycle/)。

第一版使用 k6 JSON 实时输出，runner 增量读取并聚合业务 outcome、health、request-start 与阶段时钟，原有 summary 继续保留。依据 [k6 JSON 输出说明](https://grafana.com/docs/k6/latest/results-output/real-time/json/)，不能等最终 summary 才判断早停。实现时验证固定版本的输出刷新延迟和中止后摘要保留，事件时间与接收时间均记录；读取落后超过 5 秒或原始输出丢失时停止并标记观测不足。运行前预留输出空间，原始流异步压缩归档；读取、归档和资源采样不能阻塞发压。受控服务上比较开启/关闭流式输出的发起率与 CPU，未达到目标则先解决压测端开销。

中止流程由 runner 发出有界的停止请求，记录停止请求时刻、实际停止时刻、退出码和原因，保存摘要后继续观察恢复；强制杀进程或产物丢失标记 incomplete。按固定版本验证普通阈值失败、保护中止、用户中断和执行异常的退出行为，不能只凭“退出码非零”判断。

### 4.2 时间、到达率与阶段隔离

建议把业务预热和测量合为一个 constant-arrival-rate scenario，在请求开始时按场景时钟确定 phase，避免两个业务 scenario 在预热排空时相互重叠，并保持 slot 连续。健康 scenario 独立。预热尾部请求仍归 warmup，不混入 measurement。

新增 `business_requests_started`，原有完成计数继续保存。每个测量窗口至少记录：`planned_seconds`、`actual_seconds`、起止时间、计时来源、`measurement_complete`、`stop_reason`、发起数、完成数、成功数、中断在途数、各 phase 的 dropped iterations。

- 正常结束：实际发压窗口为场景开始 + warmup 到计划测量结束；不把 setup、登录和请求排空计入分母。
- 提前结束：使用测量开始到实际停止发压的区间；停止时间若只能估计，记录来源与误差，数据只供诊断，不生成稳定容量。
- 实际到达率 = 窗口内发起请求数 / 实际发压秒数。成功吞吐 = 该发起请求集合最终成功数 / 同一秒数。报告另给完成数及错误率，排空完成后应满足发起数 = 成功数 + 失败数 + 中断数。
- 按请求开始归属 phase；测量结束后允许在途请求最多按固定 grace 排空并计入原 cohort。记录 grace，超时仍是失败，中断不算成功。k6 的 duration 与排空是不同概念，见 [graceful stop 说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/graceful-stop/)。
- 不能用第一/最后一个响应时间相减，不能直接用进程总耗时减预热，不能用 Counter 自带全测试 rate 代替测量到达率。0 秒或无测量样本不做除法、不判稳定。

旧 400 档按报告的 25.4 秒粗算约 396 RPS，足以说明 335.2 RPS 受错误分母影响；缺少精确发起时间与停止边界时，不把这个估算补写成正式实测值。

### 4.3 写语料与身份

保留全局 slot 控制混合比例；身份数从 VU 数独立出来。容量场景固定 1024 身份，限流/公平性场景单独使用 1/16/64 身份。setup 继续批量登录；身份映射校验 credential 与 corpus 的 user ID、用户名、索引一致。定期登录仍是混合路由，但它不重新定义身份基数。

资源选择以每个身份在指定路由的确定性出现次序为序号，可由全局 slot 的调度周期计算或预生成紧凑序列表；不得依赖各 VU 私有 counter 分配共享用户资源。PATCH 允许在该用户的 editable 集内轮换；DELETE 使用一次性、不回绕的索引。预热到测量不重置资源序号；每档恢复快照后才从零开始。序列表与 corpus 使用 SharedArray 分列，避免恢复每 VU 拷贝大对象的问题。

当前每用户 8 个 DELETE 资源，共 8192 个。删除路由理论占比为 `15% / 4 = 3.75%`；即使均匀轮换，500 RPS × 1800 秒也需要约 33,750 个资源；若加 30 秒预热则约 34,313 个。仅改轮换无法支撑 soak。

准备器先按完整请求计划统计每个用户的 DELETE 次数，再按该用户次数预留至少 20% 余量，校验资源归属、存在及与 read/interaction/editable 集不重叠。按 1000 RPS、30+1800 秒预算约 68,625 次 DELETE，含余量至少 82,350 个资源；实际逐用户整数分配还会更多。TTL 的 1800+1800 秒也必须完整计入：若按 1000 RPS 运行，约需 135,000 次 DELETE、至少 162,000 个资源；不能复用仅按 soak 配好的预算。耗尽应在启动前报 `corpus_exhausted`，运行中耗尽则使本档无效，禁止回绕后把 404 当成功。

正式方案采用预建扩展语料与配套快照，不在测量中额外创建、补充或重试删除资源，以维持每迭代一个被测 HTTP 请求。扩展后记录实际 post 总量、索引规模与快照 hash；所有正式档位使用同一规模。扩展语料改变了旧 5 万 post 的数据条件，与旧报告只做定性对照。

DELETE post 仅 204 为成功。DELETE like 仅 204，DELETE follow 仅 200；不存在关系由服务幂等处理，目标资源不存在的 404 为错误。交互 PUT 的幂等空操作另行统计或采样核对，事件率用实际提交计数，不能假定每个 2xx 都产生事件。出现 403/404 要保留有限失败样本，不能仅凭状态码把旧报告的 115 个 4xx 全部归因于语料。

### 4.4 前置校验、观测和报告契约

`require_observation=true` 且 backlog URL 为空时，在启动 k6 前返回配置错误；DRY_RUN 也检查这种结构错误。有 URL 但不可达/返回格式错误为 environment_failure。运行途中必需观测缺失为 capacity_insufficient 或 incomplete，保留原因，不收敛边界。

拟扩展 backlog 返回 `pending`、`leased`、`published_history_rows`、`oldest_pending_age_seconds`、`observed_at`。`pending` 保持旧口径，表示全部未发布行的总数，包含 leased；`leased` 是其中的租约子集。最老年龄覆盖所有未发布行，以免 leased 隐藏积压。空 backlog 年龄为 0，查询失败不能返回 0。history 计数使用有索引、低频方式（档前/档后及每 60 秒），避免每秒全表 COUNT 干扰被测库。

恢复要求初始 pending=0，结束后 pending=0、leased=0、oldest age=0 且连续三次 5 秒探测成立；同时检查 RabbitMQ ready/unacked、worker/indexer 进度回到约定基线。现有 runner 一次探测回到 baseline 就退出，不能证明下游也完成。即使主测量提前中止，也须观察恢复；未恢复不启动下一档。120 秒后允许延长诊断采样，但不能把超时恢复改为通过。

结果分为“测量有效性”和“容量分类”，优先判断前者：

| 条件 | 结果 | 是否更新区间 |
| --- | --- | --- |
| 完整窗口、语料有效、必需观测齐全、SLO 与恢复全部通过 | stable | 重复确认后更新 L |
| 完整有效窗口 SLO 或恢复失败；或测量期保护规则明确触发 | unstable，携带具体原因 | 复测一致后更新 U；保护中止永不更新 L |
| 压测端掉迭代 >1% 或不能证明发起率、缺必需证据 | capacity_insufficient | 否；轻微掉迭代仍记录，目标仍须达到 95% |
| 探针不可达、配置/凭据/服务启动错误、语料无效 | environment_failure | 否 |
| 用户取消、时钟边界丢失、强制终止或产物不全 | incomplete | 否 |

发起率不足不能直接归因于服务端。并列保存 SLO 失败与测量缺陷，但存在有效性问题时不得据该档更新任何端点。refine 先检查状态再更新区间；boundary 只使用已确认端点，非单调或互相矛盾结果写 `inconclusive`，不标 `confirmed_interval`。

报告拟升级为 `gopulse.k6.load.v2`，保留原始 v1 产物；config 新增字段需同步 Go 结构、严格校验与 schema。新增每档唯一 ID、attempt、父报告 hash、候选/环境/数据指纹、完整性、停止原因、实际窗口、基线、事件率和观测缺口。产物以 `run_id/stage_id/attempt` 隔离，修复当前 summary 文件名不含 run_id、重复运行可能覆盖的问题。旧短窗口报告不能自动导入正式区间；不得手工改报告状态来喂给 refine。

## 5. 观测最小集合

所有时间序列对齐到相同 UTC 和 stage 标记，阶段持续时间使用单调时钟。常规 1Hz，history 计数及慢查询计划低频采样。正式档必需信号缺失超过连续 5 秒或有效样本覆盖率不足 99%，本档不得判 stable；低频 history 按其计划槽位单独检查，不套用 1Hz 覆盖率。

| 层次 | 信号 | 当前状态与改造 |
| --- | --- | --- |
| 客户端 | 发起/完成/成功、总与成功延迟、22 路由、429/503/超时/传输错误、非预期状态 | 已有部分汇总，补开始计数、phase 时钟、错误码与流式聚合 |
| 503 归因 | `backend_busy`、`rate_limit_unavailable`、`post_read_unavailable`、`missing`、`other`，按 route 汇总 | 客户端解析实际响应 JSON 的 error_code，保留缺字段类别；有限白名单标签，不把未知原文作标签 |
| 保护与缓存 | 全局/资源拒绝、命中/回源、executor/waiter 在途及拒绝 | 已有在途、waiter 与通用拒绝；新增重建 executor/waiter 各拒绝路径的计数，避免重复计数 |
| outbox | pending/leased、最老年龄、历史行数、claim/cleanup P95/P99 与失败数、提交/确认/发布落库数、租约重投 | 后端已有 pending/age、claim/cleanup histogram、确认计数；补 runner 消费及提交/落库计数证据 |
| MySQL | API/outbox/probe 池占用与等待，活跃锁等待数、等待累计时间、deadlock、慢操作样本 | 已有分池指标；接入 MySQL exporter/performance_schema 的 InnoDB 等待与锁关联 |
| 下游 | RabbitMQ ready/unacked、消费者确认/失败，索引消费进度；纳入拓扑时的 Kafka lag | outbox published 仅代表发布完成，下游尚需单独证明 |
| 资源 | 目标各进程/容器与压测机的 CPU、RSS、IO、网络、调度滞后、重启/OOM | 复用 sampler，补远端压测机与 MySQL 锁等待采样；CPU 同时给核数与配额百分比 |

`backend_busy` 可能来自不同保护层，客户端 error_code 无法单独区分，须与同窗口服务端拒绝计数关联。日志已采样，不能从日志条数推导全量错误率。失败响应只保留脱敏的 request ID、路由、状态、error_code、耗时，禁止归档 Cookie、密码或完整私有请求体。

## 6. 实验顺序与执行参数

### 6.1 准入验证

先完成第 4 节工具验证，再冻结候选并执行 backend 单测、business/observe 集成、R09 和 550k 历史回归。多 publisher 使用真实 RabbitMQ 的 mandatory/confirm/return 加最终 outbox 落库验收，保持 ≥300 events/s 门槛；R09 保持原相对吞吐 ≥90% 门槛。历史记录只能作为对照，不能代替当前候选的实际输出。任何正式门槛失败，允许继续诊断，但不得出具全部验收通过结论。

对 history-550k 保存 pending/过期 leased/cleanup 三类 EXPLAIN，确认使用各自索引；同时实际跑 claim、保留约束下 cleanup、过期租约恢复和连接池隔离，不能只检查计划里出现索引名。记录扫描量、耗时、锁等待、候选/删除数和查询 deadline。检查 8 publisher 的生效配置及独占 channel，确认指标区分 broker 确认与最终落库。

### 6.2 测试矩阵

| 阶段 | 到达率 | 预热 / 测量 / 恢复 | 重复与判读 |
| --- | --- | --- | --- |
| 工具 smoke | 10、100 RPS，受控响应服务 | 短窗口，注入阈值/错误/中止 | 只验工具，不进容量结论 |
| 后端定向回归 | 饱和事件输入 | 按真实集成用例；补长历史运行 | ≥300 events/s 是异步门槛，不等于 300 HTTP RPS |
| 历史影响对照 | 200、400、500、600 RPS | 30 / 300 / 120 | small-history 与 history-550k 各独立 3 次，固定顺序交错，优先覆盖旧 400 不复现问题 |
| boundary | 10、20、40、80、160、320、640、1000 RPS | 30 / 120 / 120 | history-550k；到候选失稳点暂停并确认；不是 200/400/800 序列 |
| 端点确认与 refine | 已确认区间，逐步二分 | 30 / 300 / 120 | 每个候选独立 3 次；上下端点用相同 300 秒口径复核，最多 8 次二分，宽度 ≤10% |
| soak 运行点 | `0.8L` | 30 / 1800 / 120 | history-550k，独立 3 次，中途不 reset，不清历史 |
| 30 分钟容量确认 | L；失败后降低到已测候选 | 30 / 1800 / 120 | 仅在需声明 `C_30m=L` 时执行；各候选独立 3 次 |
| 超载保护 | `1.2L`、`1.5L`、`2L` | 30 / 120 / 120 | 主容量结束后独立执行；触发早停保留部分数据；未恢复停止后续档 |
| 限流/公平性 | 1/16/64 身份，围绕配置配额 | 30 / 120 / 120 | 另设场景，检查 429、身份间成功吞吐和恢复；不混入容量区间 |
| TTL A/B | 固定的已确认稳定 RPS | 每组 1800 / 1800 / 120 | 5m/30m 各自同快照、同访问序列；独立于 soak |

表中 30 秒 refine/soak 预热属于拟新增能力：当前 plan 给它们 0 秒，不能只改 JSON 宣称已启用。soak 的 1800 秒始终是测量时长，预热另计。1000 RPS 仍稳定时，报告容量下界；需要上探时另冻结 max_rps=1600 的配置并确保发压资源充足。

### 6.3 失稳确认与二分规则

1. boundary 首次疑似失稳后先完成恢复与取证，再按同一快照重复该档两次。两次补测均失稳才记为可重复失稳候选；出现通过或失稳原因变化，标记结果不一致，不立即固定 U。
2. 将稳定与失稳候选都延长到 300 秒、独立重复三次：全部通过才能确认 L，全部有效失稳才能确认 U。混合结果记录波动区；无效结果不参与投票，修复测量条件后重跑。
3. 原失稳点变成三次稳定时，以此更新 L，并继续 boundary 剩余档位。针对旧报告争议点保留 400/500/600 定向结果；只有在同条件下确认更高稳定点，才允许越过旧失稳点继续上探。低档仍反复失稳而高档通过时，停止单调二分，回查状态、缓存与观测。
4. refine 只在确认的 L/U 中点测试。三次通过更新 L，三次失稳更新 U；混合结果不更新，报告区间尚未收敛。最多 8 次中点尝试是上限，不是允许挑选最好结果的次数。
5. 支持手工指定 stable/unstable 区间，但每个端点必须引用匹配指纹的原始报告与重复验证记录。手工输入只是候选，不自动成为 confirmed。refine 报告保存继承端点和全部尝试，防止只凭本阶段结果丢失边界。
6. soak 失败时先定位失败原因；确认为持续容量不足则降低运行点，重新完整测量。不得反推未实际测试的稳定容量，也不把缩短后窗口的通过替代 1800 秒通过。

每次运行分别保留结果，摘要给中位数、最小/最大、标准差与通过次数；不把三次延迟样本合并为一个 P99，也不把失稳尝试从平均值中删除。1% 附近给出样本数与错误率区间，不能把旧 0.97% 与 1.53% 的差异直接断言为唯一因果；可重复历史对照和同窗口指标才能支持归因。

### 6.4 时间预算

不含准备、恢复快照和诊断，boundary 八档按最坏恢复窗口约 36 分钟；8 个 refine 中点各三次约 180 分钟；soak 三次约 97.5 分钟；TTL 两组约 124 分钟。历史对照 4 档 × 2 档案 × 3 次约 180 分钟，另加端点确认和可选 `C_30m`、超载、限流实验。全套应按两天以上排期，工具修复与 backend 回归另计；资源不足时先交主档案容量与运行点，TTL 和公平性单列未完成，不用短窗口替代。

## 7. TTL 与限流的独立验收

TTL 固定 API 池 8、executor 8、同一候选、相同快照和访问序列；每组重新建立相同缓存初始状态。两个 30 分钟窗口分别是预热与测量，总压测流量至少 60 分钟。`sample_capacity.py` 只负责采样，默认 1800/1800 不会自动生成流量、恢复快照或验证 hash 的真实性，必须由 runner 协调实际负载与标记。保存访问序列文件/生成算法版本、seed、SHA-256 和回放完成证据，不能只传两个相同字符串。

仅在 30m TTL 相比 5m 命中率提高 ≥10 个百分点、回源减少 ≥20%、Redis 峰值内存低于 maxmemory 的 75%、无新增缓存写失败且证据完整时采用 30m；否则维持 5m，缺证据记 inconclusive。变更 TTL 后若要发布新的容量数字，需要在该 TTL 配置下重做主流程，不继承 5m 的边界。

小身份池场景将身份选择和路由 slot 解耦，保证各身份仍覆盖所需路由；记录每身份类别配额与实际请求分布，预期 429 单独作为限流验收结果。该场景的错误预算不改变正式容量 1% SLO，不能用容量场景 0 个 429 宣称限流公平性通过。
