01 · 先建立整体认识

GoPulse 是社交内容应用：用户注册登录后，可以发布内容、评论、点赞、收藏、关注用户、搜索帖子和读取通知。超级管理员在同一个 Vue 前端管理账号角色。

后端是一个 Go 模块中的模块化业务系统，运行时拆为 API、通知 Worker 和搜索 Indexer。它们共用 MySQL 和事件契约，并非各自拥有独立数据库的微服务。MySQL 保存业务事实，Redis 加速读取并提供共享限流，RabbitMQ 传递事件，Elasticsearch 保存可重建的搜索投影。

↓ 同源 HTTP / JSON / Cookie

API · Gin → Handler → Service → Repository

03 · 浏览器如何进入系统

入口 main.ts 装载 App.vue；router.ts 设置页面和会话守卫。session 管理当前用户，community 组织社区交互。services/api.ts 封装业务请求，services/http.ts 统一 JSON、Cookie、超时和错误处理。

页面用途
/、/following、/bookmarks复用 FeedView 展示发现、关注、收藏
/posts/:id帖子详情与讨论
/me、/users/:username个人和作者资料
/relations/:kind关注及粉丝
/search、/notifications搜索与通知
/login、/register公开认证页面
/admin/roles超级管理员角色管理

请求统一发往 /api/v1，使用 credentials: include，默认请求超时为 12 秒。登录凭据由后端通过 HttpOnly Cookie 下发。路由守卫先恢复会话，未登录用户访问受保护页面时转到登录页。前端角色守卫仅控制导航，真实授权仍由后端完成。

注册 / 登录 → auth 校验与令牌签发 → 浏览器保存 Cookie → 后续请求由认证中间件识别用户 → Handler 调用业务模块。写请求还受同源检查及请求保护约束。

04 · 发帖：一次请求背后的完整链路

  1. 前端读取 GET /post-commands/context，取得 data_epoch，并生成 Idempotency-Key。
  2. 前端在 localStorage 保留用户、幂等键、纪元和原始内容，再发送 POST /posts，同时携带 X-GoPulse-Data-Epoch。
  3. 后端验证参数和运行状态。在 MySQL 事务中锁定当前运行状态，检查纪元、幂等键和请求摘要。
  4. 同一事务写入帖子、成功命令记录、v2 post.created Outbox 事件、搜索消费义务和容量占用。事务期间不调用 Redis、RabbitMQ 或 Elasticsearch。
  5. 提交后，API 返回业务结果。搜索更新仍由后台完成。
  6. Outbox 分发器领取有租约的记录，发布事件，收到发布成功结果后标记已发布。
  7. Indexer 消费事件，更新搜索投影并记录处理结果。通知 Worker 不消费 post.created。

同一有效幂等键配合相同内容会回放已有结果；内容不同会产生 idempotency_conflict。并发请求最终由数据库唯一约束兜底。结果记录有保留期限，不能把幂等保证理解为永久保存。

网络超时不等于数据库回滚。前端保留待确认记录，通过 GET /post-commands/result 查证，或使用原记录重试。切换账号时，不允许误用另一个账号的待确认发布。查询命令成功也不保证帖子当前仍可读取。

06 · 读取、缓存与搜索

普通读取由业务 Repository 查询 MySQL，并使用相应缓存适配器。帖子返回对象除正文外，还包含当前访问者的点赞、收藏、关注等状态。不能将整个带用户状态的响应视为所有用户共享的数据。

缓存实现分别位于 post/cache、post/repository_discovery、comment/cache、user/cache_profile、search/result_cache 和 platform/postcache。缓存键、版本、失效和回源规则由各模块管理；Redis 还承担共享限流，不能把 Redis 故障简单等同于“缓存没命中”。

搜索词 + 游标 → Search Service
↓ 搜索结果缓存 / Elasticsearch 候选命中
帖子 Hydrator → MySQL 当前状态与访问者数据
↓ 过滤不可见结果，补全内容和关系状态
结果 + 下一页游标 → 前端

搜索支持绑定查询、数据纪元和索引 generation 的游标；实现包含 PIT（时间点视图）和缓存偏移分页路径。PIT keep-alive 为 2 分钟，默认每页 20 条，上限 50 条。游标有签名与有效期，不应由客户端拼造。

Elasticsearch 是异步投影。刚提交的帖子可能尚未被搜到；删除后的旧命中需要经过业务可见性校验。用户搜索由 user 模块提供，不应与帖子全文搜索混为一谈。

07 · 消息可靠性与一致性

事件交换机 → 队列消费者
comment.created / post.liked / user.followedgopulse.business.v1 → gopulse.business-worker.v1业务 Worker
post.created / post.updated / post.deletedgopulse.search.v1 → gopulse.search-indexer.v1搜索 Indexer

两条链路分别具有 retry 和 dead 交换机及队列。重试队列通过消息 TTL 和 dead-letter exchange 回到主交换机。路由键保留 .v1 后缀；后缀不能用于判断消息信封一定是 v1。

Outbox 发布成功但数据库标记失败时，消息可能再次发布。因此这是至少一次投递边界，消费者必须处理重复。Publisher 确认只说明消息发布阶段完成；它不说明通知已经落库或搜索已经更新。

data_epoch 标识一代业务数据；content_revision 标识帖子内容版本；command_id 标识业务命令；event_id 标识事件；projection generation 标识搜索索引代次。这些标识分别解决恢复隔离、乱序、重试和重建问题。

businessstate 保存消费义务和消费结果，并对积压和保留数据计量。容量耗尽可拒绝新的业务写入，错误码为 business_async_backlog。隔离消息存入 business_message_parking；它与 RabbitMQ 死信队列不是同一存储。

代码仍保留 v1 兼容构造和校验路径；当前发帖命令使用 v2。判断实际路径应追踪生产者调用和运行状态，不能只看 SchemaVersion 默认常量或历史注释。

09 · 部署、维护与故障定位

Compose 启动关系：MySQL 健康 → migrate up → Elasticsearch 健康且迁移完成 → search-init --if-missing → API / Worker / Indexer → web。API 还等待 Redis、RabbitMQ，消费者等待 RabbitMQ。web 使用 gopulse/web 镜像，其余应用进程和维护命令共用 gopulse/backend 镜像。

Compose 将网络分为 edge、proxy、backend、search，后面三个为内部网络。源码运行默认 API 为 127.0.0.1:8080，Worker 和 Indexer 健康端口分别为 19102、19103，Vite 为 5173。不要把这些宿主机默认值直接当成容器对外端口。

后端只读取进程环境变量，不自动加载 .env。根 .env.example 保存配置示例；host/container 模式校验地址约束。日志使用 slog JSON，进程保留 /startup、/live、/health、/ready。就绪检查依据该进程所需依赖判断，不代表所有历史消息均已消费。

现象检查顺序
发帖超时保留原幂等键 → 查询命令结果 → 再决定原内容重试
帖子存在但搜索不到检查 Outbox → RabbitMQ 搜索队列 → Indexer → 索引状态
通知延迟检查对应事件 → 业务队列与重试/死信 → Worker → notifications
写入提示异步积压检查未完成消费义务及容量 → 排查消费失败；不要直接删除证据记录
角色操作失败检查会话与数据库角色 → 初始管理员状态 → 审计及错误码

search-reindex 从 MySQL 重建索引；--if-missing 仅在别名缺失时初始化。恢复模式要求 --restore-operation、--expected-old-epoch、--new-epoch 同时提供，且不能与 --if-missing 合用。该命令不执行数据库备份恢复。

升级迁移 22 前需停止访问旧表名的进程；迁移 23 前停止旧 Worker。删除性迁移的 down 只能重建结构，不能恢复历史数据。

11 · 建议阅读顺序与验证范围

  1. 先读本页整体图，再读 cmd/server/main.go，掌握依赖如何组装。
  2. 从前端 post-command.ts 跟进 HTTP Handler、Service、repository_command.go，理解一次写入。
  3. 接着读 Outbox dispatcher、Worker handler、search/processor 和 notification/processor，理解异步边界。
  4. 读 post 的读取与缓存文件、search/service.go，理解列表和搜索为什么需要补全。
  5. 最后核对 migrations、config、compose.yml 与集成测试，掌握故障和部署约束。

仓库验证入口：make ci-tools；make ci-check / ci-test / ci-build MODULE=backend/business；make check / test / build MODULE=frontend/web。前端首次验证先执行 make -C frontend/web install。真实依赖联调不能用单元测试结果代替。
