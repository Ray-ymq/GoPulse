# 测试六：16 核 / 12 GiB 逐级加压测试方案

状态：已完成规划。专用环境、工具适配、预检和正式压测尚未执行；本文不提供容量结论。

## 1. 目标与历史依据

[测试五](../05-测试五/2026-10-21-测试五-CPU配额对照测试报告.md)在 MySQL 4 vCPU / 2 GiB、单业务 API、Redis 关闭的条件下，120、140 RPS 均为零错误，全部请求 P95 分别为 152、158 ms。140 RPS 是该轮最高已测且通过的负载，尚未测出容量上限。

PT6 使用下述 16 核 / 12 GiB 预算，部署两个业务 API、两个 business-worker、两个 search-indexer，并启用 Redis。测试回答：

1. 当前业务组合的最后通过档、首次未通过档和最大成功吞吐分别是多少？
2. 连续加压时，限制来自 MySQL、API、异步处理、搜索、Redis、入口代理，还是 k6？
3. 首次失败前，各档位的异步积压及最老年龄如何变化？
4. 停压后能否在 10 分钟内自然排空积压，写入和异步结果是否正确？

本轮同时改变资源、实例数和 Redis 状态，结果只表示这套部署的容量。与 PT5 的比较用于描述整体变化，不能将变化全部归因于 MySQL 6 核或缓存。

## 2. 资源配置

### 2.1 总预算

以下配置按用户给定值固定。CPU 单位为 vCPU 配额，内存使用 GiB；1 GiB = 1024 MiB。

| 组件 | CPU 上限 | 内存上限 |
| --- | ---: | ---: |
| MySQL | 6 核 | 3.5 GiB，buffer pool 先保持 2 GiB |
| 搜索 Elasticsearch | 2 核 | 2 GiB，堆 1 GiB |
| backend ×2 + platform-api，合计 | 2 核 | 0.75 GiB |
| business-worker ×2，合计 | 1 核 | 0.5 GiB |
| search-indexer ×2，合计 | 1 核 | 0.5 GiB |
| RabbitMQ | 0.5 核 | 0.5 GiB |
| Redis | 0.5 核 | 0.5 GiB |
| frontend + admin-frontend，合计 | 0.25 核 | 0.25 GiB |
| k6 | 1.5 核 | 1.5 GiB |
| WSL / Docker / 系统余量 | 1 核预算 | 1.5 GiB 预算 |
| 应急预留 | 0.25 核 | 0.5 GiB |
| **合计** | **16 核** | **12 GiB** |

服务与 k6 的配额合计为 **14.75 核 / 10 GiB**。系统余量与应急预留合计为 **1.25 核 / 2 GiB**，不创建占用这些资源的容器，也不将预留重复分给其他组件。CPU 配额是使用上限，不保证各组件独占相应核心；主机调度和磁盘 I/O 仍需观测。

### 2.2 逐实例分配

下表为 PT6 的初始分配。组内及组间保持一致；需要调整时结束当前系列，另建配置编号复测。

| 服务 | 实例数 | 每实例 CPU 上限 | 每实例内存上限 |
| --- | ---: | ---: | ---: |
| `backend`、`backend-2` | 2 | 0.75 核 | 256 MiB |
| `platform-api` | 1 | 0.5 核 | 256 MiB |
| `business-worker`、`business-worker-2` | 2 | 0.5 核 | 256 MiB |
| `search-indexer`、`search-indexer-2` | 2 | 0.5 核 | 256 MiB |
| `frontend`、`admin-frontend` | 2 | 0.125 核 | 128 MiB |

其他服务和 k6 各一个实例，配额采用总预算表中的对应值。组前、组后均核验 Docker 配置及 cgroup 的 `cpu.max`、`memory.max` 和 `memory.swap.max`。所有受限容器禁用额外 swap，Docker 的内存交换总上限设为与内存上限相同；记录 WSL 的可见 CPU、内存和 swap 实际值，不将 swap 计入 12 GiB。

MySQL 设置并核验 `innodb_buffer_pool_size=2147483648`。搜索 Elasticsearch 固定 `-Xms1g -Xmx1g`，不能继承默认 Compose 中的 512 MiB 堆。正式测量时使用 `restart: no`，由采集器记录退出、OOM 和重启事件。

## 3. 部署与固定参数

### 3.1 测试范围

本轮覆盖业务 HTTP、MySQL、Redis、RabbitMQ、搜索索引以及两个前端的入口代理。k6 统一访问 `frontend` 发布端口，业务请求经现有 Nginx upstream 分发到两个 backend。每个 backend 分别采集请求数、连接池和拒绝指标，核验两个实例均实际承载请求。记录 Nginx upstream 尝试次数和重试配置，客户端请求与上游尝试分开计数。

`platform-api` 和 `admin-frontend` 保持运行，组前、组后检查管理路由及静态页面；正式业务比例不增加管理请求。管理、日志、事件和指标查询的容量不在本轮结论范围内。

资源表未包含 Monitor、Marshaller、Kafka、VictoriaMetrics 或观测 Elasticsearch，本轮不启动这些服务。现有 [Compose](../../deploy/compose.yaml) 的 `platform-api` 依赖观测 Elasticsearch 和 VictoriaMetrics，不能直接启动完整默认栈。准备阶段需要制作专用部署配置，移除相应的自动启动依赖，并固定 `ALERT_EVALUATION_ENABLED=false`、`LOG_MONITOR_URL` 为空、`GOPULSE_TRACE_ENABLED=false`。保留合法的客户端配置，验证 platform-api 的启动、就绪和本轮管理冒烟路由；不访问依赖表外服务的观测接口，不将搜索 Elasticsearch 复用为观测存储。

若裁剪后仍必须运行表外依赖，应先修订范围和资源分配，不能将这些依赖隐含计入系统余量。exporter、采样器和报告进程的运行开销计入系统余量；构建、迁移、语料生成和报告绘图在正式窗口外执行。

测试使用独立 Compose 项目、网络、卷和 Redis 数据库。恢复和清理仅作用于经身份校验的测试资源，不复用日常环境或 PT5 运行中的容器。迁移和索引初始化作为一次性任务，在空载观察前完成并退出。

### 3.2 初始参数

除已指定的资源外，按下表准备初始参数。准备完成后保存实际生效值，正式系列不再调参。

| 项目 | PT6 初始值与约束 |
| --- | --- |
| 业务 API | 每实例 `MYSQL_MAX_OPEN_CONNS=8`、`OUTBOX_MYSQL_MAX_OPEN_CONNS=4`；就绪检查专用池上限 1 |
| platform-api | `PLATFORM_API_MYSQL_MAX_OPEN_CONNS=4`；就绪检查专用池上限 1 |
| worker / indexer | 每实例 `MYSQL_MAX_OPEN_CONNS=4`；同时服务消费和就绪检查 |
| 连接总预算 | `MYSQL_TOTAL_MAX_OPEN_CONNS=60`；上述池上限合计 `2×(8+4+1)+(4+1)+2×4+2×4=47`，余下 13 用于采集、检查与管理连接 |
| 连接池公共配置 | `MYSQL_MAX_IDLE_CONNS=2`、`MYSQL_CONN_MAX_LIFETIME=3m`；核验 MySQL `max_connections` 能容纳总预算和管理余量 |
| 实例标识 | 每实例唯一 ID；backend、worker、indexer 的 `GOPULSE_REPLICA_COUNT=2`，platform-api 为 1；采集目标逐实例列全 |
| 请求保护 | 保留现有 HTTP 并发、读写资源预算和超时；业务限流保持启用，记录每实例实际值，不为提高结果临时关闭保护 |
| 异步保护 | `BUSINESS_ASYNC_MAX_OPEN_REQUIREMENTS=10000`；保留现有保留组数、字节上限和重试配置，并记录实际值 |
| Redis | 业务进程显式设置 `BACKEND_REDIS_DISABLED=false`；正文缓存 TTL 5 分钟，`REDIS_MAXMEMORY=384mb`、`REDIS_MAXMEMORY_POLICY=noeviction`；AOF 保持开启 |
| RabbitMQ | 保留现有持久化、prefetch 和重试配置；核验容器内存识别及内存水位配置，记录资源告警和发布阻塞 |
| MySQL 持久化 | 保留当前事务、redo、binlog 和刷盘配置，记录实际值；不通过降低持久性换取吞吐 |

Redis 的容器上限仍为 512 MiB，384 MiB 是本轮规划的 `maxmemory` 初值，为进程及持久化开销留出空间，不代表已验证足够。预检应覆盖缓存写入、内存峰值和错误；不能直接沿用与容器上限相同的默认 `512mb`。

配置总连接预算只提供配置约束，不能据此认定各进程共享一个全局连接池。核对总连接时必须累加全部实例和专用池。

## 4. 数据与负载

保留历史业务比例和均匀交错请求序列：读 45%、搜索 10%、通知与书签等读取 10%、内容写 15%、互动写 15%、身份与会话 5%。请求超时先固定为 5 秒。

以 PT5 使用的数据和账号集合为起点，记录数据库与索引摘要、表行数、索引文档数、账号数和语料摘要。旧语料不能直接认定足够：准备阶段必须离线遍历完整计划序列，覆盖预热、正式窗口和已规划的全部连续档位。补足每个账号有权编辑、删除的目标及其他写入所需数据，并为后续动态档位设置序列预检；语料不足时停止并汇报，不能开始对应档位。必要的数据扩充须在正式系列开始前完成，并重新建立统一基线。

连续系列开始前恢复数据库和搜索索引基线，清空专用测试队列及 Redis 数据，核验全部 epoch 的初始积压归零。恢复后先冒烟，再恢复一次，避免冒烟写入污染基线。缓存由固定 setup 和预热建立；记录预热前后命中、未命中及内存，不将本轮称为纯冷缓存测试。后续档位沿用当前状态，不恢复快照、不清缓存或积压、不重启服务。

k6 先用 512 VU，适配后允许在 1.5 核 / 1.5 GiB 内调整。正式系列前验证目标负载下的调度、内存和日志写入开销；同负载复测固定 VU 数和账号集合。高档位需要更多 VU 时，先预检并记录变更，不提高 k6 资源上限。1.5 核 / 1.5 GiB 不能保证产生任意高 RPS。

## 5. 测试安排

### 5.1 从 250 RPS 开始，每档增加 50 RPS

正式系列直接执行 **250 → 300 → 350 → 400 → 450 → …… RPS**，第 `n` 档为 `250+50×n` RPS，`n` 从 0 开始。取消 100/140 RPS 正式基线、翻倍加压和自动边界复测。

| 步骤 | 安排 | 进入下一步的条件 |
| --- | --- | --- |
| 系列准备 | 恢复基线、冒烟、再次恢复；空载观察 60 秒 | 预检、冒烟和采集全部通过 |
| 首档 | 250 RPS，预热 30 秒，正式测量 5 分钟 | 全程无业务失败且该档验收通过 |
| 后续档位 | 上一档目标增加 50 RPS，每档适应 30 秒，正式测量 5 分钟 | 全程无业务失败且该档验收通过 |
| 首次失败 | 立即停止业务负载、取消所有后续档位、保存现场并汇报 | 本轮结束，不自动重试、降档或追加其他测试 |

“出现失败”按严格口径执行：预检、setup、预热或正式窗口出现非预期业务响应、429、503、超时、传输错误、最终未完成请求、数据不一致或环境/采集故障时，立即停压并汇报，不等待失败率累计到 1%。未出现这些失败，但档位结束后的延迟、实际请求率或其他验收项未通过时，同样停止并汇报，不进入下一档。

若 250 RPS 就失败，报告“250 RPS 首档失败，本轮没有通过档”，不能用 PT5 的 140 RPS 补成本轮基线。若第 `n` 档失败且此前有通过档，报告上一通过档、当前失败档及停止原因；这个 50 RPS 区间只描述本次连续系列，不代表独立稳态容量边界。

仅当当前档通过时才增加 50 RPS。开始下一档前核验剩余语料、压测器能力及采集状态；无法满足时停止并汇报已测结果，不静默跳档或扩大资源。取消通用规范中的失败后继续超载、吞吐平台追加窗口和自动复测要求。本轮不自动追加 30 分钟稳定性测试。

### 5.2 停压与汇报

发现失败后先停止发起新业务请求，记录停止时刻和在途请求，再立即汇报当前 RPS、失败阶段、首个失败、已完成时长、上一通过档及证据路径。被中断的档位标记“失败，窗口未完成”，不能作为完整 5 分钟结果。未执行的档位标记“未执行”。

汇报后仅保留服务、只读环境/积压检查和资源采集，最多观察 10 分钟自然恢复，不追加登录、写入或其他压测流量。全部 epoch 的 open requirements 和 parked messages、RabbitMQ ready/unacked 归零后，以只读查询核对写入结果及搜索最终可见性，补充恢复结果。不能仅凭 `/ready` 判断恢复。10 分钟未排空时记录“观察窗口内未恢复”并保存现场；不自动清积压、重启或修复后续跑。

## 6. 指标、验收与停压

### 6.1 业务验收

每档要求业务失败数为 0，全部请求 P95 不超过 1 秒、P99 不超过 2 秒，实际业务请求率至少达到目标的 95%。超时、传输错误及窗口内发起但最终未完成的请求计入失败；迭代丢弃单列，不作为已发出的 HTTP 请求，但出现迭代丢弃即停止并汇报。本轮采用“首次失败即停”，不沿用通用规范允许不超过 1% 失败的继续加压规则。

同时给出成功请求 P50/P95/P99、成功吞吐、429、503、其他错误及分路由结果。setup、预热、健康检查、尾部请求和恢复检查与正式业务窗口分开统计。成功吞吐只计算达成预期业务结果的请求；404 幂等删除与首次成功删除分开记录。窗口边界请求单列，保持 `started = outcomes + unfinished` 可核对。

每档结束时还须确认采集有效、配额一致、未触发保护，记录异步积压及最老年龄；不因 HTTP 零失败而忽略异步退化。报告中的档位通过先表示该窗口的请求与环境验收通过；整链路结果还需停压后的写入核对及自然恢复证据，二者分别报告。5 分钟通过不代表长期持续容量。

### 6.2 采集要求

| 类别 | 必须保留的证据 |
| --- | --- |
| 全部容器与 k6 | 每 5 秒 CPU 使用、`cpu.stat` 节流、实际配额、内存及 swap 使用、OOM、退出和重启；分别记录每实例与角色汇总 |
| 主机与采集器 | 可用内存、CPU、swap 活动、磁盘空间、I/O 延迟/吞吐、采集进程资源开销；确认系统余量未被表外服务占用 |
| k6 | 目标/实际请求率、成功吞吐、丢弃迭代、VU 使用、调度延迟及自身资源；区分客户端未发出与服务端拒绝 |
| 入口和 API | 每实例请求数、延迟、in-flight、读写拒绝、连接池等待；入口上游尝试、错误及重试，核对流量分布 |
| MySQL | COMMIT 次数/耗时、预算锁快照、行锁增量、连接和池等待、redo/binlog I/O、buffer pool、慢查询或摘要截断状态 |
| Redis / RabbitMQ / 搜索 | 缓存命中/未命中、内存、写入错误；队列 ready/unacked、重试和资源告警；搜索堆、GC、拒绝、索引延迟 |
| 异步与正确性 | 实际提交/处理事件数、全部 epoch 积压及最老年龄、parked 消息；按资源 ID 核对新增、更新、删除和互动最终状态 |

复用现有 exporter 及窗口增量口径。正式窗口不执行额外性能诊断 SQL，写入核对在恢复结束后执行；pprof 默认关闭，需要时另开诊断组。CPU 百分比以一核为 100%，同时报告相对各自配额的使用比例。SQL 累计耗时不等于 CPU 时间，锁快照不等于逐次锁等待事件数。

采样间断或边界样本距离窗口超过 10 秒、计数回退、摘要截断影响判断或实例漏采时，标明对应证据不完整，不补零。使用正式窗口首末边界计算计数增量，按组保留原始结果，不跨组混合延迟样本。

### 6.3 停压条件

以下阈值为本轮规划值，预检核对监控信号与执行行为后冻结；修改阈值须记录原因并另建运行配置。

| 触发条件 | 动作与结果归类 |
| --- | --- |
| 首次业务失败、迭代丢弃，或档位结束后任一验收项未通过 | 立即停压并汇报，取消后续档位，不自动复测 |
| 任一被测组件或 k6 崩溃、OOM、非计划重启，或发现非预期数据丢失/一致性异常 | 立即停压并保存现场；k6 先故障时注明被测系统极限尚未测出 |
| 主机可用内存低于 1 GiB，或测试卷所在文件系统可用空间低于 20 GiB | 停压，记录资源保护触发时刻及前后样本 |
| MySQL 总连接达到 `min(131, max_connections−20)` | 停压；准备阶段核验 `max_connections` 至少覆盖 60 个预算连接及 20 个管理余量 |
| 全部 epoch 的 open requirements 合计达到 9000，或应用触发既定保留组数/字节保护 | 停压并观察自然恢复；记录阈值先于业务容量边界触发的情况 |
| 数据库检查失败、采集/保护心跳失效，配额或目标身份发生变化 | 立即停压并汇报，按故障或无效运行记录，不将缺失证据解释为正常 |
| 语料耗尽、请求序列无效，或 k6 不能维持有效负载 | 停止并汇报，不能据此判定服务容量；修复后的复测不属于本轮自动流程 |

实际请求率不足 95% 时停止并汇报，同时核对丢弃迭代、VU、调度、客户端资源与服务延迟；若不能排除压测器限制，报告“被测系统极限尚未测出”。不在运行中抬高资源、连接或积压保护阈值以继续加压。

## 8. 归档与报告

原始数据拟保存于 `.run/pt6/observations/<run-id>/`，运行清单和配置保存于 `.run/pt6/`。每组保留实际起止时间、UTC+8 时区、目标身份、逐实例配额、窗口指标、采集有效性、停压原因、恢复结果和写入核对。

正式报告和摘要放在本目录，文件日期采用实际测试日期。报告分别给出最高已测负载、最大成功吞吐、上一通过档、首次失败档、首个失败原因及自然恢复结果；记录应急预留是否动用。若压测器、积压保护或环境故障先终止，说明限制，不外推未测档位。

下一项优化只依据本轮证据选择；修改 buffer pool、连接池、资源分配、缓存策略或保护配置后，建立新的配置编号，以相同负载独立对照。原始日志、账号、令牌、DSN 和语料不提交 Git。
