# 性能测试方案3：无 Redis 的业务加压与 MySQL 故障边界

> 方案日期：2026-10-20（+08:00）
> 状态：仅编写方案，尚未执行压测。Redis 停用、工具修正和观测准备必须在后续执行前完成。

## 1. 目标与范围

通过 GoPulse 业务接口逐级增加负载，分别定位业务失稳、MySQL 持续不可用和 MySQL 进程崩溃的边界。测试期间不使用 Redis。不得用直接执行高负载 SQL 的方式替代业务请求。

本次只新增本方案，不修改业务代码、部署配置或压测工具，不启动测试环境，不执行压测。以下改造、配置调整、恢复和复测步骤均为后续执行要求。

MySQL 不一定发生崩溃。若应用保护、压测器能力或测试资源范围先限制有效加压，应报告实际测到的边界和限制，不能宣称已经测出数据库极限。

本方案以 [极限性能测试规范](../README.md) 为基础。本轮从 10 RPS 起步，每档正式测量 5 分钟；普通业务退化不自动结束极限加压。数据库故障采用独立判据。与通用规范不同的起点、时长和停止规则以本方案为准。

### 3.2 无 Redis 改造清单

当前 [配置加载](../../backend/internal/config/config.go) 在业务角色下仍要求 `REDIS_PASSWORD` 等配置；[服务装配](../../backend/cmd/server/roles.go) 会创建 Redis 客户端、帖子正文缓存和共享限流器。当前仓库不能仅通过停止 Redis 或删除密码就满足本方案。

后续执行前必须完成以下改造，并记录实现及验证证据：

1. 为业务角色提供明确的无 Redis 装配路径。该路径不创建 Redis 客户端，不发起启动检查、重连或后台探测，也不要求无效的 Redis 凭据。不得把尚未实现的开关写成已有能力。
2. 绕过 Redis 正文缓存及其读取、写入、失效和重建路径，使业务读取直接使用数据库。若保留本地缓存，必须另建场景并说明，不能与直接读取数据库的结果混用。
3. 使请求限流不再调用 Redis 的 `Eval`、`EvalSha` 或 `ScriptLoad`。基线保留限流保护，使用经验证的无 Redis 实现并固定配额。若采用本地限流，记录每实例配额、账号/IP 分布和多实例下的聚合规则，不得声称它仍有原共享限流语义。
4. 检查登录、会话、业务读写、缓存失效、异步任务及依赖检查，排除其他 Redis 访问。不得把 Redis 不可达时的熔断、超时或降级状态作为无 Redis 实现。
5. 在后续独立测试部署中移除 Redis 启动依赖及 Redis 采集任务。保留 MySQL、RabbitMQ、Elasticsearch 和必要后台任务，使业务链路完整。

执行前完成低负载验收：登录并读取当前用户，读取列表与详情，新增和编辑内容，删除有效目标，执行互动写入，并确认事件提交、worker 消费和索引更新。核对返回内容与持久化结果，不能只检查 HTTP 状态。

同时检查进程连接、网络连接尝试和依赖调用记录，确认业务及其后台任务没有 Redis 连接或调用。应覆盖启动、读写、异步处理和至少一个相关后台任务周期。仅观察“没有已建立连接”不足以排除连接失败和周期重试。验收不通过时不得开始容量扫描。

| 精测与持续测试 | refine 当前无预热；soak 使用稳定档比例，`next.json` 为 0.8；报告缺少确认区间时可能报 `boundary_not_found` | 二分每次预热 30 秒、测量 300 秒；最终补测使用最后正常档的 100%，测量 1800 秒；不伪造前置报告 |
| 语料轮换 | 当前 `sequence.mjs` 按路由访问次数选择用户和归属目标；单次运行覆盖有离线检查，但每次运行仍从头开始，删除允许 204/404 | 核对预热、测量、跨档和重复运行的实际目标，确保删除/编辑目标有效且归属正确；语料不足应暂停修正，不能算作性能故障 |
| 指标规模 | 测试二记录默认 `url`/`name` 标签产生大量时间序列 | 后续执行前限制高基数标签，保留稳定路由标签，确认采集本身不会先耗尽压测器内存 |

当前脚本分别统计 `delete_succeeded` 和 `delete_already_absent`。删除返回 404 不代表完成了一次有效删除；报告须单列其数量，从有效业务成功吞吐中排除。账号权限、语料耗尽、重复目标和脚本异常须与服务错误分开记录。若语料问题改变实际业务比例，该次结果不能用于确认边界。

预热、登录准备、正式测量、请求排空及恢复窗口必须分别标记。实际请求率按测量窗口内发出的业务请求数除以实际窗口秒数计算；成功吞吐按同一请求集合中完成业务目标的数量计算。记录跨窗口完成的请求及未完成请求的归属，避免将排空时间或登录请求计入正式测量。保留原始时间序列，核对发出数、完成数与丢弃迭代数。

原 `next.json` 的 boundary 为测量 120 秒、恢复 120 秒，与本方案不符。其 `max_rps=1000000` 是当前 runner 支持的扫描保护值，不是容量结论，也不是必须达到的目标。不得直接执行旧方案命令后宣称完成本轮测试。

## 5. 负载、观测与判据

### 5.1 工作负载

首组采用现有混合业务比例：读取 45%、搜索 10%、通知与书签等读取 10%、内容写入 15%、互动写入 15%、身份与会话 5%。固定并记录每类实际路由、成功状态、响应校验和访问分布。搜索仍使用业务接口和原有搜索依赖，不能因搜索未直接查询 MySQL 就删除该类负载。

以 1024 VU 和 5 秒客户端请求超时作为初始工具配置，并记录实际账号数与生效值。VU 可以根据压测器能力调整，但必须单独记录。有效业务成功不能只由允许状态码决定，也应核对写入和异步事件的实际完成数量。

### 5.2 独立数据库探针

探针在应用准入和连接池之外运行，通过实际业务网络路径直接访问 MySQL。使用独立、非特权的普通数据库账号，权限和连接限制应能反映业务连接能力，并计入总连接预算。保留有权限的诊断连接，用于区分普通连接耗尽和服务端整体失效。

每秒尝试一次新连接并执行 `SELECT 1`。预先固定连接与查询的总超时为小于 1 秒的值，记录实际值。每次记录时间、连接阶段、查询阶段、返回结果、错误码和耗时。探针不得因业务 5xx、`/ready` 失败或应用池耗尽而停止运行。

从第一次失败起，只有连续失败覆盖至少 30 秒、期间没有成功且采样没有中断，才判定持续不可用。探针自身资源不足、网络隔离或采样中断时应标记证据不足，不能补算为数据库失败。若进程证据先确认崩溃，应立即停止业务加压，不必等待 30 秒。

### 5.3 结果分类

| 结果 | 判定 | 必须保留的证据 |
| --- | --- | --- |
| 业务失稳 | 正式窗口业务错误率超过 1%、P95 超过 1 秒或 P99 超过 2 秒，任一成立 | 三项分别记录，总体与成功请求延迟分开统计；同时记录每秒及每分钟失败窗口 |
| MySQL 持续不可用 | 独立探针连续至少 30 秒无法连接或执行 `SELECT 1` | 探针原始记录、数据库日志、连接和等待状态；区分连接耗尽、查询超时、网络及其他原因 |
| MySQL 进程崩溃 | 证据确认 `mysqld` 非计划退出、被 OOM 终止或发生非计划重启 | 进程/容器退出事件、退出状态、OOM 记录、错误日志、启动时间与 `Uptime` 变化 |
| 未测出数据库极限 | 应用保护、压测器能力或已声明的测试资源范围先限制有效加压 | 限制原因、最高目标与实际负载、成功吞吐、数据库资源和应用拒绝指标 |

这些结果可以同时存在，必须分别填写首次发生时间和负载。业务失稳不等同于数据库故障；数据库不可连接也不必然意味着进程退出。退出码 137、单次日志缺失或一次 `Uptime` 采样异常不能单独作为 OOM 或崩溃的结论。

档位实际请求率低于目标的 95% 时，先检查压测器 CPU、内存、网络、VU、丢弃迭代及采集开销。若压测器达到瓶颈，先结束该组并调整压测能力，再恢复初始状态重测。若证据表明请求因被测系统等待而无法按时发出，应如实记录该限制；目标 RPS 不能当作实际达到的负载。

聚合指标达标仍须报告短时错误窗口，避免重复测试二“30 分钟聚合达标但存在分钟级退化”的误读。异步积压、最老积压年龄和一致性异常单独记录，不能只凭 HTTP 达标认定整条链路稳定。

| 每秒 | 独立数据库连接与 `SELECT 1` 探针；业务及 `/ready` 探测单列，不能混入正式业务流量统计 |
| 每 5 秒 | MySQL `Threads_connected`、`Threads_running`、`Max_used_connections`、连接错误、查询/事务速率、慢查询、行锁等待、死锁、InnoDB 状态与等待信息；记录计数器增量和采集耗时 |
| 每 5 秒及事件发生时 | MySQL 启动时间、`Uptime`、容器状态和重启次数；与进程生命周期事件对应 |
| 持续保留 | MySQL 错误日志、应用和后台任务日志、容器事件、退出状态、宿主机内核/cgroup OOM 记录及采集失败记录 |

等待信息按所测 MySQL 版本和权限从 Performance Schema、InnoDB 状态等来源获取。采集失败时保留错误，不把缺失值记为零。限制查询耗时和结果量，记录观测开销。当前指标若没有可用接口，须在后续执行前补齐或使用经过验证的替代采集方式，不能假设业务端已有 `/metrics`。

[现有 Compose](../../deploy/compose.yaml) 对 MySQL 配置了 `restart: on-failure:5`。后续执行前须记录实际重启策略，并确保不会掩盖首次退出：可以在独立测试部署中关闭自动重启，或持续采集事件、退出状态和每次启动信息。不能只根据故障后的存活状态判断“没有崩溃”。本次不修改该配置。

## 6. 加压步骤

### 6.1 基线组：保留应用保护

1. 完成前置验收，恢复初始快照，确认 Redis 零访问、业务链路和观测可用。保存空载指标及少量业务探测结果，作为恢复基线。
2. 保留 HTTP 并发、各资源预算、无 Redis 限流和异步准入保护。不要在本组内调整预算、连接池、实例数或后台任务。
3. 从 10 RPS 开始，按 `10、20、40、80、160、320、640、1280……` 逐档翻倍。每档在该目标下预热 30 秒，再正式测量 5 分钟。
4. 组内连续加压。档间不重启服务，不恢复快照，不清理积压，也不插入卸载恢复窗口。预热与测量分别统计，记录实际切换时间。
5. 首次业务失稳时保存在线现场，标记最后正常档和首次异常档，记录错误率、P95、P99 各自首次越线的位置。普通业务退化只记录，继续极限探索；该组停压后再观察恢复，随后独立复测业务边界。
6. 每档核对实际请求率。低于目标的 95% 时按第 5.3 节排查。有效加压被限制时，不得仅提高目标数字。
7. 遇到第 7 节停止条件时停止业务加压，保留观测并执行恢复流程。未触发故障但达到预先记录的测试范围时，同样结束该组并说明限制。

若 10 RPS 即失稳，先核对环境、语料、Redis 停用和初始积压。排除准备问题后可补测更低负载建立正常下界，并明确记录；不存在正常下界时，不能编造二分区间。

### 6.2 保护调整组：每组只改变一个变量

当应用先大量拒绝请求，且提高目标后 MySQL 活跃查询、事务吞吐、CPU 或 I/O 压力不再增长时，先结合拒绝原因和资源指标确认是哪项保护限制了数据库负载。不能仅凭 503 或数据库 CPU 未满认定保护是瓶颈。

分别建立以下调整系列。各系列以同一基线配置为参照，不把前一系列的调整叠加到后一系列。每个取值都是独立组，均从同一数据快照和队列/索引初始状态开始，从 10 RPS 重新测量。

| 系列 | 唯一调整变量 | 递增规则 | 必须固定的其他条件 |
| --- | --- | --- | --- |
| A：数据库并发预算 | `BACKEND_RESOURCE_DATABASE` | 按实际基线值的 2、4、8……倍递增，不超过代码允许的 4096 | API 连接池、实例数、HTTP 与其他资源预算 |
| B：API 连接池 | 业务进程的 `MYSQL_MAX_OPEN_CONNS` | 按实际基线值的 2、4、8……倍递增，不超过 100，且满足总连接预算 | 数据库并发预算、实例数、空闲连接和生命周期 |
| C：业务实例数 | 实际部署副本数及对应的 `GOPULSE_REPLICA_COUNT` | 按实际基线副本数翻倍，不超过 8，且满足总连接预算 | 每实例预算、连接池、MySQL 资源、worker/indexer 数量 |

例如，API 池实际为 8 时可测 16、32、64；下一次翻倍为 128，超过代码上限后结束该系列，不能静默截断为 100 并称其为翻倍档。其他系列采用相同规则。

执行前固定 `MYSQL_TOTAL_MAX_OPEN_CONNS` 和 MySQL 服务端连接预算。某个候选值需要同时增加总预算才能启动时，不在当前系列中顺带调整，应记录为预算限制。若后续单独研究更大预算，另建系列，重新建立参照组。

连接池系列只修改业务 API 进程的环境值。worker 和 indexer 也读取 `MYSQL_MAX_OPEN_CONNS`，不得通过修改全局环境同时扩大它们的连接池。

比较不同实例数下的相同 RPS 档位时，保持总目标流量一致，验证负载均衡和各实例实际负载。无 Redis 本地限流若随实例数增加而扩大聚合配额，应明确记录该耦合，并说明结果不能只归因于数据库并行能力。

所有调整组沿用每档预热 30 秒、测量 5 分钟和组内连续翻倍的规则。其他应用保护或异步预算仍先限制负载时，记录该限制；本方案不要求继续取消所有保护。若依然无法增加数据库压力，结论为“未测出数据库极限”。

### 6.3 边界复测与持续验证

首次失稳档的现场与本组停压恢复记录保存后，独立恢复环境，再做边界复测。连续加压组的历史积压会影响结果，因此其区间与独立恢复后的区间必须分别报告。

1. 在相同配置和初始快照下，重测连续组的最后正常档 `L` 与首次异常档 `H`，每次独立恢复。只有确认 `L` 正常、`H` 异常，才建立复测区间。
2. 以 `(L + H) / 2` 为下一档。每次恢复相同快照，预热 30 秒、测量 5 分钟；按同一个判据更新正常下界或异常上界。
3. 重复二分，直到 `(H - L) / L ≤ 10%`。工具次数限制、语料问题或资源范围导致未收敛时，报告实际区间和原因，不能标为已收敛。
4. 最终异常上界 `H` 共复测三次，每次独立恢复并记录故障形态。初始连续扫描不计入这三次。若结果不一致，报告复现次数和条件，重新核对区间，不用多数票掩盖差异。
5. 在最终正常下界 `L` 的 100% 请求率补测 30 分钟，另加 30 秒预热。不得用 `0.8 × L` 替代。检查聚合指标、短时退化、异步积压趋势及恢复；失败时下调候选正常档并继续确认，不能保留“30 分钟稳定”结论。

业务失稳、数据库持续不可用和进程崩溃使用不同判据。若要精测数据库故障边界，须单独建立该判据的正常/异常区间；其中“正常”仅表示未触发相应数据库故障，不代表业务达标。没有观察到崩溃时，不建立或推算崩溃区间。每次数据库故障复测一旦满足停止条件，即刻停压，实际窗口可以短于 5 分钟，但必须标记为故障中止。

## 7. 停止条件与恢复观察

### 7.1 立即停止业务加压的条件

- 独立数据库探针确认 MySQL 持续不可用达到 30 秒。
- 证据确认 MySQL、应用或其他关键依赖崩溃、OOM 或非计划重启。
- 发现非预期数据丢失或一致性异常。
- 达到执行前已记录的内存、磁盘、连接或积压停止阈值。
- 压测器或观测链路失效，已不能产生或确认有效负载。

停止阈值及其用途须在执行前说明。若阈值先于数据库故障触发，应报告受测试范围限制。普通 429、503、业务 SLO 越线或单次 `/ready` 失败只记录；未满足上述条件时，不自动结束极限加压。

不得主动杀死 `mysqld`、手动重启或人为填满磁盘来制造“压测崩溃”。停止加压后为恢复而执行的人工重启，必须与此前的非计划退出分开记录。MySQL 持续不可用已达到停止条件时，不为追求进程崩溃而继续施压。

### 7.2 恢复流程

1. 每组结束后停止业务压测流量；故障确认时必须立即停压。记录组结束原因，以及故障开始、判定和停压时间。保留低频业务探测、独立数据库探针、资源采集、日志和事件采集，说明仍在运行的后台任务。
2. 先保存现场：故障前后请求时间序列、数据库错误日志、连接及等待快照、容器事件与退出状态、OOM 记录、启动时间、`Uptime`、应用池和异步积压。数据库不可查询时保留失败记录和外部证据，不反复执行重型诊断查询。
3. 从停压起观察 10 分钟，期间不主动重启、不清理积压、不恢复快照，也不调整参数。自动重启若发生，记录完整时间线，不能归为“进程未退出”。
4. 同时检查数据库连接和 `SELECT 1`、少量真实业务读写、后台消费和积压是否恢复到执行前记录的基线。分别记录数据库可用、业务恢复和积压恢复时间，不能以 `/ready` 通过代替全部恢复。
5. 10 分钟内未恢复时，标记“观察窗口内未恢复”。保存证据后执行必要人工恢复，逐项记录动作、开始/结束时间、耗时及残留影响。若必须提前人工干预，先保存证据并说明原因，未完成的自然恢复窗口不得记为已通过。
6. 下一独立组或复测前，确认恢复完成并重新恢复规定的初始快照，校验队列、索引、语料和 Redis 零访问。不得将故障现场清理混入上一组的自然恢复结果。
