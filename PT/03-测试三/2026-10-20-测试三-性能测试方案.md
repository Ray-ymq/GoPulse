# 性能测试方案3：无 Redis 逐级加压

> 日期：2026-10-20（+08:00）。已按用户要求完成代码、工具和环境准备，停在业务预热及正式压测前。准备结果见[压测前准备报告](2026-10-20-测试三-压测前准备报告.md)。

通过 GoPulse 业务接口，从低负载逐档加压，找出业务失稳和 MySQL 故障的边界。执行主线：**准备环境 → 连续加压 → 必要时调整应用保护 → 停压观察恢复 → 复测边界**。

## 1. 测什么

| 结果 | 判据 |
| --- | --- |
| 业务失稳 | 正式测量窗口内，错误率超过 1%、P95 超过 1 秒或 P99 超过 2 秒；三项分别记录 |
| MySQL 持续不可用 | 独立数据库探针连续 30 秒无法连接或执行 `SELECT 1`，结合日志区分连接耗尽、查询超时等原因 |
| MySQL 进程崩溃 | 证据确认 `mysqld` 非计划退出、被 OOM 终止或发生非计划重启 |
| 未测出数据库极限 | 应用保护、压测器能力或预定测试资源范围先限制了有效加压 |

业务 500/503、`invalid connection` 或 `/ready` 失败，不能单独证明数据库故障。MySQL 不一定崩溃，应报告实际测到的边界。

## 2. 开始前准备

- 使用独立测试环境和可恢复数据，完成快照恢复验证。记录代码版本、数据规模、初始积压、实例数、MySQL 资源限制、各连接池、应用预算和后台任务配置。提前确定资源、磁盘、连接和积压的停止阈值。
- **先完成无 Redis 改造**：业务请求和后台任务不创建或访问 Redis 客户端；缓存读取、写入、失效和重建不访问 Redis；共享限流改用无 Redis 实现，并记录配额及多实例语义。基线保留应用保护，不能靠停止 Redis 后大量请求失败来完成测试。
- 无 Redis 模式使用 `BACKEND_REDIS_DISABLED=true`，参见[配置加载](../../backend/internal/config/config.go)和[服务装配](../../backend/cmd/server/roles.go)。本轮已完成并验证该改造。
- 验证登录、读取、写入和异步处理可用，并检查连接、连接尝试和依赖调用记录，确认没有 Redis 访问。
- **使用测试三连续执行入口**：[test3.json](../../perflab/k6/test3.json)、[操作说明](../../perflab/pt3/README.md)。本轮已修正普通业务退化中止、档间恢复及统计限制，数据库故障由独立观测确认。
- 修正实际测量时长统计，预热与正式测量分开，提前结束不能按计划时长折算 RPS。检查语料在预热、跨档和重复运行时的轮换、权限及数量；删除 404 单独统计，不计为有效删除成功。避免高基数指标先耗尽压测器资源。

沿用现有业务比例：读取 45%、搜索 10%、通知与书签等读取 10%、内容写入 15%、互动写入 15%、身份与会话 5%。以 1024 VU、5 秒客户端超时起步，记录调整及实际值。

[现有 next.json](../../perflab/k6/next.json) 的时长、档间恢复和持续测试比例与本方案不同，不能直接照用。历史现象参见[测试二报告](../02-测试二/2026-10-20-测试二-性能测试报告.md)；历史容量和连接异常的机制推断不能当作本轮结论。

## 3. 怎么加压

### 基线组

1. 从规定快照开始，保存空载和低负载指标，作为恢复基线。保留现有应用保护和必要后台任务。
2. 按 **10、20、40、80、160、320、640……RPS** 翻倍。每档**预热 30 秒、正式测量 5 分钟**。
3. 组内连续加压，不重启、不恢复快照、不清理积压。首次业务失稳时保存现场，记录最后正常档和首次异常档；普通退化继续记录，直到满足停止条件。
4. 实际请求率低于目标的 **95%** 时，先查压测器 CPU、内存、网络、VU 和丢弃迭代。若压测器先达到瓶颈，结束该组，调整后恢复初始状态重测，不能将目标 RPS 当作实际负载。

若 10 RPS 已异常，先排除环境和语料问题；必要时补测更低负载建立正常下界。

### 应用保护先挡住时

只有确认应用先拒绝请求、继续提高目标也无法增加数据库压力时，才做以下调整。每组只改一个变量，按当前值的 **2 倍**递增。

| 调整项 | 配置及代码范围 |
| --- | --- |
| 数据库并发预算 | `BACKEND_RESOURCE_DATABASE`：1～4096 |
| 业务 API 连接池 | `MYSQL_MAX_OPEN_CONNS`：1～100，只修改业务 API 进程，不同时修改 worker/indexer |
| 业务实例数 | 实际增加实例并同步 `GOPULSE_REPLICA_COUNT`：1～8 |

各调整系列以同一基线配置为参照，不叠加其他系列的调整。每组从相同快照及一致的队列、索引状态开始，重新从 10 RPS 扫描；MySQL 资源和后台任务配置保持一致。

递增受代码允许值、`MYSQL_TOTAL_MAX_OPEN_CONNS` 和 MySQL 服务端 `max_connections` 约束。核算全部实例的 API、outbox、probe、后台任务及监控连接，并预留诊断连接。不能为继续翻倍而顺带扩大总预算。实例增加后，记录流量分配及本地限流聚合配额的变化。

### 边界复测

该组停压并完成恢复观察后，独立恢复环境，再执行：

1. 在相同配置和初始快照下，确认最后正常档 `L` 和首次异常档 `H`。连续加压的结果与独立复测结果分别记录。
2. 每次恢复相同初始状态，测 `(L + H) / 2`，预热 30 秒、测量 5 分钟；按同一判据更新区间，直到 **`(H - L) / L ≤ 10%`**。
3. 最终异常档共复测 **三次**，每次独立恢复；最后正常档按 **100% 请求率补测 30 分钟**，另加 30 秒预热。结果不一致或持续测试失败时，重新确认边界，如实报告短时退化和积压。

业务失稳、数据库持续不可用和崩溃分别建立区间。未观察到某类故障时，不推算其边界；数据库故障复测也必须遵守立即停压规则。

## 4. 观察什么

- **每秒**记录目标与实际请求率、有效成功吞吐、错误分类、延迟、丢弃迭代，以及压测器、应用、MySQL 的资源、连接等待、应用拒绝和异步积压。总体与成功请求延迟分开，保留短时失败窗口，不能只看整档平均或聚合结果。
- **每秒**由应用连接池之外的独立探针新建数据库连接并执行 `SELECT 1`，记录时间、阶段、错误和耗时；固定超时并计入连接预算。连续失败覆盖 30 秒且无成功才确认持续不可用；探针失效或采样中断标为证据不足。
- **每 5 秒**采集数据库连接数、活跃查询、事务、锁及其他等待信息，同时记录启动时间、`Uptime` 和重启次数。持续保留数据库错误日志、容器事件、退出状态及宿主机 OOM 记录。

[现有 Compose](../../deploy/compose.yaml) 为 MySQL 配置了 `restart: on-failure:5`。后续测试须关闭自动重启，或完整保留退出与重启证据，避免自动重启掩盖故障。单个退出码或业务健康检查结果不足以认定崩溃。

## 5. 什么时候停，怎么恢复

**确认数据库持续不可用、关键进程崩溃/OOM/非计划重启、数据异常，或达到预定停止阈值时，立即停止业务加压。** 压测器或观测链路失效、达到预定测试范围时，也结束该组并记录限制。普通业务错误率和延迟越线不自动停止极限加压。

1. 停压后保留监控和少量恢复探测，先保存请求、数据库、容器及宿主机证据。
2. **观察 10 分钟**，期间不主动重启、不清理积压、不调整配置。分别记录数据库可用、真实业务读写、异步处理及积压的恢复情况。
3. 10 分钟内未恢复，标记“观察窗口内未恢复”。保存证据后执行必要人工恢复，记录动作和耗时；若必须提前干预，说明原因和未完成的自然恢复窗口。

不得通过主动杀进程、手动重启或人为填满磁盘制造“压测崩溃”。人工恢复与此前故障分开记录。每个独立组结束后均观察恢复，下一组再恢复规定快照。
