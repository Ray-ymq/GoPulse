## 一、结论

1. **业务边界**：从基线快照连续逐档加压，**80 RPS 稳定、160 RPS 首次失稳**。10、20、40、80 RPS 四档在 300 秒窗口内错误率均为 0.000%；160、320、640 RPS 三档错误率分别为 **32.96%、70.97%、85.17%**，P95 均达到或接近 1,500 ms 的请求超时线。
2. **稳定容量**：**80 RPS** 是本轮测得的最高稳定档，成功吞吐 **80.0 req/s**，P95 138 ms、P99 148 ms；独立恢复后复测 80 RPS 为 24,000/24,000 成功、0.000% 错误、P95 134 ms、P99 145 ms，与连续组一致。
3. **首次失稳档**：160 RPS 连续组 47,999 个请求、32,179 个成功、错误率 32.96%，P95 1,501 ms、P99 1,502 ms；独立复测 48,000 个请求、31,653 个成功、错误率 34.06%，P95 1,501 ms、P99 1,502 ms。失稳可重复。该档有效成功吞吐约 107.3 req/s，但因约三分之一的请求失败，只作为失稳窗口的吞吐，不作为容量值。
4. **失败形态**：160 RPS 起以 **503 `backend_busy`**（HTTP 并发准入 128 满）和 **500 `internal_error`**（请求 1.5 秒超时）为主，不是测试二出现的 `invalid connection` 类数据库连接失效。160 RPS 的 500 集中在 `GET /api/v1/posts/:postId`（2,168 次）、评论列表（469 次）、用户主页（462 次）等读路由。
5. **数据库证据**：160 RPS 时 MySQL 容器 CPU 平均 **198%**、峰值 215%（容器上限 2 vCPU），320/640 RPS 仍约 197%；连接数在 160 RPS 最高 26（基线池）/35（池 16），全程峰值 41（池 16 的 640 RPS），服务端 `Max_used_connections` 43，远低于 `max_connections=151` 和 131 的停压线；独立 1 Hz 探针四组合计 7,796 次全部成功（基线组 2,954 次），最大 401 ms；容器 `RestartCount=0`，MySQL `Uptime` 连续，无 OOM、无崩溃。**未观察到数据库持续不可用或崩溃；本轮业务失稳与 2 核 MySQL 的 CPU 饱和一致，而不是连接耗尽或进程故障。**
6. **API 连接池 8→16 调整**：未上移边界。160 RPS 错误率由 32.96% 升至 **44.81%**，160 RPS 连接数峰值由 26 升至 35，异步待处理需求由 28 升至 394（640 RPS 时达 1,256）；MySQL CPU 仍为 200%。扩大 API 池不是有效手段，反而加剧数据库争用，因此未继续 16→32。
7. **压测器限制**：1024 个虚拟用户时 k6 RSS 在业务加压前即达 3.5 GiB，超过 3 GiB 停压阈值；按“一次只改一个变量”将虚拟用户调整为 **512**（k6 峰值 1,978 MiB），后续连续组在 1280 RPS 档预热时再次达到 3 GiB 阈值而停压。**1280、2560 两档未执行是压测器内存限制，不是被测系统限制。**
8. **恢复**：四个组（基线连续组、池 16 系列、80 复测、160 复测）每组停压后都保留 **600 秒**自然恢复观察；真实登录、读、写、删全部返回 200/201/204，异步待处理需求回落到 0，数据库探针 0 失败，全程未重启服务、未清积压、未改配置。

## 七、适用范围与限制

1. 本报告的业务边界只对应 **300 秒测量窗口**；不把 80 RPS 外推为“长期运行容量”，也不把 160 RPS 描述为“长期不可用阈值”。
2. 数据库结论只对应 **2 核 / 2 GiB MySQL、单机部署、512 个预分配 VU** 这一组条件。160 RPS 起 MySQL CPU 达到容器上限，是本轮观察到的容量约束；不能据此推断增加 CPU、连接池或换用其他数据库后的极限。
3. 本轮没有观察到数据库连续不可用或崩溃，因此报告中不存在“数据库崩溃极限”；160 RPS 的 503/500 是应用准入和 1.5 秒超时，不是数据库连接失效。
4. 1280、2560 RPS 因 k6 RSS 达到 3 GiB 停压线未执行；这是压测器内存限制，不能解释为被测系统在 1280 RPS 的行为。
5. 1024 VU 的首次运行没有产生业务请求，不能作为任何档位的样本；本轮全部结论基于调整后的 512 VU。
6. 报告中所有业务计数、错误率和延迟来自 k6 原始采样与 runner 汇总；原始文件在 `.run/pt3/`，不进入 Git。
