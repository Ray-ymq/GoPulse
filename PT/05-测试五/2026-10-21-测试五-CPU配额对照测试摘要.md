# 测试五摘要：MySQL 2/4 vCPU 在 120/140 RPS 下的对照

状态：四组正式压测完成。完整结果见 [CPU 配额对照测试报告](2026-10-21-测试五-CPU配额对照测试报告.md)。

## 结论

在预算锁优化后的同一程序、同一数据、MySQL 2 GiB、API 连接池 8、Redis 关闭的条件下，只调整 MySQL CPU 配额：

| 负载 | 2 vCPU | 4 vCPU | 判断 |
| ---: | --- | --- | --- |
| 120 RPS | 21.44% 错误，成功 94.27 RPS，P95 1,501 ms | 0% 错误，成功 120.00 RPS，P95 152 ms | **4 vCPU 通过、2 vCPU 未通过** |
| 140 RPS | 28.18% 错误，成功 100.55 RPS，P95 1,501 ms | 0% 错误，成功 140.00 RPS，P95 158 ms | **4 vCPU 通过、2 vCPU 未通过** |

两个负载档都满足“4 vCPU 通过、2 vCPU 未通过，且 CPU 节流与排队同时减少”，支持 **CPU 配额是当前性能限制的重要因素**。

## 关键变化

| 指标 | 120 RPS（2→4 vCPU） | 140 RPS（2→4 vCPU） |
| --- | ---: | ---: |
| 错误率 | 21.44% → 0% | 28.18% → 0% |
| 成功 RPS | 94.27 → 120.00（+27.3%） | 100.55 → 140.00（+39.2%） |
| 全部 P95 | 1,501 → 152 ms（−89.9%） | 1,501 → 158 ms（−89.5%） |
| CPU 节流累计 | 1,593.1 → 0 s | 1,220.7 → 0.63 s |
| COMMIT 均值 | 15.18 → 10.25 ms | 21.18 → 11.91 ms |
| 连接池累计等待 | 20,548.8 → 0.14 s | 22,418.1 → 47.7 s |
| 行锁累计等待 | 627.5 → 224.7 s | 1,372.2 → 413.7 s |

2 vCPU 两组都顶满配额、约 98%～99.5% 的周期被节流；4 vCPU 在 120 RPS 不节流，在 140 RPS 平均 CPU 232.8%、只有 5 个节流周期。4 vCPU 120 RPS 的 CPU 均值（194.9%）不高于 2 vCPU（199.1%），却完成 27% 更多成功请求，说明 2 vCPU 相当部分 CPU 消耗在节流和锁竞争上。

## 其他验收

- 四组均达到目标请求数，未完成请求 0、迭代丢弃 0，未触发停压保护。
- 配额与内存：预期/实际 2 或 4 vCPU 一致，内存均为 2 GiB；四组均无 cgroup OOM。
- 采集：四组 `resources-summary` 和 exporter 汇总均有效，5 秒 CPU/节流采样无间断。
- 写入核对：新建、更新、删除、点赞、书签、关注均按资源 ID 核对通过；无缺失行、无内容不一致、无应用结果失败、无孤儿行；窗口边界请求单独记录（2 vCPU 组 150/157 条，4 vCPU 组 6/4 条）。
- 恢复：四组 600 秒恢复均通过，末次业务检查成功，全部 epoch 积压归零。

## 仍存在的瓶颈

4 vCPU 140 RPS 仍通过，但预算锁和提交路径没有消失：行锁累计等待 413.7 秒、预算锁最多 9 个等待者、COMMIT 均值 11.91 ms、redo/binlog misc 129.4/100.3 秒。本轮最高已测且通过负载是 140 RPS，未测出 4 vCPU 上限；继续加压应优先检查 COMMIT、日志 I/O 和预算锁。

## 限制

- 每个条件只有一组正式运行；2 vCPU 120 RPS 本轮 21.44% 错误，测试四同档为 14.57%，存在运行间波动。4 vCPU 零错误、P95 约 150 ms，结论依赖多指标同向而非单一数字。
- 预算锁为 exporter 快照指标，不是逐次等待事件计数；行锁总量覆盖全库。SQL 累计耗时不等于 CPU 时间。
