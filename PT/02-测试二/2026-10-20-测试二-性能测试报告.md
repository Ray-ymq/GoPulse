## 一、结论

1. **业务容量区间**：自动加压确认 **160 RPS 稳定、320 RPS 首次失稳**；精测后区间收敛为 **[300, 320) RPS**（300 档与 320 档相差 6.7%，小于 10% 的停止宽度）。该区间是 **300 秒窗口**口径；30 分钟持续测试显示 240 RPS 已出现分钟级过载窗口（见第 7 条），长期可用容量应低于 240 RPS。
2. **达到业务标准的负载**：300 RPS 档在 300 秒窗口内满足 SLO（错误率 0.26%、P95 51.2 ms、P99 287.2 ms、实际请求率 300.0/s）。240、280 档同样低于 1% 错误率（0.61%、0.10%）。**300 RPS 是本轮测得的最高达标档位（300 秒窗口）**。
3. **最大成功吞吐**：**299.2 req/s**（300 RPS 档，300 秒窗口）。边界加压中 320 RPS 档因失败窗口只测到 79.5 秒，成功吞吐 208.5 req/s，不能作为容量值。
4. **最高实际施加负载**：**320 RPS**（边界加压 79.5 秒、两次补充复现各约 100～110 秒）。本轮**未进入 400 RPS 及以上区间**，因此无法与测试一在 400～3200 RPS 的结论直接对比，也不能据此断言高负载保护行为。
5. **过载/失败形态**：320 RPS 下不是 503 快速拒绝，而是 **MySQL 连接进入 `invalid connection` 状态后、跨全部路由的 500/503 混合快速失败**（单次失败窗口 9～11 秒，错误率瞬时可达 15%～30%），同时 `/ready` 健康检查失败。这是当前版本最重要的稳定性缺陷，详见第五节。
6. **恢复**：停压后 `/ready` 立即恢复 200、outbox 无积压（pending 0），runner 记录的恢复耗时均小于 0.02 秒；补充复现后用真实账号请求帖子列表、关注流、通知、搜索也全部返回 200。但失败窗口内变坏的连接要等连接池裁剪或生命周期到期才清除，期间会持续产生错误。
7. **持续测试**：240 RPS × 1800 秒聚合错误率 **0.206%**（890/432,001，503 864 + 500 26），P95 62.7 ms、P99 259.3 ms，健康检查 1,800/1,800 通过，卸载后 120 秒内 `/ready` 全 200、backlog 0。但第 11 分钟和第 24 分钟各出现一次分钟级过载窗口（503 `backend_busy`，日志采样峰值约 28%/秒，MySQL CPU 升至 1.5～2.1 核），**240 RPS 不能认定为长期稳定容量**。
8. **与测试一对比**：测试一在 200 RPS 稳定、400 RPS 首次失稳，500 RPS 持续 5 分钟出现 2.9% 的 503 和 outbox 积压增长；本轮在 240～300 RPS 的 300 秒窗口内已出现周期性 5xx 失败窗口（240、300 档含 500），**相同硬件下可用容量明显低于测试一的表面结论**，且失败形态从"依赖过载拒绝"变为"连接失效 500"。

### 4.2 320 RPS 失败窗口的证据

边界 320 档和两次 320 RPS 补充复现都出现了同一形态：

补充复现（第二次）在临时诊断日志下取得的 500 原因（原始 `.run/loadtest/logs/server-diag.log`）：

| 原因 | 次数 |
| --- | --- |
| `invalid connection`（直接、`list posts`、`check post existence`、`find user`、`list recipient notifications` 包装） | 394 |
| `begin post command transaction` | 9 |
| `hydrate search results` | 6 |

- 500 的 handler 耗时集中在 1～3 ms（补充 2 的 410 条日志中 301 条为 1～2 ms、342 条不超过 3 ms），说明不是慢查询超时，而是查询在**已失效的连接**上立即失败。
- 503 只有两种：`post_read_unavailable`（帖子详情读上下文失败）与 `search_unavailable`（搜索失败）。
- 日志中 500 原因没有任何模块级 error 日志，`/metrics` 路由不存在（404）；本次依靠临时诊断补丁才拿到 `invalid connection`。
- 失败窗口内 MySQL 观测（补充 1 期间 2 秒间隔采样）：`Threads_connected` 8～22、`Threads_running` 2～14、行锁最长等待 78 ms、无死锁；`Connections` 以约 60 个/秒增长（连接频繁新建/关闭）；`Aborted_clients` 在窗口内从 36 升到 70；服务进程 fd 约 1,056（上限 1,048,576）。
- 停止加压后立即用同一账号请求帖子列表、关注流、通知、搜索，全部 200；`/ready` 200；outbox pending 0。
- 健康检查：补充 2 的 166 次 `/ready` 中失败 1 次（99.40%，低于 99.9% 阈值）即触发中止，说明 `/ready` 在失败窗口内也会不可用（`/ready` 走 MySQL 探针）。日志中 500 与 503 的数量差来自 runner 对"预期过载 503"的日志抑制，k6 计数为准。

## 五、分析与限制

### 5.1 瓶颈判断

证据指向 **MySQL 单实例**为当前瓶颈：

- 300 RPS 时 MySQL CPU 约 0.91 核，server 0.48 核、k6 0.27 核、Redis 0.03 核；MySQL 是唯一接近单核饱和的组件。
- P99 从 240 档的 48 ms 升到 280/300 档的 250/287 ms，同时出现连接层失败，符合"MySQL 排队 → 请求超过 1.5 秒 API 超时 → 连接被驱动关闭"的链路。
- 320 RPS 档的 500 是 1～2 ms 内返回的 `invalid connection`，不是 MySQL 拒绝连接（`Max_used_connections` 26，`max_connections` 充足），也不是行锁/死锁（最长 78 ms）。
- 240 RPS 持续测试的 503 是 `backend_busy`（并发/资源预算 admission），与 320 档的 `invalid connection` 是同一瓶颈的两个阶段：MySQL 延迟尖峰先推高并发，触发保护性拒绝；更长的排队又让部分请求超过 1.5 秒超时，进而出现连接失效。
- RabbitMQ/ES/Redis 的 CPU 均低于 0.4 核，未出现队列积压或拒绝。

### 5.2 `invalid connection` 机制推断（待修复验证）

现有证据支持如下因果链，但尚未通过修复验证：

1. 高负载下个别 MySQL 查询/获取连接超过 API 的 1.5 秒请求超时；
2. `RequestTimeout` 取消请求上下文，go-sql-driver 的取消监视器关闭该连接（`close()`，不发 COM_QUIT）；
3. 关闭动作与连接归还连接池存在竞态时，连接池会短暂把已关闭连接再次借出，后续查询立即返回 `invalid connection`（该错误不是 `driver.ErrBadConn`，database/sql 不会重试/剔除）；
4. 该连接在被裁剪或生命周期到期前持续产生 1～2 ms 的失败，表现为跨路由、持续数秒的 500/503 窗口；`Aborted_clients` 在窗口内上升与"连接被关闭"一致。
5. 停止加压后新请求不再命中坏连接（或池已裁剪），因此"停压即恢复"。

可验证的修复方向：把 `invalid connection` 映射为 `driver.ErrBadConn` 或对连接做健康检查/重试；复核 1.5 秒请求超时与 MySQL 尾部延迟的关系；为 500 增加原因日志和内部指标。**本轮未修改代码，结论仍需修复后复测确认。**

### 5.3 脚本与工具问题

1. **边界档位过多**：`next.json` 的 `max_rps=1000000` 让 boundary 生成 21 档直到 `boundary-rps-1e+06`；本轮在 320 失稳后停止，未受影响，但报告里出现大量 `not_executed` 档位。
2. **1% 提前中止**：320 档测量在 79.5/120 秒被 k6 `abortOnFail` 中止，实际测量时长与名义时长不一致。
3. **实际请求率折算错误**：runner 用"请求数 ÷ 名义时长"计算 `actual_request_rate`（320 档得到 212/s），掩盖了"实际 320/s、因中止不足 120 秒"的事实，也触发了 `achieved_rate_below_target` 分类。
4. **refine 报告不能直接启动 soak**：refine 全部档位 stable 时 `boundary.found=false`，`make load MODE=soak` 拒绝执行；方案的命令链在该分支下不可用。
5. **refine 无预热**：`refineStages` 不设置 `WarmupSeconds`，与 boundary 的 30 秒预热不一致。
6. **k6 时间序列爆炸**：k6 默认把 `url`/`name` 作为系统标签，22 条路由模板实际携带真实 ID/游标，2.5 分钟即产生约 200,045 条时间序列，k6 RSS 达 3 GB；30 分钟持续测试存在 OOM 风险，本轮 soak 关闭了 `url`/`name` 标签（自定义 `business_*`、`route_*` 指标不变）。
7. **删除语料旋转失效**：删除/编辑目标用 `floor(routeVisit / 账号数) % 目标数` 选择（`routeVisit` 为全局迭代计数），每次 k6 运行都从索引 0 开始。300 秒档的约 2,700～3,400 次删除只推进到索引 2～3，前约 2,048 次几乎都在重删前面运行已删除的目标（404）。boundary 阶段成功删除 1,130 个、精测再成功删除 1,219 个，300 RPS 档 3,372 次尝试仅 197 次成功（94% 为 404 并按 `delete_already_absent` 计为通过）。结果：8,192 个删除目标只有一部分被覆盖、多次运行重复覆盖同一批，内容写路径的实际负载低于名义 15%，成功率也被 404 轻微抬高。该问题需单独修复，JSON 参数无法解决。
8. **404 计入成功率**：删除已不存在的帖子被设计为"通过"，会轻微抬高成功率；本轮 300 档的实际写负载应打折理解。
9. **未测"连续两档吞吐提升不足 5%"结束条件**：本轮在 320 RPS 就失稳，未进入 400 RPS 及以上，无法验证该条件。
10. **可观测性缺口**：server 对 500 不记录原因；`/metrics` 未暴露（404）；outbox 仅通过 1 Hz `/backlog` 探针观测；健康检查失败没有单独日志。
11. **临时诊断补丁**：为取得 500 原因，曾在 `backend/internal/http/response/response.go` 加入 `GOPULSE_DIAG_ERRORS` 日志；该改动未提交，诊断后已 `git checkout` 撤销并重建，最终工作区无源码改动。

### 5.4 未测出与待验证

- 400、500、600、800、1600、3200、6400 RPS 的过载形态与保护配置行为；本轮未进入 400 RPS 以上。
- 修复 `invalid connection` 后 240～320 RPS 的稳定性，以及 300 RPS 是否真正可持续。
