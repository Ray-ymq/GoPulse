# 测试四：无 Redis 数据库专项诊断与稳定性测试方案

> 编写日期：2026-10-20（+08:00）。状态：方案已编写，尚未执行。
> 前轮依据：[测试三报告](../03-测试三/2026-10-20-测试三-性能测试报告.md)、[测试三方案](../03-测试三/2026-10-20-测试三-性能测试方案.md)。
> 本轮主线：完成观测准备 → 验证观测开销 → 复测业务边界并采集 SQL 与锁证据 → 验证持续稳定性 → 按证据实施一项优化并对照复测。
> 核心测试保持无 Redis。缓存收益和资源扩容列为后续条件实验，单独报告。

## 1. 本轮要回答的问题

本轮需要将“数据库接近满载”进一步定位到具体查询、事务或资源等待，并得到可复现的短时业务边界和 30 分钟持续测试结果。

| 问题 | 必须取得的证据 | 对应决策 |
| --- | --- | --- |
| 哪些 SQL 消耗最多数据库时间？ | 正式窗口内的 SQL 摘要增量、执行次数、扫描行数、执行计划 | 选择查询改写、索引或减少数据库调用 |
| `business_async_budget` 是否形成主要阻塞？ | 等待者与阻塞者、涉及的事务及锁持有时间、等待变化与请求退化的时间关系 | 评估事务范围和锁范围，保留预算正确性 |
| CPU 配额、磁盘 I/O、buffer pool 或应用排队各有多大影响？ | CPU 用量及配额节流、I/O 与缓存计数增量、连接池及准入等待 | 区分计算开销、I/O、数据库锁和应用排队 |
| 无 Redis 时的业务边界在哪里？ | 独立恢复后的正常档 `L`、异常档 `H`，以及重复结果 | 给出业务边界区间和重复性 |
| 正常档能否持续运行？ | 30 分钟逐秒、逐分钟指标及 10 分钟自然恢复 | 给出持续测试通过档，暴露短时故障和积压趋势 |
| 优化是否有效？ | 相同资源、数据和负载下，仅候选改动不同的对照结果 | 保留有证据支持的优化，记录代价和限制 |

本轮成功不以 RPS 必须提高为条件。若候选优化无收益，也必须留下足以支持判断的对照证据。30 分钟通过只证明该条件下通过 30 分钟，不能外推为长期生产容量。

## 2. 已知事实与待验证假设

### 2.1 已知事实

- 测试三的 100 RPS 正式运行 300 秒，30,000 次请求全部成功，P95 138 ms、P99 152 ms。
- 120 RPS 正式运行 178.2 秒，错误率 9.15%，P95 约 1,501 ms，随后因状态采样不完整停压。
- 100 RPS 时 MySQL CPU 平均约 146%；120 RPS 时平均约 197%，对应 2 vCPU 配额。
- API 连接池由 8 改为 16 后，160 RPS 错误率由 32.96% 升至 44.81%。
- 未观察到 MySQL 崩溃、非计划重启或连续 30 秒不可用。140 RPS 在施加负载前被内存保护拒绝，不能判为业务异常档。
- 测试三的 `[100, 120]` 区间相对宽度为 20%；尚未完成方案要求的 ≤10% 收敛、最终异常档三次独立确认及最终正常档 30 分钟测试。

对测试三原始记录的补充统计如下。这里只统计正式业务窗口内的数据库状态快照；同一锁等待可能出现在多次快照中，不能将快照数当作独立锁等待事件数。

| 档位 | 数据库状态快照数 | 存在等待锁的快照数 | 主要等待对象 |
| --- | --- | --- | --- |
| 100 RPS | 60 | 7 | `business_async_budget` |
| 120 RPS | 36 | 31 | `business_async_budget`，另有 `business_event_requirements` |

原始文件分别为 `.run/pt3/observations/20261020T180728/database-state.jsonl` 和 `.run/pt3/observations/20261020T182401/database-state.jsonl`。窗口边界取对应目录的 `requests-per-second.jsonl` 中 `phase=measurement` 的最早及最晚时间。该统计支持继续调查预算锁，尚不能证明其为唯一或首要瓶颈。

### 2.2 待验证假设

| 编号 | 假设 | 验证方法 | 不足以证明该假设的现象 |
| --- | --- | --- | --- |
| H1 | 关注流或其他查询扫描、排序及聚合开销较大 | SQL 摘要增量、代表性参数的 `EXPLAIN ANALYZE`、单路由诊断 | 某路由延迟高，或某路由错误最多 |
| H2 | API、outbox、worker/indexer 在预算表上形成事务竞争 | `data_lock_waits` 阻塞链、线程到服务角色的映射、事务时间线 | 只看到表上有已授予的锁，或异步积压较低 |

| H4 | 128 MiB buffer pool 或存储等待放大查询成本 | buffer pool 读请求和物理读增量、文件 I/O、磁盘延迟与内存分类 | buffer pool 小，或容器总内存接近阈值 |
| H5 | 数据库退化导致连接池、HTTP 准入依次排队 | 请求、连接池等待、数据库等待和准入拒绝的统一时间线 | 503 多，或连接数低于服务端连接上限 |

## 3. 工具选型与使用边界

允许使用开源或商业工具。默认采用现有工具链和 MySQL 原生诊断，减少引入新组件造成的测量差异。可用其他工具替换采集、展示或分析环节，但必须保留同等原始证据和统计口径。

| 用途 | 首选工具 | 使用方式与限制 |
| --- | --- | --- |
| HTTP 业务负载 | 仓库固定的 k6 v0.56.0、现有 Go runner 和业务脚本 | 保持开放到达率模型；本轮固定版本，不在对照中途升级 |
| SQL 聚合 | MySQL 8.4 Performance Schema、`sys.statement_analysis` | 采集累计值快照，离线计算窗口增量；区分业务与观测 SQL |
| 锁与事务 | `data_lock_waits`、`data_locks`、`threads`、`INNODB_TRX` | 建立等待者到阻塞者的关系，关联服务角色和 SQL 摘要 |
| 执行计划 | `EXPLAIN FORMAT=JSON`、`EXPLAIN ANALYZE` | 在独立诊断窗口使用代表性读查询；不混入容量测量 |
| 系统资源 | cgroup v2、`pidstat`、`iostat`、`vmstat`、容器事件与内核日志 | 原始计数为依据；图表只用于辅助阅读 |
| 应用指标 | 已有内部 metrics、结构化日志 | 采集 API、worker、indexer 的连接池、准入、异步和缓存指标 |
| MySQL CPU 剖析 | Linux `perf`，必要时 eBPF 工具 | 仅在独立诊断复测中启用；先验证 WSL2 内核、权限、符号和采样可用性 |
| Go 进程剖析 | `pprof` CPU、goroutine、block/mutex profile | 当前未确认有可直接使用的入口；需要时增加测试专用内部入口并验证开销 |
| 图表与汇总 | 现有 Prometheus/Grafana，或离线 Python/SQL 分析工具 | 若展示服务与被测服务同机，固定其资源并纳入开销评估；优先离线生成图表 |
| 辅助 SQL 样本 | MySQL 慢查询日志及离线聚合工具 | 只有摘要无法解释问题时才启用，作为独立诊断组；慢日志不包含全部查询成本 |

若使用商业数据库监控或 APM，执行前记录产品版本、agent 配置、采样比例、数据保存位置和导出格式。商业工具必须支持本轮 MySQL 和运行环境；其分位数、SQL 排名及 trace 不能替代本方案规定的计数核对。

所有工具先固定版本及校验和。凭据从私有配置文件读取，命令示例、报告及 Git 提交中不得包含密码、令牌、DSN 或业务语料。

开放到达率模型的依据见 [k6 官方说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。工具文档可能描述比 v0.56.0 更新的参数；实际命令必须以本轮固定二进制的帮助和离线验证为准。

## 4. 固定的基线条件

### 4.1 部署与资源

| 项目 | 核心测试固定值 | 执行前核对方式 |
| --- | --- | --- |
| 应用 | API、worker、indexer 各一个进程，服务角色沿用测试三 | 进程身份、二进制摘要、启动参数及角色日志 |
| MySQL | 8.4.0，2 vCPU、2 GiB，无 swap，自动重启关闭 | 容器 inspect、cgroup 配额和数据库变量 |
| MySQL 配置 | buffer pool 128 MiB，`max_connections=151` | 保存 `SHOW VARIABLES` 的相关项 |
| API 连接池 | 8 | 进程环境和连接池指标同时确认 |
| 其他连接池 | worker 8、indexer 8、outbox 4、业务 probe 1 | 进程配置和实际指标；与外部诊断连接分别核算 |
| 总连接预算 | `MYSQL_TOTAL_MAX_OPEN_CONNS=60` | 先列出所有连接来源，再检查总上限 |
| HTTP 保护 | 最大并发 128；auth/read/write/database/rebuild=16/64/32/32/8；waiter 256 | 配置快照和指标 |
| 超时 | 应用请求 1.5 秒；k6 客户端 5 秒 | 代码版本、配置和模拟慢请求校验 |
| 身份限流 | 无 Redis 的进程内实现；配额沿用测试三 | 配置快照；429 单独统计，不隐藏为非业务请求 |
| Redis | `BACKEND_REDIS_DISABLED=true`，无业务 Redis 调用 | 服务装配、依赖清单、连接及调用证据 |
| RabbitMQ/Elasticsearch | 版本、资源、消费者和索引配置沿用测试三 | 保存实际配置，不只引用历史报告 |
| 压测器 | k6 512 个业务 VU，另加 1 个健康探测 VU | 启动计划、VU 指标、RSS 和 dropped iterations |
| 运行位置 | 第一轮桥接沿用同一 WSL2 宿主 | 记录宿主 CPU、内存、内核及其他进程负载 |

独立数据库可用性探针最多 1 个连接，关键状态采样最多 1 个连接，诊断采样最多 2 个连接，人工诊断最多 1 个连接。加上 API、后台、outbox、业务 probe 和容器健康检查，仍须满足 60 的总预算。若实际工具使用更多连接，必须先修改连接清单；不得在执行中静默增加预算。

同机资源竞争也是本轮条件的一部分。若 k6 先受限，可以另建独立压测机系列，但必须重新运行桥接组；不能直接把跨宿主结果拼入同一容量区间。

### 4.2 数据与初始状态

1. 使用测试三的 `baseline.sql` 及对应搜索基线作为桥接数据。校验 SQL 快照 sha256 为 `1580922c1027a5dbe3d60856664bf6e34c8de2e2d60a4ab91689e52c1e491fcd`；不存在或不一致时，先确认数据来源。
2. 恢复 MySQL、搜索索引和本测试环境的队列状态。恢复操作只能指向经过实例身份核对的独立测试环境。
3. 核对用户 5,000、帖子 360,709、评论 151,709 等关键基线计数，同时核对索引内容及版本摘要。历史搜索文档数与 MySQL 帖子数不同，不能用两个总数不相等直接判为本轮数据损坏。
4. 确认迁移版本及 dirty 状态、环境 mode/status/data epoch、消费者、outbox 待处理和未关闭 requirements。记录历史已发布 outbox 和保留证据的数量，不清空历史数据来改善结果。
5. 验证账号密码、编辑和删除权限、目标存在性、语料容量及互不冲突的目标集合。setup 登录、业务预热、测量、恢复探测分别分配目标。
6. 每个独立组均恢复同一快照；同一组内不恢复、不清积压、不重启。恢复后的数据相同不代表 buffer pool、操作系统页缓存或 Performance Schema 累计值相同，必须另外记录这些状态。

语料需求按完整请求序列计算，包含预热、正式测量和恢复探测。以 110 RPS、30 秒预热和 1800 秒测量估算，业务请求总数为 201,300；内容写占 15%，其中删除占四分之一时，至少需要约 7,549 个有效删除目标，另加功能与恢复探测目标。最终数量以实际路由序列及目标分配验证为准，不能只用估算值证明语料足够。

本轮采用“规定预热后的运行状态”，不宣称 MySQL 物理冷缓存。每组启动后先观察空载 60 秒，再预热 30 秒。若预热结束时仍有明显启动、索引恢复或队列消费活动，该组标为初始状态不合格；调整后的预热规则必须同时应用于全部对照组。

## 5. 正式执行前必须完成的工具准备

现有入口位于 [perflab/pt3/](../../perflab/pt3/README.md)。它可以独立执行一个 RPS 档位，并支持 300 秒或 1800 秒测量，但当前不能完整覆盖本方案。下表是准备工作，不是已经实现的功能。

| 缺口 | 必须完成的行为 | 验证方式 |
| --- | --- | --- |
| 多项状态查询共享 2 秒 context | 将独立可用性探针、关键安全状态和 SQL/锁诊断分离；每项诊断有独立超时、开始/结束时间和错误标记 | 模拟一项诊断超时，确认其他采样继续；关键安全状态失效仍能停压 |
| SQL 汇总缺少窗口增量 | 保存测量前后及每 10 秒摘要，按 schema+digest 计算增量；处理重启、计数重置和摘要丢失 | 用已知执行次数的模拟查询核对，不将历史累计成本归入本轮 |
| 锁采样没有阻塞关系 | 采集 `data_lock_waits` 并关联线程、事务和 `data_locks`；保留截断标记 | 在独立测试库建立受控锁等待，校验阻塞者映射；不在正式业务压测时制造故障 |
| 发出与完成时间没有分别记录 | 请求开始时记录 start 计数，结束时记录 outcome；保留开始阶段和完成时间，正确统计收尾和中断 | 模拟跨窗口慢请求、客户端超时和强制中断，核对请求计数守恒 |
| 阶段及目标集合需要独立控制 | 支持混合负载与按条件启用的诊断路由集合；固定序列和分布，避免写入目标重复 | 检查每路由次数及预热/测量分配；删除 404 不计成功 |
| 输出路径固定在测试三 | 为测试四提供独立状态、配置、快照引用和逐组归档；禁止覆盖测试三产物 | 验证 dry-run、恢复目标核对、旧 PID 识别和新 run ID |
| 长时间内存与文件增长未验证 | 只为实际组分配指标对象，采用低基数标签；流式保存原始延迟和计数 | 对模拟服务执行 1800 秒验证，检查内存趋势、磁盘估算和分位数复算 |
| 恢复结果未合并进主报告 | 将 runner、独立观测器和 600 秒恢复结果按 run ID 合并 | 处理 runner 成功但恢复失败、runner 中断但恢复成功等情况 |
| 商业工具或额外 agent 开销不明 | 固定其开关和采样配置，纳入第 8 节开销对照 | 导出原始结果并核对本地计数 |

建议在 `perflab/pt4/` 提供本轮编排及采样入口，在 `perflab/k6/test4.json` 固定执行配置。它们是待实现路径，本文不提供假定已存在的启动命令。可以复用已有模块，但不得仅复制目录并保留指向测试三的恢复目标、PID 或输出路径。

准备清单至少包含：代码 commit、工作区状态、二进制和配置摘要、数据与索引摘要、工具版本、采样配置、允许的环境身份、全部连接预算、停止阈值和功能验证结果。任何受记录文件变化后，重新构建和验证，不手工改摘要来绕过检查。

### 5.1 观测失效处理规则

- 1 Hz 新连接 `SELECT 1` 探针继续使用 1 秒超时，不占业务连接池。连续失败覆盖 30 秒且期间无成功，才判为数据库持续不可用。
- 关键状态每 5 秒采样：连接预算、异步预算、环境身份及 schema 状态。连续 8 秒无法取得有效关键状态，停止负载并记为观测失效。
- SQL 摘要、执行中语句和锁关系属于诊断采样。单项超时记录缺失；连续 3 个计划周期没有有效结果时，停止该诊断组，记为证据不足，不记为数据库故障。
- 将诊断查询超时与数据库不可用分开，但保留原有内存、连接、积压、进程和安全心跳停压规则。
- 每个采集器限制并发和连接数。前一轮查询未结束时不叠加下一轮；记录跳过的采样周期。
- 关键状态读取成功但确认环境身份变化、dirty 状态或预算越线时，立即停压。

关键状态与诊断队列不能共用会被慢诊断占满的连接池。上述规则必须先通过离线或独立模拟验证。

## 6. 指标、采样与统计口径

### 6.1 采样计划

| 数据 | 常规频率 | 主要字段 |
| --- | --- | --- |
| 业务请求 | 每次请求；另输出每秒汇总 | 路由模板、阶段、开始/完成时间、状态、业务错误码、总体及成功请求延迟 |
| 应用与压测器 | 1 秒 | CPU、RSS、VU、丢弃迭代、准入拒绝、连接池 open/in-use/wait、异步指标 |
| 宿主与容器 | 1 秒 | CPU 配额及用量、节流、可用内存、磁盘、网络、内存事件 |
| 独立 `SELECT 1` | 1 秒 | 新连接阶段、查询阶段、成功与否、耗时、错误 |
| 关键状态 | 5 秒 | 连接数、环境身份、schema、异步预算；记录采样用时 |
| SQL 摘要 | 10 秒，测量边界另存快照 | 次数、累计耗时、锁时间、行数、排序、临时表及错误 |
| 事务与阻塞链 | 5 秒 | 请求/阻塞线程、事务年龄、等待对象、SQL digest、服务角色 |
| 密集阻塞链 | 独立诊断组中 1 秒，最多 60 秒 | 同上；启用前验证采样开销 |
| CPU profile | 独立诊断组 30～60 秒 | 样本、符号覆盖、采样丢失、采样期间负载与开销 |
| 数据库日志、容器事件、内核事件 | 连续 | 退出、重启、OOM、错误及时间戳 |
| 真实业务恢复探测 | 停压后每 10 秒 | 登录、读、写、删、异步结果，计数独立于业务负载 |

所有证据包含 UTC 时间、`run_id`、组名和配置摘要；人类阅读的报告可同时显示 +08:00。使用单调时钟计算耗时。跨机器时校对时间差，记录最大误差；无法对齐的短时事件不得强行建立先后关系。

### 6.2 HTTP 与负载

保持混合业务比例：读 45%、搜索 10%、通知/书签等读 10%、内容写 15%、互动写 15%、身份与会话 5%，沿用 22 条路由模板。setup、健康检查和恢复探测不计入目标业务 RPS，单独记录其数据库开销。

- 实际发出 RPS = 正式窗口内开始的业务请求数 / 实际施压秒数。
- 完成 RPS = 正式窗口内完成的业务请求数 / 实际施压秒数，单独列出。
- 业务错误率按“正式窗口内开始的请求”归组，等待其正常收尾后统计最终结果。超时、传输失败、未完成或中断请求不得消失，也不得计成功。
- 有效成功吞吐按上述请求组的有效成功数 / 实际施压秒数计算；这是请求组统计，须与同墙钟窗口完成的成功吞吐分别标明。
- 丢弃率 = dropped iterations /（实际启动迭代 + dropped iterations）。确认一个业务迭代对应一个业务请求；setup 不进入该公式。
- 提前结束时，以实际开始和停止施压时间计算窗口；完整、提前结束、未执行分别标记。
- 停压收尾不再发出新业务请求；收尾最多等待客户端超时及编排容差。记录尾部请求，不延长名义施压秒数来稀释错误率。

保留现有 `business_latency` 的 HTTP duration 作为与测试三对照的延迟指标，同时新增请求调用前后测得的端到端耗时。两者分别输出，说明连接等待等阶段的差异。若指标含义或计数方式发生改变，必须注明；不能把统计修正造成的变化记作业务优化收益。

输出整体、各业务类别和各路由的 P50/P95/P99、错误率及错误分类。总体延迟与成功请求延迟分开。原始延迟用于离线复算，不能平均逐秒 P95/P99 来代替完整窗口分位数。

错误同时按 HTTP 状态、有限集合的业务错误码和客户端错误分类。区分 503 `backend_busy`、其他业务不可用、500、客户端超时和传输失败；具体原因需由日志或诊断证据确认，不能将所有 500 归为应用超时。按生成序列核对路由的预期次数；中断或丢弃造成的组成变化单列，不重新归一化后隐藏偏差。

只使用路由模板、状态分类等有限标签。帖子 ID、用户名、URL 查询参数、request ID、SQL 参数和 trace ID 不作为指标标签。

### 6.3 SQL、CPU、内存与锁

- SQL 按 schema+digest 保存完整快照，离线按执行次数、总耗时、扫描行数、每次扫描量和错误增量分别排序。每 10 秒只取“累计 Top N”会漏掉本轮新热点，因此不采用这种截断方式。
- 保存 `COUNT_STAR`、`SUM_TIMER_WAIT`、`SUM_LOCK_TIME`、`SUM_ROWS_EXAMINED`、`SUM_ROWS_SENT`、临时表、排序和错误字段；实际字段以 MySQL 8.4 实例元数据为准。空 digest、摘要表容量不足及丢失计数单独记录。
- `SUM_TIMER_WAIT` 是语句事件时间，不能等同于 CPU 时间。具体 CPU 热点需要结合进程 CPU 和剖析证据。语句 `SUM_LOCK_TIME` 也不能单独替代 InnoDB 行锁阻塞链。
- 所有累计计数按窗口求增量。Uptime、计数或摘要重置时中断比较，不把负增量改为 0 后继续使用。正式窗口中不清空 Performance Schema 汇总表。
- 业务连接按 API、worker、indexer、outbox 角色识别；可通过连接属性、线程映射或经验证的调用追踪完成。观测 SQL 单独分组；同一 schema 中的 SQL 不一定来自业务。
- CPU 记录 `usage_usec`、`nr_periods`、`nr_throttled`、`throttled_usec` 和 `cpu.max`。节流时间不直接等于业务响应时间，不能从单个百分比推算扩核后的收益。
- 内存同时记录 `memory.current`、`memory.stat` 的 anon/file/kernel、`memory.events`、MySQL buffer pool 和进程 RSS。`docker stats` 的展示值不能替换 cgroup 总内存停压值。
- 采集 buffer pool 逻辑读、物理读、等待空闲页、脏页、I/O 和磁盘延迟增量。写入 fsync、redo/binlog 等等待按实际可用指标记录。
- 锁关系记录等待者与阻塞者 thread/transaction ID、表、索引、锁模式、事务开始及等待开始时间。采样得到的等待持续时间是观测估计，不宣称覆盖所有短等待。

SQL 摘要和锁关系字段依据见 [MySQL 语句摘要表](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-statement-summary-tables.html)及 [data_lock_waits](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-lock-waits-table.html)。cgroup 字段语义见 [Linux 官方文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)。

## 7. 判定标准

### 7.1 短时业务档位

完成完整 300 秒正式窗口，且同时满足以下要求，才标记“短时通过”：

- 总体业务错误率 ≤1%。
- P95 ≤1,000 ms，P99 ≤2,000 ms。
- 实际发出 RPS ≥目标的 95%，丢弃迭代率 ≤1%。
- 实际路由和业务类别比例符合计划；没有语料耗尽、重复删除误判或环境身份变化。
- 没有数据一致性异常；必要观测有效，恢复验证完成。

若整档通过但某路由、某分钟或异步链路异常，报告必须列出，不能只显示整体通过。普通业务 SLO 越线标记为异常，不自动等同于数据库故障。

### 7.2 30 分钟持续测试

在短时正常档的完整请求率下运行 1800 秒，不乘 0.8。通过要求：

1. 整体达到 7.1 节的错误率、延迟和负载要求。
2. 每个不重叠的 60 秒正式窗口均满足同样的错误率和延迟要求；样本数和每秒曲线同时展示，不能用整体平均掩盖分钟级失败。
3. 每条路由在整个正式窗口的错误率 ≤1%；低样本路由注明样本数，不单凭分位数排序推断根因。
4. 不出现连续 5 个完整秒业务成功数为 0。其他逐秒尖峰保留并解释，不另行添加未经约定的逐秒 1% 判据。
5. 没有数据库持续不可用、关键进程退出、OOM、非计划重启或一致性错误。
6. 最后 10 分钟异步 open requirements、outbox 待处理量和最老待处理年龄未呈持续累积。每分钟保存均值、最大值和末值；任一待处理数量的分钟末值连续 5 次严格增加，且同段最老待处理年龄也连续增加时，本轮判为持续累积。其他增长形态列为异常并结合事件处理速率与恢复结果判断，不能仅因未命中此规则而忽略。
7. 停压后 600 秒内恢复到本组空载和功能基线，异步需求及队列回到规定初始状态。

同一候选正常档独立执行两次持续测试，两次都通过，才称为“本轮两次 30 分钟持续测试通过档”。出现不一致时，保留全部样本并定位原因；不能挑选较好一次。

若持续测试失败，记录失败档，以不高于 `0.8 × 失败档 RPS` 的负载重新确认短时行为，再执行持续测试；该降档结果作为新系列，不回写原短时边界。80% 只是寻找下一个候选的规则，不保证它一定稳定。

### 7.3 业务结果与异步正确性

除运行前功能检查和恢复探测外，负载脚本保留可追踪的写入样本。按固定种子从创建、编辑、删除和各类互动中，每类选择最多 100 个成功样本；不足 100 个时保留全部。原始记录可包含必要业务 ID 和命令 ID，但不将它们作为指标标签，也不写入公开报告。

在 600 秒恢复窗口结束后，以只读检查核对这些样本：

- 创建、编辑和删除结果符合实际操作顺序与版本，查询可见性和权限正确。
- 点赞、关注和书签符合目标用户的最终操作，不能只核对全表数量。
- 适用的搜索、通知、outbox 和 requirement 结果一致；重复投递不得形成重复业务副作用。
- 预算没有负数、需求漏记或不合理的未关闭记录。检查使用已有业务契约和验证接口，不能仅以“队列为空”代替。
- 对超时、500 或中断的写入单独保留结果不确定样本。按命令或事实记录核对是否已经提交，不假定 HTTP 失败必然回滚，也不因事后查到提交就将原 HTTP 失败改记成功。

样本无法关联或观察窗口内未能确认时，报告证据缺口；不得填写“正确性通过”。候选优化涉及预算、幂等或事务边界时，还需覆盖并发和异常路径的专项集成验证。

## 8. 阶段 A：观测准备与开销验证

### A0：功能和环境验证

1. 完成第 5 节工具准备及离线验证，校验恢复目标、准备清单和停止阈值。
2. 恢复基线，验证真实登录、列表、详情、关注流、评论、搜索、通知和书签。
3. 验证创建、编辑、删除及互动结果，检查搜索与通知的异步处理；探测请求单独记录，测量前恢复规定初始状态。
4. 保存 60 秒空载数据，确认无 Redis 调用、初始积压正确、观测心跳有效、内存和连接低于停止阈值。
5. 用模拟服务验证“业务错误记录”“观测失效停压”“实际时长”“中断请求计数”和恢复汇总。不得通过终止正式数据库制造测试故障。

### A1：观测开销对照

在 100 RPS、预热 30 秒、测量 300 秒的条件下，执行以下顺序，每次独立恢复并观察恢复 600 秒：

| 组 | 开启内容 | 目的 |
| --- | --- | --- |
| A1-轻量-1 | 安全探针、关键状态、基础资源与现有应用指标 | 取得轻量观测参考 |
| A1-诊断 | 上述内容 + 本轮常规 SQL 摘要与锁/事务采样 | 验证常规诊断对结果的影响 |
| A1-轻量-2 | 与 A1-轻量-1 相同 | 识别顺序和环境漂移 |

Performance Schema 的 instruments/consumers 在三组中保持一致；此对照主要评估额外查询和采集开销。若需要改变 instruments/consumers，另做成对实验，全部主测试固定最终配置。

本轮预设的开销复核线：诊断组相对两次轻量组中位值的 P95 增幅 >5%、MySQL 平均 CPU 增加 >10 个百分点，或错误率增加 >0.2 个百分点时，先降低非关键采样频率、限制查询规模或将密集采样移至独立组，然后重新验证。这些是工程复核线，不是统计显著性结论。

如果 100 RPS 轻量组已失稳，先处理桥接差异，再选取已确认正常档评估开销。不得在不稳定的参考条件上声称观测“没有影响”。

## 9. 阶段 B：混合业务边界与证据采集

全部使用通过 A 阶段的固定常规观测；每组预热 30 秒、测量 300 秒、自然恢复 600 秒，每次独立恢复快照。

| 组 | 负载 | 次数 | 目的 |
| --- | --- | --- | --- |
| B80 | 80 RPS 混合业务 | 2 | 核对已知正常下界和重复性 |
| B100 | 100 RPS 混合业务 | 2 | 核对最高已知短时正常档，取得完整 SQL 与锁证据 |
| B120 | 120 RPS 混合业务 | 2 | 确认异常是否可重复，获得完整或按规则停压的窗口 |
| B-mid | 首个候选 110 RPS | 至少 1；冲突时追加 | 收敛正常/异常区间 |
| B-H | 最终异常档 `H` | 累计 3 次有效独立组 | 确认异常档重复性 |

前两轮采用 80→100→120 和 120→100→80 的顺序；每组仍独立恢复，以便发现时间顺序影响。若反向组触发资源保护，该结果是保护中止，不强行补齐目标请求数。

### 9.1 边界更新规则

1. 先按结果确认 `L`、`H`。测试三数据只提供候选，不替代本轮结果。
2. 若 100 正常、120 异常，测 110。110 正常时得到 `[110,120]`，相对宽度约 9.09%；110 异常时得到 `[100,110]`，相对宽度为 10%。
3. 若同档两次结果冲突，再测一次并调查差异。只要存在有效独立失败，就不能用多数通过将该档命名为可靠正常档；保留“结果不一致”，重新寻找可重复的 `L`。
4. 若 100 已异常，依次在 80～100 范围二分；80 也异常时降至 40，重新建立正常下界。
5. 若 120 正常，依次测 140、160、200，找到异常后再二分。本轮核心搜索上限为 200 RPS；达到上限仍正常时报告“上限内未找到异常”，另行规划更高负载。
6. 正常与异常区间满足 `(H-L)/L ≤10%` 后停止进一步精测。最终异常档累计取得三次独立有效确认；符合配置、时长和证据要求的 B120 等已有组可以计入，不能将测试三旧样本计入本轮三次。

提前中止分情况处理：完整且合格的组可用于“短时通过”；已取得明确业务越线证据但提前停压的组可标记“异常，窗口不完整”，并报告实际时长；未施加负载、语料错误或观测不足且无法判断的组不进入正常/异常边界。不得把保护拒绝的 140 RPS 当作异常上界。

完成 B 阶段后，先整理 SQL 和事务成本排名，再决定阶段 C 的具体组数。无需重扫测试三的 320～2560 RPS 来定位当前 100～120 RPS 附近的问题。

## 10. 阶段 C：按证据触发的专项诊断

本阶段按需改变业务组成或采样强度，只用于定位机制。改变业务组成的组不能用于声明混合业务容量；启用额外剖析的组也不能直接替代常规观测组。每个短时组仍预热 30 秒、测量 300 秒、自然恢复 600 秒，并恢复相同数据。

| 编号 | 触发证据 | 诊断负载与档位 | 重点输出 |
| --- | --- | --- | --- |
| C-feed | 关注流 SQL 总耗时、扫描或排序突出 | 仅关注流，5、10、20 RPS；异常或资源停压后不继续升档 | 每请求扫描量、排序/临时表、关注数量与执行计划 |
| C-detail | 详情多次数据库调用或动态统计成本突出 | 仅详情，10、20、40 RPS，保持既定帖子与账号分布 | SQL 调用数、作者/互动读取、每请求成本与连接等待 |
| C-other-read | 评论、主页或其他读路由的 SQL 证据突出 | 对应路由先用混合正常档的实际路由 RPS，再按 2 倍递增，最多 3 档 | 正常与慢参数的计划差异，区分排队受害者和成本来源 |
| C-write | 预算表阻塞链突出 | 内容写与互动写各占 50%，总计 10、20、30 RPS；各类别内保持原路由比例 | API 与后台事务的阻塞关系、预算锁持有时间和写入成本 |
| C-role | 同一预算锁的持有者经常来自后台角色 | 在正常混合档与异常候选档各复测一次，不关闭后台任务 | 将连接线程映射到 API/outbox/worker/indexer，核对持锁 SQL |
| C-profile | SQL 与锁证据仍不能解释 CPU 或应用开销 | 原混合正常档及异常候选档，各独立复测一次；仅其中 30～60 秒启用 profile | CPU 栈、符号覆盖、采样丢失和剖析开销 |

同一假设可以先执行最接近正常混合业务实际到达率的一档，已有证据充分时停止扩大诊断矩阵。任何诊断中止都保留原始结果；不要为了凑齐矩阵继续增加负载。

### 10.1 SQL 执行计划检查

对正式窗口内总耗时、扫描量或错误增量靠前的 5～10 个业务 SQL 模板执行以下操作：

1. 选择正常、慢及高关联数量等代表性参数。不要只选择空结果或数据最少的账号。
2. 保存脱敏参数分类、表与索引定义、数据量、优化器统计信息状态及 `EXPLAIN FORMAT=JSON`。
3. 在无业务加压的独立诊断窗口，对受支持的只读查询执行 `EXPLAIN ANALYZE`，记录实际行数、循环次数、排序和各节点耗时。
4. 若执行计划需要更新统计信息或增加索引，作为候选改动进入阶段 E，不能在同一基线组中执行后继续测量。

`EXPLAIN ANALYZE` 会实际执行查询。写查询、加锁查询及有副作用的语句不在原业务数据上直接分析；使用隔离副本或只做不会执行语句的计划检查。语义及支持范围以 [MySQL EXPLAIN 文档](https://dev.mysql.com/doc/refman/8.4/en/explain.html)为准。

### 10.2 预算表锁检查

重点检查 [命令预算锁](../../backend/internal/businessstate/commands.go)、[requirement 注册](../../backend/internal/businessstate/evidence.go)及相关结算/清理事务。

- 识别同一预算行的等待链，区分锁持有者与排队者；记录是否存在长事务、全表范围锁或不同角色相互等待。
- 对每条主要链还原“事务开始 → 获取预算锁 → 其他 SQL → 提交/回滚”，找出锁内执行的工作。
- 同时记录预算需求的新增、结算和清理速率。积压低不能证明预算更新成本低。
- 预算锁可能用于保证全局容量和一致性。不得通过直接删除锁、关闭后台任务或忽略预算错误来获得“性能提升”；候选设计必须保留并发正确性。

若锁采样有行数限制，输出总行数估计、实际返回数和截断标记；只见到前 200 行时不能声称已排除其他阻塞对象。

### 10.3 profile 和慢日志

WSL2 上先验证 `perf` 能否对 MySQL 宿主 PID 采到有效调用栈。不能采样或符号不足时，记录限制，继续依靠 SQL、锁和资源证据；不把空火焰图解释为 CPU 无热点。

Go CPU profile 默认采 30 秒；block/mutex profile 只在排队或锁证据需要时启用。入口只在测试内部地址提供，并与主容量组分开。使用方式见 [Go pprof 文档](https://pkg.go.dev/net/http/pprof)。

确需慢查询日志时，先记录原配置，在独立诊断组使用 `FILE` 输出、`long_query_time=0.05` 秒，并核对新连接是否使用该会话设置。采完后恢复配置，记录文件增长和开销。不要在主容量对照中开启全量 general log。慢日志字段和设置依据见 [MySQL 慢查询日志文档](https://dev.mysql.com/doc/refman/8.4/en/slow-query-log.html)。

## 11. 阶段 D：持续运行与自然恢复

### D1：候选正常档 30 分钟测试

使用 B 阶段最终正常档 `L`，执行两次独立组，每次：

1. 恢复快照并完成环境与功能检查。
2. 空载观察 60 秒，预热 30 秒。
3. 在完整 `L` RPS 下测量 1800 秒，保持常规观测，不启用密集剖析。
4. 每分钟输出总体、各路由、数据库等待、异步积压及内存趋势；保存逐秒原始计数。
5. 停压后观察自然恢复 600 秒，再执行独立组恢复。

D1 可在阶段 C 的专项诊断前后安排，但必须在任何候选优化前取得基线持续结果。不得在两次持续测试之间改变配置或实现后仍称为同一基线。

### D2：恢复判定

停止业务加压后，继续保留全部安全观测和低频真实业务探测。前 600 秒内不主动重启、不清理积压、不更改连接池或资源。

分别记录：

- 独立数据库探针恢复成功的时间，以及是否发生过连续 30 秒不可用。
- 登录、列表/详情、创建、读取新内容和删除的结果。只检查 `/ready` 不足以证明业务恢复。
- 测试写入对应的搜索、通知等适用异步结果，以及未关闭 requirements、消息队列和 outbox 的回落情况。
- CPU、连接池等待、内存及最老积压年龄是否回到本组空载参考范围。页缓存未完全回落不单独判为业务未恢复，内存停压规则仍保持有效。

600 秒内未恢复则记录“观察窗口内未恢复”。保存证据后再做必要人工恢复，单独记录动作、时刻及耗时。恢复探测自身产生的请求和事件必须单列。

## 12. 阶段 E：单项优化与对照复测

只有 SQL、锁或资源证据足以指向具体机制后，才选择候选优化。每次只验证一项完整改动。

| 证据指向 | 可选候选 | 必须保留或验证的行为 |
| --- | --- | --- |
| 大量无效扫描、排序或重复读取 | 改写 SQL、增加合适索引、合并数据库调用 | 排序、游标分页、权限、可见性、互动状态及结果一致性 |
| 预算行锁持有时间过长 | 缩短锁内工作、调整事务边界或预算实现 | 原有预算上限、幂等、提交/回滚一致性和异常恢复 |
| buffer pool 物理读或 I/O 等待明显 | 单独调整 buffer pool | 保持 MySQL 总内存限制，重新核算内存保护余量 |
| CPU 配额限制且查询/锁成本已解释 | 单独将 MySQL CPU 2→4，内存等条件固定 | 单独报告资源收益，不记为代码优化或原资源容量 |

候选代码先通过受影响模块的静态检查、单测及有意义的集成验证，再冻结二进制和配置。涉及索引或数据结构变化时，使用同一业务数据来源，并记录候选迁移差异、索引构建后状态和统计信息；“同快照”指相同业务事实，不要求结构变更前后文件字节相同。

资源实验还须将该组的预期资源配置写入准备清单和观测器校验配置。例如 CPU 4 核组不能继续使用硬编码为 2 核的身份校验，也不能直接关闭资源变化检查；组内仍禁止修改配额。

对照执行采用以下安排：

1. 在原正常档和原异常档分别执行基线 A 与候选 B。每档至少采用 A→B→B→A 四个独立恢复组；原基线最近且条件完全一致的有效组可计入，但必须列明。
2. 比较错误率、延迟、成功吞吐、SQL 执行与扫描量、锁等待、CPU 秒/成功请求、磁盘及内存。混合业务 CPU 秒/成功请求包含后台和固定观测成本，不冒充纯业务 SQL CPU 成本。
3. 候选在原异常档通过后，按 B 阶段规则寻找新边界，并对最终异常档累计确认三次。
4. 在候选最终正常档重复两次 30 分钟测试，按第 7 节验收，并保留 600 秒恢复。
5. 没有重复收益、出现一致性问题或只转移瓶颈时，如实记录；不能仅凭单次 P95 更低保留改动。

容量提升按相同测试类型计算，例如“候选两次持续通过档 / 基线两次持续通过档 − 1”。若基线没有持续通过档，该提升比例不计算；分别报告实测结果。

## 13. 条件实验 F：缓存收益评估

该阶段在无 Redis 基线和诊断结论明确后执行。若本轮目标只要求无 Redis，交付 E 阶段结果即可，F 不阻塞核心结论。

当前 [服务装配](../../backend/cmd/server/roles.go)中的 `BACKEND_REDIS_DISABLED` 同时控制 Redis 客户端、正文缓存及共享限流实现。因此，直接切换该开关只能比较整套 Redis 模式，不能将变化全部归因于缓存。

当前正文缓存与无缓存模式还使用不同的读取管线。F0 与 F1/F2 的比较应表述为“正文缓存功能的净收益”，其中包含查询组织和重建协调的变化。若要单独分析命中本身的收益，增加同一读取管线下“命中/强制回源”的对照，并继续固定限流与保护配置。

要单独评估正文缓存，先增加并验证独立控制能力：所有对照组固定相同的限流实现、配额、重建保护、实例数和数据库条件，只改变正文缓存模式。分别定义：

| 组 | 内容 | 说明 |
| --- | --- | --- |
| F0 | 缓存关闭 | 与无 Redis 基线相同的业务读取语义 |
| F1 | 缓存开启，初始正文 key 为空 | 记录从首个请求起的填充过程；30 秒预热后另报稳态窗口，不把整个窗口称为冷缓存 |
| F2 | 缓存开启，规定工作集已预热 | 记录预热方法、工作集大小、命中率和 Redis 内存 |

使用相同混合业务在原正常档和原异常档各对照两次；若观察到收益，再按 B、D 阶段确认边界和持续表现。额外执行热点重复读与分散读时，单独标为读取分布实验，不能替代原混合业务结果。

输出 Redis 开销、正文命中率、回源次数、MySQL SQL 调用与扫描量、锁等待、成功吞吐和持续结果。正文缓存仍可能保留版本、可见性及用户互动等数据库读取；不预设开启后容量一定提高。

缓存一致性需检查编辑后读取、删除后读取、不同用户权限、互动状态及版本切换。Redis 故障与恢复可作为后续独立可靠性实验，不在正常缓存收益测量期间插入故障。

## 14. 停止条件与异常分类

核心测试沿用测试三的资源保护线。阈值作用于实际采集源，不能在执行中为继续加压临时放宽。

| 条件 | 动作与分类 |
| --- | --- |
| 宿主可用内存 <1 GiB | 立即停压，资源保护 |
| 可用磁盘 <20 GiB | 立即停压，资源保护 |
| MySQL cgroup `memory.current` ≥1.8 GiB | 立即停压，资源保护；同时保存 anon/file/kernel 与事件 |
| k6 RSS ≥3 GiB | 立即停压，压测器限制 |
| MySQL 已连接数 ≥131 | 立即停压，连接保护；上限仍为 151 |
| 未关闭 requirements ≥9,000 | 立即停压，异步预算保护 |
| 数据库探针采样间隔 >2.5 秒 | 停压，观测链路失效 |
| 关键状态连续 8 秒无有效样本，或 guard 心跳超过 3 秒 | 停压，观测链路失效 |
| 连续 3 个周期缺少必须的诊断证据 | 停止诊断组，证据不足，不记数据库故障 |
| 独立新连接探针连续失败 30 秒且无成功 | 立即停压，数据库持续不可用；结合日志分析原因 |
| 应用或依赖退出、OOM、非计划重启 | 立即停压，记录进程或容器故障 |
| 环境身份、schema 或业务数据一致性异常 | 立即停压，保存现场 |
| 语料耗尽、目标权限不符或删除目标异常重复 | 停压，负载数据无效，不进入容量判定 |
| 完整窗口实际发出率 <目标 95%，或丢弃率 >1% | 结束该组，检查压测器；结合资源证据区分压测器和系统退化 |
| 普通业务错误率或延迟超标 | 标记业务异常，短时组按计划完成以保留完整窗口，其他安全条件仍优先 |

持续测试若连续两个完整 60 秒窗口不满足业务标准，允许结束该组，标为“持续测试失败、提前结束”，按实际时长报告并进入 600 秒恢复；不得将其记为完整 1800 秒窗口。

MySQL 内存未降到阈值以下时不得启动下一组。先分析内存类别和恢复状态；若必须重建测试容器，记录动作，并对受影响的全部对照组采用相同初始化规则。不能仅重置较差的一侧来改善对照。

发出停压信号后立即停止安排新业务迭代，尽量保留客户端超时内的请求收尾；关键故障时资源保护优先。保存停压时刻、最后启动请求、尾部结果及观测持续状态。数据库持续不可用、崩溃、业务失稳、压测器受限和证据不足分别报告。

## 17. 工作量与交付验收

以下只是排期估算，不代表已执行或保证完成时间：

- 一个 5 分钟组包含 30 秒预热、300 秒测量和 600 秒恢复，合计 15.5 分钟，另加 60 秒空载、快照恢复及功能验证。

3. 同一候选正常档两次 30 分钟持续测试及各自 600 秒恢复结果；失败时保留失败结论和后续降档结果。
4. SQL 成本排名、主要阻塞链、CPU/IO/内存/应用排队时间线，以及根因判断的置信度和限制。
5. 至少完成对已取得证据的优化决策；若实施候选改动，提供同条件对照、正确性验证和新持续测试结果。
6. 所有本轮文件变更完成必要验证并按仓库规范提交；报告不得将计划命令、跳过的测试或未执行阶段记为通过。

缓存实验、CPU 扩容实验或其他条件实验未执行时，在报告中标明，不影响已完成核心测试的事实记录。核心验收未满足时，也可以交付阶段报告，但必须明确尚不能确认的结论。

## 18. 采集查询参考

以下查询用于实现采集器，不代表采集器已经完成。使用专用采样账号、固定连接数和客户端查询超时；默认数据库必须选为本轮业务数据库。先在准备阶段检查字段、权限、查询耗时和输出规模，再按第 6 节频率采样。

### 18.1 SQL 摘要原始快照

保存以下查询的完整结果，再按 `(SCHEMA_NAME, DIGEST)` 离线计算增量。不要直接对该查询排序后只保留累计耗时最高的几条。

```sql
SELECT
    SCHEMA_NAME, DIGEST, DIGEST_TEXT,
    COUNT_STAR, SUM_TIMER_WAIT, SUM_LOCK_TIME,
    SUM_ROWS_EXAMINED, SUM_ROWS_SENT,
    SUM_CREATED_TMP_TABLES, SUM_CREATED_TMP_DISK_TABLES,
    SUM_SORT_ROWS, SUM_ERRORS
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = DATABASE() OR DIGEST IS NULL;
```

采集器另存采样开始和结束时间、Uptime、摘要丢失状态及查询错误。空 digest 单独报告；观测查询和业务查询按第 6.3 节识别，不以此 SQL 的 schema 过滤作为业务归属证明。

### 18.2 等待者与阻塞者

```sql
SELECT
    w.REQUESTING_THREAD_ID AS waiting_thread_id,
    rt.PROCESSLIST_ID AS waiting_connection_id,
    w.BLOCKING_THREAD_ID AS blocking_thread_id,
    bt.PROCESSLIST_ID AS blocking_connection_id,
    rl.OBJECT_SCHEMA, rl.OBJECT_NAME, rl.INDEX_NAME,
    rl.LOCK_TYPE, rl.LOCK_MODE, rl.LOCK_STATUS,
    wt.trx_started AS waiting_trx_started,
    wt.trx_wait_started AS waiting_since,
    blt.trx_started AS blocking_trx_started,
    blt.trx_rows_locked AS blocking_rows_locked,
    blt.trx_rows_modified AS blocking_rows_modified
FROM performance_schema.data_lock_waits AS w
LEFT JOIN performance_schema.threads AS rt
    ON rt.THREAD_ID = w.REQUESTING_THREAD_ID
LEFT JOIN performance_schema.threads AS bt
    ON bt.THREAD_ID = w.BLOCKING_THREAD_ID
LEFT JOIN performance_schema.data_locks AS rl
    ON rl.ENGINE = w.ENGINE
    AND rl.ENGINE_LOCK_ID = w.REQUESTING_ENGINE_LOCK_ID
LEFT JOIN information_schema.INNODB_TRX AS wt
    ON wt.trx_mysql_thread_id = rt.PROCESSLIST_ID
LEFT JOIN information_schema.INNODB_TRX AS blt
    ON blt.trx_mysql_thread_id = bt.PROCESSLIST_ID
LIMIT 201;
```

返回 201 行时，采集器保留前 200 行并设置 `truncated=true`；不能将这些行当作全量阻塞链。各系统视图读取期间事务可能结束，关联字段可能为空，应保留这种情况。当前 SQL 或 digest、连接属性及服务角色通过同一采样周期的补充映射记录；不要将采集器的当前语句误认为已完成事务中的持锁语句。

执行计划、慢日志和 CPU profile 仍按第 10 节在独立诊断窗口采集。这些查询不替代关键安全状态、可用性探针或业务正确性检查。
