# 测试四补充验证：采集修复、100/120 RPS 对照与预算锁优化

状态：已完成采集修复、100/120 RPS 基线、120 RPS 改动复测和写入正确性核对。

## 执行范围

本轮沿用测试四固定条件：原数据与业务比例、Redis 关闭、MySQL 2 vCPU / 2 GiB、API MySQL 连接池上限 8。每组恢复、冒烟、再次恢复、清空性能模式汇总后空载 60 秒，再执行 30 秒预热、300 秒正式测量和 600 秒恢复。超时和未完成请求计为失败。

本轮先修复采集链路，再跑 100 与 120 RPS 对照，随后只改一项事务路径并以相同 120 RPS 条件复测。三组配置摘要和证据目录见文末。

## 采集接入与修复

测试三准备入口已接入仓库内 MySQL exporter 插件和官方 node_exporter。插件采集 17 类数据：连接/线程、缓冲池、日志、锁与事务、语句摘要、语句事件、文件 I/O、表/索引 I/O、内部等待、错误等；官方 node_exporter 补充主机 CPU、内存、磁盘和网络。

本轮修复了两个会直接影响结论的问题：

1. 空行截断。`file_io`、`wait_events` 和表访问查询原先会返回累计计数为 0 的历史 instrument/文件行，128 行上限被无效行占满，导致 `collector_truncated=1`，redo/binlog 行和 `wait/synch/*` 行被挤掉。现在查询增加 `COUNT_STAR>0` 条件，只导出窗口内实际出现的行；`wait_events` 覆盖 mutex、condition、rwlock 和 sxlock。
2. 诊断 instrument 未启用。准备阶段以 root 连接启用 30 个 `wait/synch/*` instrument 并复核 `setup_instruments`，任何一项未启用即失败；配置写入 `prepared.json`。每组正式窗口前清空 statement digest、statement event、error 和 wait 四类汇总表，避免恢复/迁移摘要占满 digest 和 I/O 行。

采集验证运行中 17/17 采集器 `success=1`、`truncated=0`，`digest_lost=0`；三组正式测量窗口均由 `metrics-summary.json` 复核为 `valid`。恢复期执行的额外核对查询可能让摘要超过有界输出并产生窗口外截断，不进入报告窗口。Exporter 每 5 秒落盘 `exporter-metrics.jsonl`，采样时间戳完整。指标汇总同时修正了边界序列的判定：只在收尾边界出现的序列不判为不完整；窗口内首次出现的标签组合此前计数按 0 计，保留为 `partial_series`；出现后再次缺失仍判为不完整。

## 三个问题

### 1. 预算表被哪些事务阻塞

120 RPS 窗口内共 6,471 次预算行锁等待、累计 620.2 秒，单次最长 0.844 秒，最多 9 个等待者；100 RPS 为 3,185 次 / 63.6 秒 / 0.714 秒 / 6 个等待者。

身份级采样（每 5 秒读取 `performance_schema.data_lock_waits`/`data_locks` 并关联事务）共 179 行，全部落在 `gopulse_load.business_async_budget.PRIMARY`，锁数据为当前 epoch 的单行主键；等待和阻塞模式均为 `X,REC_NOT_GAP`。阻塞方分两类：一类处于 COMMIT，另一类是 post-create 事务在执行 DML（等待方/阻塞方的语句摘要为空，因为写入使用二进制协议且 INSERT/UPDATE/DELETE 不进入 digest）。等待方的语句摘要以 `business_environment ... FOR SHARE` 为主，说明等待者已持有环境共享锁和数据库连接，在预算行上排队。

因此，预算表被 **post-create 事务的 COMMIT 和写入阶段**阻塞。锁本身是单行、非间隙的排他记录锁，没有表锁或间隙锁放大；问题是持锁事务跨越了 post/命令/obligation/outbox 写入和 COMMIT。

### 2. 哪些 SQL 的区间耗时和扫描量增长最多

按 `statement_digest` 窗口增量（120 RPS 对 100 RPS）：

| SQL | 100 RPS 次数 / 耗时 | 120 RPS 次数 / 耗时 | 单次耗时变化 |
| --- | ---: | ---: | ---: |
| COMMIT | 14,215 / 76.77 s | 15,158 / 199.84 s | 5.40 → 13.18 ms |
| `business_environment` 普通 SELECT | 10,674 / 1.78 s | 11,464 / 4.55 s | 0.167 → 0.397 ms |
| `business_environment ... FOR SHARE` | 7,482 / 0.91 s | 7,840 / 1.48 s | 0.122 → 0.188 ms |
| `business_async_budget ... FOR UPDATE` | 3,431 / 0.43 s | 3,807 / 1.22 s | 0.125 → 0.321 ms |
| `statement/com/Execute` 总计 | 117,418 / 509.4 s | 118,788 / 2,493.8 s | 4.34 → 20.99 ms |
| `statement/sql/commit` 总计 | 14,238 / 77.15 s | 15,162 / 199.87 s | 5.42 → 13.18 ms |

绝对增长最大的是 COMMIT（+122.7 秒），其次是 `statement/com/Execute` 中的写 DML（无法按 digest 拆分）。预算 `FOR UPDATE` 的单次耗时增长 2.6 倍，但总耗时只有 1.22 秒；锁等待的 620 秒计入事务和连接等待，不计入该 SELECT 的 digest 时间。

扫描量方面，窗口内扫描行数最大的 SQL 是观测器自身的性能模式查询（约 338k、90k、25.9k、19.2k、17.0k 行），不是业务 SQL。业务 SQL 中 environment 普通 SELECT、`FOR SHARE` 和预算 `FOR UPDATE` 每次均只扫 1 行，扫描次数随请求量从 100 到 120 约增 1.1–1.2 倍，未出现单次扫描放大。写入 DML 使用二进制协议且不进入 digest，扫描量不可见；这部分成本只能从 `Execute`、表/索引 I/O 和锁等待观察。表 I/O 上，`posts` 的 feed 索引 fetch 次数基本持平（51.4M → 52.1M），但累计等待从 397 秒涨到 1,711 秒（4.3×）；`business_async_budget` 的主键 fetch 等待从 57 秒涨到 440 秒，预算行初始化写入从约 6 秒涨到 188 秒。扫描次数没有明显增长，单位扫描成本随 CPU 节流上升。

### 3. COMMIT 变慢是否伴随日志 I/O 或内部等待增加

是，但主要是日志 fsync 和 CPU，不是内部锁等待。

| 指标 | 100 RPS | 120 RPS |
| --- | ---: | ---: |
| redo misc 次数 / 时间 | 50,881 / 52.44 s | 50,020 / 105.43 s |
| binlog misc 次数 / 时间 | 12,674 / 37.00 s | 13,082 / 69.34 s |
| 内部等待合计（前 12 项） | 约 0.78 s | 约 4.0 s |
| 最大内部等待 | `trx_mutex` 0.289 s | `buf_pool_LRU_list_mutex` 1.256 s |
| `log_files_mutex` | 0.102 s | 0.511 s |
| `log_writer_mutex` | 0.147 s | 0.294 s |

redo/binlog 的 misc 操作次数基本不变，单次时间约翻倍（redo 1.03 → 2.11 ms，binlog 2.92 → 5.30 ms），与 CPU 节流和 fsync 排队一致。COMMIT 累计 199.9 秒，而 binlog+redo misc 合计约 174.8 秒；内部互斥等待合计约 4 秒，不能解释 COMMIT 的增长。`sync_binlog=1` 下每次提交的组提交/fsync 是固定成本，CPU 饱和放大了它。

### 4. CPU 节流与 API 连接池等待

120 RPS 的 MySQL cgroup CPU 为 199.87%（2 vCPU 配额用满），2,950 个 100 ms 周期中有 2,948 个被节流，累计节流 1,576.8 秒；100 RPS 为 154.4%、221 个周期、6.39 秒。120 RPS 的 API 连接池 8 个连接全部占用，出现 53,018 次、21,541 秒等待，HTTP in-flight 峰值 97；读资源容量拒绝 3,418 次、写 398 次。

这与“CPU 饱和 → 单次 SQL/COMMIT 变慢 → 写事务长时间占用连接 → 连接池排队 → 读容量拒绝”的链路一致。预算行锁等待（620 秒）和连接池等待（21,541 秒）同时放大，但连接池等待远大于锁等待，且内部互斥等待只有数秒，根因是 2 vCPU 配额饱和，预算锁是次要放大器。

## 改动

只改一处事务路径：post-create 原先在事务开头初始化并 `SELECT ... ORDER BY data_epoch FOR UPDATE` 锁住 `business_async_budget`，随后执行 post、command、requirement、outbox 写入和 COMMIT；现在把预算行锁和扣账推迟到这些写入之后、COMMIT 之前，新增 `AccountPostCreateTx`，`ReservePostCreateTx` 只负责 command/requirement 写入。

- 限额检查、`foundCurrent`、全局 retained groups/bytes 检查和 `ErrBusinessAsyncBacklog` 映射保持不变。
- 预算行锁仍在同一事务内获取，超限时整笔回滚，不改变幂等和所有权语义。
- 新增集成断言：扣账仍发生；预算超限时返回 `ErrBusinessAsyncBacklog`，且不留下 post 行。

这样，预算行锁的持有时间从“全部写入 + 扣账 + COMMIT”缩短为“扣账 + COMMIT”，直接针对 620 秒锁等待的持锁区间；不改变 SQL 语义，也不减少写入量，因此不掩盖 CPU 饱和这个根因。

## 结论

**瓶颈判断。** 在固定 2 vCPU / 2 GiB、API 池 8 的条件下，120 RPS 的退化由 MySQL CPU 配额饱和主导：CPU 达到 198.9%–199.87%，2,950 个 100 ms 周期中约 2,850–2,950 个被节流，累计节流 1,180–1,577 秒。CPU 饱和把单次 COMMIT 从 5.42 ms 推高到 13–22 ms，把连接池等待推高到 1.8–2.2 万秒，并触发 1,864–3,418 次读容量拒绝。预算表行锁等待（620–1,222 秒）和 9–11 个等待者是同一压力下的次要放大器，不是根因：InnoDB 内部互斥等待合计只有约 4 秒，远小于连接池等待和 COMMIT 时间；锁等待的阻塞方是执行 DML/COMMIT 的 post-create 事务，锁本身是单行 `X,REC_NOT_GAP`，没有间隙锁或表锁放大。COMMIT 变慢主要对应 binlog+redo misc 从 174.8 秒增至 275.4 秒，而不是内部日志互斥等待增加。

**改动验证。** 把预算行锁和扣账从 post-create 事务开头推迟到 post/command/requirement/outbox 写入之后、COMMIT 之前，在相同 120 RPS 下把错误率从 23.44% 降到 14.57%，成功 P50/P95 从 546.65/1,341.11 ms 降到 427.92/1,283.42 ms，读容量拒绝从 3,418 降到 1,864，连接池累计等待下降 15.5%，写路由成功率提高 3–9 个百分点。写入正确性通过：post.create 命令与 posts 行 1:1、内容有效，search 应用结果 0 失败，likes/bookmarks/follows 零孤儿，预算 `open_requirements=0` 且无漏扣。集成测试同时覆盖“扣账仍发生”和“超限整笔回滚、不泄漏 post”。

**改动没有解决的。** 预算行锁等待反而从 620.2 秒增至 1,222.1 秒，最多等待者从 9 增至 11，最长等待从 0.844 秒增至 1.355 秒；复测 COMMIT 均值 22.17 ms、累计 360.15 秒，binlog+redo misc 约 275.4 秒。原因是锁在 COMMIT 完成前不能释放，临界区由提交/fsync 主导；把锁前的写入移出临界区缩短了前置段，但没有缩短提交段。复测还完成了更多请求和提交（成功请求 +11.6%，COMMIT +7.1%），锁队列因此更长。改动应作为“改善准入和延迟的部分优化”保留，但不能宣称已修复 120 RPS 的 CPU/提交瓶颈；下一步应优先减少提交次数/fsync 成本或提高 vCPU 配额，而不是继续调整锁顺序。

**限制。** 每个条件只有一组正式运行；错误率下降幅度较大且在各写路由上一致，但单次运行仍可能受主机 I/O 和调度波动影响。锁等待上升与复测 COMMIT 时间、日志 misc 时间上升方向一致，尚不能拆分“提交更慢”和“完成更多工作”各自的贡献。报告中的 SQL 累计耗时是数据库观测窗口的累计等待，不等于 CPU 时间；写 DML 不进入 digest，其成本通过 `statement/com/Execute`、表/索引 I/O 和锁等待间接观察。

`prepare.py` 只在没有活动组时执行；修改源码后必须重新准备。正式窗口内不得执行额外 SQL 探测，否则会进入 digest/history 并污染计数。每组结束后用无参数 `stop.py` 停止测试服务。
