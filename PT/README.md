# 极限性能测试规范

本项目通过基线验证、拐点复测、持续超载和卸载恢复，测量当前配置下的容量边界、最大成功吞吐及过载保护能力。

各轮使用对应方案规定的环境、起点和验收要求。下文的历史起点不替代后续专项方案。

- [测试三：无 Redis 逐级加压方案](03-测试三/2026-10-20-测试三-性能测试方案.md)
- [测试三：实测报告](03-测试三/2026-10-20-测试三-性能测试报告.md)
- [测试四：无 Redis 数据库专项诊断与稳定性测试方案](04-测试四/2026-10-20-测试四-数据库专项诊断与稳定性测试方案.md)
- [测试四：工具准备与验证记录](04-测试四/2026-10-20-测试四-工具准备与验证记录.md)

## 1. 测试依据与目标

2026-10-19 的测试结果显示：

- 自动加压时，200 RPS 稳定，400 RPS 首次失稳。
- 干净状态下，400、500 RPS 的 503 比例低于 1%，600、800 RPS 已超过 1%。
- 500 RPS 持续 5 分钟后，错误率升高，outbox 积压增长至 12,299 条。
- 3200 RPS 时，85.3% 的请求返回 503，但进程仍存活。

因此，后续极限测试从 **200 RPS** 开始，重点覆盖 **400～800 RPS** 的历史拐点，再向 **1600、3200、6400 RPS 及更高档位**加压。

历史数据只用于确定起点和对照档位。当前版本的容量必须重新测量。

每轮测试需要回答：

1. 从哪个负载开始不满足业务要求？
2. 成功吞吐最高达到多少，继续加压后如何变化？
3. 过载时是快速拒绝、延迟增长、积压扩大，还是服务故障？
4. 停止加压后能否自行恢复，是否需要人工干预？
5. 哪些证据支持瓶颈判断？

## 2. 测试条件

每轮执行前，固定并记录以下条件：

| 类别 | 必须记录的内容 |
| --- | --- |
| 版本 | 被测代码 commit、未提交改动、脚本及压测工具版本 |
| 部署 | 服务角色、实例数、依赖版本、压测器与服务是否同机 |
| 资源 | CPU、内存、连接池、并发预算、限流及超时配置 |
| 数据 | 用户与业务数据规模、历史 outbox 数量、缓存状态、初始积压 |
| 负载 | 业务比例、访问分布、账号数量、虚拟用户数和请求超时 |

首次对照沿用上一轮业务比例：读 45%、搜索 10%、通知与书签等读取 10%、内容写 15%、互动写 15%、身份与会话 5%。调整比例时必须说明原因，结果单独比较。

测试数据应支持计划时长内的读写操作。编辑、删除目标必须满足权限和归属要求；语料耗尽不得混记为服务性能故障。

压测器必须同步采集资源指标。虚拟用户数量可以按实际请求率调整，不能因固定为某个数量而限制加压。

## 3. 加压安排

### 3.1 基线与极限加压

按以下顺序执行：

| 阶段 | 目标请求率 | 预热 | 正式测量 |
| --- | --- | --- | --- |
| 基线验证 | 200 RPS | 30 秒 | 2 分钟 |
| 拐点复测 | 400、500、600、800 RPS | 每档 30 秒 | 每档 2 分钟 |
| 超载测试 | 1600、3200、6400 RPS | 每档 30 秒 | 每档 2 分钟 |
| 继续加压 | 从上一档继续翻倍 | 每档 30 秒 | 每档 2 分钟 |

预热用于适应当前档位，预热指标与正式测量分别统计。

200 RPS 基线异常时，先检查环境、数据及版本变化。必要时降低负载重新建立基线，不能直接沿用历史容量结论。

基线通过后，各档连续执行，保留前一档产生的缓存、历史数据和积压。不得在档位之间清表、排空积压或重启服务。该组结果用于观察连续加压下的退化过程。

### 3.2 持续退化复测

独立执行 **500 RPS × 5 分钟**，用于对比上一轮持续退化问题。

开始前恢复到规定的数据状态，记录初始缓存、历史 outbox 和积压。运行过程中不清理积压、不调整参数。

该测试重点比较错误率、成功吞吐、数据库等待及积压增长趋势。5 分钟通过只能说明该窗口内通过，不能直接认定为长期持续容量。

### 3.3 卸载恢复

连续加压和持续退化复测结束后，分别停止测试流量，观察恢复，最长 **10 分钟**。

记录业务成功率、延迟、资源占用、积压量和最老积压年龄。恢复期间不主动清理数据或重启服务。

10 分钟内未达到预先记录的基线，标记为“观察窗口内未恢复”。需要人工处理时，先保存现场，再记录操作及恢复结果。

## 4. 业务边界与极限判定

### 4.1 业务容量边界

本轮以以下标准判定业务质量：

- P95 不超过 1 秒，P99 不超过 2 秒。
- 业务失败率不超过 1%。
- 实际请求率至少达到目标的 95%。
- 同时记录迭代丢弃和异步积压，不能仅凭 HTTP 指标认定整条链路稳定。

首次不满足标准时，记录最后通过档和首次未通过档。需要更精确边界时，另行补测区间内档位。

**超过业务阈值只标记退化，不直接结束超载测试。** 执行前必须核对脚本，避免 1% 错误阈值提前中止整轮测试。

### 4.2 极限加压结束条件

不把 3200、6400 RPS 或配置中的扫描上限作为预设容量。

满足以下任一条件时结束继续加压：

- 连续两个递增档位的成功吞吐提升均不足 5%，且拒绝率、延迟或积压继续恶化。随后在最高已测档追加 5 分钟，验证持续过载表现。
- 压测器无法继续产生有效负载。
- 触发本节规定的故障终止条件。

吞吐平台表示当前工作负载和保护配置下的有效吞吐边界。必须结合资源与拒绝指标，区分应用主动保护、依赖瓶颈和资源耗尽。

### 4.3 故障终止条件

发生以下情况时，立即停止加压并保存证据：

- 应用或关键依赖崩溃、OOM，或发生非计划重启。
- 发现非预期的数据丢失或一致性异常。
- 达到本轮执行前确定的内存、磁盘、连接或积压保护阈值。

普通业务请求出现 429、503，或单次健康检查失败，不自动等同于故障终止。应结合持续时间、成功吞吐和依赖状态判断。

如果压测器先达到瓶颈，报告明确注明“被测系统极限尚未测出”。

## 5. 指标要求

各档位采用一致的测量窗口，至少记录：

| 类别 | 指标 |
| --- | --- |
| 请求 | 目标与实际请求率、成功吞吐、请求数、未发出的迭代数 |
| 延迟 | 总体及成功请求的 P50、P95、P99 |
| 错误 | 429、503、其他非预期响应、超时、传输错误 |
| 资源 | 压测器、应用及依赖的 CPU、内存、连接、等待和磁盘使用 |
| 异步链路 | 实际提交与处理事件数、积压量、最老积压年龄 |
| 恢复 | 恢复耗时、残留影响、是否需要人工干预 |

成功吞吐按达成业务目标的请求统计。快速返回的失败请求不能计入成功吞吐，也不能用来证明延迟表现良好。

异步吞吐按实际事件统计，不用 HTTP 请求量或写请求比例推算。

## 6. 报告要求

报告按以下顺序组织：

1. **结论**：业务容量区间、最大成功吞吐、过载表现和恢复结果。
2. **测试条件**：版本、部署、资源、数据及工作负载。
3. **执行记录**：各档位实际负载、时长、干预操作和中止原因。
4. **测量结果**：指标表、变化趋势及历史对比。
5. **分析与限制**：异常证据、瓶颈推断、缺失观测和待验证问题。

报告必须区分：

- 达到业务标准的负载。
- 观测到的最大成功吞吐。
- 最高实际施加的负载。

三者不得混用。进程存活、健康检查通过和业务链路恢复也必须分别说明。

## 7. 资料归档

规范统一维护在 `PT/README.md`。

每轮方案、报告和摘要放在同一测试目录中，例如 `PT/01-测试一/`。文件名使用：

`YYYY-MM-DD-测试编号-内容.md`

方案使用编写日期；报告和摘要使用实际测试日期。正文记录完整起止时间和时区。

原始 JSON、资源采样和日志保存在被忽略的 `.run/` 下，报告记录对应路径。提交前检查文档及日志摘录，不得包含密码、令牌、DSN、credentials 或 corpus。
