# 性能测试规范

本规范规定 GoPulse 性能测试的设计、执行、判定和记录要求。每轮测试先形成方案，再按方案执行，最后依据实测证据形成报告。

## 1. 明确测试目标

每轮测试必须说明要回答的问题，并选择对应的测试方式。

| 测试方式 | 要回答的问题 | 结论必须包含 |
| --- | --- | --- |
| 容量测试 | 在给定条件下，系统能承受多大负载 | 已测稳定与失稳档位、是否找到边界及持续验证结果 |
| 稳定性测试 | 固定负载持续运行后，性能是否退化 | 延迟、错误、资源和异步积压的变化趋势 |
| 过载恢复测试 | 超出承载能力后，系统如何拒绝请求并恢复 | 拒绝行为、故障范围、恢复时间和残留影响 |
| 对照测试 | 某项改动是否改善性能 | 相同条件下的基线、改动后结果及重复测量差异 |

测试范围必须明确到业务场景或处理链路。仅测 HTTP 接口时，不得据此宣称异步链路容量已通过验证。

## 2. 在执行前确定方案

方案必须写清以下条件，不得在看到结果后修改通过标准：

- **环境**：代码版本、压测工具版本、部署方式、实例数、资源限制和关键运行参数。
- **数据**：数据规模、生成方式、历史记录量、缓存状态、初始积压和测试账号分布。
- **负载**：请求率、并发设置、业务比例、访问分布、请求超时和预期业务结果。
- **时间**：各档位的预热、测量、恢复时长，以及重复运行安排。
- **判定**：延迟、错误率、负载达成率、资源和积压的允许范围，以及停止加压的条件。

参数可以按测试目标设置，具体数值写入本轮方案。工具默认值必须核对后使用，不自动视为本轮验收标准。

## 3. 保证测试条件可比较

测试期间固定环境和配置，记录代码的 commit 及影响结果的未提交改动。压测器与被测服务共用资源时，必须记录双方资源占用，并说明对结果的影响。

每次运行前记录数据、缓存和积压的起始状态。连续加压时保留前一档的残留影响；独立复测时恢复到方案规定的起始状态。运行中清空积压、重启服务或调整参数，都必须单独记录，不能与未干预的结果混合比较。

工作负载必须覆盖方案规定的业务比例和访问分布。写入、编辑和删除使用满足权限与归属要求的数据；冷读与热点测试分别控制语料及缓存状态。语料耗尽或业务比例偏离时，必须标记受影响的阶段。

对照测试每次只改变待验证因素，其余条件保持一致。对差异较大或临近阈值的结果进行复测，报告说明波动范围，不只选取最好的一次。

## 4. 按阶段执行并观察恢复

容量测试先逐档加压寻找稳定与失稳区间，再细化区间，最后在选定负载下持续验证。达到扫描上限仍未失稳时，只能说明边界尚未找到。

每个测量阶段开始前完成预热。初始化、登录和预热流量与正式业务测量分别统计。每档记录实际开始时间、结束时间和中止原因，不用计划时长替代实际时长。

达到方案规定的停止条件后停止加压，保留错误、日志和资源证据。随后继续观察业务可用性、异步积压及资源占用，直到恢复到规定基线或达到恢复观察时限。不得仅凭健康检查通过认定恢复完成。

## 5. 统一指标和判定口径

同一档位的指标使用相同测量窗口，注明单位、统计对象和计算方式。

| 指标 | 记录要求 |
| --- | --- |
| 负载与吞吐 | 同时记录目标与实际请求率、成功吞吐（均以请求/秒计），以及未发出的迭代数 |
| 延迟 | 记录 P50、P95、P99，注明是否包含失败请求；成功请求延迟与总体延迟不得混用 |
| 错误 | 按业务结果判定，分别统计 429、503、其他非预期响应、超时和传输错误 |
| 资源 | 记录压测器、应用及依赖的 CPU、内存、连接使用和等待情况；缺失项明确注明 |
| 异步处理 | 记录实际提交事件数、处理完成数、积压量、最老积压年龄和恢复时间 |

异步吞吐按实际事件统计，不用 HTTP 请求数或写请求比例替代。删除成功与目标已不存在分别记录；工具允许某个响应码，不等于该请求达成了业务目标。

结果按证据判定：

- **通过**：完成规定时长，实际负载满足要求，且全部适用指标符合标准。
- **未通过**：有证据确认至少一项标准未满足，注明触发指标、时间和负载。
- **结论不充分**：压测器能力不足、必要指标缺失或执行不完整，无法支持相应结论。已确认的失败仍须保留。

短时通过只能支持该时长和负载下的结论。持续容量必须有持续运行结果；瓶颈归因必须有对应窗口的指标、日志或诊断证据。现象、推断和已验证原因分别表述。

## 6. 形成可复核的报告

报告按“结论、测试条件、执行记录、结果、分析与限制”组织。至少包含：

1. 测试编号、日期、目标、代码与工具版本、生效配置及数据状态。
2. 复现入口、各阶段计划与实际时长、干预操作、停止原因和恢复过程。
3. 各档位的主要指标、判定结果，以及对照测试的基线与差异。
4. 支撑结论的原始产物位置、异常证据、缺失观测和待验证问题。

容量数字必须同时注明环境、工作负载、持续时间和通过标准。测试未执行的部分明确标记，不以预计值补齐。结论修订时说明新增证据，不覆盖原始测量事实。

## 7. 资料归档

本规范统一维护在 `PT/README.md`。每轮方案、报告和摘要放在同一测试目录中，目录使用 `序号-测试编号`，例如 `01-测试一`。

文件名使用 `YYYY-MM-DD-测试编号-内容.md`，例如 `2026-10-19-测试一-极限压测报告.md`。方案使用编写日期；报告和摘要使用实际测试日期。跨日测试在正文记录完整起止时间和时区。

原始 JSON、资源采样和日志保存在被忽略的 `.run/` 中，报告记录对应路径。提交的文档必须脱敏，不得包含 DSN、密码、令牌、credentials 或 corpus。
